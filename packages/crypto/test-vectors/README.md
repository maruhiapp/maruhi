All keys, IDs, and values are deterministic dummies (pattern byte strings); no real secrets are included.

## How the expected values are computed (independent reference tools)

Expected values are computed on **an implementation stack different from** the one under test (WebCrypto + panva `hpke`):

- `tools/generate_reference.py` — Python 3.11 + pyca/cryptography. Generates encoding / variable-encryption / chain-entries / recovery-wrap (the invite files invite-accept-signature / invite-link come from the same tool)
- `tools/generate-dek-wrap.mjs` — hpke-js (@hpke/core 1.9.0 + @hpke/dhkem-x25519 1.8.0). Generates dek-wrap. Since panva hpke deliberately offers no way to derandomize Seal (docs/notes/spike-c.md), fixing the Seal direction uses hpke-js, which accepts an injected ekm. spike-c already verified that hpke-js itself matches the official RFC 9180 vectors including the Seal direction
- `tools/generate-lease-wrap.mjs` — also hpke-js. Generates lease-wrap. Reads dek-wrap.json and re-wraps the same coordinates and DEK as its `server-basic` to a workload ephemeral key (expresses §9.1's "the server only opens its own wrap and re-wraps" with real data)
- `tools/generate-sealed-value.mjs` — also hpke-js. Generates sealed-value. Reads dek-wrap.json and seals two dummy proposed values (a primary and a companion of one proposal) to the same recipient device key and coordinates as its `basic` (expresses §5.3's "a sealed value goes to the device key that also receives DEK wraps" with real data)
- `tools/generate-master-key-wrap.mjs` — also hpke-js + WebCrypto. Generates master-key-wrap. Reads recovery-wrap.json and wraps the same B and user_id as its basic to each recipient of passkey-prf / guardian groups / handoff (guardian approval) (expresses §8's "ledger = the set of per-recipient wraps of the same B" with real data. Since 2026-09-20 DK, B = the reserve-key blob)
- `tools/verify_reference.mjs` — cross-check verification on yet another implementation stack: verifies encoding / AES-GCM / HKDF / Ed25519 / SHA-256 under WebCrypto (Bun), and dek-wrap via **Open with a KeyPair passed to panva hpke (the library the implementation will adopt)**. Commit only after confirming all PASS

Regeneration and re-verification (run in the `tools/` directory):

```sh
cd tools
bun install            # hpke-js / panva hpke (exact pins)
bun run generate       # generate-dek-wrap.mjs → generate-lease-wrap.mjs → generate-sealed-value.mjs →
                       #   python3 generate_reference.py → generate-master-key-wrap.mjs
                       #   (this order is correct: generate-lease-wrap.mjs and
                       #   generate_reference.py both read dek-wrap.json, and
                       #   generate-master-key-wrap.mjs reads recovery-wrap.json,
                       #   which generate_reference.py writes)
bun run verify         # verify_reference.mjs (exit 0 = all verifications pass)
oxfmt ../*.json        # apply the repository formatting (committed vectors are already oxfmt-formatted)
bun run regen-check    # regen-check.mjs: the same generate in a scratch copy, compared with the committed files (CI 7c)
bun run delta -- --base origin/main   # vector-delta.mjs: the review summary of CI 7d (see "Reviewing a crypto change")
```

- As a precondition of any PR that modifies vectors, confirm that `git status`
  is empty after generate → `oxfmt` (byte-exact reproduction). Do not mix
  environment-derived diffs with spec-change-derived diffs. CI step 7c checks
  this on every run (`regen-check`, formatting ignored)
- On environments where the system pyca/cryptography is broken (e.g.
  `pyo3_runtime.PanicException` from a missing `_cffi_backend`), use a venv:
  `python3 -m venv /tmp/vecgen && /tmp/vecgen/bin/pip install cryptography` →
  `/tmp/vecgen/bin/python generate_reference.py` (the output is
  version-independent — everything is deterministic keys, nonces, and ekm)

`tools/` is a throwaway reference tool, not product code. Product code (`packages/crypto/src`) must not import it.

## Reviewing a crypto change (CI steps 7c / 7d)

Two CI steps support the owner's review of a PR that touches `packages/crypto`. **Neither approves anything**; they make the review smaller and its blind spots visible.

- **7c — regeneration check** (`tools/regen-check.mjs`, every run): runs `bun run generate` in a scratch copy of this directory and fails when a committed vector file differs from the regenerated one, formatting ignored (both sides parsed as JSON; key order counts). So the committed vectors are exactly what the generator in the same PR produces: reviewing the generator diff plus the vector delta below covers the vector files. CI takes pyca/cryptography from the Ubuntu archive (`python3-cryptography`, installed with zsh); the output does not depend on its version (see above).
- **7d — vector-delta summary** (`tools/vector-delta.mjs`, pull requests only): compares `packages/crypto` at the merge-base with the PR head and writes a report to the job summary. Locally: `bun run delta -- --base origin/main` (or `--base <rev> --head <rev>`). Unit tests: `tools/vector-delta.test.mjs` (root `bun run test`).

The report lists:

1. **Vector entries**: every object in an array of objects is an entry, named by `name` / `seq` / `after_seq` (else by index — an insertion into such an array shows as changes); what is left of a top-level key (field orders, descriptions) is one fixture entry, except a **keyed map of named records** — the top-level keys `extended_chains`, `keys`, `environment_deks`, `guardian_keypairs` and `extra_keys` (an explicit list in `vector-delta.mjs`, `KEYED_FIXTURE_MAPS`) — whose every member is its own fixture entry `file › map › key`: a new derived chain or key reads as added, and editing one chain's `expected_*` is that chain's change. The list is explicit because no structural rule can tell a map of named records from one record whose fields are objects, and splitting such a record would turn a byte change into an added part (downward); an unlisted map keeps the coarse identity (upward), and a listed map's non-object members stay together as one entry named after the key. A removed member is never rebase material: a rename would otherwise explain a re-key of every vector it signs. A member's removal is classed like a top-level fixture's removal, never as a changed vector and never as a narrowing by itself: a lone `keys` member removed classes R2, and a derived chain removed with its negatives classes R1 / R2 through its own entries (positives narrow; negatives only under the rule below). The removal still appears in the Removed list, so the report shows it; it does not by itself raise the class to R3. Each entry is unchanged / removed / added / changed. A changed entry shows which kinds of leaves moved: `outcome` (an explicit allow-list: `must_fail`, `expected_reason`, `expected_error`, the expected verifier state `expected_head_states` / `expected_members` / `expected_environments` / `expected_server_grants` / `expected_checkpoints` / `expected_policy` / `expected_pending`, and `kind` in a negative; any other key — `expected_hex`, `expected_*_hex`, `expected_line` or a future `expected_*` — is data, the upward side), `prose` (`note` / `description` / `*_note`, or sentence-like text of six or more words) or `data` (everything else). Counting an input sentence as prose hides nothing: 7c ties every input to its output bytes, so a meaningful input edit also moves `data`. A changed entry is **rebased** when its old version referenced material only removed positives or fixtures had (a removed positive of the same file named through `base` / `prev_base` / `predecessor`, or a long hex value no unchanged entry carries) — it had to move with the deletion, and an encoding change cannot hide in it because the unchanged vectors of the same encoding would move too.
2. **Domain-separation strings**: `${…}/name` templates and `maruhi/vN/…` literals in `src` (comments excluded; `${…}/name-v${…}` becomes the pattern `name-v*`), `domain`-like strings in the vectors, and the leading field of every §2.1-encoded hex value. "New" means covered by neither a base src pattern nor a base vector domain.
3. **Chain ops**: string `case` labels in `src` (the switches on the op: the §6.1 payload canonicalization in `chain-canonical.ts` and the approval dispatch in `chain-verify.ts`), the strings `src` declares under an `op:` / `inner_op:` property with the `| "…"` members that follow (the `ChainOperation` union the canonicalization switches on, which tsc requires a new op to join, however the dispatch is written), and the `op` / `inner_op` values in the vectors. A chain entry's signed bytes begin with the bare suite, not a `maruhi/vN/…` domain: its op is its domain separation, so ops are compared like domain strings ("new" = in no base src label and no base non-negative entry).
4. **`SUPPORTED_*` constants** in `src` whose array literal changed, and whether the new set is a subset of the old.
5. **Encodings, suites and primitives**: signed-bytes shapes (leading domain × field count of every §2.1 hex value in a non-negative entry — negatives are malformed on purpose; an encoding led by the bare suite, such as a chain entry or the variable AAD, has the shape `<suite> ×N`), field orders (a string list under a `*_order` key; a list inside a map there is identified together with its map key, so chain-entries.json's `payload_field_order.<op>` — the op table the generator builds every payload from — makes a new op or a changed payload order a new field order, even when the list equals another op's; the `*_order` key name itself is not part of it, so renaming a declaration adds nothing), suite identifiers, WebCrypto algorithm names, `subtle.*` methods, external modules and the `hpke` members used, and `packages/crypto` runtime `dependencies`.
6. **Changed files** by category; a code file counts as comments / formatting only when both its comment-free token text and its transpiled runtime form (Bun.Transpiler) are unchanged (Python: whitespace only).

Risk classes — the highest matching class wins, and a rule that cannot tell picks the higher class:

| Class | Meaning | Mechanical rule |
|---|---|---|
| R0 | comments / docs only | only docs, prose leaves, and comment / formatting-only code edits |
| R1 | deletion / narrowing | a narrowing — positives removed, negatives removed together with the surface they exercised (see below), or a `SUPPORTED_*` set shrunk — and nothing of R2 / R3: no surviving vector changed bytes except rebased ones, no new domain string, supported sets only shrink. Implementation changes that carry out the narrowing and added entries on existing shapes are admitted |
| R2 | logic change keeping the encodings | a surviving vector's expected outcome changed, a `SUPPORTED_*` set did anything but shrink, a negative was removed while the surface it exercised remains, or code / config / vectors changed with no narrowing |
| R3 | new signed bytes / primitive / domain | a new domain string or suite, a new chain op (a `src` `case` label or `op:` declaration, or a vector `op` / `inner_op`), a new signed-bytes shape (domain- or suite-led) or field order (a chain op's payload order included — a new op or a changed order of an existing one), a new primitive or `hpke` member, a runtime dependency change, or a surviving vector whose bytes changed without being rebased |

Removing a positive can only narrow what is accepted; removing a negative can widen it (the rejection and the check behind it may leave together). So a removed negative counts as narrowing only when the surface it exercised left head too: a signed-bytes shape no head positive has, a domain with no head positive shape left (a retired layout keeps negatives over its domain, so mere presence does not count), a suite no head positive and no head src uses while a base positive did, or derivation from a removed positive that itself exercised retired surface (named through `base` / `prev_base` / `predecessor`, or sharing a long hex value no head entry carries — e.g. a v2 signature replayed under the v1 domain). The report shows what retired each removed negative, or **surface remains**.

Negatives never vouch for a surface. Every comparison that could lower a class reads positives and fixtures only: the retired surface above, what base already knew (a domain, chain op, suite or field order only a base negative used is still new once head adopts it in src, a positive or a fixture; an item appearing nowhere in base is new wherever it appears, a negative that merely survives adds nothing), and the material that makes a changed entry "rebased" (only removed positives and fixtures; entry names only through the reference keys, never from free text). Only "what head now carries" includes negatives, which errs upward. A shrunk `SUPPORTED_*` set is still narrowing evidence of its own, but it never vouches for a removed negative.

The `*` of a src domain pattern (`name-v${layout}` → `name-v*`) stands for a layout number only: it covers `name-v3`, never `name-vault` or `name-v2-hybrid`.

How the owner uses the summary:

- Read the class and its "Why this class" lines, then check the facts against the PR description: removed entries are exactly what the PR retires, added entries re-pin surviving rules, each rebased entry names the removed material it followed, and the domain / `SUPPORTED_*` lines match the spec change.
- R0: glance at the cosmetic file list. R1: read the `src` diffs (R1 admits them) and confirm each removal. R2: review the logic against `docs/CRYPTO_SPEC.md`, and each outcome change one by one. R3: the full crypto review of CLAUDE.md (spec first, vectors first, human approval).
- A class lower than the change deserves is a bug in the rules (they are meant to err only upward): say so in the review and fix the rule. The report covers `packages/crypto` only; for `docs/CRYPTO_SPEC.md` it only says whether it changed.

## What the vectors pin down (points to check especially in human review)

1. **§2.1 encoding**: concatenation of `uint32-BE length + UTF-8 body`. Numbers are stringified in base 10. The vectors pin that `("ab","c")` and `("a","bc")` produce different byte strings
2. **Chain normalization (the substance of §6.1's "the implementation is pinned by test vectors")**:
   - `signed_bytes = LP(suite, seq, prev_hash_hex, op, actor_user_id, actor_key_fingerprint_hex, payload_bytes, timestamp_ms)`
   - `payload_bytes` = the LP encoding of the op's fixed field order (`canonicalization.payload_field_order` in chain-entries.json), embedded as a single field (nested LP)
   - `entry_bytes = LP(the 8 fields of signed_bytes, signature_hex)`; `entry_hash = SHA-256(entry_bytes)` becomes the next entry's `prev_hash`
   - Binary values (prev_hash / public keys / FP / signature) go onto the LP as **lowercase hex strings** (not raw bytes)
3. **Key fingerprint**: the first 16 bytes of `SHA-256(enc_pub(32B) || sig_pub(32B))`. Since both public keys are fixed-length, this is a raw concatenation (the §2.1 LP applies to AAD / info / canonicalization byte strings). → Confirm the validity of this interpretation in review
4. **The aad of the §5 DEK wrap is empty** (the info carries the context binding). §4 variable encryption uses AAD; the §8 recovery wrap uses AAD + a fixed info string
5. **§8 HKDF salt = empty**: negative `wrong-salt` pins "undecryptable with any non-empty salt"
6. **Server-key fingerprint (2026-08-02 owner ruling)**: the first 16 bytes of `SHA-256(server_enc_pub(32B))`. The §3 user-FP definition (enc||sig) cannot apply because a server holds only an enc key (§9). Written into CRYPTO_SPEC §9
7. **grant_server's scope_environments (2026-08-02 owner ruling)**: the environment_id list is LP-encoded (nested LP) and its **lowercase hex string** goes onto the payload as one field, `scope_environments_lp_hex` (isomorphic to the binary_encoding convention). The list order is part of the signed byte string (pinned by negatives `grant-server-scope-reorder` / `grant-server-scope-flat-concat`). Generation SHOULD sort and deduplicate (verification treats it as a set). Written into CRYPTO_SPEC §6.2
8. **Re-grants widen the scope only (2026-08-02 owner ruling)**: a grant_server to the same server key as an active grant is accepted only when old scope ⊆ new scope. Narrowing must go through `revoke_server` (which carries the §7 all-environment rotation duty) (pinned by negative `authz-grant-scope-narrowed`)
9. **Epoch = a per-environment counter (2026-08-02 owner ruling, option 3; updated to follow convention 13 of 2026-08-03)**: the epoch starts at 1 at `create_environment`, and `rotate_epoch`'s new_epoch must strictly equal "current epoch + 1". Rollback, duplicates, and jumps are rejected (pinned by negatives `authz-epoch-rollback` / `authz-epoch-duplicate` / `authz-epoch-jump` / `authz-epoch-first-jump` [the first rotate on an epoch-1 environment right after create may only be 2]). **The "initial value 1 if unobserved" default is abolished** (convention 13's `unknown-environment`)
10. **Field size limits (2026-08-02 owner ruling, option 2)**: free-form string fields are at most 1024 bytes in UTF-8; scope_environments has at most 256 elements. Exceeding either is invalid (pinned by negatives `authz-field-too-long` / `authz-scope-too-many`; since these are consensus rules of chain validity, the constants are pinned by vectors)
11. **§5.1 registration signature of the DEK wrap (2026-08-02 owner ruling 2-E; drafted in session 09)**: `signed_bytes = LP("<suite>/dek-wrap-sig", project_id, environment_id, epoch, recipient_user_id, recipient_enc_pub_hex, enc_hex, ciphertext_hex, signer_user_id)` is signed by the signer's chain sig key (Ed25519). The suite binding is a domain string (pinned by negative `suite-mismatch`); binary values go onto the LP as lowercase hex strings (same as convention 2's binary_encoding). The `signer_user_id` binding defends against attribution swapping, made possible at drafting time by a chain that allowed multiple members with the same public key (pinned by negative `transplant-signer` — session 09 review loop 1; kept as an independent defense layer even after convention 12's member-key uniqueness banned the root cause). Negatives pin signature tampering (`tampered-signature`), wrap tampering (`tampered-ciphertext` / `tampered-enc`), coordinate transplants (`transplant-project` / `-environment` / `-epoch` / `-recipient`), recipient-key substitution (`recipient-key-mismatch`), and signer-key mismatch (`wrong-signer-key`). No raw-concatenation negative exists (the positive's signed_bytes match check directly fails a mis-encoding implementation — there is no nested-LP subtlety like the one flat-concat guards in chain-entries). **This vector itself is also a human-review target in PR review** (committed together with the §5.1 spec drafting, ahead of the implementation)
12. **Member-key uniqueness (decided 2026-08-03 — session 10; CRYPTO_SPEC §6.2)**: `add_member` is rejected when **either** of the target's enc / sig public keys matches a **same-kind** key of the current member set (pinned by negatives `authz-add-member-duplicate-key` / `-duplicate-enc-key` / `-duplicate-sig-key` / `-duplicate-owner-key`; expected reason `duplicate-member-key`). The check is per individual enc / sig key (not an FP = enc‖sig match — the two one-key-reuse negatives pin this). Genesis-derived owner keys are also indexed (`-duplicate-owner-key` pins this — fails an implementation that indexes only add_member-derived keys). The prohibition covers **only the current member set**: a removed member's keys are rejected neither on a return under the same user_id nor on reuse under a different user_id (pinned by the `valid_appends` positives `readd-removed-member-same-key` / `reuse-removed-member-key-new-user` — a verifier that mis-implements "no duplication against all of history" fails here). The check order is role rule → `duplicate-member` (user_id) → `duplicate-member-key` (key): role → key order is pinned by negative `authz-add-member-role-precedes-duplicate-key`, user_id → key order by negative `authz-add-member-duplicate-user-precedes-key` (+ the implementation test "add_member duplicate user id wins over duplicate key") (the existing `authz-admin-adds-admin` does not depend on order, since the reused key's owner is a removed member — it stays insufficient-role). **This vector itself is also a human-review target in PR review** (committed together with the §6.2 consensus-rule revision, ahead of the implementation)

13. **Chain binding of the environment lifecycle + the DEK commitment (2026-08-03 session 12 = CRYPTO_SPEC 0.4-draft §5.2 / §6.2; vectorized in session 13's implementation PR-1)**: environments are created by the chain op `create_environment` (payload order `[environment_id, dek_commitment_hex]`), and `rotate_epoch` carries the new epoch's `dek_commitment_hex` at the end of its payload (4 fields). The commitment is `lower_hex(SHA-256(LP("<suite>/dek-commit", project_id, environment_id, epoch, dek_hex)))` (project_id = the genesis entry hash; the standalone vector is dek-commitment.json, and the chain-published values are real computations from the dummy DEKs of the `environment_deks` section). Consensus rules: environment_id is **unique across the whole chain history** (negative `authz-create-env-duplicate`), and `rotate_epoch` requires a preceding `create_environment` (negative `authz-rotate-unknown-environment` — new_epoch 2 is a value the old "unobserved = 1" semantics would have accepted, and it fails a default-fallback implementation). The required role for `create_environment` is member or above (negative `authz-create-env-reader`). The authorization-stage check order = role → duplicate / unknown → epoch ordering (negatives `authz-create-env-role-precedes-duplicate` / `authz-rotate-role-precedes-unknown` / `authz-rotate-unknown-precedes-epoch`). The `dek_commitment_hex` format (lowercase hex, 64 chars) belongs to the **payload structure check**, preceding authorization (negatives `create-env-commitment-uppercase-hex` / `create-env-commitment-bad-length` / `rotate-commitment-uppercase-hex` / `create-env-commitment-format-precedes-role`). The commitment is also signed over (negatives `create-env-tampered-commitment` / `rotate-tampered-commitment`). The acceptance boundary is pinned by `valid_appends`' `create-environment-fresh-id` (creating an unused ID) and `rotate-freshly-created-environment` (rotate right after create = 2). **With this revision the canonical chain was fully regenerated** (the old chain contained a rotate without a preceding create, which is invalid under the new consensus rules — not a mere append; the full impact list is docs/notes/session-12.md §8-4). **This vector itself is also a human-review target in PR review** (committed ahead of the implementation)

## panva hpke's constraints and the verification approach (the spike-c findings)

- panva cannot derandomize a single-shot Seal → **implementation tests are written as "Open-direction vector match + DeriveKeyPair match + self round-trip"**. The full pinning of the Seal direction is carried by these hpke-js-generated vectors (+ the official RFC 9180 vectors)

## Conventions for negative vectors

Each element of the `negative` array carries `must_fail: true` and specifies only the fields to substitute (`decrypt_aad_hex` / `open_info_hex` / `ciphertext_hex` etc.) against the vector named by `base` (or `base_seq`). Implementation tests must check with them that "decryption / verification fails" (detecting tampering, transplants, reordering).

chain-entries.json additionally has negatives of `kind: "authorization"` (added in session 04). These are complete entries that are **cryptographically valid** (signature, normalization, and prev_hash all correct) and must be rejected only by the verification rules (§6.2 role permissions, epoch ordering, the re-grant rule). ※ Negatives of `invalid-payload` rejected at the payload-structure stage (field-size limits, dek_commitment_hex format violations) are also carried under this `kind`, since they have the same data shape of a complete entry + `expected_reason` — the rejection **stage** is prescribed by expected_reason (and the order-pinning negatives). They carry a complete entry in `entry` and the expected rejection reason in `expected_reason` (`insufficient-role` / `actor-not-member` / `last-owner-protected` / `actor-key-mismatch` / `grant-scope-narrowed` / `epoch-out-of-sequence` / `duplicate-member` / `duplicate-member-key` / `duplicate-environment` / `unknown-environment` / `invalid-payload`; 2026-09-14 ES / PF1's `scope-role-mismatch` / `scope-not-contained` / `environment-out-of-scope` / `approval-required` / `approval-not-required` / `approval-quorum-unreachable` / `unknown-proposal` / `duplicate-approval` / `proposal-expired` / `proposal-void` — convention 27; 2026-09-20 DK's `unknown-device` / `last-device-protected` / `device-cap-exceeded` — convention 28). `verify_reference.mjs` confirms the signature is **valid** (guaranteeing the rejection reason is not a cryptographic verification), and rejection by the permission rules is checked by implementation tests.

In addition, `expected_head_states` (added in session 04; semantics extended in session 13 = convention 13) pins, per `after_seq` point, the expected values derived from a verified chain: "the current member set (with role + scope — 2026-09-14 ES; with the device set `devices` — 2026-09-20 DK; omitted = the single first key) + the active grant_server set + **the environment set** (per environment: current epoch, creation seq, epoch-start seqs, per-epoch DEK commitments — §6.3's "valid interval of each epoch") + **the four-eyes policy and pending proposals** (2026-09-14 PF1 — convention 27)" (it pins the output of the §6.3 client-verification API). The old `environment_epochs` (observed epochs with default 1) was replaced by the derivation of the environment set.

The `valid_appends` of chain-entries.json (added in session 10) are complete **valid** entries that can be appended independently to the canonical chain (or to the derived chain named by `chain` — convention 27); they pin the **acceptance-side boundary** of the consensus rules (the 2 cases of member-key uniqueness's "prohibited range = the current member set only" + the 2 cases of the environment lifecycle — convention 13; scope containment and the acceptance side of four-eyes — convention 27). They carry a complete entry in `entry`, the post-acceptance current member set (role + scope) in `expected_members`, the post-acceptance current epoch per environment in `expected_environments`, and the post-acceptance policy and pending proposals in `expected_policy` / `expected_pending`. `verify_reference.mjs` confirms the validity of signature, normalization, and prev_hash; acceptance itself is checked by implementation tests.
