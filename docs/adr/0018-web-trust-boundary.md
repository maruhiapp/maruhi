# ADR-0018: The web trust boundary — hosted Web does not ship a decryptor (values and keys stay on each person's machine; screens roll out in stages)

Status: proposed 2026-08-18 (owner consent in the 2026-08-16~18 design dialogue — docs/notes/session-29.md). Accepted upon merge of PR #82. **Revision 1** (2026-08-18 owner ruling — GUI shell comparison and early fixing of the UI contract; docs/notes/session-30.md) is approved upon merge of the PR containing this revision. **Revision 2** (2026-08-28 W0 ruling — fixing the screen boundary of keyless Web and resolving item 5; docs/notes/session-39.md, screen catalog in docs/notes/web-dashboard-design.md) is approved upon merge of the PR containing this revision.

**Context**: In E2EE, decryption happens on the client, so XSS in the web frontend = leakage of every secret (CLAUDE.md: "the Web dashboard is the TCB"). The original web-dashboard concept put keys in the browser (CRYPTO_SPEC §3 "browser: IndexedDB") and did value display, push, invite acceptance (AUTH_SPEC §15-3), member add, and server grant all in the browser — meaning **the JS the operator ships becomes the decryptor**. We investigated mitigations (strict CSP / transparency logs = WEBCAT / Code Verify-style / IWA / reproducible builds + multiple signatures), but none removes the structure itself in which the distributor can be malicious (transparency is detection, not pre-execution blocking — a signed malicious build shipped to everyone passes). We also considered and rejected sharing the owner's localhost screen to other members via Tunnel / Cloudflare Mesh, and carrying a value-bearing screen to other devices over a plain Quick Tunnel (history and rejection reasons in session-29).

**Decision**:

1. **The hosted / self-host-bundled Web (`apps/web`) holds no keys and no plaintext**. What may live there: sessions; browsing metadata such as projects, environments, and variable names; issuing invite links; member lists; audit UI; needs-rotation flags; API token management (none of which needs decryption. **Additional token issuance and raw-value display were sent back to undecided by Revision 1 item 5** — listing and revocation are kept as-is). What must not live there: key generation, recovery display/restore, value display/push, invite acceptance (= declaring a key), signing / DEK-wrap operations such as `member add` / `server grant`. **The hosted bundle contains no decrypt or wrap code paths** — merely hiding the UI behind roles or feature flags is banned (as long as the shipped JS retains the capability, one XSS returns us to the original concept)
2. **Value and key operations happen on each person's machine (CLI); screens roll out in stages**. Each stage can be stopped independently, and the conditions for the next stage are satisfied in advance:
   - **Stage 1 — polish the TUI**: improve terminal display of "look-at" features such as `rotation list` / `audit` / `env diff`. Zero attack-surface increase; fully consistent with ADR-0016's TTY primary boundary
   - **Stage 2 — `maruhi ui` v1 (valueless)**: the CLI serves a screen on 127.0.0.1 only. In addition to management + browsing, it hosts the things where localhost's strengths apply (an invite-acceptance screen, a large display of the 12 fingerprint words, a key-generation wizard). Signing and wrapping stay in the CLI process; the browser does rendering and approval UI only. **No values, plaintext, or key material reach the DOM**. The local API requires authentication (one-time token + Origin check etc.)
   - **Stage 3 — `maruhi ui` with values**: predicated on demonstrated demand and a **separate ADR**. That ADR must cover the local API's authentication scheme, its relation to ADR-0016's primary boundary ("only human terminals pass") — localhost HTTP is by definition a "not-a-terminal" path, so the exception must be defined — and an explicit statement of the risk that **browser extensions enter the TCB**. If it cannot be written, we do not do it
3. **No screen sharing**. We do not build paths to show an owner's / admin's `maruhi ui` to other members via Tunnel / Mesh / screen streaming etc. — the owner's machine would become a de facto vault server, and permissions (the owner's key, not the viewer's role), availability (a single laptop), audit (the actor diverges between the key that actually opened and the viewer), and invitations (viewers are not members) all break at once. What teams share is ciphertext and keyless management metadata only. One's own other devices (a valueless remote control / QR-paired E2EE session) remain a future consideration — if a pairing session is ever built, a CRYPTO_SPEC revision comes first (within HPKE; inventing in-house tunnel crypto is banned)
4. **`maruhi ui` is a CLI-side artifact (MIT), and its artifact may contain only MIT-covered code**. "A screen that decrypts must have verifiable source and be buildable yourself" is aligned to the same license side as the CLI. The brand theme (`apps/web/theme` — ADR-0013) is shared, but it currently sits under `apps/web/LICENSE.md` (FSL-1.1-MIT) coverage, so **moving the theme onto the MIT side before sharing is a precondition for starting stage 2** (either a per-directory LICENSE declaration or a move to a neutral package [e.g. `packages/theme`] — both inside ADR-0003's implementation-record mechanism "MIT overrides via per-directory LICENSE". Coverage treatment is identical whether the source is copied in or the built CSS is bundled). If the move option is chosen, the CLAUDE.md styling rule "the sole home of brand definitions is `apps/web/theme/`" is updated in the same PR (no follow-up needed with the directory-LICENSE option). Artifacts stay separate (the hosted bundle and the ui bundle are not shared)

**Rationale**: (1) The owner's consistent criterion is **minimizing operator culpability**, and making "the operator ships no decryptor" structurally true is the only root fix (every mitigation is detection-bound). (2) ADR-0016 is mid-way through reversing the value-display boundary from deny-list (fail-open) to "only human terminals pass" (fail-closed), and a localhost value API would be a new opening on that boundary — shipping valueless avoids building both this regression and the substance of the browser-extension problem (third-party code the user installed) touching value DOM in the first place. (3) Demand for "wanting a screen" is unverified in dogfooding, and the cost of maintaining two artifacts in full form from day one — keyless Web + keyed ui — does not fit a solo development's scale. (4) Tunnel / Cloudflare Mesh (2026-04 GA; formerly WARP Connector) narrows "who it reaches", not "who decrypts" — Mesh is hub-and-spoke with all traffic via Cloudflare (Gateway inspection is the design idea), so carrying a value-bearing screen over it returns to "the path operator can see the contents".

**Consequences**:

- CRYPTO_SPEC §3's "browser: IndexedDB + non-extractable setting" contradicts this ADR's direction, so it is a future spec-revision candidate (the spec is the single source of truth — the order revise → approve → implement is unchanged). No work until the value-bearing ui ADR (stage 3)
- AUTH_SPEC §15-3's "the Web acceptance screen interprets the same format when the Web dashboard is implemented" is a revision candidate: a person who opens an invite link gets a static guidance page (saying acceptance happens in the CLI / `maruhi ui`). The link's fragment format itself is unchanged
- AUTH_SPEC §6's token list / additional-issuance UI ("to be designed when the Web dashboard is implemented") can live on keyless Web (no decryption needed) (**additional issuance and raw-value display were sent back to undecided by Revision 1 item 5** — listing and revocation kept as-is)
- Wave 3 W0 (screen design) starts from "who sees this screen". The design includes the option of shrinking keyless Web down to a static guidance page (pushing management to ui as well, minimizing the operator's delivery surface)
- SECURITY_REVIEW 2026-08-14 L-1 "CSRF header not applied to session-driven value pulls" (Low) was **fixed on 2026-08-15** (requires `x-maruhi-csrf: 1` — AUTH_SPEC §12-7). While the premise that hosted Web never pulls values shrinks the surface on which it can occur, the implemented defense is kept, not removed (insurance for self-hosted modified clients and stage 3)
- ROADMAP Phase 2 "audit-log UI, Web dashboard" gains a note pointing at this ADR
- In agent environments `maruhi ui` is also fail-closed: it does not open the value API (trivially true for v1, which is valueless; redefined in the stage-3 ADR)

## Revision 1 (2026-08-18): early fixing of the UI contract, ceremonies pinned to TTY, shell selection postponed

A revision following the comparison of the 3 GUI shell options (localhost browser / IWA / signed desktop; history and fact-checking in session-30). What is being fixed now is **not the shell but the contract between the UI and the key-holding process**.

1. **The contract between the UI and the key-holding process is fixed in advance as a precondition for starting stage 2 (shell-independent)**. The contract is **narrow per-operation APIs only** — no generic sign / wrap / decrypt endpoints (enumerating operations plus per-operation confirmation semantics minimizes the surface on which a compromised UI could use the CLI as a signing oracle). No values, plaintext, or key material are handed to the UI layer (reconfirming decision 2). The frontend is written as a client of this contract, keeping the shell (localhost / signed desktop / IWA) substitutable
2. **Ceremonies stay on TTY even with a GUI**. The "large display of the 12 fingerprint words" from decision 2 stage 2 is retracted. Fingerprint display/confirmation (mutual invite confirmation, `server grant` server-key confirmation) happens on the key-holding process's terminal (the same line as ADR-0016 decision 7's primary boundary). Reason: a ceremony's integrity depends on "the words displayed = the words the key-holding process computed"; under a configuration where the UI layer (browser extensions, WebView compromise) can swap the display, the ceremony lands in the UI's TCB. The GUI goes only as far as guiding to the ceremony ("look at your terminal")
3. **The shell is not chosen; it is sent to the stage-3 (value-bearing GUI) ruling**. Dogfooding stays on localhost (decision 2's authentication requirements = one-time token + Origin check etc., unchanged). Re-compare when demand for a value-bearing GUI is demonstrated:
   - **Signed desktop (Tauri + CLI sidecar)**: the front-runner at this time. No extensions get in and no TCP listener is needed. However it is among the largest dependency additions this repo would take (Rust toolchain = outside the existing quality gate; WebView runtime supply chain — WebView2 is externally updated on Windows, distro WebKitGTK on Linux; operating the updater signing key). Starting work is naturally judged after macOS notarization completes (ROADMAP — it overlaps with desktop signing and infrastructure)
   - **IWA (Isolated Web Apps)**: signed bundles, fixed origin, and isolation from normal extensions fit the model, but currently distribution requires Google's allowlist (an early-adopter program premised on partner contact), it is Chrome-only, and it has no path to the OS keychain. Re-evaluate once general distribution becomes possible
   - **Shell comparison** is added to the required topics of the stage-3 ADR (decision 2 of the body)
4. **Corrections to the evaluation are recorded** (ruling material from session-30): (a) the localhost UI's screen assets are also bundled and shipped inside the CLI binary — the difference from "the Web the operator serves every time" is preserved here too, and the substantive deltas between localhost and desktop are two: **extension contamination** and **the presence of a TCP listener**. (b) The signing-oracle problem is common to both configurations and so is the mitigation (items 1 and 2 of this revision). (c) The TTY check is not "human authentication" but a fail-closed guard against misoperation (local processes that can create a PTY pass — a clarification of ADR-0016's positioning, not a change)
5. **Handoff to W0 (undecided)**: of "API token management" in decision 1's allowlist, and "token list / additional-issuance UI can live on keyless Web" in Consequences — **token issuance and raw-value display** are credential generation, and "no decryption needed" and "low privilege" are different things (tokens are currently all-project admin and non-expiring by default — AUTH_SPEC §6 / SECURITY_REVIEW L-2). At W0, re-rule including the option of narrowing the hosted-Web boundary to the side that "also does not generate or display credentials" (issuance/raw-value display only on CLI / `maruhi ui`; Web goes as far as listing and revocation). The ruling material also covers whether raw tokens may appear in `maruhi ui`'s DOM (extension contamination = item 4 of this revision) or whether they stay terminal-only **(→ resolved in Revision 2: no issuance API added, device flow only; Web goes as far as listing/revocation; raw values are terminal-only — not even in `maruhi ui`'s DOM)**

## Revision 2 (2026-08-28): the W0 screen ruling — Web goes as far as "read + revoke"; credential generation/display goes to the terminal

A revision following W0 (screen design — persona analysis, comparison of 3 forms, and gap analysis are in docs/notes/web-dashboard-design.md; the ruling's history and rejected options are docs/notes/session-39.md rulings AM-AT). Narrows decision 1's allowlist and resolves Revision 1 item 5's undecided points.

1. **The keyless Web (`apps/web`) form is "static guidance + authenticated reads + revocation-type mutations only" (revision of decision 1's allowlist)**. The mutation boundary principle: **the only mutations placed on Web are ones that reduce credentials or visibility (invitation revocation, token revocation, logout). Credential generation (issuing invitations, issuing tokens), warning dismissal (`rotation dismiss` — the governance operation that clears a class-1 warning for all members), and chain writes are not placed there**. Decision 1's "what may live there" is reinterpreted under this principle (metadata browsing, member lists, audit UI, needs-rotation flags = retained as reads. Issuing invite links = removed [item 2 below]. API token management = listing and revocation only [item 3 below]). **This boundary cannot be enforced by omitting UI or bundle code — same-origin XSS is not bound by the bundle's code paths and can call any API in the victim's session (a correction from the PR #103 review). Enforcement is "don't put the capability in the bundle" (decision 1) plus a server-side capability restriction on the session principal (AUTH_SPEC §5 — restrict the APIs a session can call to an allowlist of reads + revocation-type + auth-type operations and reject the rest; the fail-closed form is the same as ADR-0016), implemented before the first screen holding a session (W2)**. Screens are kept individually stoppable and degradable; the minimal static-guidance-page form remains permanently available as the degraded form stopped at W1 (comparison and adoption reasons in W0 design document §2)
2. **Issuing invite links is excluded from Web**. An invite link's out-of-band anchors (AUTH_SPEC §15-3's `h` / `s` = the issuer's verified head, `if` = the issuer key's FP) require the issuing client's verified chain state and keys, and keyless Web has neither — normalizing anchor-less links as a regular path would make second-class links that lack the out-of-band anchor's detection material in CRYPTO_SPEC §6.3 the norm, and a form that fills in the server-reported head poisons the anchor's very meaning (out-of-band material for distrusting the server). Additionally an invite token is a bearer capability, so issuance is credential generation (the same side as item 3). Issuance is CLI / `maruhi ui` (stage 2) only; Web invitation management goes as far as listing, revocation, and guidance on how to issue
3. **Resolving Revision 1 item 5 — token issuance and raw-value display are terminal-only**: (a) the issuance path stays as device flow (AUTH_SPEC §4) only (in the 2026-08-31 full §4 revision the mechanism was replaced by a "server-mediated web-flow handoff" — session-48 ruling DF; this item's invariant "the issuance path is §4 CLI login only, with human approval" is maintained unchanged), and **no UI / API for additional issuance is built** (the raw value's place of existence is pinned to "the one terminal display at issuance" — zero attack-surface increment). (b) hosted Web goes **as far as listing and revocation** (list responses carry no raw values or hashes). (c) **raw values do not appear in `maruhi ui`'s DOM either** (browser-extension contamination = Revision 1 item 4; extensions cannot touch a terminal's display — this difference is preserved). If issuance from ui is ever needed, it is added to Revision 1 item 1's per-operation contract as a ceremony-type operation of "request issuance; the raw value is displayed on the key-holding process's terminal" (this item does not prevent that). (d) SECURITY_REVIEW L-2 (non-expiring) is resolved at the same time because this ruling is "the design point of token-management UI": an AUTH_SPEC §6 revision will specify a default TTL (draft value 90 days) + renewal on re-login
4. **Display discipline — keyless Web does not implement verification and does not call anything "verified"**. The Web bundle contains no chain/signature-verification code (under a configuration where the verifier and the data distributor are the same operator-served domain, a badge is nothing but a performance of verification — the same argument as Context; bundling a crypto subset would also complicate decision 1's bundle inspection). Every display is marked "as reported by the server", and wherever a verified display is needed the user is directed to the CLI (`maruhi project verify` / `audit verify` / `audit reconcile`). Key fingerprints shown on Web are **reference values** for cross-checking against audit/chain displays, and are never presented as verification material for mutual confirmation (the ceremony — Revision 1 item 2)
5. **A person who opens an invite link gets a fully static guidance page** (AUTH_SPEC §15-3 revision — finalizing the revision announced in Consequences): it displays only guidance that acceptance happens in the CLI and **does not interpret the URL fragment**. This invariant is enforced by construction, not convention — **the page carries no scripts at all** (served as an independent static asset outside the SPA, pinned by a per-path CSP `script-src 'none'` — AUTH_SPEC §15-3; implemented in W1). The invite token is never placed in our own code's script context, structurally cutting off drift into a Web acceptance screen. The link's fragment format and the accepting client's (CLI) interpretation are unchanged
6. The screen set (S1-S10), the gap analysis against implemented APIs (missing: project-list API, token list / targeted-revocation API — enumeration only), and the implementation split (W1-W3b, including each stage's independent stoppability) are all in docs/notes/web-dashboard-design.md as the source of truth
