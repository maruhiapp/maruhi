# ADR-0018: Web の信頼境界 — ホステッド Web は復号器を配らない(値・鍵は各人の機械。画面は段階導入)

Status: 2026-08-18 提案(2026-08-16〜18 の設計対話で所有者同意 — docs/notes/session-29.md)。PR #82 のマージをもって Accepted。**改訂 1**(2026-08-18 所有者裁定 — GUI シェル比較と UI 契約の先行確定。docs/notes/session-30.md)は本改訂を含む PR のマージをもって承認。**改訂 2**(2026-08-28 W0 裁定 — 鍵なし Web の画面境界の確定と 5 項の解消。docs/notes/session-39.md、画面目録は docs/notes/web-dashboard-design.md)は本改訂を含む PR のマージをもって承認。

**Context**: E2EE では復号がクライアントで起きるため、Web フロントの XSS = 全シークレットの漏洩である(CLAUDE.md「Web ダッシュボードは TCB」)。当初の Web ダッシュボード構想は、鍵をブラウザに置き(CRYPTO_SPEC §3「ブラウザ: IndexedDB」)、値の表示・push・招待受諾(AUTH_SPEC §15-3)・member add・server grant までブラウザで行う形だった — つまり**運営が配信する JS が復号器になる**。緩和技術を調査したが(厳格 CSP / 透明性ログ = WEBCAT・Code Verify 系 / IWA / 再現可能ビルド + 複数署名)、いずれも「配る側が悪意を持てる」構造自体は消えない(透明性は検知であり実行前ブロックではない。全員への署名済み悪意ビルドは通る)。また owner の localhost 画面を Tunnel / Cloudflare Mesh で他メンバーへ共有する案、および素の Quick Tunnel で値付き画面を他端末へ運ぶ案も検討し、却下した(経緯と却下理由は session-29)。

**Decision**:

1. **ホステッド / セルフホスト同梱の Web(`apps/web`)は鍵・平文を持たない**。置いてよいもの: セッション、プロジェクト・環境・変数名等のメタデータ閲覧、招待リンクの発行、メンバー一覧、監査 UI、要ローテーションフラグ、API トークン管理(いずれも復号不要。**トークンの追加発行・生値表示は改訂 1・5 項で未裁定へ差し戻し** — 一覧・失効は据え置き)。置かないもの: 鍵生成、リカバリーの表示・復元、値の表示・push、招待の受諾(= 鍵の宣言)、`member add` / `server grant` 等の署名・DEK ラップ操作。**ホステッド用バンドルに復号・ラップのコードパスを含めない** — role やフィーチャーフラグで UI を隠すだけの形は禁止(配った JS に能力が残る限り XSS 一発で当初構想に戻る)
2. **値・鍵の操作は各人の機械(CLI)で行い、画面は段階導入する**。各段は独立に停止可能とし、次段へ進む条件を先に満たす:
   - **第 1 段 — TUI を磨く**: `rotation list` / `audit` / `env diff` 等の「眺める」系の端末表示改善。攻撃面の増加ゼロ、ADR-0016 の TTY 一次境界と完全に整合
   - **第 2 段 — `maruhi ui` v1(値なし)**: CLI が 127.0.0.1 のみで画面を出す。管理 + 閲覧に加え、localhost の強みが効くもの(招待受諾の画面、指紋 12 語の大きな表示、鍵生成ウィザード)を置く。署名・ラップは CLI プロセス、ブラウザは描画と承認 UI のみ。**値・平文・鍵素材を DOM に出さない**。ローカル API には認証(ワンタイムトークン + Origin 検査等)を課す
   - **第 3 段 — 値あり `maruhi ui`**: 需要の実証と**独立 ADR** を前提とする。その ADR はローカル API の認証方式、ADR-0016 の一次境界(「人間の端末だけ通す」)との関係 — localhost HTTP は定義上「端末でない」経路であり、例外の定義が要る —、および**ブラウザ拡張が TCB に入る**リスクの明示を含まなければならない。書けなければやらない
3. **画面の共有は行わない**。owner / admin の `maruhi ui` を他メンバーへ Tunnel / Mesh / 画面配信等で見せる経路は作らない — owner 機が事実上の vault サーバーになり、権限(見る人の role でなく owner の鍵)・可用性(一台のラップトップ)・監査(actor = 実際に開いた鍵と閲覧者の乖離)・招待(視聴者はメンバーでない)が同時に壊れる。チームで共有するのは暗号文と鍵なしの管理メタデータのみ。自分の他端末(値なしリモコン / QR 配対の E2EE セッション)は将来の検討課題として残す — 配対セッションを作る場合は CRYPTO_SPEC の改訂が先(HPKE の範囲で。独自トンネル暗号の発明は禁止)
4. **`maruhi ui` は CLI 側の配布物(MIT)とし、その成果物に含めてよいのは MIT 被覆のコードのみとする**。「復号する画面はソースを検証でき、自分でビルドできる」を CLI と同じライセンス側に揃える。ブランドテーマ(`apps/web/theme` — ADR-0013)は共有するが、現状は `apps/web/LICENSE.md`(FSL-1.1-MIT)の被覆下にあるため、**共有に先立って theme を MIT 側へ置き直すことを第 2 段着手の前提とする**(ディレクトリ単位の LICENSE 明示、または中立パッケージ〔例: `packages/theme`〕への移動 — いずれも ADR-0003 実施記録の「MIT はディレクトリ単位の LICENSE で上書き」の機構内。ソース取り込みでもビルド済み CSS の同梱でも被覆の扱いは同じ)。移動側を選ぶ場合は CLAUDE.md styling 規律の「ブランド定義は `apps/web/theme/` が唯一の置き場所」の追随更新を同じ PR で行う(ディレクトリ LICENSE 側なら追随不要)。成果物は分離する(ホステッド用バンドルと ui バンドルを共用しない)

**Rationale**: (1) 所有者の一貫した基準は**運営の非の最小化**であり、「運営は復号器を配らない」を構造で真にするのが唯一の根本対策(緩和技術はどれも検知どまり)。(2) ADR-0016 は値表示の境界を deny-list(fail-open)から「人間の端末だけ通す」(fail-closed)へ反転させる途中であり、localhost の値 API はこの境界への新しい口になる — 値なしで出せばこの逆行と、ブラウザ拡張(ユーザーが入れた第三者コード)が値の DOM に触れる問題の本体を、最初から作らない。(3)「画面が欲しい」の需要はドッグフーディングで未検証であり、鍵なし Web + 鍵あり ui の 2 成果物を最初から完全形で維持するコストは個人開発の規模に合わない。(4) Tunnel / Cloudflare Mesh(2026-04 GA。旧 WARP Connector)は「誰に届くか」を狭める道具であって「誰が復号するか」を変えない — Mesh は星型で全トラフィックが Cloudflare 経由(Gateway 検査が設計思想)であり、値付き画面の運搬に使うと「経路の運営が中身を見られる」形に戻る。

**Consequences**:

- CRYPTO_SPEC §3 の「ブラウザ: IndexedDB + 非抽出設定」は本 ADR の方向と矛盾するため、将来の仕様改訂候補(仕様が唯一の正 — 改訂 → 承認 → 実装の順は不変)。値あり ui の ADR(第 3 段)までは着手しない
- AUTH_SPEC §15-3 の「Web の受諾画面は Web ダッシュボード実装時に同じ形式を解釈する」は改訂候補: 招待リンクを開いた人には静的な案内ページ(受諾は CLI / `maruhi ui` で行う旨)を出す。リンクのフラグメント形式自体は変えない
- AUTH_SPEC §6 のトークン一覧・追加発行 UI(「Web ダッシュボード実装時に設計」)は鍵なし Web に置ける(復号不要)(**追加発行・生値表示は改訂 1・5 項で未裁定へ差し戻し** — 一覧・失効は据え置き)
- Wave 3 W0(画面設計)は「誰がこの画面を見るか」から始める。鍵なし Web を静的案内ページまで縮める選択肢(管理も ui へ寄せ、運営の配信面を最小化)を含めて設計する
- SECURITY_REVIEW 2026-08-14 の L-1「セッション主体の値付き pull への CSRF ヘッダー未適用」(Low)は **2026-08-15 に修正済み**(`x-maruhi-csrf: 1` 要求 — AUTH_SPEC §12-7)。ホステッド Web が値を pull しない前提では発生面自体が縮むが、実装済みの防御は撤去せず維持する(セルフホスト改造クライアント・第 3 段の保険)
- ROADMAP Phase 2「監査ログ UI、Web ダッシュボード」に本 ADR の注記を追加
- エージェント環境では `maruhi ui` も fail-closed: 値 API を開かない(v1 は値なしのため自明。第 3 段の ADR で再定義)

## 改訂 1(2026-08-18): UI 契約の先行確定・儀式の TTY 固定・シェル選定の先送り

GUI シェル 3 案(localhost ブラウザ / IWA / 署名済みデスクトップ)の比較(経緯と事実確認は session-30)を受けた改訂。いま確定するのは**シェルではなく、UI と鍵保持プロセスの間の契約**である。

1. **UI と鍵保持プロセスの契約を第 2 段着手の前提として先に確定する(シェル非依存)**。契約は**操作別の狭い API のみ**とし、汎用の sign / wrap / decrypt エンドポイントを作らない(UI 側の侵害が CLI を署名オラクルとして使う面を、操作の列挙と各操作の確認意味論で最小化する)。値・平文・鍵素材を UI 層に渡さない(決定 2 の再確認)。フロントエンドはこの契約のクライアントとして書き、シェル(localhost / 署名済みデスクトップ / IWA)を差し替え可能に保つ
2. **儀式は GUI があっても TTY に残す**。決定 2 第 2 段の「指紋 12 語の大きな表示」を撤回する。指紋の表示・確認(招待の相互確認・`server grant` のサーバー鍵確認)は鍵保持プロセスの端末で行う(ADR-0016 決定 7 の一次境界と同じ線)。理由: 儀式の完全性は「表示された語 = 鍵保持プロセスが計算した語」に依存し、UI 層(ブラウザ拡張・WebView 侵害)が表示をすり替えられる構成では儀式が UI の TCB に載ってしまう。GUI は儀式への導線(「端末を見てください」)までとする
3. **シェルの選定は行わず、第 3 段(値あり GUI)の裁定に送る**。ドッグフーディングは localhost(決定 2 の認証要件 = ワンタイムトークン + Origin 検査等のまま)。値あり GUI の需要が実証された時点で再比較する:
   - **署名済みデスクトップ(Tauri + CLI sidecar)**: 現時点の本命。拡張機能が入らず TCP リスナーも不要。ただし本リポジトリ最大級の依存追加になる(Rust ツールチェーン = 既存品質ゲートの対象外、WebView ランタイムの供給網 — Windows は WebView2 が外部更新・Linux は distro の WebKitGTK、updater 署名鍵の運用)。着工判断は macOS 公証(ROADMAP — デスクトップ署名とインフラが重なる)の完了後が自然
   - **IWA(Isolated Web Apps)**: 署名済みバンドル・固定 origin・通常拡張から隔離とモデルは合うが、現状は Google の allowlist(パートナー接触前提の early adopter program)で一般配布不可・Chrome 限定・OS キーチェーンへの経路もない。一般配布可能になった時点で再評価
   - 第 3 段 ADR の必須論点(本文決定 2)に**シェル比較**を追加する
4. **評価の補正を記録する**(session-30 の裁定材料): (a) localhost UI の画面アセットも CLI バイナリに同梱されて配られる — 「運営が毎回配信する Web」との差はここでも保たれており、localhost とデスクトップの実質差分は**拡張機能の混入**と **TCP リスナーの存在**の 2 点。(b) 署名オラクル問題は両構成に共通で、緩和も同じ(本改訂 1・2 項)。(c) TTY 判定は「人間の認証」ではなく fail-closed の誤操作ガードである(PTY を作れるローカルプロセスは通る — ADR-0016 の位置づけの明確化であり変更ではない)
5. **W0 への申し送り(未裁定)**: 決定 1 の許可リストに含まれる「API トークン管理」、および Consequences の「トークン一覧・追加発行 UI は鍵なし Web に置ける」のうち、**トークンの発行・生値の表示**は credential の生成であり、「復号不要」と「低権限」は別物(現状トークンは既定で全プロジェクト admin・無期限 — AUTH_SPEC §6 / SECURITY_REVIEW L-2)。W0 で、hosted Web の境界を「credential も生成・表示しない」側へ狭める選択肢(発行・生値表示は CLI / `maruhi ui` のみ、Web は一覧・失効まで)を含めて再裁定する。その際、生値トークンを `maruhi ui` の DOM に出してよいか(拡張機能の混入 = 本改訂 4 項の面)、それとも端末限定に留めるかも裁定材料に含める **(→ 改訂 2 で解消: 発行 API は追加せず device flow のみ、Web は一覧・失効まで、生値は端末限定 — `maruhi ui` の DOM にも出さない)**

## 改訂 2(2026-08-28): W0 画面裁定 — Web は「読み取り + 失効」まで、credential の生成・表示は端末へ

W0(画面設計 — ペルソナ分析・3 形比較・gap 分析は docs/notes/web-dashboard-design.md、裁定の経緯と棄却案は docs/notes/session-39.md 裁定 AM〜AT)を受けた改訂。決定 1 の許可リストを狭め、改訂 1・5 項の未裁定を解消する。

1. **鍵なし Web(`apps/web`)の形は「静的案内 + 認証済み読み取り + 失効系 mutation のみ」とする(決定 1 の許可リストの改訂)**。mutation の境界原則: **Web に置く mutation は資格・可視性を減らす方向(招待の失効・トークンの失効・ログアウト)のみ。資格の生成(招待発行・トークン発行)、警告の消去(`rotation dismiss` — クラス 1 警告を全メンバーから消すガバナンス操作)、チェーン書き込みは置かない**。決定 1 の「置いてよいもの」はこの原則で読み替える(メタデータ閲覧・メンバー一覧・監査 UI・要ローテーションフラグ = 読み取りとして存置。招待リンクの発行 = 削除〔下記 2〕。API トークン管理 = 一覧・失効のみ〔下記 3〕)。**この境界は UI・バンドルの省略では強制にならない — 同一オリジン XSS はバンドルのコードパスに拘束されず、被害者のセッションで任意の API を呼べる(PR #103 レビューでの補正)。強制は「バンドルに能力を入れない」(決定 1)に加えて、サーバー側のセッション主体の能力制限(AUTH_SPEC §5 — セッションが呼べる API を読み取り + 失効系 + 認証系の肯定列挙に制限し、それ以外を拒否する。fail-closed の型は ADR-0016 と同じ)で行い、セッションを持つ画面の初出(W2)より前に実装する**。画面は個別に停止・縮退可能に保ち、静的案内ページ最小形は W1 のみで止めた縮退形としていつでも選べる(比較と採用理由は W0 設計文書 §2)
2. **招待リンクの発行を Web から除外する**。招待リンクの帯域外アンカー(AUTH_SPEC §15-3 の `h` / `s` = 発行者の検証済みヘッド、`if` = 発行者鍵 FP)は発行者クライアントの検証済みチェーン状態と鍵を要し、鍵なし Web はどちらも持たない — アンカーなしリンクの正規経路化は CRYPTO_SPEC §6.3 帯域外アンカーの検出材料を欠く第二級リンクを常態化させ、サーバー申告ヘッドを埋める形はアンカーの意味(サーバー不信の帯域外材料)自体を毒化する。加えて招待トークンは bearer capability であり、発行は credential の生成(3 項と同じ側)。発行は CLI / `maruhi ui`(第 2 段)のみとし、Web の招待管理は一覧・失効 + 発行手順の案内までとする
3. **改訂 1・5 項の解消 — トークンの発行・生値表示は端末限定**: (a) 発行経路は device flow(AUTH_SPEC §4)のみを据え置き(2026-08-31 の §4 全面改訂で機構は「サーバー仲介 web-flow ハンドオフ」へ置換 — session-48 裁定 DF。本項の不変条件「発行経路は §4 の CLI ログインのみ・人間の承認つき」は不変のまま維持される)、**追加発行の UI / API を作らない**(生値の存在場所を「発行時の端末表示 1 箇所」に固定 — 攻撃面の増分ゼロ)。(b) hosted Web は**一覧・失効まで**(一覧応答に生値・ハッシュを載せない)。(c) **`maruhi ui` の DOM にも生値を出さない**(ブラウザ拡張の混入 = 改訂 1・4 項。ターミナルの表示には拡張が触れない — この差を保つ)。将来 ui からの発行が必要になれば、改訂 1・1 項の操作別契約に「発行を依頼し、生値は鍵保持プロセスの端末に表示する」儀式型操作として追加する(本項はそれを妨げない)。(d) SECURITY_REVIEW L-2(無期限)は本裁定が「トークン管理 UI の設計時点」であるため同時解消: AUTH_SPEC §6 改訂で既定 TTL(起草値 90 日)+ 再ログイン更新を規定する
4. **表示規律 — 鍵なし Web は検証を実装せず、「検証済み」を名乗らない**。Web バンドルにチェーン・署名検証のコードを入れない(検証者とデータ配布者が同一の運営配信ドメインにある構図では、バッジは検証の演出にしかならない — Context と同じ論法。crypto サブセットの同梱は決定 1 のバンドル検査も複雑化させる)。全表示は「サーバー申告(as reported by the server)」と明示し、検証済み表示が要る場面は CLI(`maruhi project verify` / `audit verify` / `audit reconcile`)へ誘導する。Web に表示する鍵フィンガープリントは監査・チェーン表示との突合用の**参照値**であり、相互確認(儀式 — 改訂 1・2 項)の照合材料として提示しない
5. **招待リンクを開いた人には完全静的な案内ページを出す**(AUTH_SPEC §15-3 改訂 — Consequences の予告済み改訂の確定): 受諾は CLI で行う旨の案内のみを表示し、**URL フラグメントを解釈しない**。この不変条件は規約でなく構成で強制する — **ページはスクリプトを一切持たない**(SPA 外の独立静的アセットとして配信し、per-path の CSP `script-src 'none'` で固定する — AUTH_SPEC §15-3。実装は W1)。招待トークンを自前コードの script 文脈に載せず、Web 受諾画面への漂流を構造的に断つ。リンクのフラグメント形式・受諾クライアント(CLI)の解釈は不変
6. 画面集合(S1〜S10)・実装済み API との gap 分析(不足: プロジェクト一覧 API、トークン一覧・指定失効 API — 列挙のみ)・実装分割(W1〜W3b。各段の独立停止可能性込み)は docs/notes/web-dashboard-design.md を正とする
