# ADR-0016: The CLI argument layer is effect/unstable/cli (gunshi abolished) + the value-display boundary is TTY-primary

Status: proposed 2026-08-16. Accepted as owner approval upon merge of the migration PR (promoting the spike to src).

**Context**: gunshi 0.37.1 has multiple shapes that "silently let through invocations that contradict the declaration and produce **the opposite of what was written**" (12 shapes measured. `docs/notes/cli-parser-alternatives.md` §2). Examples: treats `--show=false` as `true` without reading the value; silently discards repeats of the same option as last-wins; drops an empty string after `--` from rest; resolves commands across `--`. maruhi had been plugging these from the outside in `apps/cli/src/args.ts` (911 lines) and per-command tests, but new gaps kept appearing through review rounds 7-10 (08b8a98 / 0ea3a34 / ef7cba1). The ef7cba1 shape in particular (if `--show` sneaks into the `$FLAGS` of `maruhi pull --no-show $FLAGS`, **all secrets are printed to the terminal**) is a case where the parser's silence turns directly into a secret leak.

Meanwhile, effect v4 ships a CLI as a bundled unstable module (`effect/unstable/cli`). Measuring the same 12 shapes on both beta.107 and rc.109 showed **10 shapes disappear structurally**, and a 3-command spike (`pull` / `run` / `env create`; `apps/cli/test/support/` + 32 conformance checks) confirmed the remaining 2 (silence on duplicates, the help output destination) can also be closed with Effect mechanisms. effect is already tracking 4.0.0-rc.109 (a corollary of ADR-0011; zero source changes, all gates green).

It was also confirmed that `gunshi/agent` (detection of AI-agent environments) is just a thin wrapper over std-env's `agentInfo` — not a gunshi-specific lock-in.

**Decision**:

1. **The argument layer is `effect/unstable/cli`. gunshi is abolished entirely** (including `gunshi/agent`). The only added dependency is `@effect/platform-bun` (`BunServices.layer` supplies `FileSystem` / `Path` / `Stdio` / `Terminal` / `Crypto` / `ChildProcessSpawner`); its version is aligned with `effect` (currently 4.0.0-rc.109) and pinned exactly
2. **Do not write our own scans for argument checking**. Everything is expressed as declarations: repeated flags = `Flag.atMost(1)` (**always attach it, even to booleans** — a bare `Flag.boolean` resolves duplicates silently and the result depends on the order typed); empty or whitespace-only values = `Flag.withSchema` (Schema); `maruhi run`'s required run target = `Argument.atLeast(1)` + `Argument.filter`. The scan routines in `args.ts` (detecting values on booleans, rebuilding rest, recounting positionals, generating candidates, gunshi's error mapping) are deleted (a function-level estimate: 525 / 911 lines)
3. **Diagnostics are injected by implementing `CliOutput.Formatter` and providing `CliOutput.layer`**. `renderErrors` stays default and **the render call remains upstream (`showHelp` → `Console`)** — if the runner grows its own render branch, a hole appears where paths added upstream later pass straight through. What may appear in message text is **only declared names, candidates, counts, and expected types**. In addition to `UnexpectedArgument.arguments` / `InvalidValue.value`, **`InvalidValue.expected`** can also contain the entered value (upstream's `Param.filter` inserts `onNone(a)` verbatim), so `expected` is printed **only when it matches wording we wrote**. `formatHelpDoc` prints the full text only for an explicit `--help` run; attached to an error it is one line of usage
4. **Exit codes live on the error types via `Runtime.errorExitCode`**. No mapping table on the runner. The sole exception is `ShowHelp`: upstream declares `errors.length ? 1 : 0` (= **malformed invocations would exit 1**), so we **remap it to 2 in the teardown passed to `makeRunMain({ teardown })`** (`CliConfig` has no exit-code setting; this hook is all upstream offers). Tests go through the same teardown, because hand-computing on the harness side cannot check the production startup path
5. **Built-in global flags are restricted to `--help` / `--version` via `CliConfig`**. By default `--wizard` / `--completions` / `--log-level` sprout on every command, and **`maruhi pull --wizard` actually launches the interactive wizard** (measured). A secrets tool must not carry undeclared interactive or output paths. If shell completion is ever needed, it is decided separately as an explicit command (`maruhi completions`)
6. **`env` / `server` / `invite` / `member` become true nested subcommands**. The rejection machinery for "options that don't apply to that operation" (`ENV_ACTION_FLAGS` / `optionRestrictedTo` / `actionFlagRejection` / `withoutPositionals`) — needed only because gunshi's single-level constraint forced operations into positional arguments — is abolished
7. **The value-display boundary (`pull --show`) is a fail-closed two-layer design**. Primary boundary = **both** `stdin` and `stdout` are terminals (`Stdio.stdinIsTerminal` / `stdoutIsTerminal`). Secondary layer = known-agent environment variables (**std-env as a direct dependency**, exact pin, synchronous API). All decision inputs are obtained via Effect services; `process.*` is never read directly.

   **Scope (2026-08-16 owner ruling)**: the CLI has 9 other gates that consult `isAgent`.

8. **`maruhi run` keeps `--` mandatory**. The check is done in an Effect that reads `Stdio.args` (`TerminatorRequired`, exit 2)
9. **stdout carries only command output**. Help and diagnostics are routed to stderr by replacing `Console`. This is held as a **mechanism**, not a discipline: command output flows to `Stdio`'s stdout Sink, rendering goes to `Console` (stderr), and writes to real fds that take neither path are caught by a safety net — with three separate paths, cross-talk is detectable in tests
10. **Migration is staged**. First the PR promoting the spike's 3 commands (`pull` / `run` / `env create`) to src, then commands with operation-flag machinery (`env rotate` / `diff`, `server`, `invite`, `member`), then the rest. There is no bulk migration of all 14 subcommands at once
11. **`maruhi run` does not pass `MARUHI_*` environment variables to its child** (2026-08-27 deepsec S6). In keychain-less / CI environments, `MARUHI_TOKEN` / `MARUHI_TOKEN_ORIGIN` are inputs for the parent CLI to resolve a session, not values for the run to consume. Passing them to the child would let dependency code read a PAT that is longer-lived and broader-scoped than the injected values, usable even after the run ends. The parent's general environment and the decrypted `extraEnv` are passed as before, but the `MARUHI_` prefix is stripped case-insensitively from both. **A nested maruhi does not implicitly inherit the parent's env token**: in interactive environments with an OS keychain it can resolve independently via the keychain, but calling maruhi again inside `maruhi run -- make` in keychain-less / CI is not supported. Do the needed maruhi operations outside the run and pass only the values the child actually consumes

**Rationale**: (1) The dangerous gunshi-derived shapes disappear **structurally** — plugging them from the outside has shown over 4 rounds of review that the gaps never run out. (2) The argument layer unifies on Effect typed errors (`Schema.TaggedError`); the current `runCli`'s `Execute` bridge, the `Effect.runPromise` round-trip, and the defense that keeps defects from masquerading as usage errors all become unnecessary. (3) Checking, diagnostics, exit codes, and terminal detection all sit on Effect substitution points, so the in-house part shrinks to "the message text itself". (4) The deny-list for agent detection is **fail-open** — environment-variable standardization is unsettled (`AGENT` and `AI_AGENT` coexist; Claude Code / Cursor / Gemini CLI each do their own; VS Code / Copilot take the opposite stance), and the detection libraries' coverage is not even mutually a subset. Reversing from "block the ones we know" to "only let human terminals through" means **unknown agents are also blocked by default**. Measured: under Claude Code, `isTTY` on `stdin/stdout/stderr` were all false.

**Consequences**: Most of the existing CLI tests — **the ones checking how arguments are written (`args.test.ts` and the isomorphic per-command cases) — become unnecessary**. In the migration PR they are replaced, not deleted, by checks that "the same shapes are rejected by declarations (`Flag` / `Argument`)"; the dangerous shapes (duplicates, empty values, empty string after `--`, whether values may be displayed) are kept without exception. The ADR-0015 npm distribution bundle also folds in `@effect/platform-bun` (the policy of not propagating into the user's dependency graph is unchanged). `Bun.secrets` / `Bun.spawn` remain confined to `live.ts` (within ADR-0004). `effect/unstable/cli` is an unstable module and its API may move between rc → stable (a corollary of ADR-0011: exact pin + updates as separate PRs; from beta.107 → rc.109 neither the 12 shapes' behavior nor the probe sources needed changes). There are 6 UX changes:

1. **`maruhi pull --show > secrets.txt` is refused** (it is an operation that drops plaintext onto disk; refusal is correct under the diskless invariant)
2. **Help attached to argument errors becomes a single usage line**
3. **In the three ceremony spots, the "stdin is a terminal but stdout is piped" shape is refused** (the ruled portion of decision 7), because the primary boundary requires **both** stdin and stdout to be terminals. Only paths that leave out-of-band fingerprint verification to the CLI are affected; **CI paths that pass the flag are unaffected** (the ceremony is reached only when no fingerprint flag is given):

   | Command | Affected shape | Workaround |
   |---|---|---|
   | `maruhi invite accept <link>` | piping stdout, e.g. `\| tee audit.log` | pass `--inviter-fingerprint <fp>` |
   | `maruhi member add` | same as above | pass `--expect-fingerprint <fp>` |
   | `maruhi server grant` | same as above | pass `--expect-fingerprint <fp>` |

   In a ceremony where fingerprints are compared by eye, piping stdout means the human cannot read the words, so refusal is correct.
4. **Recovery-code display/input only passes when all of stdin / stdout / stderr are TTYs**. `2>` or CI capture could persist the code, so they are refused. `key recovery` / `key recover` without a TTY exits 1. If automatic issuance from `key generate` hits the same refusal, the guidance says master-key generation itself has completed and the code can be issued later on an interactive terminal
5. **A `maruhi run` child does not receive the parent's `MARUHI_*`**. Configurations where a nested maruhi implicitly uses the parent's PAT under keychain-less / CI stop working. The general environment and actual injected values are inherited as before
6. **`maruhi invite create` does not issue unless all three channels are TTYs**. The practice of capturing the link printed to stdout in scripts is abolished; only the path where a human hands it over a person-to-person channel from an interactive terminal is allowed

Dependencies: `@effect/platform-bun` (+ `@effect/platform-node-shared`) and `std-env` are added; `gunshi` is gone. The bundle's effective growth is ~190KB (noise against a 62-96MB standalone binary). Fallback path: swap only the parser to `@stricli/core` (zero dependencies — the only candidate whose parser itself refuses duplicates and values on booleans); in that case the wiring to Effect becomes in-house again as today. `Bun.isAIAgent()` is not adopted because it is a Zig internal, not a public JS API (if Bun 1.4 exposes it to JS, re-decide it as a secondary-layer implementation; its detection coverage is narrower than std-env's).

**Addendum (2026-08-17 — completion of stage 3 and its rulings)**: migration of all commands is complete and gunshi was removed from the dependencies (implementation of decisions 1 and 2). Rulings that became necessary during migration are recorded here:

1. **bare `maruhi audit` = list is kept**. Measurement confirmed that a parent with a handler (`Command.make(name, config, handler)` + `Command.withSubcommands`) runs its handler on a bare invocation, runs only the child when a subcommand is given, and produces `UnknownSubcommand` (exit 2 via teardown) for unknown subcommands. Since the parent has the same declaration as list, `maruhi audit --limit 5` also passes as before (the parent's declaration is also poured into COMMAND_SPECS for diagnostics — GROUP_PARENT_CONFIGS in effect-cli.ts)
2. **bare `maruhi` (no arguments) keeps exit 0; output moves stdout → stderr**. A bare root is treated as a help request (same as `maruhi --help`). Keeping the gunshi-era exit 0 and "usage + command list", the output destination follows decision 9 (stdout carries only command output). A bare **subcommand level** (`maruhi env` alone) remains a malformed invocation as before (exit 2). Exception: **only `--version` output goes to stdout** (`V=$(maruhi --version)` is a command output — a contract since the gunshi era — version.test.ts)
3. **Hidden flags** (login's `--github-base-url` / `--github-poll-interval`) are built with `Param.makeSingle({ hidden: true })`. Measured: both upstream's help rendering and typo candidates exclude hidden flags. maruhi's own diagnostics list (specOf) also walks wrappers (Map / Variadic / Transform / Optional) down to the leaf to exclude hidden ones
4. **The dedicated diagnostic for invocations with no command name before `--` is kept** (`maruhi -- run printenv`). Effect's diagnostic can only say "extra argument" and cannot convey the fix (put the command name first). The scan that depended on gunshi's `parseArgs` (old args.ts's `commandTokens` / `commandNameAfterTerminator`) was replaced by a minimal in-house lexer inside runCli (classifying tokens only up to `--`; it is material for routing, not the "checking scan" decision 2 bans)
5. **args.ts was deleted in full**. The attribution table in notes/cli-parser-alternatives.md §6 estimated "12 functions / 222 lines remain as policy", but as the spike's rounds 2-3 measured, everything was replaced by declarations (`Flag.atMost(1)` / `withSchema` / `Argument.atLeast(1)`) and the Formatter; all that remained was item 4's minimal lexer (~30 lines, cli.ts)
6. The rest of decision 6's rejection machinery (`AUDIT_ACTION_FLAGS` / `optionRestrictedTo` / `actionFlagRejection` for audit) also became unnecessary with separated declarations and was deleted
7. **Behavior changes**: a number flag with no value / an unparsable number goes from gunshi's internal error (exit 1) to `InvalidValue` (usage = exit 2). `rotation dismiss --all=false` goes from "reads no value → true" to "false, as written" (shape #2 of the 12). A leading empty argument (`maruhi "" pull`) goes from skipped to root `UnknownSubcommand` (exit 2). `maruhi maruhi` is now just an unknown command. **Writing audit's flags before the subcommand, like `maruhi audit --limit 5 list`, exits 2** (upstream does not inherit a parent's local flags into subcommands) — the diagnostic points out where to put them (after the subcommand, or bare `maruhi audit`). Also **`--version` / `--help` short-circuit first as built-ins** (upstream spec): malformed invocations mixed into the same argv (`maruhi --version --bogus`) are not reported and exit 0. Accepted because such invocations cannot reach a value-writing path (pinned in a test)
8. **Tokens after `--` fill positional-argument slots** (measured upstream: the parser folds them into `[...result.arguments, ...afterEndOfOptions]` — the same property already noted in decision 8's implementation comment). `maruhi config set -- defaultEnvironment dev` passes with exit 0, and it works as **the POSIX escape hatch for writing positionals that start with `-`**, e.g. `maruhi member remove -- -user-with-dash`. No token is silently discarded — anything beyond the positional slots is an extra positional as before (exit 2). Only `run` treats what follows `--` specially as the command line to execute (commandAfterTerminator in effect-cli.ts), per decision 8. This folding is accepted and pinned in a test (a ruling prompted by a Pullfrog review comment)
