# ADR-0012: IaC is Alchemy v2 Effect style + self-hosting also supported via wrangler (Revision 1: the hosted pair is adopted)

**Context**: The deploys we operate ourselves (cloud edition, development environments) and the distributed artifact users self-host have different requirements.
**Decision**: Operations side uses Alchemy v2's Effect style (typed wiring of infrastructure and runtime). The self-hosted distribution always keeps a path that stands up with plain wrangler config / a Deploy to Cloudflare button, and never forces an Alchemy dependency on users.
**Rationale**: "One click to stand up in your own account" is the core of the product's value, so the distribution's dependencies must be minimal. Double-maintaining deploy definitions is accepted as the price of lowering the barrier to entry.
**Consequences**: Fallback path: Alchemy's async style, or a full retreat to wrangler. CI verifies the self-hosted path (wrangler only) deploy.

## Revision 1 (2026-11-14): the hosted pair is adopted

Status: owner decisions 2026-11-13 (adopt Alchemy for the ops-side deploy) and 2026-11-14 (the hosted state store; D1 / R2 lookup-only, confirmed by an independent second-opinion review); accepted upon merge of the PR containing this revision. The original decision stands for the self-hosted distribution; this revision settles how the ops side is actually declared, and refines the original "Effect style" wording: the stack program is an Effect program, but the application-facing declarations use the async (props) form, so the application source stays Alchemy-independent and the `cf` path keeps working unchanged.

**Decision**: `alchemy.run.ts` at the repository root declares exactly two workers — the hosted worker (`maruhi-server-hosted`) and the apex site (`maruhi-site`) — and nothing else.

1. **Async Worker form.** Each worker is declared with `main` pointing at the existing entry module plus props (bindings, triggers, observability, assets). No Effect-native Worker / Durable Object notation enters the application source; `ProjectChainDO` stays a plain exported class in `apps/server`, its binding declared with the provider's `DurableObjectLike` shape (`kind: "Cloudflare.DurableObject"`, `className`, `storage: "sqlite"`, no `scriptName` — the reconcile adopts the existing class by name).
2. **Hosted state store.** State is `Cloudflare.state()` — Alchemy's hosted store (a per-account state worker + secrets store, bootstrapped once with `alchemy state bootstrap`). Every run of this program, local plans included, uses the hosted store — the file-state default exists only when `state:` is omitted, which this program never does; that is why every plan or deploy run — the operator's, there is no CI plan step (point 6) — needs account credentials and the one-time bootstrap. The alternative (a self-built store behind `state:`) is rejected: state durability and shareability cannot be retrofitted cheaply, and the added surface is one small ops-account worker plus one secret, in an account a token holder can already operate fully.
3. **D1 and R2 are lookup-only.** `Cloudflare.D1.Database.lookup` / `Cloudflare.R2.Bucket.lookup` bind the existing database (`maruhi`) and bucket (`maruhi-ops-backup`) by name; Alchemy never creates, migrates, updates or deletes them. Reasons: the provider's R2 reconcile clears lifecycle rules / CORS / domains when the props omit them, so managing the bucket would silently delete its load-bearing `retain-35d` lifecycle rule (ops task O2; the DR design's 35-day expiry of encrypted D1 exports) on the adopting deploy — a removal policy does not cover reconcile-time sync; and managed D1 adoption is one-way (the migration history converts to Alchemy's ledger), couples every worker deploy to that ledger, and makes `db:migrate:hosted` a dual-writer hazard. Lookup writes nothing to state and has no delete path, while `alchemy plan` still verifies the targets exist. Revisit managed adoption only when Alchemy is past beta **and** a concrete drift incident or deploy mis-ordering has occurred.
4. **Names and stage are pinned.** Worker names are set exactly with the `name` prop (Alchemy's default physical naming is not used for them — the hosted name is load-bearing: the restore worker binds its DO namespace cross-worker by name). Deploys and plans always pass the stage explicitly (root scripts `alchemy:deploy` / `alchemy:plan`, both `--stage prod`).
5. **Secrets are declared, values stay out of band.** All four hosted Workers Secrets (`GITHUB_CLIENT_ID`, `GITHUB_CLIENT_SECRET`, `SERVER_ENC_KEY_IKM`, `OPS_ALERT_WEBHOOK_URL`) are declared as `Config.Redacted` env entries. An Alchemy upload rebuilds the binding list from the program, so an undeclared secret binding would be dropped; the values are read from the deploy environment and uploaded as `secret_text` on every deploy, never stored in the repository.
6. **CI verifies both paths — the Alchemy side statically.** The hosted and site `cf` dry-runs are removed, and `apps/server/scripts/check-hosted-config.ts` now compares `alchemy.run.ts` against the cf hosted config as a third carrier of the hosted shape, alongside the typecheck and lint the program already gets. The live `alchemy plan` is an operator step, not a CI step: evaluating the program needs the account credentials and the four hosted secret values, and `ci.yml` holds no secrets by supply-chain policy (`apps/cli/test/workflows-supply-chain.test.ts` classifies it as an unprivileged workflow). The self-host and restore dry-runs stay on `cf`.

**Consequences**:
- The self-host worker and the restore worker are unchanged (plain `cf`, `apps/server/cloudflare.config.ts`); the self-hosting path remains Alchemy-free, as the original decision requires.
- The apex site's own `cf` deploy script (`apps/site`'s `deploy`) is removed: after this revision the site deploys only through the root Alchemy scripts. A `cf` deploy would run outside Alchemy's state and fight the next reconcile. The `apps/site/cloudflare.config.ts` declaration stays for local preview; it no longer deploys anything.
- Deploying the hosted pair requires all four secret values in the deploy environment. They are write-only in Cloudflare, so the operator must hold them (notably `SERVER_ENC_KEY_IKM`); this is a precondition of the first adopting deploy.
- Alchemy injects its own `ALCHEMY_*` plain-text metadata bindings into the hosted worker's env. They are inert for the application (its env contract reads named fields only) and are accepted as part of the framework's runtime contract.
- The first Alchemy deploy of the hosted pair is an adoption (`alchemy deploy --adopt`), reviewed through `alchemy plan --adopt` beforehand. On the current provider (2.0.0-beta.87, pinned exactly per ADR-0011), the Durable Object's storage is carried by the provider's declarative exports map, where the storage Cloudflare already reports wins; the declared `sqlite` applies only to a class that does not exist yet.
- The hosted shape now has three carriers (cf config, wrangler mirror, `alchemy.run.ts`); the drift check above is what holds them together.
