# ADR-0012: IaC is Alchemy v2 Effect style + self-hosting also supported via wrangler (Revision 3: hosted secrets live in the Secrets Store)

**Context**: The deploys we operate ourselves (cloud edition, development environments) and the distributed artifact users self-host have different requirements.
**Decision**: Operations side uses Alchemy v2's Effect style (typed wiring of infrastructure and runtime). The self-hosted distribution always keeps a path that stands up with plain wrangler config / a Deploy to Cloudflare button, and never forces an Alchemy dependency on users.
**Rationale**: "One click to stand up in your own account" is the core of the product's value, so the distribution's dependencies must be minimal. Double-maintaining deploy definitions is accepted as the price of lowering the barrier to entry.
**Consequences**: Fallback path: Alchemy's async style, or a full retreat to wrangler. CI verifies the self-hosted path (wrangler only) deploy.

## Revision 1 (2026-11-14): the hosted pair is adopted

Status: owner decisions 2026-11-13 (adopt Alchemy for the ops-side deploy) and 2026-11-14 (the hosted state store; D1 / R2 lookup-only, confirmed by an independent second-opinion review); accepted upon merge of the PR containing this revision. The original decision stands for the self-hosted distribution; this revision settles how the ops side is actually declared, and refines the original "Effect style" wording: the stack program is an Effect program, but the application-facing declarations use the async (props) form, so the application source stays Alchemy-independent and the `cf` path keeps working unchanged.

**Decision**: `alchemy.run.ts` at the repository root declares exactly two workers — the hosted worker (`maruhi-server-hosted`) and the apex site (`maruhi-site`) — and nothing else.

1. **Async Worker form.** Each worker is declared with `main` pointing at the existing entry module plus props (bindings, triggers, observability, assets). No Effect-native Worker / Durable Object notation enters the application source; `ProjectChainDO` stays a plain exported class in `apps/server`, its binding declared with the provider's `DurableObjectLike` shape (`kind: "Cloudflare.DurableObject"`, `className`, `storage: "sqlite"`, no `scriptName` — the reconcile adopts the existing class by name).
2. **Hosted state store.** State is `Cloudflare.state()` — Alchemy's hosted store (a per-account state worker + secrets store, bootstrapped once with `alchemy state bootstrap`). Every run of this program, local plans included, uses the hosted store — the file-state default exists only when `state:` is omitted, which this program never does; that is why every plan or deploy run — the operator's, there is no CI plan step (point 6) — needs account credentials and the one-time bootstrap. The alternative (a self-built store behind `state:`) is rejected: state durability and shareability cannot be retrofitted cheaply, and the added surface is one small ops-account worker plus one secret, in an account a token holder can already operate fully.
3. **D1 and R2 are lookup-only.** `Cloudflare.D1.Database.lookup` / `Cloudflare.R2.Bucket.lookup` bind the existing database (`maruhi`) and bucket (`maruhi-ops-backup`) by name; Alchemy never creates, migrates, updates or deletes them. Reasons: the provider's R2 reconcile clears lifecycle rules / CORS / domains when the props omit them, so managing the bucket would silently delete its load-bearing `retain-35d` lifecycle rule (ops task O2; the DR design's 35-day expiry of encrypted D1 exports) on the adopting deploy — a removal policy does not cover reconcile-time sync; and managed D1 adoption is one-way (the migration history converts to Alchemy's ledger), couples every worker deploy to that ledger, and makes `db:migrate:hosted` a dual-writer hazard. Lookup writes nothing to state and has no delete path, while `alchemy plan` still verifies the targets exist. Revisit managed adoption only when Alchemy is past beta **and** a concrete drift incident or deploy mis-ordering has occurred. **Superseded by Revision 2 (2026-11-15).**
4. **Names and stage are pinned.** Worker names are set exactly with the `name` prop (Alchemy's default physical naming is not used for them — the hosted name is load-bearing: the restore worker binds its DO namespace cross-worker by name). Deploys and plans always pass the stage explicitly (root scripts `alchemy:deploy` / `alchemy:plan`, both `--stage prod`).
5. **Secrets are declared, values stay out of band.** All four hosted Workers Secrets (`GITHUB_CLIENT_ID`, `GITHUB_CLIENT_SECRET`, `SERVER_ENC_KEY_IKM`, `OPS_ALERT_WEBHOOK_URL`) are declared as `Config.Redacted` env entries. An Alchemy upload rebuilds the binding list from the program, so an undeclared secret binding would be dropped; the values are read from the deploy environment and uploaded as `secret_text` on every deploy, never stored in the repository. **Superseded by Revision 3 (2026-11-15).**
6. **CI verifies both paths — the Alchemy side statically.** The hosted and site `cf` dry-runs are removed, and `apps/server/scripts/check-hosted-config.ts` now compares `alchemy.run.ts` against the cf hosted config as a third carrier of the hosted shape, alongside the typecheck and lint the program already gets. The live `alchemy plan` is an operator step, not a CI step: evaluating the program needs the account credentials and the four hosted secret values, and `ci.yml` holds no secrets by supply-chain policy (`apps/cli/test/workflows-supply-chain.test.ts` classifies it as an unprivileged workflow). The self-host and restore dry-runs stay on `cf`. (The secret-values clause is superseded by Revision 3: evaluating the program no longer needs the values, only the account credentials.)

**Consequences**:
- The self-host worker and the restore worker are unchanged (plain `cf`, `apps/server/cloudflare.config.ts`); the self-hosting path remains Alchemy-free, as the original decision requires.
- The apex site's own `cf` deploy script (`apps/site`'s `deploy`) is removed: after this revision the site deploys only through the root Alchemy scripts. A `cf` deploy would run outside Alchemy's state and fight the next reconcile. The `apps/site/cloudflare.config.ts` declaration stays for local preview; it no longer deploys anything.
- Deploying the hosted pair requires all four secret values in the deploy environment. They are write-only in Cloudflare, so the operator must hold them (notably `SERVER_ENC_KEY_IKM`); this is a precondition of the first adopting deploy. **Superseded by Revision 3 (2026-11-15).**
- Alchemy injects its own `ALCHEMY_*` plain-text metadata bindings into the hosted worker's env. They are inert for the application (its env contract reads named fields only) and are accepted as part of the framework's runtime contract.
- The first Alchemy deploy of the hosted pair is an adoption (`alchemy deploy --adopt`), reviewed through `alchemy plan --adopt` beforehand. On the current provider (2.0.0-beta.87, pinned exactly per ADR-0011), the Durable Object's storage is carried by the provider's declarative exports map, where the storage Cloudflare already reports wins; the declared `sqlite` applies only to a class that does not exist yet.
- The hosted shape now has three carriers (cf config, wrangler mirror, `alchemy.run.ts`); the drift check above is what holds them together.

## Revision 2 (2026-11-15): D1 and R2 are managed

Status: owner ruling 2026-11-15 (Alchemy's beta status must not count against adoption — maruhi releases much later, by which time Alchemy is expected to be GA) and an independent re-evaluation of Revision 1 point 3 against the installed provider source (2.0.0-beta.87). Accepted upon merge of the PR containing this revision. **This revision supersedes Revision 1 point 3**; points 1, 2, 4, 5 and 6 stand.

**Decision**: the hosted database (`maruhi`) and the ops backup bucket (`maruhi-ops-backup`) are managed Alchemy resources in `alchemy.run.ts`, not lookups.

1. **What the re-evaluation corrected.** (a) Managing the D1 *resource* and adopting Alchemy *migrations* are separable in the provider: migration sync runs only when the `migrations` prop is declared, so Revision 1's "managed adoption is one-way" is a property of that prop, not of management as such. (b) The R2 reconcile behavior Revision 1 cited is real and documented — lifecycle rules / CORS / domains / public access sync to the declared props, and an omitted prop reads as "clear" — but the reconcile diffs the declaration against the live bucket and writes only on a mismatch, so declaring the full recorded configuration in full neutralizes the deletion risk Revision 1 treated as decisive. (The comparison is order-sensitive; the rules are declared in the bucket's creation order, and a residual mismatch would be a content-identical re-PUT, never a deletion.) (c) Revision 1's revisit condition bundled the beta question with an incident-driven posture; the mechanics were already fully inspectable in the installed source, and the owner has since ruled the beta factor out.
2. **R2: managed, full configuration declared.** `alchemy.run.ts` declares the bucket's complete recorded configuration: the `retain-35d` rule (ops task O2 — expire objects at 35 days, abort multipart uploads at 1 day; declared as Age conditions in seconds: 3024000 / 86400), the default multipart abort rule every bucket is created with (7 days = 604800 seconds), `cors: []`, `domains: []`, `publicAccess: false`. No `locationHint` / `jurisdiction` (both are replace triggers in the provider's diff) and no `storageClass` (the live bucket is Standard, the provider's default). Managing the bucket also buys what lookup never could: the desired configuration is tracked in state and re-asserted by every reconcile that touches the bucket, so a dashboard edit to the retention rule is corrected on the next deploy that updates the bucket. (On this provider version it does **not** surface as plan drift — the plan diff compares declared props against persisted props, not against a live read — so drift correction rides on deploys, not on plans.)
3. **D1: managed, with migrations.** The database is declared with `name: "maruhi"` and `migrations: "apps/server/drizzle"`. The existing drizzle-kit files drive Alchemy's pipeline as-is (no file conversion); the first deploy converts the wrangler-written `d1_migrations` history into `__alchemy_migrations` — one-way, fail-closed (a history row with no matching local file stops the deploy), the old table left frozen — and pending migrations then apply as part of every deploy, in order. The conversion surface is at its lifetime minimum now: exactly one applied migration, pre-launch, no users; it only grows from here. The hosted migrate script in `apps/server/package.json` is removed in the same change: the dual-writer hazard Revision 1 named is real, and the fix is to have exactly one writer of the ledger, not zero managers. `db:migrate` / `db:migrate:local` (self-host and local) are untouched. Hosted and self-host share the migration *files*, never a database; the self-host path stays Alchemy-free, as the original decision requires.
4. **Both resources are protected.** Each declaration is piped through `RemovalPolicy.protect()`: a plan that would delete or replace either resource fails with `ProtectedResource` before anything is applied. This closes the one asymmetry lookup genuinely had — no delete path — since under protect a replace (e.g. from a name, jurisdiction or location change) is refused at plan time rather than executed, and removing the declaration is refused too (the policy persists on the state row).
5. **Operator preconditions (the adopting deploy).** The declarations are built from the repository's recorded ground truth (the O2 recipe; the hosted-ops notes); the environment that wrote them has no Cloudflare credentials, so the live bucket and database state has **not** been dumped yet. Before the adopting deploy the operator: (a) dumps the live bucket's lifecycle rules, CORS, custom domains and managed-domain (public access) state, and the hosted database's `d1_migrations` rows, and reconciles any difference against the declarations — the recorded gaps are that the bucket's CORS is unrecorded (declared `[]` on the strength of O2's "no public access / no custom domain" record) and the default multipart rule's exact live id is recorded only by its display name, "Default Multipart Abort Rule". The dump is the only guard for custom domains in particular: the adoption reconcile removes only domains present in prior state, of which there is none, so an unrecorded live domain would survive adoption while state records `domains: []`; (b) reviews `alchemy plan --stage prod --adopt`. The adoption plan cannot diff the bucket's sub-resources against live state (the engine adopts with the declared props as the baseline and force-updates), so the step (a) dump comparison is the sub-resource guard; the plan-level stop conditions are: the database or the bucket shown as **replace** or **delete** rather than adopt/update, or any resource beyond the expected set — any of those means STOP; (c) after the deploy, confirms a second plan is empty for both resources, `__alchemy_migrations` holds the converted rows, `d1_migrations` is unchanged, and a fresh dump of the bucket's lifecycle rules / CORS / domains matches the declarations exactly.

**Consequences**:
- Hosted D1 migrations now run through `bun run alchemy:deploy`; the hosted operator sequence (hosted-ops.md O9) has no separate migrate step. The migrate-before-deploy ordering is structural — the worker binds the database resource, whose reconcile (migrations included) completes first — not operator memory.
- The hosted shape's carriers stay three (cf config, wrangler mirror, `alchemy.run.ts`); `check-hosted-config.ts` now asserts the managed declarations (the lifecycle rule set with its seconds values, CORS / domains / public access, the migrations prop, the omitted replace-trigger and in-place-update props, and `protect()` on both resources).
- Exit cost, stated plainly: leaving Alchemy management later means a manual backfill from `__alchemy_migrations` (which stays readable, with `d1_migrations` frozen as the pre-conversion record) — a runbook task, not an impossibility.

## Revision 3 (2026-11-15): hosted secrets live in the Secrets Store

Status: owner decision 2026-11-15 (all four hosted secrets move to the Secrets Store; long-term best was the criterion and implementation cost was explicitly discounted). Accepted upon merge of the PR containing this revision. **This revision supersedes Revision 1 point 5, the Revision 1 consequence that deploying requires all four secret values in the deploy environment, and the secret-values clause of Revision 1 point 6**; every other point of Revisions 1 and 2 stands.

**Decision**: the hosted worker's four secret values (`GITHUB_CLIENT_ID`, `GITHUB_CLIENT_SECRET`, `SERVER_ENC_KEY_IKM`, `OPS_ALERT_WEBHOOK_URL`) are provisioned through the account's default Secrets Store, not uploaded per deploy.

1. **Deposit once, look up forever.** The operator deposits the four current values into the account's default Secrets Store once, under their env names. `alchemy.run.ts` finds the store by name (`Cloudflare.SecretsStore.Store.lookup({ name: "default_secrets_store" })`) and looks each secret up in it (`Cloudflare.SecretsStore.Secret.lookup`). A lookup is metadata-only and Unowned: the stack never creates, updates or deletes the secrets, the values never leave Cloudflare, and no plan or deploy environment carries them. If a store secret does not exist, the lookup yields undefined and the plan fails closed — depositing is therefore a hard precondition of the first deploy under this shape, and the operator sequence (hosted-ops.md O9) orders it before the plan.
2. **Runtime shape: both binding forms, one resolution.** The hosted worker receives each value as a `SecretsStoreSecret` binding object, read asynchronously through `.get()`. `apps/server/src/worker-env.ts` resolves both shapes — a plain string (self-host Workers Secret, `.dev.vars`, tests) or a store object (hosted) — once per env at service construction, into the same resolved service values the consumers already used; the consumers' behavior is unchanged. A store read that fails resolves to undefined, deliberately indistinguishable from unset: each consumer's existing absence semantics covers it without hardening or softening (the OAuth pair fails closed with 503 `SetupIncomplete`; an unreadable IKM is an unconfigured server key; an unreadable webhook URL disables the alerts). Resolution happens once per env, so a value updated in the store is picked up as worker isolates recycle; a redeploy forces it.
3. **Self-host is unchanged.** The self-host path keeps plain Workers Secrets registered with `cf workers secrets update` (AUTH_SPEC §3-2's unified-registration ruling governs that path and is not amended by this revision); `docs/SELF_HOSTING.md`'s self-host recipe stands as-is. (Its optional hosted-*mode* ops deployment binds the same store secrets as the operator's, since it is the same mode of the same config; that subsection's registration step follows point 4.) The restore worker carries no secrets under either shape.
4. **The cf mirror declares the same bindings by store id.** The cf binding form (`bindings.secretsStoreSecret`) requires the store's literal id, where Alchemy resolves by name. The id is an account identifier, not a secret; it lives in exactly one place, the `SECRETS_STORE_ID` constant in `apps/server/cloudflare.config.ts`. `check-hosted-config.ts` asserts the agreement the two forms allow: the cf hosted config binds exactly the four names as store secrets sharing one store id, the Alchemy program looks up exactly the same four names in the default store and binds each under its own env name, no `Config.Redacted` entries remain, and neither the self-host nor the restore config (nor the wrangler mirror, whose harness injects string values) declares a store binding. The id's correctness itself is an operator duty, recorded at the constant.
5. **What this buys and what it costs.** Deploys stop carrying secret values entirely: the deploy environment needs only the account credentials, and the operator no longer has to hold the four values (notably the write-only `SERVER_ENC_KEY_IKM`) for every deploy — the password-manager entry that held them is needed only until the adopting deploy's fingerprint check passes (the deposited IKM must reproduce the live `serverKeyFingerprintHex` on `/auth/config`), and can then be retired. Rotation of any of the four becomes a store update followed by a redeploy (or isolate recycle), with no value passing through a shell environment. The cost, accepted: one more account-level resource whose contents sit outside the stack's state (by design — the values were never state), and a plan-time hard dependency on the store secrets existing.

**Consequences**:
- The hosted shape's carriers stay three; `check-hosted-config.ts`'s secret assertions change from "four `Config.Redacted` declarations" to the lookup/store-binding agreement of point 4.
- The first deploy under this revision is an operator sequence, not a plain deploy: deposit the four values → record the real store id in `cloudflare.config.ts` if the placeholder is still in place → `alchemy plan` → deploy → confirm `/auth/config`'s `serverKeyFingerprintHex` is unchanged → retire the password-manager entry (hosted-ops.md O9 carries the steps). Deploying before depositing fails at plan time, by design (point 1).
- CRYPTO_SPEC §9 gains a provisioning note (the IKM's home on hosted is the Secrets Store; derivation, fingerprint and grant semantics are unchanged) and AUTH_SPEC §3 a cross-reference note (§3-2 governs the self-host path; the hosted channel changed, the §3-3 self-diagnosis semantics did not).
