# ADR-0014: Product evolution policy — the zero-knowledge team secrets platform is the mainline; agent isolation is the next wedge

Status: proposed 2026-08-07. Accepted as owner approval upon merge of PR #37. **Revision 1** (2026-08-30 H0 — substitution of the hosted ordering in decision 5; the ruling record is docs/notes/session-47.md, the design is docs/notes/hosted-design.md) is approved upon merge of the PR containing this revision.

**Context**: The competitive-comparison discussion (2026-08-07) sorted out the positioning. dotenvx = encrypted `.env`; Varlock = AI-safe config layer (schema, leak detection, credential proxy); Keyway = server-side-encryption vault (similar experience, different trust model); Infisical = the front-running competitor (vault + diskless run + agent proxy); 1Password / Bitwarden = adjacent competitors (human-vault trust and installed-base effects). An important correction: **diskless injection also exists in Infisical and is not a differentiator on its own**. maruhi's difference lies in "is zero-knowledge selective disclosure the default", "is diskless an invariant strong enough to prohibit `.env` generation", and "how far are membership and authenticity cryptographically bound".

**Decision**:

1. **The core is a selective-disclosure E2EE team secrets platform (reconfirming ADR-0002)**. The winning line is not "absolutely the safest" but "the set of parties you don't have to trust is wider than the competitors'". Diskless is a necessary condition but not exclusive to us; we keep it as an invariant (CLAUDE.md absolute rules)
2. **Promote agent isolation to the Phase 3 mainline**. In priority order: (1) valueless schemas (only names, types, descriptions, and required-ness are disclosed to agents; `maruhi schema` / MCP; no `.env.schema` file as a source of truth) → (2) credential brokering (`maruhi proxy run`: agents receive only placeholders, swapped for real values at the communication boundary; combined with the E2EE store, consistent all the way to "neither server nor agent holds plaintext") → (3) JIT / DO leases → (4) codifying no-reveal (value display for humans becomes a privileged operation; display refusal on agent detection stays the default) → (5) leak detection / log redaction (ancillary features)
3. **Counter human error with mechanisms, not "education"**: no-reveal, via-broker, short-lived credentials, approval-gated break-glass (four-eyes — enterprise follow-up), needs-rotation detection (→ upstream automatic rotation where possible). Do not make "humans cannot hold secrets" the default (it would not be adopted as a developer tool)
4. **Recovery is "assisted in a form we cannot read"**: a form where the operator holds the kit and can restore is a worse trust concentration than selective disclosure and is banned for breaking zero-knowledge. The measures: refine the Phase 1 recovery-code UX → sealed backups to user-owned storage (encrypted by passphrase / passkey) → reduce kit dependence via passkey PRF (CRYPTO_SPEC open item #2)
5. **Describe the weight of adoption in carved-out pieces**: the daily cloud experience (login → put secrets in → `maruhi run`) can be as light as Keyway. The ceremonies that remain as the price of zero-knowledge (initial key generation and recovery-kit storage, fingerprint confirmation on invite, device migration) are not hidden — they are honestly carved out as "first time and invites only". Self-hosting is the advanced path; the cloud is presented as "the first five minutes". ~~**The hosted cloud edition is not moved earlier (this ADR's ruling)**: Phase 1's completion criterion (dogfooding) and Phase 2's publication come first, and work-start date = the WorkOS re-decision point (ADR-0009) is maintained. This ADR hands off "the first five minutes" as an experience requirement on the hosted edition at work start; until then the adoption path is self-hosted + the initial setup wizard (Phase 1)~~ **(→ replaced by Revision 1 on 2026-08-30 — below. The "first five minutes" experience requirement and the honest carve-out are unchanged)**

**Not adopted (guardrails)**: drifting back to a worldview where `.env` is the source of truth (storing encrypted `.env` in git, making dotenvx compatibility the face of the product, device-local encrypted `.env.local`) / operator-readable custody of recovery kits / OS-level guarantees of hiding screen contents / defaulting to "humans cannot have secrets" / differentiating on "has diskless run" alone / talking about security by feature count / the expression "absolutely the safest".

**Rationale**: The high ceiling is the zero-knowledge team platform (it answers head-on the points enterprises pay for — audit, permissions, offboarding rotation, self-hosting, "no plaintext shown to the vendor"). The strongest wind right now is agent isolation, and that direction already matches ROADMAP Phase 3 (the foundation of MCP, DO leases, credential brokering). What we steal from Varlock is only the idea of agent isolation — swallowing the `.env` worldview whole would move us toward "Infisical + dotenv improvements" and kill differentiation. The limits that cannot be eliminated in principle (revoking already-read values, complete compromise of a legitimate device, availability, semantic correctness of plaintext) are already spelled out in CRYPTO_SPEC §14.3; we speak honestly about them in the threat-model document (Phase 2) and compensate with product features (needs-rotation detection etc.).

**Consequences**: Reflected on the ROADMAP (Phase 2 team-sharing explicitly gains invite-unregistered-users = CRYPTO_SPEC open item #9 and a zero-knowledge operational UX for fingerprint confirmation; head gossip gains environment manifest and checkpoint design = open item #12. Phase 3 gains valueless schemas, no-reveal codification, and leak detection, with credential brokering made concrete as `maruhi proxy run`. The future gains sealed backups, four-eyes approval, upstream auto-rotation, and a mechanism for the rotation-completion window = CRYPTO_SPEC §14.3-5 (ii)). These correspond to Phase A (polish the mainline) = existing Phases 1-2, Phase B (agent isolation) = existing Phase 3, and Phase C (remaining authenticity, enterprise) = existing Phase 2 leftovers + future; phases are not reorganized. The pitch line evolves in stages: "no plaintext shown to the operator" → "no plaintext given to operator or agent" → "even when humans err, the secret is not there".

## Revision 1 (2026-08-30): Substitution of decision 5 — moving the hosted cloud edition earlier (H series)

A revision following the 2026-08-30 owner ruling ((1) the docs site is deferred, (2) the hosted cloud edition is top priority and is "completed as a service", (3) valueless schemas are fully implemented while MCP delivery is deferred). The ruling's history and rejected options are docs/notes/session-47.md (rulings CY-DE); the design, gap analysis, and implementation split (H1-H6) are in docs/notes/hosted-design.md, which is the source of truth.

1. **Move the hosted cloud edition earlier and put it on the real schedule as the H series**. The order is as follows (reflected on the ROADMAP):

   > Dogfooding (including private preview — parallel and ongoing) / S1-S3 (valueless-schema signing, acceptance, verification surface) running alongside H1-H4 (signup control, quota, operations, legal) → H5 release ceremony (SECURITY.md + threat-model document + pre-release checklist) → **going public** → invite-only beta → open beta → GA (billing, docs site)

2. **Answers to the premises of the old decision 5**:
   - "Phase 1's completion criterion (dogfooding) comes first" → **dogfooding is redefined from a completion criterion (a preceding gate) to a parallel ongoing activity**. The verification deploy has existed since 2026-08-10 (session-19) and Phase 1 is feature-complete — there is no value in "waiting a few weeks" for its own sake; starting alongside the H series and continuing through invite-only beta produces faster learning. The proof of "all my projects have no .env left" is borne by the private preview's first user (the owner themself)
   - "Phase 2's publication comes first" → **the order is kept (publication → external beta), but the basis is replaced from "phases in series" to "verifiability of zero-knowledge = the precondition for accepting external tenants"**. The E2EE design builds the server as the party under verification (the object of distrust) (CRYPTO_SPEC §14); the external claim "the operator cannot read" is supported by the source verifiability of the client that performs decryption (CLI / crypto — MIT). Holding unspecified external tenants' secrets while remaining private would be collecting secrets on an unverifiable promise, which runs counter to minimizing operator culpability (ADR-0018). Publication is not an independent milestone; it becomes **a gate of the H series (H5)**. The docs site (Wave 3 G) is removed from the requirements for publication (owner ruling — README + SELF_HOSTING suffice at publication; the docs site is due by GA)
   - "Work-start date = the WorkOS re-decision point (ADR-0009)" → **the re-decision was carried out (2026-08-30)**: v1 continues with the direct GitHub OAuth implementation. The record and the next re-decision point live in ADR-0009's re-decision record as the source of truth
3. **The "first five minutes" experience requirement is made concrete as the opening condition of invite-only beta (H6)**: signup → put secrets in → `maruhi run` must complete with no Cloudflare account, no OAuth App creation, and no wrangler. The zero-knowledge ceremonies (key generation, recovery-kit storage) are shown honestly as "first time only", not hidden (decision 5's carve-out is unchanged)
4. **Harden the signing and wire surface before holding external tenants**: the valueless-schema S1-S3 (test vectors, crypto, acceptance, CLI verification surface) land before invite-only beta opens (signature/acceptance-surface changes are cheapest before external tenants exist — resolving the session-46 §9 handoff; S4-S5 are not gates). Details in hosted-design.md §4
5. **The guardrails (things not adopted) are unchanged**. In addition, hosted-specific: no operator-readable recovery custody and no operator-side export of values (reconfirming decision 4); the line between zero telemetry and operational observation, and fail-loud quotas (no silent degradation), follow the norms in hosted-design.md §3 / §5
