# ADR-0015: CLI distribution = compiled binaries as primary + npm as a Bun-required bundled JS

Status: proposed 2026-08-14. Accepted as owner approval upon merge of the release-infrastructure PR (Phase 2 Wave 1 / PR-3).

**Context**: The `maruhi` CLI implements the OS-keychain boundary with `Bun.secrets` and child-process injection with `Bun.spawn` (both only in `apps/cli/src/live.ts`), so **it does not run on Node.js**. Because the design stops with a typed error instead of falling back to a plaintext file when no keychain exists (the diskless invariant), the distribution form carries this runtime constraint. `bun build --compile` cross-compiles successfully for all 5 targets (linux-x64/arm64, darwin-x64/arm64, windows-x64); binaries are 62-96MB raw (23-37MB gzipped). An unscoped `maruhi` placeholder is already published on npm. `bun publish` does not yet support provenance (oven-sh/bun#15601). The follow-up PR-4 (install script + brew tap) stands on this decision.

**Decision**:

1. **Primary distribution is compiled standalone binaries on GitHub Releases** (5 targets, `maruhi-<target>.tar.gz` + `checksums.txt`). Users are not required to have Bun. Generation is consolidated in `apps/cli/scripts/build-binaries.ts`, and the tag-driven release workflow (`.github/workflows/release.yml`) runs quality gate (reusing ci.yml's `workflow_call`) → smoke on 5 real OS runners (launch + `--version` verification) → publish, in that order
2. **npm (unscoped `maruhi`) ships a single bundled JS that requires Bun**. Workspace dependencies (`@maruhi/core` etc.) and the beta `effect` are folded into the bundle and **never propagated into the user's dependency graph** (a corollary of ADR-0011: unstable dependencies go out only as a pinned, single artifact). `@maruhi/{core,crypto,api-schema}` are not published individually until the API is stable (a separate ADR when we do). When launched under Node.js, an entry guard prints guidance and exits 1 (not a deep `ReferenceError`)
3. **Not adopted**: (a) the esbuild approach of putting binaries in per-platform optionalDependencies — it duplicates 380MB+ per release into the npm registry, too high a price for fixing the `npm i -g maruhi` failure mode (no Bun). (b) a thin installer that fetches from GitHub Releases in postinstall — it breaks in environments with postinstall scripts disabled (bun's default, many corporate CIs), and external fetching at install time is bad on the supply-chain front as well
4. **The single source of version truth is `apps/cli/package.json`** (imported by `cli.ts`; a test pins the match against `--version` output). Releases use repo-wide `v<version>` tags (never per-package tags); the workflow checks the tag matches package.json before building artifacts. Prereleases use `-rc.N`; the GitHub Release is marked prerelease and npm goes to dist-tag `next`. The first release is `v0.1.0-rc.1` to validate the pipeline itself, then `v0.1.0`
5. **npm publish uses the npm CLI + trusted publishing (OIDC) + `--provenance`**. No long-lived tokens in GitHub Secrets. Only pushing a `v*` tag is a publish path
6. **The `mh` alias**: npm provides it automatically via two `bin` entries. The binary distribution puts only the single `maruhi` binary in the archive; the link is the installer's responsibility (PR-4's install script / brew tap) — shipping two binaries for every target just doubles transfer for no gain
7. **windows-x64 ships as experimental**. The Credential Manager path is unverified, but when the keychain is absent or malfunctioning it fails closed (no plaintext fallback, a typed error), so it cannot break on the dangerous side. The release workflow runs a launch smoke on a real runner every time
8. **Release notes are GitHub-generated**. No CHANGELOG file until 1.0 (creating one now would be a dead letter with neither writer nor readers; re-decide at 1.0)

**Rationale**: The protagonist of distribution is the zero-dependency standalone binary (a secrets-management tool cannot choose the environment it is installed into). The npm path's main uses are "Bun users' `bun install -g maruhi`" and future `bunx` runs, where a 1.2MB bundled JS is optimal; there is no reason to bring a 380MB/release binary into npm. Following the reality that provenance can only be attached via the npm CLI (bun unsupported), auth is made secret-less via OIDC. Avoiding propagation of the beta dependency (effect) is specified as a byproduct of bundling/compiling.

**Consequences**: The operating procedure is `docs/RELEASING.md` (owner's human tasks: confirm npm-org publish permission and set up the trusted publisher). PR-4 is written assuming GitHub Releases `maruhi-<target>.tar.gz` + `checksums.txt`. macOS notarization is separate, 2-3 weeks before publication (ROADMAP; until then the README explains Gatekeeper quarantine on browser downloads). Remaining future considerations: adding linux musl / x64-baseline targets, GitHub artifact attestation for binaries, and a replacement darwin-x64 smoke when the `macos-15-intel` runner retires (2027-08).
