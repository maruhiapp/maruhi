## 1. Principles

1. **GitHub is a means of authentication, not the seat of identity**. The principal inside the system is always the internal user_id
2. **No automatic account linking by email** (defends against account-linking attacks). Linking is always an explicit operation from a logged-in session
3. **Sessions are DB-backed and revocable**. Sessions consisting only of a stateless JWT are forbidden
4. **CLI / API tokens are issued by maruhi itself**. GitHub tokens are never stored or repurposed
5. User creation goes through a single idempotent entrance (get-or-create), not tightly coupled to an authentication flow

## 2. Data model

```sql
users (
  id            TEXT PRIMARY KEY,   -- ULID. The internal user_id. The principal identifier across all systems
  email         TEXT,               -- For display / notification. Forbidden as an identifier
  email_verified INTEGER NOT NULL DEFAULT 0,
  created_at, updated_at
)

linked_identities (
  user_id          TEXT NOT NULL REFERENCES users(id),
  provider         TEXT NOT NULL,   -- 'github' (future: 'workos' etc.)
  provider_user_id TEXT NOT NULL,   -- GitHub's numeric ID (not the login name. login is changeable)
  provider_login   TEXT,            -- Display snapshot
  linked_at,
  PRIMARY KEY (provider, provider_user_id)
)

organizations (
  id, slug, name, created_at
  -- Future columns (not created now): sso_connection_id, allowed_domains, enforce_sso
)

memberships (
  org_id, user_id, role,            -- role: 'owner' | 'admin' | 'member'
  PRIMARY KEY (org_id, user_id)
)

sessions (
  id            TEXT PRIMARY KEY,   -- Stores the SHA-256 hash of a random 256-bit value (the raw value is never stored)
  user_id       TEXT NOT NULL,
  auth_method   TEXT NOT NULL,      -- 'github_oauth' (future: 'sso' etc.). Needed for SSO-enforcement policies
  created_at, expires_at, last_used_at
)

api_tokens (
  id            TEXT PRIMARY KEY,
  user_id       TEXT NOT NULL,
  name          TEXT NOT NULL,
  token_hash    TEXT NOT NULL,      -- SHA-256. The raw token is shown once at issuance
  token_prefix  TEXT NOT NULL,      -- For display (e.g. maruhi_pat_Ab12…)
  scopes        TEXT NOT NULL,      -- JSON array
  expires_at, created_at, last_used_at
)
```

Rules:
- All references from every other table / structure — projects, audit logs, membership chains, etc. — use `users.id` only. Using `provider_user_id` as a foreign key is forbidden
- Lookups happen only by `(provider, provider_user_id)`. No code path searches or matches users by email
- **memberships.role (the org role) does not participate in project access**. The sole source of truth for a project's data access and operation permissions is the membership chain of CRYPTO_SPEC §6 (the §9-2 decision)

## 3. Web login (GitHub OAuth Authorization Code Flow)

**Self-hosting prerequisite**: GitHub OAuth (web flow — since the §4 revision of 2026-08-31, CLI login also uses this via the server) needs an OAuth App's client_id / client_secret, which maruhi cannot distribute centrally (the callback URL differs per deployment). **Each self-hosting user must create their own GitHub OAuth App**.

**The first-time setup wizard's form (session 19 design, 2026-08-10. Owner approval occurs on the implementation PR's merge)**:

1. **The source of truth for installation steps is `docs/SELF_HOSTING.md`** (a wrangler command sequence verified on a real deploy + OAuth App creation guidance). Every setup step is a wrangler operation needing Cloudflare credentials, and neither the maruhi CLI nor the server holds CF credentials. No interactive CLI wizard is built — self-hosting is the advanced path (ADR-0014 ruling 5), and a copy-pasteable verified runbook is minimal and sufficient
2. **client_id / client_secret are both registered as Workers Secrets (`wrangler secret put` ×2). No runtime registration API or "Web registration form on first access" is built**: client_id is public information (§4) and not secret-worthy — unifying the registration path to secrets removes the need to edit `wrangler.jsonc` (a commit to a fork) and lets `secret put`'s immediate application complete the configuration without a redeploy (deploys via the Deploy to Cloudflare button presume a path that does not edit the replicated repository. 2026-08-11 revision — the old spec distributed client_id via wrangler vars). Reason for no Web registration form: an unauthenticated first-registration surface becomes a path where "whoever accesses a freshly deployed instance first registers their own OAuth App and takes over the instance"; preventing it would require distributing another bootstrap secret (not worth the added complexity. Fixing configuration at deploy time is the minimum)
3. **Self-diagnosis of an unconfigured server**: a server whose OAuth App configuration is incomplete (client_id is the placeholder `replace-with-your-github-oauth-app-client-id` (backward-compatibility defense for forks of the old template that distributed client_id via wrangler vars) / empty / missing, **or client_secret is unregistered / empty**) returns 503 `SetupIncomplete` (reason: `github-oauth-unconfigured`) from `GET /auth/config` (§4), `GET /auth/github/start`, and `POST /auth/cli/start` (§4 — the 2026-08-31 revision. Replaces the old `/auth/device/exchange`), guiding to the setup guide (it must not degrade into a GitHub error page or an opaque token-exchange failure = `AuthFlow` 400 that hides the cause). Since secret registration is also a condition, `/auth/config`'s 200 serves as the confirmation that "client_id / client_secret are both registered" (`SELF_HOSTING.md`'s "6. Smoke-check")
4. The CLI's client_id auto-resolution happens via §4's public config endpoint (a self-hoster's CLI config needs only the `server` field). **(2026-08-31 §4 revision)**: the auto-resolution itself is abolished — the CLI no longer talks to GitHub directly and needs no client_id ("the CLI config needs only `server`" is unchanged)

1. `GET /auth/github/start`: issues a `state` (128-bit random), stores it in an HttpOnly cookie, and redirects to GitHub. Scope is minimal (`read:user user:email`)
2. `GET /auth/github/callback`: verifies `state` (mismatch → immediate rejection) → code exchange → fetch user info from the GitHub API
3. `getOrCreateUser(provider='github', provider_user_id, profile)`:
   - Present in linked_identities → return that user
   - Absent → create users + linked_identities (email is stored with `email_verified=1` only if verified on GitHub's side)
4. Issue a session (§5)

- GitHub's access token is discarded immediately (never stored)
- Linking another provider from a logged-in state is allowed only through the "explicit link" flow (logged-in session + new OAuth completion)
- **(2026-08-31 ruling DH)** This section is **the sole entrance for signup (account creation)** — §4's CLI login creates no account (identity lookup only). H1's signupPolicy gate and the acceptance of signup invite codes sit immediately before this section 3.'s "absent → create" branch (hosted-design.md §2-2)

**Signup control (2026-09-01 H1 — implementing hosted-design.md §2-2 / §8 gap 1. The merge of the implementation PR containing this revision constitutes owner approval)**:

- **`signupPolicy` (`open` | `invite` | `closed`. Default `open` = identical to the legacy behavior)** is a deployment-unit server acceptance policy (same class as §12-11 schemaPolicy — not carried on the chain or signatures. A malicious server can always ignore its own acceptance policy, so chaining it adds no adversarial guarantee). Its location is the D1 deployment-settings table (`deployment_settings` — key/value). The only way to change it is the operator's wrangler / SQL path (no admin UI or authenticated config endpoint is built — avoids adding attack surface. Procedure in `docs/SELF_HOSTING.md`). **An unknown stored value is treated as `closed` (fail-closed — an operator misconfiguration doesn't silently turn into `open`. The effective value is observable via `/auth/config`'s advisory)**
- **The judgment point is the single gate immediately before this section 3.'s "absent → create"**. It does not affect existing users' login, token verification, project-invite acceptance, recovery, or the chain API at all (only new creation is blocked). `closed` = refuse all new creation. `invite` = create only when a valid signup invite code is presented. **The judgment uses the setting at acceptance time** (same rule as §12-11): the implementation folds the policy condition and the code-consumption CAS into **conditions of the same D1 transaction as account creation**, leaving no race window between the read and the creation for a settings transition
- **The rejection's form**: after the OAuth dance completes (no material to judge "is this new?" exists before then — a structural consequence), the rejection is a scriptless guidance page (same delivery discipline as §15-3's invite landing page — CSP `script-src 'none'`, English). **On rejection, no rows of users / linked_identities / organizations / memberships are created (fail-closed)**. The audit is `auth.signup_denied` (AUDIT_SPEC §3.1 — actor is a type=user row with no user_id, fixed-window cap, does not record provider identifiers). This record feeds H3's "count of signup rejections" tripwire (hosted-design.md §5-2)
- **Signup invite codes**: `maruhi_sgn_` + a Base62 256-bit random bearer, **single-use (consumption CAS)**, expiring (drafted value 7 days — same as §15). Storage is the SHA-256 hash of the whole presented string only; the raw value is shown once at issuance (following §5 / §15's discipline). A code carries **only permission to create an account** — it is bound to no project, org, or role. No allowlist of provider identifiers (GitHub ID / login) or emails is built (does not re-introduce the rejected options of §2's rules and §10's prohibitions — hosted-design.md §2-2). Issuance is an operator operation (a script bundled in the repository + the wrangler d1 path — no issuance API or UI is built)
- **Code transport and pre-validation**: the signup link is `GET /auth/github/start?signup_code=<code>`. The server **pre-validates at start** (exists, unconsumed, unexpired — with a per-IP rate limit); if invalid, it ends on a scriptless guidance page **before** the GitHub redirect happens (a fail-fast that doesn't run the OAuth dance for an invalid code. No dedicated pre-validation endpoint — the check is folded into the start handler). A valid code is carried to the callback as **its SHA-256 hash** on a `__Host-` cookie (HttpOnly) (the callback needs only the hash comparison and the consumption CAS — there is no point where the raw value reappears, so the raw value appears on the wire only once in the start request and never remains in the browser's cookie store. Applying the "the raw value only at issuance" discipline [§5 / §15] to the transport surface — PR #133 second-round exploration). **The cookie value is bound to the OAuth state issued at the same time, and the callback adopts it only when the state matches** (a `__Host-` / path=/ cookie is also sent on later unrelated OAuth completions in the same browser, so without the binding a carried-over code could be consumed by another flow — PR #133 review handling). The cookie is revoked once on every callback termination that returns HTML / 302 (success, denial, the CLI browser leg); a value left on a typed-error termination (400 / 429 carrying no Set-Cookie) is neutralized by the state binding (it expires naturally with the 10-minute maxAge). Pre-validation is not an existence oracle (256-bit random, single-use — same level as §15 invite tokens). The code appearing in the start URL's query (it remains in browser history) is accepted — a code is single-use, short-lived, and carries only creation permission, a different weight of carried privilege than §4-1's flowToken (a PAT-acquisition credential — forbidden from the browser channel)
- **Timing of consumption**: a CAS inside **the same D1 batch (transaction) as account creation** (users / linked_identities / the personal org / audit). It structurally eliminates both the shape where a failed creation attempt burns just the code and the shape where creation succeeded but the code remains unconsumed. A code presented under `open` is pre-validated but **not** consumed — the gate requires no code
- **`GET /auth/config` (§4) returns `signupPolicy` as an advisory** (public information — the same content as the landing's "beta is invitation-only". The session-47 §10-2 revision ruling). It is never an input to verification / authorization rules. Against an old server lacking this field, the client proceeds as before (a missing advisory does not break login)
- **Relation to the CLI (§4)**: since CLI login creates no account (ruling DH), this gate does not exist on the CLI path (no code rides start's payload). The CLI checks the advisory before start and, on `invite` / `closed`, guides a would-be new user to "sign up on the Web first, then `maruhi login`" (hosted-design.md §2-2 (i)(ii) — **a misoperation guard, not an authorization**. The source of truth for acceptance is this section's server-side gate. Fail-closed holds even in a server-only intermediate state — same §9 H1 row)

## 4. CLI login (server-mediated web-flow handoff)

**Full revision of 2026-08-31 (session-48 ruling DF — design comparison and rejected options in docs/notes/session-48.md. The merge of this revision's PR constitutes owner approval)**: replaced the old mechanism (GitHub Device Flow, RFC 8628 — the CLI talked to github.com directly and carried the obtained GitHub token to the server). The motivation is hosting (docs/notes/hosted-design.md §3-4 / §8 gap 9): device flow's user-code entry has a shared cap of **50/hour per OAuth App** (summed across all tenants on hosted), and the consumption point (the user's browser → github.com) has no observation or control point on maruhi's server. This mechanism moves one login's GitHub consumption to one token claim of web flow (2,000/hour per App — secondary) and puts every consumption point behind the server (self-counting and per-IP cutoff become possible). Secondary gains: (1) total abolition of the carried-token-verification attack surface — audience verification (the check-token API), GitHub-token format pre-checks (former L-3), the unauthenticated outbound relay; (2) making the CLI provider-independent (the principle below). Note that web flow's code → token exchange requires a client_secret (GitHub's spec), so a CLI-only web flow is structurally impossible and this mechanism is always server-mediated — the callback URL registered on GitHub's side stays the single URL of §3 (no extra step appears in a self-hoster's OAuth App setup. Conversely, "Enable Device Flow" becomes unneeded — it may be disabled after implementation, and disabling it also erases adversarial consumption of the old 50/hour surface).

**Principle: the CLI does not know the identity provider (2026-08-31 owner requirement).** All the CLI knows is its own deployment's server URL; provider selection, the OAuth dance, and identity verification all live server-side (§3's mechanism). No provider-specific field is placed on this section's wire, and `verificationUrl` is an opaque URL to the CLI. A future IdP addition (§7) completes inside the browser leg (the server's authentication surface) without changing this section's wire or the CLI.

**Principle: CLI login creates no account (2026-08-31 supplementary ruling DH — session-48.md).** This section performs **only authentication of existing accounts and distribution of a PAT**. The sole entrance of signup (account creation) is §3's Web login, where H1's signupPolicy gate and signup invite-code acceptance also sit (they do not ride this section's payloads). An identity without an account that completes the browser leg is guided to the signup-guidance page (§4-1 (4) (ii)) and **causes no irreversible side effect until approval**. Also by ruling DH, **start creates no state on the server** (unrecorded — a flow row is born only "at the instant an existing account holder completes OAuth"). Together these make the unauthenticated surface's state management (formerly: capacity, evacuation, protection CAS) and the pre-approval side-effect ordering problem (formerly: a signup code consumed ahead) disappear structurally.

### 4-1. Flow

1. **Start `POST /auth/cli/start` (unauthenticated, unrecorded — ruling DH)**: payload = `{ tokenName?, scopes?, expiresInDays? }` (the issuance-parameter semantics are §6 — identical to the old device exchange. H1's signup invite code **does not ride this payload** — acceptance happens only in §3's Web signup [ruling DH]). Response = `{ flowId, flowToken, userCode, verificationUrl, expiresInSeconds, pollIntervalSeconds }`. **The server stores nothing at this point** — the flow's authenticity is verified statelessly via a signature (below)
   - `flowId` is a public correlator (it appears in verificationUrl's query) but is an **unguessable random** (drafted value 128-bit). `flowToken` is a bearer credential opaque to the CLI; the implementation uses a **self-contained signed form**: a MAC by the flow-signing key (§4-2) whose signed input includes ≥256-bit random entropy + **flowId** + the expiry. **Including flowId in the signed input is a requirement** — start is unauthenticated and free, so anyone can issue themselves a legitimate flowToken, and without the binding, recombination "victim's flowId (public correlator) + own flowToken" would let someone poll another's flow (the successor after unrecording of the old rule's "(flowId, flowToken) pair matches a stored row" check — relocated into the MAC's signed input, not deleted). On poll acceptance the server verifies the MAC, the expiry, and **the match between the in-signature flowId and the presented flowId** (it neither stores nor hash-stores — there is no row). **flowToken is never placed on the browser channel (URL, approval page, redirect)** — structurally cuts the path where browser history / referrers aggregate CLI credentials (the reason flowId / flowToken are split into two identifiers — invariant)
   - `verificationUrl` carries flowId, the expiry, userCode, and **the issuance parameters (tokenName / scopes / expiresInDays — needed for the approval page's display and row creation)**, and bears a **browser-leg MAC (vsig)** covering all of them. vsig is a MAC **domain-separated** from flowToken (§4-2 — via a purpose tag, one fails verification as the other), so knowledge of the URL grants no polling credential at all. A verify arrival with no / tampered / expired vsig ends on a uniform error page **before** any GitHub redirect happens (no OAuth dance for a fabricated flowId — fail-closed)
   - `userCode` is a short display code for comparison (**not a secret** — shown on both the CLI and the approval page; a friction device the human cross-checks. Keeps approval at the same explicitness as the old device flow's code entry)
   - The flow TTL is drafted at 15 minutes (included in the signature). A per-IP rate limit sits first in the handler (the same Workers Rate Limiting binding pattern as the old device exchange. Drafted value 10/min/IP — after unrecording this protects CPU, not the DB). An unconfigured server returns §3's self-diagnosis 503 `SetupIncomplete` (fail-closed before reaching GitHub)
   - The old rule's "bounding flow rows' lifetime and total volume" (opportunistic deletion + deployment-wide cap + evacuation) was **replaced structurally by ruling DH**: since start creates no row, there is no pool to fill on the unauthenticated surface. The row-volume discipline moved to §4-1 (4) (iii) (the creation point)
2. **The CLI's display**: shows verificationUrl and userCode. Automatic browser launch may be attempted only when "stdin / stdout are an interactive terminal and non-agent" (the judgment materials reuse ADR-0016 decision 7's existing services [Stdio / AgentProfile] — this is a UX branch, not a new security gate). Even when auto-launch fails or is inapplicable (agent, CI, SSH, container), display + polling alone completes — this single degraded path covers every environment
3. **The browser leg `GET /auth/cli/verify?flow=<flowId>&…`**: first statelessly verifies vsig and the expiry (§4-1 (1) — failures get a uniform error page), then runs the same web OAuth as §3's stages 1–2 (issue and verify state, code exchange, fetch user info) (state carries the flow binding [the vsig'd parameter set]. GitHub's callback stays §3's single URL). §3's stage 3 is replaced by **account lookup only** (not get-or-create — ruling DH. It does not create), and **stage 4 (session issuance §5) is not performed** — a CLI login's product is only the PAT of §4-1 (5), without the side effect of a Web session (least privilege that creates no credential approval doesn't need. A user who wants Web too in the browser goes through §3 separately). **An existing Web session is not a credential for approval**: a fresh OAuth completion is required every time. No operation of this section is **added** to §5's session-capability permission enumeration (closing, outside the enumeration, the path where session-cookie theft / Web XSS escalates to "approving a CLI login" = de facto token issuance — consistent with ADR-0018 revision 2's "issuance is terminal-only")
4. **Approval**: the callback's processing order is fixed as follows. (i) Complete §3's stage 2 (state verification, code exchange, fetch user info), **finalizing the GitHub OAuth completion** (if it fails here, nothing below happens — that the flow-row creation happens only after OAuth completion is the premise of (iii)'s volume discipline. State verification alone cannot exclude a non-browser caller that self-supplies the cookie and query). (ii) **Account resolution (lookup only — does not create)**: look up the authenticated identity in linked_identities. **If absent, return the "signup-guidance page" and end** — a scriptless page carrying only the path to §3's Web login (= the sole signup entrance; under H1, the signupPolicy gate and signup invite-code acceptance are there too) and **the flow-resume link (= verificationUrl — restorable from the vsig'd parameter set inside state)**. Since this page itself is a one-time OAuth callback response and **reloading it cannot resume the flow**, the guidance must return to the verify URL (reopening the verificationUrl still displayed on the CLI is equivalent). No flow row is created, no ticket issued, **no irreversible side effect at all** (the information "this identity has no account" goes only to the person themselves, so it is not an oracle). If the user finishes signup and opens the resume link (verificationUrl), the same flow can continue by redoing from (i) if still within the TTL. (iii) **Flow-row creation CAS (create-or-match)**: the flow row is born **for the first time** at this instant, already carrying the authenticated user_id, the issuance parameters (from the vsig'd URL), the expiry, and the approval ticket (the state corresponding to the old rule's "protection" and "binding" is fixed at creation — no intermediate state exists). If a row with the same flowId already exists: **a re-arrival of the same user_id** (reload, multiple browsers) is treated as success — a new approval ticket is issued (replacing the old) and the approval page is re-rendered (idempotent). **If a different user_id is already there, end on a uniform error without rotating the ticket** (closes both paths: a later different identity revoking the first-come approver's ticket, and hijacking the flow to bind a different account to the CLI). A row that is expired / approved / denied / consumed also gets a uniform error page (same discipline as §4-2 — don't differentiate the rejection reason by flow state). **The row-volume discipline sits at this creation point**: opportunistic deletion of expired rows is bundled at the head of the creation batch, and creations exceeding the deployment-wide cap of concurrent unconsumed rows (drafted value 1,000) are refused with a uniform error page and raised to H3's alerting (reaching the cap requires running "existing account × OAuth completion" concurrently cap-many times; unlike the old start pool that could be filled for free, cheap sticky occupancy does not arise — no evacuation mechanism needed. Recovers naturally with the 15-min TTL. The cap value is tunable as a self-host acceptance policy). (iv) The server returns the **approval page**. In addition to userCode, the page displays **which account is about to approve (the authenticated identity's display name)** and **this flow's PAT grant contents — tokenName, requested scopes, validity (after expiresInDays) — in human-readable form** (the former visualizes account mix-ups — the main path of §4-3's stuck branches. The latter exists because start's payload is unauthenticated and caller-chosen, so an approver must not be allowed to approve without ever seeing the grant contents — under §4-3's phishing residual this is an improvement over the old device flow); **tokenName is rendered inert as unauthenticated input** (no format or markup interpretation, single line, visually separated from the approval wording. The acceptance-time charset constraint is §6 — a shared protection effective on the list API and dashboard, not just the approval page. The residual of smuggling an approval instruction into the name is §4-3); and it demands the explicit operation "**approve only if it matches the code shown on the CLI**" (with a deny operation alongside). The approval credential is a **single-use, short-lived approval ticket** embedded in the page (256-bit random, hash-only storage, issued in the same transaction as the row's creation / re-arrival. A new ticket is issued on every re-arrival of the same user_id, revoking and replacing the flow's old ticket — at most one valid ticket at a time. **Only the last-opened page can approve**; approval on an earlier page gets a uniform rejection — the trade-off is §4-3); it is not a session. Approval is a CAS of the flow row's awaiting → approved (user_id was fixed at creation). The deny operation is a CAS awaiting → denied. The page's delivery discipline is identical to §15-3's invite landing page (**scriptless** — form POST only, CSP `script-src 'none'`): the price of moving the approval surface from github.com to the maruhi origin (Web = TCB) is minimized by zero script surface
5. **Acquisition `POST /auth/cli/poll` (unauthenticated)**: payload = `{ flowId, flowToken }`. The server first **statelessly verifies** flowToken's MAC, expiry, and **the match between the in-signature flowId and the payload's flowId** (any failure gets the same uniform typed error — §4-2. flowToken is dedicated to its flow; recombining with another flow's flowId is not a credential). After verification succeeds, it looks up the row by flowId: **no row → typed pending** (the browser leg just hasn't arrived yet — the normal path of an unrecorded start). If the row is approved, it first **CASes approved → consumed, and only the winner** performs §6's issuance inside this response (same-name rotation, issuance cap, default TTL, `auth.token_created` audit — all unchanged. The issuance parameters are the row's stored values) and returns `{ token, tokenId, userId, expiresAtMs }` (the same response shape as the old device exchange) (**the CAS gates issuance** — flowToken is a bearer not bound to one process and concurrent polls are expected input. Single-use = structural exclusion of double distribution is achieved by issuance happening only after the CAS. A CAS loser gets a uniform rejection). If issuance fails after the CAS succeeds, the flow ends as consumed and the CLI logs in again (fail-closed leaving no half-distribution — an undistributed PAT does not exist). **consumed / denied rows are not deleted until the flowToken's expiry + slack (drafted +5 min)** — deleting earlier would make them morph into "no row = pending" and the CLI would wait on a completed flow forever (the cleanup target is only post-expiry — §4-1 (4) (iii)'s opportunistic deletion). **A PAT's raw value is never placed in the DB at any point** (§10. Issuance happens only inside the processing of the distribution request). pending is a typed response instructing continuation; the polling interval's floor is 5 seconds (the server may reject excess polling with 429). The per-IP rate limit uses the same binding pattern as start

### 4-2. Verification, error, and audit discipline

- **Uniform rejection applies to credential mismatch**: polls failing flowToken's MAC verification, expiry verification, or **the pair-match verification with flowId (in-signature flowId ≠ presented flowId — §4-1 (1))**, and verify arrivals failing vsig verification, are refused with a uniform typed error / error page (no oracle for a flow's existence or state — same discipline as §11-2). A legitimate flowToken holder (= the flow's own creator) may get pending / denied / expired distinguished as typed responses (it's the state of a flow they created; it carries no new information). Unknown / expired / used approval tickets also get a uniform rejection
- **The flow-signing key (ruling DH)**: the MAC used for start's unrecording (**2 lineages: for flowToken and for vsig**) is **HMAC-SHA-256 (WebCrypto)** with a server-side secret key. **The two MACs are domain-separated by a purpose tag** (a fixed purpose identifier at the head of the signed input — e.g. `cli-flow-token` / `cli-verify-url`. Or derive the key per purpose via HKDF). **The concatenation of signed input is a uniquely-decodable encoding** (length-prefixing etc. — field-boundary ambiguity must not collapse different input sequences into the same bytes). Without these 2 clauses, a vsig whose signed fields overlap (a value flowing through the browser channel) could pass verification as a flowToken by implementation discretion, breaking "URL knowledge grants no polling credential" (§4-1 (1)). The key is auto-generated on first use and stored in D1 (**doesn't add a self-host setup step** — no additional Workers Secret registration). Concurrent first use is resolved by idempotent creation (first wins — the `INSERT` unique constraint + read-back; the later-generated value is discarded and the existing key used. The same D1-batch idiom as §6's initialization. The branch where 2 requests write different keys and revoke in-flight flows is closed at spec stage). This key is not E2EE key material (outside CRYPTO_SPEC's scope — it never touches plaintext secrets, only protecting the integrity of short-lived login-flow credentials. Not an invented protocol — integrity protection of a self-contained token by standard primitives). Key rotation = revoking in-flight flows (≤ 15 min); recovery is the CLI logging in again (acceptable). Note the unrecorded pending flow becomes the only "not DB-backed" credential, but **it is not a session** (it alone permits nothing — approval state and the product PAT are all DB-backed; the stateless-session ban [ADR / §5] targets something different. There's no cancel operation pre-callback, but the 15-min TTL and required approval make it unnecessary)
- GitHub's access token, as in §3, exists only in memory during callback processing and is not stored (§10 invariant)
- Audit: approval (user_id fixed) = `auth.login_succeeded` (authMethod is `cli_handoff` — added to AUDIT_SPEC §3.1's vocabulary. Existing rows' `device_flow` remains as a historical value). Failures follow the existing `auth.login_failed` fixed-window bucket discipline. Token issuance = `auth.token_created` (§6's existing discipline)
- Existing defenses on the web OAuth callback (§3) — the query size cap, the per-IP rate limit, the ops-side WAF (`docs/SELF_HOSTING.md`) — unchanged also protect this flow's browser leg (the callback remains a surface with unauthenticated outbound [code exchange])

### 4-3. Residuals and future extensions (explicit)

- **Phishing residual (same shape as the old mechanism — not a worsening)**: the shape where an attacker runs start and gets a victim to open the verificationUrl and approve remains (the same shape as RFC 8628 device-code phishing. Since GitHub silently completes re-authorization of an authorized app, the last defense is the explicit operation and the userCode-matching wording of maruhi's approval page). The approval surface moving to the maruhi origin is an intended trade-off (hosted-design.md §3-4 — ruling DF); the scriptless delivery and CSP discipline (CLAUDE.md) carry the defense
- **Floods on start / poll (post-ruling-DH positioning)**: since start is unrecorded and poll begins with stateless verification, **no state exists** that an unauthenticated flood can leave on the server — the impact degenerates to CPU and the rate-limit budget (accepted — per-IP limits, the ops-side WAF). The old rule (evacuation-type cap and its residual, all-rows-protected 429) disappears premise and all [a pending pool creatable for free]; this item replaces it. Reaching the cap on the flow-row creation surface (§4-1 (4) (iii)) is a uniform error page + H3 alert (reaching it needs cap-many concurrent runs of "existing account × OAuth completion", which can't be maintained cheaply. Recovers naturally by TTL)
- **Spoofing the approval wording (via tokenName)**: tokenName is free text chosen by the unauthenticated caller; CSP blocks XSS but not text forgery (smuggling "approve even if the code doesn't match" into the name). Mitigation is §6's charset constraint (rejecting control and bidirectional-control characters at acceptance) + §4-1 (4)'s inert rendering and visual separation. Accepted as part of the phishing residual (above)
- **Reopening the approval page revokes the earlier page's approval capability (the price of ticket-replacement revocation)**: if the same flow's approval page is opened multiple times (reload, multiple browsers — same user_id), only the last-opened one can approve; approving on an earlier page gives a uniform error (accepted — choosing the friction of "just reopen" over the complexity of keeping multiple tickets valid concurrently. Recovery at worst is the CLI logging in again). **A flow whose row was created by a different user_id is thereafter unapprovable by any identity** (the row's user_id is fixed at creation and never lifted or overwritten — accepted: the main legitimate arrival path is a mix-up by holders of multiple GitHub accounts [open with the wrong account → reopen with the right one], and the approval page's identity display [§4-1 (4) (iv)] lets them notice the mix-up. Recovery is always the CLI logging in again = a new flow suffices — **by ruling DH nothing is consumed before approval**, so the "a signup code burns on the wrong-account side" branch the old rule deferred to H1 has disappeared [signup and invite-code acceptance exist only in §3; the CLI login flow consumes nothing]. Note: if the wrong account **has no** maruhi account, it ends on the signup guidance and no row is created, so reopening with the right account continues **the same flow**. The approval page's wording, per §4-2's discipline, does not differentiate reasons like "logged in as another account")
- **Loopback delivery (reserved as an additive future extension)**: a shape delivering the approval product directly to the CLI's temporary listener via a 302 to `http://127.0.0.1:<port>` closes the phishing residual structurally by binding browser and CLI to the same machine. Keep a shape that can be added **non-destructively on the wire** as a delivery hint added to start (not included in the initial implementation — docs/notes/session-48.md handoff)
- The old `POST /auth/device/exchange`, audience verification (check-token), and the GitHub-token format pre-check (former L-3) were removed from the spec by this revision (no backward-compatibility clause since pre-publication — same line as §12-10 (1)). The implementation's removal order (a grace window on the server's receiving side) is left to the implementation PR's judgment (H1b in hosted-design.md §9). Of former L-3's 2 defense layers, the Workers Rate Limiting binding pattern (per source IP, handler-first, 429 `AuthRateLimited`) is inherited by §4-1's start / poll

- **Public config endpoint `GET /auth/config` (session-11 ruling B, 2026-08-03. Implemented in session 19 on 2026-08-10)**: unauthenticated, returns `{ githubClientId }`. client_id is public information (it appears in plaintext in the authorize URL's query), so the growth of the unauthenticated surface is acceptable (ruling (ii)). An unconfigured server (§3's self-diagnosis conditions — including unregistered client_secret) returns 503 `SetupIncomplete`. **Publishing the server-key FP (drafted 2026-08-12. Implementation merged in PR #63 on 2026-08-13)**: when the deployment keypair (CRYPTO_SPEC §9) is configured, the response adds `serverKeyFingerprintHex` and `serverEncPubHex` (32-byte hex) — the former is the comparison target when running grant_server (the server-key confirmation of the same §9), the latter is the distribution channel of "the enc public key the server distributes" of the same §9 (the very public key placed on a grant_server payload). Both are public information; on an unconfigured deployment both fields are omitted. **(2026-08-31 addendum — §4 revision)**: this endpoint survives (200 = the semantics of the configured self-diagnosis / smoke check, the distribution channel of serverKey info, the carrier of the `signupPolicy` advisory — hosted-design.md §2-2. **Implemented in H1 on 2026-09-01 — see §3's signup control**). The `githubClientId` field also stays as public information, but the CLI stops consuming it (below)
- **The CLI's client_id resolution is abolished (2026-08-31 — §4 revision)**: the old resolution order (`--github-client-id` flag → config's `githubClientId` → `GET /auth/config`) is deleted along with its consumer now that the CLI no longer talks to GitHub directly. The config `githubClientId` override (formerly for GHES / testing — ruling (iii)) is also deleted — mock injection for tests suffices by swapping the server URL


## 5. Sessions

- Generation: 256-bit random. The client gets the raw value; the DB stores only the hash
- Cookie: `__Host-maruhi_session` / `HttpOnly` / `Secure` / `SameSite=Lax` / `Path=/`
- TTL: 30 days (sliding renewal). Immediately revocable by server-side deletion
- CSRF: SameSite=Lax + write-type requests require a custom header (done wholesale in the HttpApi middleware). GETs that hold state require it additionally in the handler outside the middleware (the explicit list in §11-4)
- **Capability restriction of session principals (2026-08-28 W0 ruling — ADR-0018 revision 2・item 1. Implemented in Wave 3 W2b — before the first Web screen holding a session [W2])**: the session cookie is the credential most exposed to XSS (a same-origin XSS can attach the CSRF header itself), so Web's boundary principle (reading + revocation-type only) is not enforceable by omitting UI / bundle. The APIs a session principal may call are restricted by **positive enumeration** — permitted: **auth / self-info family** (§3's flows, logout, `GET /auth/me`, `GET /auth/recovery/status`, `GET /auth/key-wraps` [§13-7 — 2026-09-12 KL3. Status display only, carrying no wraps or segments], **`GET /auth/devices`** [§13-11 — 2026-09-19 DK. Reading the device registry. Carries only display names, key FPs, and public keys — no secrets]), **reads** (chain fetch [§11], environment list, metadata-only pull [§12-7], audit read [AUDIT_SPEC §7], the rotation-needed flag view, invite list [§15-2], token list [§6], **project list [§11-5 — returns only the caller's own memberships. Design document S4]**), **revocation-type** (invite revocation [§15-2], targeted token revocation [§6]). **Everything outside the enumeration is refused for session principals** (fail-closed — a new endpoint's default is "session-inaccessible"; opening it to sessions requires adding it to this enumeration in the same revision. The rejection's position is consistent with §11-2's existence concealment and §12-3's judgment order, and the implementation PR guarantees effectiveness with a pinned acceptance-path test. The recommended implementation form is the same type as §12-10 (1): a declaration baked into the endpoint contract = a single implementation point, no per-handler manual checks). In particular, the following have no legitimate session path and are explicitly refused: with-values bulk pull (§12-7 — audit-trail contamination via sessions = erases the very surface SECURITY_REVIEW L-1 arose on), DEK fetch / register / delete (§12-6 — deletion is the only signature-free destructive operation), chain append / init (§11), all environment / variable mutations (§12-4 / §12-5), invite issuance / acceptance (§15-2), rotation dismiss (AUDIT_SPEC §7), recovery-blob register / fetch (§13-2), register / fetch / delete on the reserve-key wrap ledger (formerly the master-key wrap ledger — 2026-09-19 DK), guardian segment fetch, and handoff request / query / approve / fetch / cancel (§13-7 — only the status display `GET /auth/key-wraps` is open to sessions), and device add requests / device-registry writes / deletions (§13-11 — terminal-only. 2026-09-19 DK). Operations needing a signature never succeed under keyless XSS anyway, but they're included in the explicit refusal so the defense doesn't depend on the implementation details of signature verification. The CLI and `maruhi ui` are token principals and unaffected

## 6. API tokens

- Format: `maruhi_pat_` + Base62 random (≥256-bit). The prefix distinguishes the type and supports secret scanning
- Scope: per project × permission (read / write / admin). Effective permission is min(token scope, the owner's chain role) (§9-2). **Effective per-environment access is decided by the on-chain scope (CRYPTO_SPEC §6.2 — 2026-09-14 ES)**. Future: per-token environment scope (an off-chain ACL further narrowing the chain scope — not started, addable additively), short-lived lease tokens for agents (Phase 3, interlocked with CRYPTO_SPEC)
- Verification: compare the presented token's SHA-256 against the DB. Timing-safe comparison
- **Scope representation (2026-08-02 decision)**: a scope is an array of `{ project: <project_id> | "*", permission: "read" | "write" | "admin" }`. `"*"` is a wildcard meaning "all of the owner's projects" (used by the CLI's working token. Since effective permission is always bound to the chain role by min(scope, chain role), even a wildcard cannot exceed the person's chain permission). The requested scope is specified at CLI login start (§4's `POST /auth/cli/start` — 2026-08-31 follow-through. Formerly at device flow exchange); when omitted it's `[{ project: "*", permission: "admin" }]`
- **Permission level each operation requires (2026-08-02 decision. Revised 2026-08-03)**: chain get = read. Chain append depends on the entry's op (for `checkpoint` and `revoke_device` it depends including the payload — `checkpoint` on whether audit_head_hash is empty or not, `revoke_device` on whether target_user_id is the calling principal themself or another [2026-09-19 DK]) — `create_environment` / `rotate_epoch` = write (**but these 2 ops are accepted only via §12-4's composite request; the generic chain-append API refuses them with a typed error** — so the generic path can't bypass the atomicity of chain entry + accompanying data), `checkpoint` = **write if audit_head_hash is empty, admin if non-empty** (via the generic append path — §16-2. 2026-08-18), `add_member` / `remove_member` / `change_role` / `grant_server` / `revoke_server` / **`set_approval_policy` / `propose` / `approve` / `withdraw`** = admin (the four-eyes' 4 ops are the same level as their inner ops — 2026-09-14 PF1), **`add_device` and `revoke_device` of one's own device = write; `revoke_device` of another's device = admin** (2026-09-19 DK — §11-1). Project creation (genesis init) = admin. The source of truth for per-op authorization (who may execute an op) remains the chain role (CRYPTO_SPEC §6.2); this table is the token-scope-side necessary condition. The per-op levels of the data plane (variables, environments, DEK) are defined in §12-3's table
- **v1's boundary (2026-08-02 decision. Updated by the 2026-08-28 W0 ruling — ADR-0018 revision 2・item 3)**: the only token-issuance path is CLI login (§4 — 2026-08-31 follow-through. Formerly device flow) — **no additional-issuance UI / API is built** (the places a raw value appears on wire or screen are pinned to "one terminal display at issuance". The raw value appears on neither Web nor `maruhi ui`'s DOM). **The terminal display's implementation form (2026-08-30 W3a ruling CK — originating at the PR #108 review)**: display does not happen by default (the CLI only saves to the keychain); the explicit opt-in `maruhi login --show-token` carries it. Displayability passes the same fail-closed 2-layer gate as value display (ADR-0016 decision 7 — interactive terminal × non-agent) **before any communication** — a PAT is a credential to all secrets, so the discipline of not flowing it into an agent's transcript or CI log is at the same level as values. The use case is supplying `MARUHI_TOKEN` to lease-incapable execution environments (a consequence of ruling CF — without a supply path, explicit TTL doesn't hold). The management-family API offers, in addition to "revoking one's own token" (revoking the presented token itself, token-principal only — for CLI logout), the following 2 surfaces for the Web dashboard's token management (**up to list & revoke** — same revision item 1) (implemented in W3a on 2026-08-30 — docs/notes/web-dashboard-design.md §7): (1) **list `GET /auth/tokens`** — returns the id / name / token_prefix / scopes / created_at / last_used_at / expires_at of the caller's own tokens. **Raw values and token_hash are never returned** (the response schema holds no such column = closed structurally). Expired tokens are also returned (the inventory surface — refusal is the verification-time 401's job; rows are cleaned by targeted revocation and same-name rotation. Rows keep counting toward the 100-per-user cap too). Bounded at 100, so no paging. No audit event is recorded (a read of self-information touching no values or keys — same discipline as §11-5). (2) **targeted revocation** (`DELETE /auth/tokens/:tokenId`) — authorization is a session principal or a token containing `*` × admin scope (same level as §13-2's key-material condition: blocks the availability attack where a stolen scoped token revokes other tokens). **The target is only the caller's own tokens**: specifying another user's or a nonexistent token id is uniformly refused with **404** (the discipline of not silently succeeding — same as §12-6's deletions. The uniform response leaks nothing about whether another's token id exists). Audit is `auth.token_revoked` (AUDIT_SPEC §3.1 — actor = the executing principal, the target id is the payload). **The list's token-principal condition (2026-08-30 W3a ruling CH)**: the list also requires `*` × admin scope from token principals (same reason as self-axis auditing — AUDIT_SPEC §7's self read: an account-wide token inventory [names, prefixes, scopes] is reconnaissance material and not exposed to an easily-leaked scoped token). **Judgment order (same ruling CG)**: authentication (401 — expired / revoked / unknown tokens uniformly fold to anonymous via §5/§6's verification) → session capability restriction & CSRF (§5 — middleware) → the token-principal condition (403 insufficient-permission — **computed only from the calling principal's credential, carries no information about the target**. Same argument as §12-3's authorization-first exception) → target resolution (not owned by self / nonexistent = uniform 404). No rename API is built (reissuing under the same name = rotation suffices; doesn't grow the write surface)
- **Default TTL (drafted 2026-08-28 — resolving SECURITY_REVIEW 2026-08-14 L-2. ADR-0018 revision 2・item 3. Implemented + handoff resolved in W3a on 2026-08-30)**: tokens issued at CLI login (§4) carry a default TTL (default value: **90 days** from issuance — fixed into expires_at at issuance; deliberately asymmetric to the session §5's sliding renewal: tokens are forced to re-authenticate periodically). An expired token is refused with 401 at verification (same treatment as revoked — the expired / revoked / unknown distinction doesn't appear on the wire). Renewal is re-login = same-name rotation (above). Adjusting the value on self-host is allowed like raising an acceptance policy (not a consensus rule — the constant is api-schema's `DEFAULT_TOKEN_TTL_DAYS`). **Migration rule for existing (non-expiring) tokens (2026-08-30 W3a ruling CE)**: the introduction migration re-anchors existing rows with expires_at NULL to "**application time + the default TTL (90 days)**" — the issuance-time origin (created_at + 90 days) was rejected because it would mass-invalidate all existing tokens older than 90 days at application time (a silent stop), and non-retroactivity was rejected because it would permanently preserve L-2 in existing rows (the rejected-options comparison is docs/notes/session-44.md). Additionally, the verification side **treats a NULL expires_at as expired (fail-closed)**: even if only the new code is deployed without the migration applied, non-expiring tokens don't resurrect — re-login (same-name rotation) issues an expires_at-bearing row and self-heals. **Explicit TTL specification at issuance (same ruling CF — resolving the handoff for lease-incapable execution environments)**: `POST /auth/cli/start` (§4 — 2026-08-31 follow-through. Formerly `/auth/device/exchange`) accepts `expiresInDays` (integer **1..365** — the cap enforced by the wire Schema). It's the release valve for unattended PAT use in execution environments without lease support (§14) (GitLab CI / k8s / cron etc. — supported issuers at v1 = GitHub Actions only), extending to max 1 year only when explicit, keeping the 90-day default (issuance is only via CLI login §4 = the human browser-approval path). The option of returning to a non-expiring default is not taken (re-introducing L-2 — per the PR #103 review handoff). Extending supported issuers (GitLab etc.) is handled separately as a non-exclusive long-term path (§14's future extension). **Self-observation of expiry (same ruling CI — second-round exploration)**: `GET /auth/me` returns the presented token's `tokenExpiresAtMs` to a token principal (same "attribute of the credential you presented" as §16-2's tokenScopes — discloses no new information). It gives an unattended PAT the material to treat expiry as advance warning rather than a sudden 401; even a scoped token can learn its own expiry without opening the list (token principals need `*` × admin — above)
- **A same-named token is a rotation (added 2026-08-02)**: issuing to the same (user, name) is a reissuance accompanied by revoking the existing token (re-login = rotation). Revocation and insertion happen atomically; even under concurrent issuance there's only 1 same-named token (guaranteed by a DB unique constraint)
- **Issuance cap (added 2026-08-02, atomicized by deepsec S7 on 2026-08-27)**: distinct-named tokens cap at 100 per user (excess → 429. Same-name rotation is possible even at the cap). The cap check and the new insert happen atomically in the same `INSERT … SELECT … WHERE`, so concurrent issuances under different token names can't observe the same under-limit state and exceed the cap. Same-name rotation serializes detection of the existing row, `auth.token_created` carrying the old id, and replacement in a D1 batch. Token names are ≤128 characters and **contain no control or bidirectional-control (bidi) characters** (2026-08-31 addendum — refused by the wire Schema: the name is rendered as caller-supplied text on the approval page §4-1 (4), the list API, and the dashboard, so the shared protection of the display surface is placed at acceptance. **The implementation is taken over by H1b** — tightening the existing `tokenName` Schema together with §4's new endpoints. **Non-retroactive**: the constraint applies at acceptance; names stored under the old Schema are not cleaned — pre-publication, real data is operator-derived only, and the display surface already presumes inert rendering); scopes are ≤100 entries; a scope's project is only a project-ID format or `"*"` (cutting off api_tokens bloating DoS by an authenticated principal)
- **Correspondence with device keys (2026-09-19 DK)**: the token issued at CLI login (default name `cli:<hostname>`) is 1 per device and lives on the same device as the device key. A device's revocation (`revoke_device` — CRYPTO_SPEC §6.2) is a chain fact, independent of tokens, but the client proposes targeted revocation of that device's token (this section) at revocation time (SHOULD — the candidate and TTL materials are this section (1)'s list `GET /auth/tokens`: the row matching the registry's `tokenId`, or failing that the row matching the default name `cli:<hostname>`, shown with that row's `expires_at`. `GET /auth/me`'s `tokenExpiresAtMs` [this section's default-TTL item, ruling CI] is the **presented token's** expiry and is not material about another device's token); if the user declines, it displays "that token remains valid" together with the token's **actual expiry** (default 90 days, but extensible to max 365 days at issuance, and a self-hoster can change it via `DEFAULT_TOKEN_TTL_DAYS`) (CRYPTO_SPEC §14.2-11's non-guarantee). **The feasibility condition**: the list requires `*` × admin from a token principal (ruling CH), while `revoke_device` of one's own device is write-level (§11-1), so a client executing the revocation with a write-only token can't read the list — in that case the candidate presentation and expiry display are omitted, conveying only the fact "this device's token remains; revoke it on a device holding a `*` × admin token or on the Web (token list / targeted revocation)" (the revocation path itself isn't premised on `*` × admin — the default login token is `*` × admin and normally suffices. 2026-09-20 K1 review handling, design record §6 K1-15). The server does not revoke tokens on `revoke_device` acceptance (the registry is advisory and never an authorization input — §13-11. The option of placing token revocation in the chain acceptance's side effects is not taken because it would make identifying the revoke target depend on an advisory row — design record dk-design.md §6 K1-15. Could flip by owner ruling). The correspondence is held by the device registry's (§13-11) `tokenId` (optional, advisory)

## 11. Connection to the chain API (2026-08-02 owner ruling)

The provision for the junction between AUTH_SPEC (request authentication) and CRYPTO_SPEC §6 (chain authorization).

### 11-1. Correspondence between authenticated principals and chain actors

- All chain-operation APIs (init / get / append) are **authentication-required**
- Append-type operations (init / append) accept only on an **exact match between the authenticated principal's internal user_id and entry.actor.user_id**. A mismatch is refused
- This match requirement is **API acceptance policy**, not a chain-validity consensus rule (CRYPTO_SPEC §6.1). The chain format remains verifiable independent of the user_id's format (ULID or not) — bringing ID format into the validity rules would break provider independence for no cryptographic gain. Production chains end up carrying internal ULIDs as a result. Crypto's test vectors (bounded strings of arbitrary format) stay correct unchanged; the server integration test seeds a users row with the vector ID to align
- Existence verification of `add_member`'s target (target_user_id) is not done at chain acceptance (consensus rules don't depend on the auth DB). The counterpart's real existence and key authenticity are the invite mechanism's job (§15, CRYPTO_SPEC §6.5 — drafted 2026-08-12)
- **The four-eyes' 4 ops (`set_approval_policy` / `propose` / `approve` / `withdraw` — CRYPTO_SPEC §6.2. 2026-09-14 PF1) are accepted on the generic append API** (they carry no accompanying data). The acceptance side effects of an `approve` reaching quorum are identical to the inner op's (CRYPTO_SPEC §6.4). The pending-proposal cap is §12-8
- **`add_device` / `revoke_device` (CRYPTO_SPEC §6.2. 2026-09-19 DK) are accepted on the generic append API** (they carry no accompanying data). Token level (§6's table — the token-scope-side necessary condition. The source of truth for an op's authorization is the chain role [same §6.2: `add_device` and `revoke_device` of one's own device are role-agnostic, reader-allowed]): `add_device`, and `revoke_device` **whose target = self** = **write** (same level as §12-3's reader self-backfill — adding a device accompanies the subsequent backfill [write], and revocation accompanies the subsequent rotate [write]. A read token can't do it). `revoke_device` **whose target = another** = **admin** (same as `remove_member`). The K1 review (2026-09-20 pullfrog) corrected "uniformly admin" — it had left readers / members unable to add their own device or revoke a stolen one. `revoke_device`'s acceptance side effects = deleting the target device's declaration rows (§16-1), rotation-needed detection (AUDIT_SPEC §4.1), the mirror (AUDIT_SPEC §3.4). The device-count cap is §12-8

### 11-2. Responses to non-members are uniformly 404

- Even an authenticated principal who is not a chain-derived member (or holds no in-scope token) gets **404 (ProjectNotFound)** for both get and append, concealing the project ID's existence. The response is indistinguishable from an uninitialized project's (the ID is the genesis hash — effectively a capability)

### 11-3. Project creation (init) and org consistency

- An init request **requires org_id**, and creation permission is **member or above** in the target org (§9-1). `projects.org_id` is NOT NULL
- Order: org permission check (D1) → DO genesis acceptance → D1 `projects` row insert. **The DO (the chain) is the point of determination**; the projects row is subordinate metadata of org attribution (not the source of truth for in-project permissions — CRYPTO_SPEC §6.4)
- Partial-failure repair (idempotent): if it fails after DO acceptance but before row insertion, re-init of the same genesis gets already-initialized from the DO. Then, if "projects row missing + authenticated principal = genesis actor", insert the row and return success. Other already-initialized cases are 409
- **Project-count / org acceptance cap (2026-09-02 H2 — docs/notes/hosted-design.md §3-3 / §8 gap 2. Ruling CZ. The merge of the implementation PR containing this revision constitutes owner approval)**: an acceptance-policy cap on the number of **active projects per org** (drafted value **100** — the constant is `apps/server/src/policy.ts`. Also listed in §12-8's table). DO materialization = consumption of operator storage, bounding the creation surface per authenticated tenant (paired with H1's signup control closing the new-account surface). Not a consensus rule (same character as §12-8 — free to raise on self-host)
  - **Judgment point**: **after** "org permission check (D1)" and **before** "DO genesis acceptance" in the order above. The judgment material is the D1 `projects` row count for that org (the `proj_org` index). Since the 403 (non-org-member) precedes the cap judgment, a principal outside the org never learns that org's project-count information (whether the cap is reached)
  - **The "active" definition**: since v1 has no project-deletion API, **all `projects` rows of that org** are counted. A revision introducing a deletion API must also redefine this to "excluding deleted (tombstone) rows" and simultaneously state that deletion frees slots (the org-level version of §12-8's "freed by deletion" principle — this provision is its revisit condition)
  - **Rejection form**: typed **429 `ProjectLimit`** (payload = `limit`). It joins the same 429 vocabulary as per-user quantity caps (§6 token-issuance cap) and per-project pending-invite caps (§15-2) (a different layer than §12-8's in-project resource caps = 422). No silent degradation
  - **The partial-failure repair path (above) is not blocked by the cap**: even at the cap, the DO is asked init with a "don't admit new initialization (report-only)" instruction, and if the DO returns already-initialized it proceeds to the normal repair (missing row + authenticated principal = genesis actor → insert the row) or 409. **Only new (uninitialized) geneses are refused with 429**. If the cap judgment skipped the DO query, a project decided on the DO side but missing its D1 row (a crash window) would be permanently refused repair, fixing a "invisible in D1 but real in the DO" inconsistency — so at-cap judgment is made inside the DO's serialization, composited with "is it uninitialized"
  - **Concurrent-init race**: the 3 stages — count (D1) → DO acceptance (the determination point) → `projects` row insert (D1, subordinate) — can't be atomic, so several inits running concurrently just under the cap can observe the same under-limit and slightly exceed it. This is **accepted** (it's an acceptance policy, not a crypto boundary — same argument as §13-3's fetch counting. The excess is bounded by concurrency). The form of applying the token-issuance cap's (§6) `INSERT … SELECT` atomicity to `projects` row insertion is not taken: the insert is a subordinate write that comes **after** DO acceptance, and refusing there would itself create the inconsistency of a DO-confirmed project lacking a row (the same shape as breaking the repair path). The form of conditionally inserting the row before DO acceptance is also not taken (an inversion of the order "the DO determines, the row is subordinate" — a row for a genesis verifyChain rejected would remain, and in tombstone-less v1 it would consume a slot forever)
  - **Per-org implication**: since no org-creation API exists and every user has only a personal org (§9-1), v1's effect is **100 projects per user**. This implication disappears when an org-creation API is introduced (the cap itself stays per-org)
  - **The shared resource consumed by the rejection path (the session-47 §10 lesson)**: one indexed count on D1. At the cap, additionally one report-only query to the DO — for an uninitialized genesis, a named DO materialization (empty table sets) happens. This is the same class as the known residual (A-4) an authenticated principal can already reach via GET on arbitrary IDs; this cap creates no new consumption surface (accepting this consumption over the option that skips the query and blocks the repair path)

### 11-4. Endpoint placement

- All authentication endpoints — **including the OAuth redirect family (§3 start / callback)** — are placed in **api-schema's HttpApi definitions** (keeping the shared source of server implementation and client derivation single)
- Typed 401 / 403 errors (Unauthorized / Forbidden) are shared in api-schema and placed on authentication-required endpoint declarations
- The CSRF (§5) custom header is `x-maruhi-csrf: 1` (the name's source of truth is api-schema's shared constant `CSRF_HEADER_NAME` — 2026-08-30 W3a. Resolves the session-43 §14 handoff). Required on write-type requests authenticated by a session cookie (Authorization-header token auth is out of scope since it can't be issued cross-site). **GETs holding state** additionally require it of session principals per each section's explicit provision (bulk pull [with values] = §12-7, recovery-blob fetch = §13-2). "State" here means writes to audit rows and counters. **Deliberately out of scope**: (1) infrastructure-side costs like DO materialization (the countermeasure belongs to the same handoff design judgment as rate-limiting unauthenticated probes), (2) the session's sliding expiry renewal (§5 — a persistent write that can fire on every session-authenticated request, but it only extends the victim's own session, gains a cross-site caller nothing, and is already thinned to hourly granularity)


### 11-5. Project list (2026-08-29 W2a drafting — resolving the missing API of design document S4)

"The list of projects of which I am a chain-derived member." Since membership's source of truth is the chain-derived state inside each project DO (CRYPTO_SPEC §6.4) and no cross-cutting index exists, a **discovery-only D1 projection** is introduced. The design rulings and rejected options (the fan-out of org-scoped candidate enumeration = rejected for structurally missing cross-org members; the projection-only form = rejected for non-self-healing expulsion ghosts) are in docs/notes/session-42.md (rulings BI–BL).

- **Endpoint**: `GET /projects` (authentication required). Response = `{ projects: [{ projectId, role }], nextAfter? }` — `role` is **the acceptance-time chain-derived role each project DO returns at read time** (non-secret server-declared metadata. The display discipline is design document §4). Org attribution, creation time, and head information are not carried (the minimal form that doesn't newly disclose another org's attribution info to a cross-org member. Extensions happen additively)
- **Derivation form**: the D1 projection `project_members(project_id, user_id)` (a set with no role or state columns) serves as the **candidate index**, and at list time each candidate's membership is confirmed with its project DO. The response carries only rows that passed confirmation — **the projection is never used for any authorization judgment** (authorization and roles' source of truth remains the chain, as before. A derivation cache compatible with CRYPTO_SPEC §6.4's "ban on two sources of truth"). A candidate row the DO answered is not a member (a stale ghost) is excluded from the response and deleted at read time so it converges. **Confirmation failures are isolated per candidate (clarified 2026-08-29 — PR #106 review reflection)**: when one candidate's DO can't answer the confirmation due to unreachability or an internal fault (stored-chain corruption etc.), only that row is omitted from the response (the candidate row is kept — deletion only on the DO's explicit non-member answer — so it can reappear after the fault recovers), and the enumeration of the remaining candidates still succeeds — on a discovery endpoint, one project's outage must not become the whole enumeration's 500. The failure direction is only "looks smaller" (no structural failure exists in the direction of promoting an out-of-scope row). **This failure direction is an intended contract including a full DO-layer outage**: a response on which every candidate's confirmation failed becomes `200 { projects: [] }`, indistinguishable on the wire from "no memberships" — the list is a discovery surface, not an availability / health signal (an individual project's state is told by the real error of direct-ID access), and a response form carrying the distinction would put unconfirmed candidate info onto the wire, so it isn't provided (the W2 screen implementation is built on this premise). Operator-facing observation of the omission is carried by the server logs (static messages only — no request-derived identifiers are written)
- **Maintaining the projection** (the chain-acceptance path + self-healing): (1) accepting an init = insert the genesis actor's row in the same D1 batch as the `projects` row; (2) after `add_member` acceptance = insert the row; (3) after `remove_member` acceptance = delete the row ((2)(3) are transactions separate from DO acceptance, and failures don't propagate to the response under the same discipline as §15-2's completed cross-check — the consequence is only a display gap / a ghost, and the latter is eliminated by read-time confirmation); (4) lazy insertion on a successful chain get (§11's get) — doubles as the self-healing of a missed add and **the unmanned backfill of pre-existing projects created before the projection was introduced** (a migration path; no dedicated migration operation is provided). Disappearing from the list after expulsion doesn't depend on (3)'s success ((3) is candidate-set hygiene)
- **Consistency with existence concealment (§11-2)**: it holds no designation of a target project (path / query), and the response is only the caller's own memberships — no surface exists where a non-member could probe the existence of an arbitrary ID. It has no 404-type errors (declaration errors are only authentication ones)
- **Authorization**: session principal = allowed (§5's permission enumeration "project list" — the implementation adds it to `SESSION_ALLOWED_ENDPOINTS` in the same revision). Token principal = responds with only the **intersection of the candidates and its scope** (only rows whose scope granting read-or-above covers the target project. A `*` scope covers all) — out-of-scope projects simply don't appear, the same amount of information as the "out of scope = 404" elsewhere. **The intersection must happen at the candidate-index stage (clarified 2026-08-29 — PR #106 security-review point)**: since the `nextAfter` cursor is minted from the end of a candidate page, placing the intersection as a mere filter on the response rows would leak an out-of-scope project_id (the ID = genesis hash = effectively a capability — §11-2) onto the cursor. **It is this endpoint's invariant that no field of the response (including `nextAfter`) carries any project_id other than ones the calling credential may see**. Residual (accepted): for a session / `*` scope principal, `nextAfter` can carry the ID of the caller's own stale projection row (a post-expulsion ghost — a transient state before read-time convergence), but it derives from the caller's own membership history (the ID was held while a member) and carries no new information
- **Acceptance policy**: paging = `after` (an exclusive cursor on projectId, optional) + a server-fixed 100 entries / page (project_id ascending; `nextAfter` is returned only when the D1 candidate page is full). It bounds one call's DO confirmations to the page limit. No rate limit is placed — the grounds being that **one call's cost ceiling is bound by the fixed page (≤ 100 DO confirmations), independent of the projection's row count** (corrected 2026-08-29 — PR #106 review reflection: the initial "the projection's row count can't be inflated by others" was inaccurate — §11-1 doesn't require an accepted invite's existence at add_member acceptance, so another project's admin who knows one's public key can inflate one's projection row count via an unconsented add_member. The consequence is junk memberships entering the list [visible griefing — the attacker self-funds the project / chain, and the list rather visualizes the unconsented addition to the person] and an increased page count; one call's resource consumption doesn't grow). No audit events are recorded (a read of self-information not touching values or keys). No CSRF header is required of session principals either (§11-4's "state" = carrying no write to audit rows or counters. A ghost row's read-time deletion is the same "derived-cache convergence to chain truth" as §12-6's old-key wrap cleanup — even if induced cross-site, only the same convergence as a legitimate list happens, with no gain)

## 12. Connection to the variable-value / environment / DEK APIs (2026-08-02 session 07 ruling)

This section provisions the API surface of the data plane of CRYPTO_SPEC §3–§5 / §7 (key hierarchy, variable encryption, value signatures, metadata statements, DEK wraps, commitments, epochs). It follows the same discipline as §11: every endpoint requires authentication, responses to non-members and the out-of-scope are uniformly 404 (§11-2), and effective permission = min(token scope, chain role) (§9-2). This chapter's rules are, in principle, **the server's API acceptance policy**. However, since 2026-08-03 (session 12), for the verifications whose norm lives on the crypto-spec side (value / metadata signatures = CRYPTO_SPEC §4.1 / §4.2, DEK commitments = §5.2, the environment lifecycle = §6.2), this chapter is **the concretization** of their wire and acceptance surfaces, and changing the norm requires a CRYPTO_SPEC revision.

### 12-1. Resource model and identifiers

- The set of environments / variables and their display names are **plaintext metadata** inside the project DO (CRYPTO_SPEC §4 — only values are encrypted). **The authenticity of the name ↔ ID correspondence and of the active / declared / deleted state is carried by the signed metadata statements (CRYPTO_SPEC §4.2)** (2026-08-03. declared is 2026-08-30's layout v2): variable creation (declarations included), rename, schema setting, and deletion, and environment rename / deletion each accompany a statement, and the server stores and distributes the statement and its signature together
- `environment_id` / `variable_id` are **client-numbered stable identifiers** (the numbering actor of CRYPTO_SPEC §3's "numbered at environment creation" is the client). This is so that the client can fix the values entering the AAD / HPKE info (§4 / §5) before encrypting and wrapping — server numbering would split the flow into 2 round trips "obtain ID → wrap → register", producing the intermediate state "the environment exists but no DEK wrap exists yet"
- Format (acceptance policy): `^[A-Za-z0-9][A-Za-z0-9_-]{0,63}$`. environment_id is unique **within the project**, variable_id unique **within the environment**
- **No ID reuse**: a deleted variable's ID cannot be reused (refusal via the tombstone + CRYPTO_SPEC §4.2's "no re-activation after deleted"). **The ban on environment-ID reuse was promoted to a chain consensus rule by the chain-op-ification of environment creation (CRYPTO_SPEC §6.2 `create_environment`. 2026-08-03)** (unique across the whole history — the server tombstone degenerates into a derived cache). Because epoch and version enter the AAD, this structurally avoids creating a state where ciphertexts of the same AAD coordinates could exist twice across generations
- The display name (name) is renameable plaintext metadata. **The actor performing NFC normalization is the client (before signing); the server does not normalize** (acceptance policy): the server checks at acceptance that name is in NFC normal form, refusing a non-normalized one with 422 — it holds no path that modifies the signed byte string after acceptance (compatibility with CRYPTO_SPEC §4.2's byte-exact verification). Case is distinguished (matching the semantics of POSIX environment-variable names). Name uniqueness (environment names within the project, variable names within the environment. Judged by byte-exact full equality — since every accepted name is in NFC normal form, equivalent to NFC equality. Deleted ones are out of scope) is enforced by the server, and the client also verifies it against the distributed set of active statements (the cross-environment parity check uses variable names — CRYPTO_SPEC §4). **Name → variable_id resolution and the CLI's execution-control variable-name denylist (session 11) likewise apply the same comparison rules (byte-exact, case-sensitive) to the names of verified statements**. The client NFC-normalizes the lookup key before matching, and warns when it finds a non-NFC-normal-form name in a distributed statement (SHOULD — the NFC check is a server acceptance policy, and a malicious server can distribute signed statements bearing non-NFC names. Byte-exact matching produces no misresolution, but it doesn't make the coexistence of visually identical names invisible either)

### 12-2. Wire representations (the concretization of CRYPTO_SPEC §10)

Variable values pass the API boundary only as `EncryptedPayload`:

```
EncryptedPayload = {
  suite: "maruhi/v1",
  aad: { projectId, environmentId, epoch, variableId, version },  // the declared AAD components
  nonceHex,                    // 96-bit random nonce (lowercase hex, 24 chars)
  ciphertextHex,               // AES-256-GCM ct || tag (lowercase hex, ≥16 bytes incl. tag)
  // the value write signature (CRYPTO_SPEC §4.1. 2026-08-03 session 12):
  prevValueSigHashHex,         // the SHA-256 of the previous version's value_signed_bytes (empty string at version 1)
  chainHeadHashHex,            // the entry_hash of the chain head the writer last verified (64 chars)
  chainHeadSeq,                // that head's seq
  signatureHex                 // Ed25519, 64 bytes. writer_user_id is the calling principal on push (§12-5) and writerUserId on distribution
}

VariableMetaStatement = {     // variable creation / rename / schema setting / deletion (CRYPTO_SPEC §4.2)
  suite: "maruhi/v1",
  environmentId, variableId,
  name,                        // the NFC-normalized display name (§12-1)
  status,                      // "active" | "deleted" | "declared" (declared is layout v2 only — CRYPTO_SPEC §4.2)
  metaVersion,                 // a 1-based serial
  prevMetaSigHashHex,          // the SHA-256 of the previous statement's signed_bytes (empty string at metaVersion 1)
  // layout v2 (CRYPTO_SPEC §4.2 — 2026-08-30. On a v1 statement all 4 fields below are absent):
  layoutVersion,               // 2 (omitted = 1. The verifier checks the supported range before signature verification — an excess is a typed "unsupported layout" error)
  varType,                     // "" | "string" | "number" | "boolean" | "url" ("" = unspecified)
  required,                    // boolean (explicit and required in v2)
  description,                 // a free string (cap / charset acceptance checks are §12-8. Display is always neutralized by the client — same section)
```

- The representation of binary sequences is unified to **lowercase hex**, same as the chain (§6.1)
- **The wire rules of the variable meta statement's layout v2 (2026-08-30 — CRYPTO_SPEC §4.2)**: v1 statements (no schema fields) are distributed and accepted with the conventional field structure as-is (**no new fields are added to a v1 distribution** — keeping a form that doesn't depend on the decode behavior of non-strict existing clients). A v2 statement carries `layoutVersion` = 2 and the schema fields (varType / required / description), and the LP-signed target is the field sequence of the v2 domain string (same §4.2). `layoutVersion`'s wire type is **an integer with no fixed upper bound**, and the client explicitly refuses a supported-range excess **before** signature verification as "unsupported layout (client update required)" (the honest breakage mode where a later version bump doesn't appear to old clients as an invalid signature — same §4.2). The acceptance side is strict (§12-10 (1)), so a v2 sent to an old server is structurally refused with 400 as an unknown field (the §12-10 (2) design norm applies as-is). `EnvironmentMetaStatement` is outside this revision's scope (stays v1)
- **Distribution (pull / fetch) responses carry the signature's verification material (2026-08-03)**: values carry `writerUserId` + `writerKeyFingerprintHex`, meta statements `authorUserId` + `authorKeyFingerprintHex`, and environment manifests `issuerUserId` + `issuerKeyFingerprintHex` (2026-08-18) (the same shape as RecipientDek's signerUserId + signerKeyFingerprintHex — the recipient cross-checks them against the chain history and performs CRYPTO_SPEC §6.3's client verification). **Every response returning a name (bulk pull, the environment list, etc.) carries a verifiable statement (+ the author info), not a bare snapshot of the name** (the client must not trust a name that hasn't gone through statement verification). Push / meta-operation requests don't carry these (the calling principal = the signer is the contract — the same rule as §5.1 / §12-5). The DEK commitment (CRYPTO_SPEC §5.2) is distributed inside a chain entry, so data-plane responses carry no independent field for it
- **The DEK distribution response (RecipientDek) carries the signature and the signer information (session 09's reflection of the 2026-08-02 ruling 2-E)**: on top of the stored wrap's `signatureHex` it returns `signerUserId` and `signerKeyFingerprintHex` (the key FP of the chain-derived member at registration acceptance). From these and the chain history the recipient can perform the distribution-time client verification (CRYPTO_SPEC §5.1)
- **suite rides the entire persistent data structure (the 2026-08-02 session-07 review ruling)**: WrappedDek's wire carries suite, and the server's stored rows (variable versions, DEK wraps) carry a suite column too. The DEK distribution response (RecipientDek) and the pull response (EncryptedPayload) also return the stored suite. Consistent with CRYPTO_SPEC §2 design principle 4 "every persistent data structure carries a suite identifier"; no crypto-spec change accompanies it (HPKE info stays CRYPTO_SPEC §5 as before). On the API schema it stays pinned to the Literal `"maruhi/v1"` (the suite–epoch binding decision at `maruhi/v2` introduction is deferred to the v2 design — no preemption)
- **The server cannot cryptographically verify the AAD** (E2EE — it holds no decryption key). What the server does is (1a) an agreement check between the declared AAD components and the **URL coordinates** (project / environment / variable) — a self-consistency check computable from the request contents alone, a mismatch is 422 (the only target of §12-3's authorization-precedence exception), (1b) an agreement check of the declared version / epoch against **project state** (the expected version, the current epoch) — performed **after** the authorization judgment, a mismatch returning 409 with the current value (§12-5's CAS / epoch response. Letting a state-dependent check precede authorization would break §11-2's existence concealment), (2) structural checks (hex format, nonce length, ciphertext minimum length, size caps), and (3) **value / metadata signature verification (§12-5. 2026-08-03 — like §12-6's registration signature, a signature verification possible for the server too since it needs no decryption)**. The actual enforcement of context binding is decryption failure (CRYPTO_SPEC §4), and its verification is carried by the crypto layer's test vectors

### 12-3. Authorization (per-op required permissions. The data-plane extension of §6's table)

| op | Token scope | Chain role | scope (2026-09-14 ES) |
|---|---|---|---|
| Bulk pull (with values) / own-DEK fetch | read | reader or above | environment ∈ scope |
| Bulk pull (metadata only — §12-7) / environment list | read | reader or above | any (all environments) |
| Variable creation (incl. declared creation / the activation composite — §12-5) / push / rename / schema setting / deletion, environment rename, DEK wrap registration | write | member or above | environment ∈ scope (DEK wrap registration: the recipient side too — §12-6) |
| DEK wrap registration (**when every recipient is the calling principal's own device key** — 2026-09-19 DK) | write | **reader or above** | environment ∈ the calling principal's (the signing device's) effective scope (the recipient side too) |
| Environment creation | write | member or above | scope = all (CRYPTO_SPEC §6.2) |
| Environment deletion, DEK wrap deletion (§12-6's repair path) | admin | admin or above | environment ∈ scope |

- The judgment order is identical to §11's precedent: authentication (401) → for write operations the size precheck (413 — resource protection takes precedence over semantic judgments) → token scope (out of scope = 404, insufficient level = 403) → chain-derived membership (non-member = 404) → chain role (insufficient = 403) → **scope (403 `InsufficientScope` — the same stage as the environment-existence judgment: an environment's existence is already known chain-derived. 2026-09-14 ES)** → semantic checks. **The authorization-time double check** (operations carrying a signature — below) reaches scope too: environment ∈ scope at both acceptance time and declared-head time (CRYPTO_SPEC §6.3's 3′)
- As an exception, **the agreement check between the declared AAD and the URL coordinates (§12-2's 1a) may precede the authorization judgment, like the size check**: its response (422) is a self-consistency check computable from the request contents alone and carries no project existence / state information, so it's compatible with §11-2's existence concealment (an out-of-scope principal sending an AAD-inconsistent request gets 422, not 404). **The state-dependent agreement checks (§12-2's 1b — version / epoch) and signature verification (same 3) are outside this exception**, and are performed after the authorization judgment (clarified 2026-08-03)
- A 404 about environment / variable existence (EnvironmentNotFound / VariableNotFound) is returned **only to a chain-derived member** (the project's own existence concealment §11-2 always precedes)
- A reader can fetch but cannot push (CRYPTO_SPEC §6.2). The source of truth of chain role stays the chain; this table is the token-scope-side necessary condition + the role floor the server enforces
- **Reader self-backfill (2026-09-19 DK)**: the path by which a reader re-wraps its own DEKs to its own new devices (the reserve key included) (CRYPTO_SPEC §7's device-addition backfill). The reader legitimately holds those DEKs, and re-wrapping them to its own key adds no capability to anyone else. If even one recipient is another's key, member or above as before. The scope / role judgments are made on the signing device's effective permission (CRYPTO_SPEC §6.2 — 2026-09-19 DK)
- **The authorization-time double check (2026-08-03)**: an operation carrying a signature (push / meta operations) must satisfy, on top of the conventional "the current member's role at acceptance time", "**the role at declared-head time**" (CRYPTO_SPEC §6.3's 3). The table's role levels apply the same value at both times (value push / variable creation / rename / deletion / environment creation / rename = member, environment deletion = admin)

### 12-4. Environment management (2026-08-03 session 12 revision — following the chain-op-ification of environment creation)

- **Creation is accepted atomically as a composite request**: the request carries (1) the `create_environment` chain entry (environment_id + the epoch-1 dek_commitment_hex — CRYPTO_SPEC §6.2. Verified as an ordinary chain append including the parent-head CAS), (2) the `EnvironmentMetaStatement` (metaVersion 1, status active — carries the display name), (3) **the epoch-1 DEK wrap complete set** (the recipient set R(E) — below / 2026-09-14 ES. Formerly: all current members + valid grant_server server keys [when within the disclosure scope — 2026-08-12]. Must pass §12-6's verification), (4) **the `EnvironmentManifest` (manifestVersion 1, epoch 1, the empty variable set's digest — CRYPTO_SPEC §4.3. 2026-08-18)**, and (5) **the boundary `checkpoint` chain entry (2026-08-19 session 32 — CRYPTO_SPEC §6.3's mandatory bundling)**: bundling only that environment's single tuple (epoch 1, manifestVersion 1, the bundled manifest's signed_bytes hash, the empty variable set's values_digest. The treatment of audit_head_hash follows the existing rules of §6.2 / §16-2 as-is), and the project DO **accepts the 2-chain-entry append (create = H+1, checkpoint = H+2. The CAS parent is the declared head H) and the data registration atomically in a single transaction** (CRYPTO_SPEC §6.4's composite acceptance). It creates none of the intermediate states "the environment exists but nobody can hold the DEK", "the commitment exists but no wrap does", or "the environment exists but no manifest does" (the grounds that a spec-conforming new environment structurally has no manifest-uninitialized state — CRYPTO_SPEC §6.3). The chain entries' (both create's and checkpoint's) actor, the statement's author, the wraps' signer, and the manifest's issuer must all strictly equal the calling principal. On a retry after a head CAS failure (409), all of both entries, the statement, and the manifest are re-signed
- **The in-composite declared head (clarified 2026-08-03)**: the bundled statements' `chainHeadHashHex` / `chainHeadSeq` are **the current head before the append (= identical to the bundled chain entries' prev)**, and the server's head-existence check (§12-5's 2) is performed against **the pre-append chain** (the form declaring the bundled entry itself as the head isn't accepted — eliminating the ambiguity where implementations split on which chain to check). On a retry after a head CAS failure (409), **both** the chain entry (its prev_hash changed) and the bundled statements (their declared head changed) are re-signed. The wrap set is rebuilt only when the recipient set R(E) changed between retries. Note that at the env meta statement's (metaVersion 1) declared-head time the environment doesn't yet exist, but meta-statement verification doesn't check the environment's existence (stating explicitly that this is asymmetric with the value signature's epoch consistency — CRYPTO_SPEC §6.3's 4)
- **Creation's acceptance conditions**: `create_environment`'s consensus rules (environment_id is unique across the whole chain history — CRYPTO_SPEC §6.2) subsume the conventional "doesn't exist / isn't a tombstone / no rotate observed" checks (the tombstone / environment row degenerates into a chain-derived cache, never an independent source of truth). The current epoch at creation is always the initial value 1 (CRYPTO_SPEC §3)
- **Rotation is also a composite request**: the `rotate_epoch` chain entry (with the new epoch's `dek_commitment_hex`) + **the new epoch's wrap complete set** + **the `EnvironmentManifest` re-issued at the new epoch (manifestVersion + 1 — the meta set is unchanged but the manifest reflects the epoch advance; CRYPTO_SPEC §4.3. 2026-08-18)** + **the boundary `checkpoint` chain entry (2026-08-19 session 32 — a per-environment tuple of: new_epoch, the bundled manifest's manifestVersion + signed_bytes hash, and the values_digest reconstructed from current values at acceptance [not-yet-re-encrypted = old epoch — a legitimate §12-7 state])** — accepted atomically as 2 chain entries (rotate = H+1, checkpoint = H+2) + data registrations in a single transaction (abolishing the old "chain append → first wrap registration" 2-request split — the split normalized the intermediate state "a new epoch exists but nobody holds the DEK"). If the values_digest cross-check (CRYPTO_SPEC §6.4 — the post-composite-application baseline) doesn't match the stored state at acceptance time (a concurrent push after the declared head was fixed), refuse with 422 and the client re-pulls (the same read a re-encryption needs — doubles as drop prevention) then retries in a bounded way. Re-encryption of current values (CRYPTO_SPEC §7) is a subsequent ordinary push (§12-5), not part of the composite (avoids a giant request whose size depends on the value count. While un-re-encrypted, the old epoch's latest values keep being distributed — see §12-7). **A rotate composite targeting a deleted (tombstone) environment is refused with 404 (EnvironmentNotFound)** (CRYPTO_SPEC §7's "all environments" doesn't include deleted ones — don't create an obligation a spec-conforming client can't fulfill). The wrap complete set targets **the recipient set R(E) (CRYPTO_SPEC §6.2 — 2026-09-14 ES. Formerly: current member set + valid grant_server server keys [when the environment is in the disclosure scope])** (2026-08-12 revision — resolving the old "v1 = current members only" line. - **In-composite consistency checks (clarified 2026-08-03. Manifest added 2026-08-18. Checkpoint added 2026-08-19)**: the server requires coordinate equality among bundled sub-payloads as an acceptance condition — creation: the chain entry payload's environment_id = the statement's environmentId = all wraps' environment coordinate = the manifest's environmentId = **the checkpoint tuple's environment_id**, and all wraps' epoch = 1 = the manifest's epoch = **the checkpoint tuple's epoch**. At creation it's an empty enumeration). **A combination whose parts verify independently but whose coordinates disagree (a statement for another environment, a wrap for another epoch, etc.) must not be accepted**. Applying §12-6's "registerable epochs are 1..current epoch" to composite-bundled wraps uses **the chain state after the bundled entries' application** (equivalent to the epoch-match check above. Judging against the pre-append state would reject every legitimate rotation composite's new-epoch wraps as "for a future epoch")
- **The recipient set R(E) (2026-09-14 ES)**: the creation composite's (3) wrap complete set targets **the recipient set R(E) (CRYPTO_SPEC §6.2 — current members whose scope contains E + valid grant_servers whose disclosure scope contains it)**. Since the creator must have scope = all (the `environment-out-of-scope` consensus rule — it fails at chain-entry verification), R(E) resolves to all-scope members (+ disclosing grants). The rotation composite's new-epoch wrap complete set also targets R(E). The actor must satisfy E ∈ scope (consensus rule)

Wraps for all environments × all epochs in the target scope can exceed §12-8's request cap (environment 100 × many epochs × the target members), so a single request's atomicity can't cover it, and the deficit can converge via §6.3's wrap-destination match check and §12-6's append path — hence not a composite target
- ~~Chain acceptance does not cross-check environment metadata~~ (abolished 2026-08-03): `rotate_epoch` requires the environment_id's `create_environment` to precede it (CRYPTO_SPEC §6.2's consensus rule). The deletion's `EnvironmentMetaStatement` (status deleted) keeps being stored and distributed (CRYPTO_SPEC §4.2 — detection material for denying / silently reviving a deletion). ### 12-5. Variables and versioning

- version is a 1-based serial, part of the AAD (CRYPTO_SPEC §4). **The server cannot number versions** (numbering would diverge from the declared AAD), so push is accepted via CAS: only declared version == current latest version + 1 is accepted; a mismatch returns 409 with the current latest version (number only)
- **Post-409 retry procedure (2026-08-03 — connecting CRYPTO_SPEC §4.1's chaining with CAS)**: the client fetches the winning latest version (§12-7), **passes it through all of §6.3's verifications**, recomputes its signed_bytes hash itself, uses it as `prevValueSigHashHex`, re-encrypts and re-signs at the new version, and retries. **The 409 response must not carry the winner's signed_bytes hash** (if it did, the client would chain with its own signature onto an unverified server-declared value — a malicious server could make it sign a chain into a forged prev, contaminating the evidence chain). The metaVersion CAS (below) retry applies **the same-shape procedure to statements**: fetch the winning latest statement → all of §6.3's verifications → recompute its signed_bytes hash yourself → use it as `prevMetaSigHashHex` → re-sign a new statement at metaVersion + 1 and retry (no re-encryption occurs since no value is involved. The discipline of not including the winner's hash in a 409 response is the same)
- **The only epoch a push may reference is the current epoch** (the chain-derived ChainState.environmentEpochs value; right after `create_environment` it's the initial value 1). A push for an old epoch gets 409 returning the current epoch. On a post-rotation conflict, this response lets the client fetch the new DEK, re-encrypt, and retry. **Stored past versions keep their original epochs** (CRYPTO_SPEC §7) — this rule binds only new acceptance to the current epoch
- **Value-signature verification (2026-08-03 — CRYPTO_SPEC §4.1 / §6.4)**: the following are added to a push's acceptance conditions. A verification failure is refused with 422 (`signature-invalid` / `chain-head-unknown` / `chain-head-state-mismatch`):
  1. The signature is verified with **the calling principal's acceptance-time chain-derived sig key**, and the signature's writer_user_id likewise uses the calling principal's user_id (the same "calling principal = signer" rule as §12-6's registration signature. Bringing in a value signed by someone else is refused)
  2. `chainHeadHashHex` must equal the entry hash at seq = `chainHeadSeq` of its own chain
  3. **Authorization-time (common)**: in the chain-derived state at the declared head, the calling principal holds the required role for the operation (the table of §12-3's double judgment), **and the sig key bound to that user_id at the declared head equals the acceptance-time key used for verification** (clarified 2026-08-03: refuses the shape where a principal removed then re-added under a different key declares a head inside its old membership interval. Consistency for not having the server store data that client verification — CRYPTO_SPEC §6.3's 1, the head-time key binding — would entirely refuse)
  4. **Epoch consistency (values only — written identically to CRYPTO_SPEC §6.3's 4)**: the environment's current epoch at the declared head must equal the declared AAD's epoch (note this is a different check than the current-epoch-at-acceptance check above: if a rotation interposes between the declared head and acceptance, the acceptance-time check refuses with 409). **A value signature whose declared-head seq precedes the environment's `create_environment` seq is invalid** (identical to the latter half of §6.3's 4 — forbids an implementation that supplies a default value for a head where the epoch is undefined). Meta statements have no AAD / epoch field (CRYPTO_SPEC §4.2), so they're outside this check
  5. `prevValueSigHashHex` must equal the stored signed_bytes hash of the immediately preceding version (empty string for version 1). The server keeps each version's signed_bytes hash on its stored row
- **No independent check of epoch monotonicity (CRYPTO_SPEC §4.1) is placed on the server (clarified 2026-08-03)**: "acceptance is current-epoch only" (above) plus the current epoch's time monotonicity (rotate_epoch is +1 only — CRYPTO_SPEC §6.3) **structurally** guarantee that any accepted new version's epoch is ≥ every stored version's epoch. An independent comparison check is redundant and isn't added (since this implication is a consequence of these rules, a future revision loosening "acceptance is current-epoch only" must revisit how epoch monotonicity is guaranteed)
- **The signature's coordinates are reconstructed from server-side values (2026-08-03)**: the project_id used to verify signed_bytes comes from the DO's own chain (the genesis hash); the environment / variable coordinates come from the URL and storage destination. They're not built from client-declared values (the declared AAD) (the same invariant as CRYPTO_SPEC §5.1 implementation's "project_id comes from the DO's own chain" — session 09 §3 — and not implicitly dependent on the match-with-declared-AAD check of §12-2). **This rule applies to both value signatures and meta-statement signatures**: the signed coordinate fields — `var_meta_signed_bytes` has project_id / environment_id / variable_id; `env_meta_signed_bytes` has project_id / environment_id (only the fields present in each LP of CRYPTO_SPEC §4.2. env meta has no variable_id) — are likewise reconstructed from the URL / storage coordinates, not built from the wire's declared `environmentId` / `variableId` (structurally eliminating the mix-up of storing a signature valid for different coordinates under the request path's coordinates)
- The server's stored row carries, per value, the signature, the writer (user_id + key FP), the declared head (hash + seq), and the prev hash — returned as-is on distribution (§12-7). The audit event `var.version_pushed` mirrors the writer's key FP (AUDIT_SPEC §3.3)
- **The re-encryption marker (2026-08-15 session 25 owner ruling — Wave 2 B2)**: a push request may carry an optional boolean `reencryption` (default false). Its semantics is **the writer's self-declaration** that "this version is a re-encryption of the immediately preceding version's identical plaintext into a new epoch (a re-push accompanying CRYPTO_SPEC §7's mandatory rotation)"; the server can't see the plaintext (E2EE) so it doesn't — can't — verify the truth. The server only mirrors this declaration into `var.version_pushed`'s audit payload; it has no effect on the acceptance judgment or the value signature (CRYPTO_SPEC §4.1 — the marker isn't in the signed input). Its only use is deriving the resolution of rotation-needed detection (AUDIT_SPEC §4.1 procedure 5 — a marked push isn't counted as resolution). A false declaration's impact stays confined to the advisory flag's accuracy, and the failure direction is safe (a wrong "true" declaration = the flag remains. A wrong omitted / false declaration = identical to the literal pre-supplement behavior). A conforming client performing CRYPTO_SPEC §7's re-encryption push attaches the marker (SHOULD)
- **Composite acceptance of the environment manifest (2026-08-18 — CRYPTO_SPEC §4.3)**: every operation that changes meta state — variable creation / rename / deletion, environment rename (§12-4), environment creation / rotation (§12-4's composites) — bundles an `EnvironmentManifest` (manifestVersion = latest + 1) reflecting the post-operation meta state, and the server accepts the statement and the manifest **atomically**. Manifest acceptance conditions: (1) strict equality of calling principal = issuer (the signature is verified with the acceptance-time chain-derived sig key — same rule as values / meta), (2) the declared head's existence (above 2), (3) authorization-time (above 3 — the role level is the same as the bundled operation itself), (4) **epoch consistency**: the manifest's epoch equals the environment's current epoch at the declared head (the manifest version of the values' above 4. For a rotation composite's bundled manifest it's the state after the bundled entries' application = new_epoch — same judgment basis as §12-4), (5) prev chaining (`prevManifestSigHashHex` = the stored signed_bytes hash of the immediately preceding manifestVersion. manifestVersion 1 is the empty string), (6) CAS on manifestVersion (declared == latest + 1. **For an environment with no stored manifest — a migration for environments created before manifests were introduced — latest is treated as 0 and manifestVersion 1 [prev empty string] is accepted (clarified 2026-08-18 — the PR-M1 migration path. After migration completes it joins the normal CAS; no dedicated initialization endpoint is provided — the acceptance path is only bundling into a meta operation)**. **Accepting a v1 in a non-composite meta operation requires the declared head = the current head at acceptance time (2026-08-18 — PR #81 review handling)**: a v1 is accepted from latest 0, and even if a rotation interposes after the declared head, this CAS can't refuse it with 409 — since the argument of "no independent current-epoch check at acceptance" below doesn't hold for v1 alone, the epoch-consistency guarantee is substituted by the same-shape requirement as the composite path's declared-head pinning (§12-4) (blocking a bootstrap that bakes in a stale epoch. A mismatch is 422 `payload-mismatch` [field: manifestChainHead]). Judged in the same transaction as the bundled metaVersion CAS, and a 409 retry re-signs **both** the statement and the manifest), (7) **digest recomputation match**: the server recomputes variablesDigestHex / envMetaVersion / envMetaSigHashHex from the post-acceptance meta state (all variable statements — including tombstones — and the environment meta statement after applying the bundled statement) and refuses with 422 unless it matches the manifest's declared values (meta is plaintext and the server can fully verify it — no E2EE constraint. CRYPTO_SPEC §4.3). Server-side reconstruction of the coordinates (project / environment) is identical to the rule above. **Value pushes don't touch the manifest** (limiting the issuance trigger — CRYPTO_SPEC §4.3). **The server needs to hold only the latest manifest per environment (2026-08-18 pullfrog review handling — no verification path needing past rows exists)**: the prev check (5) uses the latest signed_bytes hash, distribution (§12-7) uses the latest, and checkpoint acceptance verification (CRYPTO_SPEC §6.4) matches against the latest at acceptance — none of them reference history. The asymmetry with meta statements (every metaVersion kept) is intentional — statement history is distributed as tombstone distribution and prev-chaining retry material, while manifest verification completes with the latest 1 (CRYPTO_SPEC §4.3). Equivocation evidence is carried by the client-side floor and reception records (the server is the suspect; what the server holds can't be an evidence source). **Caution on serializing concurrent meta operations (for the implementation PR)**: the old metaVersion CAS was independent per variable, but adding the manifest CAS serializes all meta operations in the same environment on the environment-wide manifestVersion — a batch variable import (batch creation from CI etc.) should run sequentially to avoid amplified 409 retries. Verification-failure error typing shares the existing ones: signature / digest mismatch / epoch inconsistency = 422 (`signature-invalid` / `manifest-digest-mismatch` / `manifest-epoch-mismatch`), manifestVersion conflict = 409 (returns only the latest manifestVersion — same discipline as §12-5's not putting the winner's hash on it). **No independent check against the current epoch at acceptance time is placed (clarified 2026-08-18)**: since a `rotate_epoch` composite always re-issues the manifest (§12-4), a rotation interposed after the declared head makes the manifestVersion CAS (6) refuse with 409 — this implication depends on "rotation re-issues the manifest", so a future revision loosening the issuance trigger must revisit how epoch consistency is guaranteed (the same shape as §12-5's epoch-monotonicity note)
- Variable creation bundles the first value (version 1) with the `VariableMetaStatement` (metaVersion 1) (a variable without a value doesn't exist — **the only exception is declared creation below**). **The bundled version-1 value undergoes the same verification as an ordinary push (above 1–5)** (creation can't bypass value-signature verification). Rename / delete statements are accepted via the metaVersion CAS (declared == latest + 1), and a 409 returns the latest metaVersion. Statement signature verification is **above 1–3 (signer match / head existence / role at the declared head) + prev chaining (`prevMetaSigHashHex`'s metaVersion chain — same shape as above 5)**. Epoch consistency (above 4) is value-only and doesn't apply to meta statements. **This meta-statement acceptance rule is common to `VariableMetaStatement` and `EnvironmentMetaStatement`** (it also applies to environment rename / deletion — §12-4 — and the statements bundled into a composite creation. The composite-specific declared-head rule is §12-4; deletion's role level admin is §12-3). **The server stores each metaVersion's statement (with its signed_bytes hash, signature, and author info) per variable / environment** (the prev check is against the stored immediately-preceding metaVersion's hash; 409 retries and §12-7's distribution material are also served by these stored rows — same shape as the value stored-row provision)
- Deletion is a variable tombstone + deletion of every version's ciphertext. The deletion `VariableMetaStatement` (status deleted) keeps being stored and distributed. The audit-side existence interval is carried by the var.created / var.deleted events (rotation-needed detection covers deleted variables too — AUDIT_SPEC §4.1)
- **Acceptance of layout v2 / declared / activation (2026-08-30 session 46 — CRYPTO_SPEC §4.2 layout v2. Design comparison in docs/notes/session-46.md rulings CR・CS)**:
  - **Accepting a v2 statement**: signature verification uses the signed_bytes of the layout the wire's `layoutVersion` (§12-2) selects (v2 = `maruhi/v1/var-meta-sig-v2` — CRYPTO_SPEC §4.2). The verification rules are identical to the previous 1–3 + prev chaining (the schema fields are inside the signed input, so no independent authenticity check is needed). varType's closed set and required's type are Schema validation (400); description's cap and charset are §12-8. **A new adoption of v2 is accepted only while the project's schema policy (§12-11) is enabled or above**: in a disabled project, a metaVersion-1 v2 statement (both declared and value-bundled) and a v2 re-issuance to a variable whose previous statement is v1 are refused with 422 (`schema-policy-disabled`) (the activation gate — old-verifier protection. CRYPTO_SPEC §4.2 finding F). **Continuation statements (deletion / activation / rename / schema re-issuance) of a variable whose previous statement is already v2 are accepted regardless of the policy** (2026-08-30 PR #112 pullfrog review handling: what the gate protects is "the appearance of new v2 statements an un-updated client can't read", and for a variable already distributed as v2 that's already unachievable — stopping continuations too would freeze deletion / activation of existing v2 variables on downgrade, breaking §12-11's reversibility). The judgment reads the acceptance-time policy (inside the project DO's serialization). v1 statements are accepted as before regardless of the policy
  - **Declaration (declared creation)**: as a variant of variable creation, a composite is added that accepts "**a `VariableMetaStatement` with status declared + schema fields (metaVersion 1) + an `EnvironmentManifest`**" **with no value** (the only exception to "a variable without a value doesn't exist"). Verification is identical to value-bundled creation (only the value-signature verification is out of scope since there's no value). A declared variable stays at stored-version 0 and counts against the active-variable cap (§12-8)
  - **Activation (declared → active)**: the first value push to a declared variable is accepted as a composite of "`EncryptedPayload` (version 1) + a status-active statement (metaVersion + 1, v2) + `EnvironmentManifest`" (it accompanies a manifest re-issuance because meta state changes — the invariant "value pushes don't touch the manifest" [CRYPTO_SPEC §4.3] covers ordinary pushes; an activation is a composite containing a meta operation). The verification of the value signature, statement signature, and manifest is the composition of the existing rules (above 1–5 + manifest composite acceptance (1)–(7)). An ordinary push (not an activation composite) to a declared variable is refused with 422 (`activation-required`)
  - **Transition acceptance checks**: active → declared and deleted → declared (and the existing deleted → active) are refused with 422 (CRYPTO_SPEC §4.2's transition rules)
  - **Layout monotonicity (CRYPTO_SPEC §4.2 — 2026-08-30 PR #112 review handling)**: a v1 subsequent statement (including a rename) to a variable whose previous statement is v2 is refused with 422 (`layout-regression`) (blocks the silent disappearance of schema fields via rename and the bypass of locked — "create as v2 → drop to v1 via rename")
  - **Schema re-issuance**: a change of only an existing variable's schema fields (name / status unchanged, metaVersion + 1 v2 statement) is accepted under the same rules as a rename (signatures 1–3 + prev chaining + metaVersion CAS + bundled manifest)
  - **Delete statement's schema fields**: must match the previous statement's schema fields and layout (the acceptance check of the same convention as name's "keep the immediately-preceding active name"). Deleting a declared variable is the same shape (a status-deleted statement keeping the schema fields)
  - **schema-locked (§12-11's locked)**: variable creation (metaVersion 1 — both declared and value-bundled) requires layoutVersion 2 and a non-empty varType; failure is refused with 422 (`schema-required`) (blocks at write time the "creation of an undeclared variable" — a typo'd shadow variable. Finding E of the exploration memo). **This is a one-time check at creation, not a continuous invariant (clarified in 2026-08-30 PR #112 review handling)**: returning varType to `""` in a later explicit schema re-issuance isn't prevented even under locked (an explicit operation leaving signatures and audit — treated the same as lowering required, not the blocked "silent creation by typo"). It also doesn't reach back to the activation of a declared variable created without varType during the enabled period (activation is not a creation)
  - This section's composites (declared creation / activation) belong to §12-10 (1)'s "value push / meta operations (§12-5)" class (strict acceptance). §12-10 (3)'s effect confirmation applies the existing per-kind rules as-is: the statement / manifest surface is metadata-only pull (§12-7); activation's value surface is the CAS + floor self-recording (the existing value-push discipline)

### 12-6. DEK wrap storage and distribution (the server side of CRYPTO_SPEC §6.3's ghost-member countermeasure)

- Recipient identification uses **both user_id and the enc public key** (invariant. Since 2026-09-19 DK, the same user_id can hold multiple enc public keys [device keys], so the public key identifies the device); both must strictly match a chain-derived current member's **valid device key**, **and the target environment must be within that device's effective scope** (2026-09-14 ES / 2026-09-19 DK — CRYPTO_SPEC §6.2. Out of scope is 422 `scope-out-of-range` — the same reason code as a server-directed wrap outside the disclosure scope), or acceptance is refused. The storage slot is **(environment_id, epoch, recipient_user_id, recipient_enc_pub_hex)** (2026-09-19 DK — formerly (environment_id, epoch, recipient_user_id). One slot per device. Overwrite ban, exact-match, missing-only append, and the repair path are unchanged). With user_id alone, "a wrap to a key different from the one on the chain" (effectively a ghost member) can't be detected; with the public key alone, it can't be cross-checked against HPKE info's recipient_user_id (CRYPTO_SPEC §5)
- **Registration-signature verification (2026-08-02 session 07 owner ruling 2-E. CRYPTO_SPEC §5.1)**: on **every path** that inserts a wrap (both the DEK registration API and the wraps bundled into environment creation; re-registration after deletion on the repair path is likewise an append path), each wrap's `signatureHex` is verified. Acceptance conditions are (1) **strict equality of API calling principal = signer** (the signature is verified with the calling principal's chain-derived sig public key, and the signature's signer_user_id likewise uses the calling principal's user_id — bringing in a wrap signed by someone else is refused. Another member holding the same public key can't exist in the first place by CRYPTO_SPEC §6.2's member-key uniqueness — 2026-08-03 — but the signer_user_id binding is an independent defense layer: even if a key-duplicated member existed, the refusal is a signer mismatch), (2) a match against the signed input (CRYPTO_SPEC §5.1's signed_bytes. It binds the URL's project / environment coordinates and the wire's epoch / recipient / enc / ct, plus the signer's user_id). Verification failure is refused with 422 (`signature-invalid`). This verification was the first client-signature verification over non-chain data (the only one as of 2026-08-02. Value / metadata signatures — §12-5 — were added on 2026-08-03), and it grounds the attribution of a poisoned wrap without trusting the server (cross-checkable against the audit event's signer FP — AUDIT_SPEC §3.3)
- The **initial registration** of an (environment, epoch) wrap set (epoch 1 at environment creation, the bulk registration of the new epoch after rotation) requires **an exact match with R(E) (in-scope current members + valid grant_servers inside the disclosure scope — CRYPTO_SPEC §6.2. 2026-09-14 ES)** (the same target as §12-4's wrap complete set — 2026-08-12 revision. The judgment applies identically across recipient classes): missing, out-of-set recipients, key mismatches, and duplicates are all refused with 422
- Afterwards, only **appending the missing** is allowed (the path where the inviter wraps every epoch's DEK to the new member after add_member and registers them — CRYPTO_SPEC §7). **Overwriting an existing (environment, epoch, recipient) is forbidden** (409). A wrap's contents are unverifiable by the server, so permitting overwrite would enable an availability attack replacing a valid wrap with an undecryptable blob. **A registration enumerates at least 1 wrap** (an empty `deks: []` is a Schema-validation 400. Changed 2026-08-03 from 204 no-op — there's no meaningful use case for that call shape, and a silent no-op hides a client bug [mistaking an empty-array send for a completed registration]; unified with the delete side's empty-enumeration 400 under the same "don't silently succeed" discipline. The bundled `deks` of environment creation is out of scope: an empty set is already refused by the exact-match requirement's 422 recipient-missing)
- **The overwrite-forbidden 409's response content (2026-08-15 session 25 owner ruling — Wave 2 B2, resolving the PR #69 handoff)**: a `DekWrapExists` (409) response carries, in addition to `{epoch, recipientUserId}`, the occupying wrap's **stored recipient enc public key** as `storedRecipientEncPubHex` (SHOULD. The field is optional — servers predating this supplement don't send it = a backward-compatible addition only). The public key is non-secret (all historical keys are already distributed to all members via the chain), and disclosure is limited to the registration path's authorization level (member or above). Use: on a backfill-409 for a re-added member, the client judges whether the occupied slot is an old-key wrap (a target of the repair path's delete → re-register) or a current-key wrap (already registered = idempotent) **by exact comparison against the stored row, not by inference from key history** — a wrap's decryptability is equivalent to the recipient enc key matching (HPKE), which makes this the complete judgment material. A client prioritizes the field when the response carries it, and may fall back to the old inference heuristic only when it's absent (a self-hosted server of a mismatched version)
- **Old-key wrap cleanup at re-addition acceptance (2026-08-15 session 25 owner ruling — Wave 2 B2)**: when accepting an `add_member`, the server deletes, within the same acceptance task, those stored wraps addressed to the target user_id (recipient class member) **whose recipient enc public key doesn't match the added key (= the added device key. A re-addition starts from one device — 2026-09-19 DK)**. It doesn't delete on `revoke_device` (same as `remove_member` — the existing discipline of reviving by re-registering the same key — 2026-09-19 DK). This is storage convergence toward chain-derived truth (enforcing §6.3's "the wrap destination strictly matches a current member's key" invariant), and the deletion targets are only ghost wraps definitionally undecryptable under the current chain — no legitimate current-key wrap is targeted, and the overwrite ban (blocking the availability attack) stays invariant. The target's historical access is served by the post-addition backfill (new-key wraps for all epochs — CRYPTO_SPEC §7). Deletions are recorded per recipient as `dek.deleted` (actor = system, with the cause and the corresponding chain seq in the payload — AUDIT_SPEC §3.3). The server recipient class is outside this cleanup (a re-grant that changes the key changes the server-key FP = the slot identifier itself, so no stale slot arises). Nothing is deleted on remove_member (on re-addition with the same key the existing wraps revive as valid as-is — cleanup happens only at re-addition, when "the key changed" is certain)
- Registerable epochs are 1 through the current epoch (wraps for a future epoch are refused). The reference state for the judgment differs by path (clarified 2026-08-03): the standalone registration API (backfill / repair re-registration) uses **the chain state at acceptance**; wraps bundled in a composite request (§12-4) use **the state after the bundled entries' application** (the bundled wraps' epoch must equal the epoch the bundled entries establish — creation = 1, rotate = new_epoch — required by §12-4, so effectively equivalent)
- **Repair path: wrap deletion → re-register the missing (2026-08-02 session 07 review owner ruling)**: while keeping the overwrite ban, the sole repair means for an undecryptable poisoned wrap (a registrant's bug or malice) is **explicit per-(environment, epoch, recipient) wrap deletion**. After deletion, the correct wrap is re-registered via the "append the missing" path above (if every wrap of an epoch was deleted, its re-registration is an initial registration requiring an exact match). **Re-registration also requires the registration signature** (the append path always accompanies registration-signature verification — the re-registrant wraps and signs themself). The required permission is **the same level as environment deletion (token scope admin × chain role admin or above — §12-3)**: deletion is an operation that strips other members' decryptability, and placing it at member level would resurrect via the delete path the availability attack the overwrite ban blocks. Deleting a nonexistent tuple is refused with 404, and **a deletion enumerates at least 1 entry** (an empty enumeration is a Schema-validation 400. Don't allow a call shape of a destructive API that leaves no audit trace at all — the same "don't silently succeed" discipline as 404). Deletion is recorded as an audit event (`dek.deleted` — AUDIT_SPEC §3.3) per recipient
- Distribution is only to the addressee: an authenticated principal can fetch only wraps whose recipient is themself (all members including readers — CRYPTO_SPEC §6.2)
- **Relation to the DEK commitment (2026-08-03 — CRYPTO_SPEC §5.2)**: the server **cannot** verify that a wrap's contents match the commitment (E2EE). The cross-check is done by the recipient after opening, and a mismatching wrap becomes a target of this section's repair path (delete → re-register) as a poisoned wrap. After the commitment's introduction, this section's acceptance conditions (recipient match / exact match / overwrite ban / registration signature) are unchanged; the repair path's meaning only widens from "undecryptable poison" to "undecryptable or commitment-mismatching poison"
- **Server-key-directed wraps (2026-08-12 revision — resolving the old Phase 2 line)**: a wrap of recipient class server identifies its recipient by **both the server-key FP + the enc public key** (strictly matching a chain-derived valid grant_server's payload) (the counterpart to the member class's "user_id + enc public key" since it has no user_id). The server-key FP is used in HPKE info's recipient_user_id position (CRYPTO_SPEC §9). The registration signature (same §5.1), overwrite ban, and repair path (delete → re-register. Delete permission = admin) are identical to the member-directed rules. A server-directed wrap to an environment outside the disclosure scope is refused with 422
- **Since epoch-1 and rotation wrap registrations moved to §12-4's composite requests**, the paths remaining for this section's standalone registration API are the 6: "post-add_member backfill to the new member (environments of the target's scope)", "**post-scope-widening backfill for the widened environments (2026-09-14 — the actor who signed the widening registers all epochs. By the containment rule the actor holds the DEKs)**", "**server-directed backfill of all in-disclosure-scope environments × all epochs by the grant executor (owner) right after a grant_server is accepted (2026-08-12 — same shape as the post-add_member backfill. CRYPTO_SPEC §7's wrap-executor rule)**", "the repair path's re-registration", "**backfill by the approver (owner) who completed the application, for an add_member / scope widening (member-directed) or grant_server (server-directed) applied via four-eyes (2026-09-14 PF1 — CRYPTO_SPEC §7. The acceptance rules are common with the other paths: signer = calling principal, recipient = R(E), overwrite ban)**", and "**post-`add_device` backfill of all epochs to the new device by the same person's device (2026-09-19 DK — environments in the new device's effective scope. Includes the reserve key — CRYPTO_SPEC §7. A reader's self-backfill is §12-3)**" (the acceptance rules stay common to all paths. R(E) is device-axis — CRYPTO_SPEC §6.2). **The registrant (signer) must also have the target environment in scope** (registration by someone who can't hold the DEK is structurally impossible, but it's stated as an acceptance condition. Since the signer = the calling principal [(1) above], this axis is identical to §12-3's calling-principal scope judgment = 403 `InsufficientScope`. The scope is judged by **the signing device's effective scope**, and the match between the calling principal's user_id and the signing device's user_id is carried by §5.1's signer_user_id binding — 2026-09-19 DK. Separate from the recipient-axis 422 `scope-out-of-range`, and the judgment order is per §12-3: the calling principal's scope [403] comes first)

### 12-7. Bulk pull (the fetch path of CLI `maruhi run` / Web)

- A per-environment single request returns all active variables' latest versions (EncryptedPayload. Self-describing including the declared AAD) + the current epoch + **wrapped DEKs of all epochs addressed to the calling principal**
- **Bundling the verification material (2026-08-03. Manifest / checkpoint material added 2026-08-18)**: each value bundles its signature block and writer info (§12-2); each variable / environment bundles the latest `VariableMetaStatement` / `EnvironmentMetaStatement` and author info; **each environment also bundles the latest `EnvironmentManifest` and issuer info, plus the deleted statements of deleted variables (digest-recomputation material — common to both with-values and metadata-only modes)**. **If a latest `checkpoint` containing an entry for this environment exists (the per-environment criterion of CRYPTO_SPEC §6.3), a with-values response also bundles "the value-snapshot enumeration at that checkpoint" (the list of variable_id / version / value_signed_bytes hashes — the one the server stored when accepting the checkpoint)** (the material for the client's checkpoint-consistency verification — CRYPTO_SPEC §6.3. The metadata-only mode carries no values and is out of scope). The client uses only what passes CRYPTO_SPEC §6.3's verifications (signatures / head binding / authorization-time / epoch consistency / coordinate consistency / manifest digest recomputation / checkpoint consistency) and §5.2's commitment cross-check. Name → variable_id resolution goes through verified statements
- The latest version's epoch can differ per variable (until post-rotation re-encryption completes — CRYPTO_SPEC §7). That's why wraps of all epochs are bundled
- Audit: var.read is recorded **as 1 row per environment per with-values bulk pull** (the aggregate form — the enumeration of returned variables [variableId / epoch / version] is carried in the payload. AUDIT_SPEC §3.3. 2026-09-02 revision — formerly 1 row per variable. If zero variables are returned, nothing is recorded)
- **The with-values bulk pull's CSRF header (session principals only — added 2026-08-15)**: the bulk pull is a GET but holds state in the form of var.read audit recording, and a `SameSite=Lax` session cookie is also sent on cross-site top-level navigations, so session principals are required to send the same `x-maruhi-csrf: 1` as write-type requests (§5) (absence → 403). It blocks audit-trail contamination where a third-party site carves a forged `var.read` in the victim's session (including mixing into rotation-needed detection — AUDIT_SPEC §4.1), the same discipline as §13-2's blob fetch (whose state is §13-3's fetch counting). Bearer tokens can't be attached cross-site, so they're out of scope. The metadata-only mode records no audit and is out of scope. **Note that §5's capability restriction (2026-08-28 — since the W2b implementation) itself refuses a session principal's with-values bulk pull**: this paragraph's CSRF requirement is kept as a pre-existing defense and as insurance for a future revision that loosens the restriction (not removed — the same discipline as ADR-0018's "an implemented defense is kept, not removed")
- **Metadata-only mode (2026-08-10 session 20 — session-11 ruling 3)**: a fetch path in the same per-environment unit that **returns no values (ciphertexts) and no DEKs** (a standalone endpoint). Response = the environment's latest statement + the current epoch + all active variables' latest `VariableMetaStatement`s (with author info) + deleted variables' deleted statements + **the latest `EnvironmentManifest` (with issuer info — 2026-08-18. The completeness of meta verification is at the same level in this mode)**. The bundling of verification material and the client's verification obligation (CRYPTO_SPEC §6.3's meta verification / manifest verification / name resolution via verified statements) are identical to the bulk pull, and authorization is at the same level (token scope read × chain role reader — the same row of §12-3). Uses are reads that need no value, like name → variable_id resolution (the CLI push resolution path)
- **Distribution of declared variables (2026-08-30 — CRYPTO_SPEC §4.2 layout v2)**: a status-declared variable distributes only its latest `VariableMetaStatement` (+ author info); no value or version exists (common to both with-values and metadata-only modes). A value missing from a with-values response for a variable holding a verified status-active statement is refused by the client as missing (CRYPTO_SPEC §6.3's value-distribution requirement — declared is the only legitimate value-less state). Declared variables never appear in a checkpoint's value-snapshot enumeration (values_digest is active only — CRYPTO_SPEC §6.2). The project's `schemaPolicy` (§12-11) is bundled into environment lists and both pull responses as an advisory field (for client UX — never an input to verification rules)
- **The metadata-only mode records no `var.read` ("don't record as read what wasn't read")**: `var.read`'s recording condition is the distribution of ciphertext (AUDIT_SPEC §3.3). Recording a metadata-only response would mix operations that read no value into the "certainly fetched" rank of rotation-needed detection (AUDIT_SPEC §4), breaking the detection's semantics. The reverse discipline (record everything read) is carried by the bulk pull side's "1 row per environment enumerating every returned variable in the payload" (the 2026-09-02 aggregate form)
- **Scope (2026-09-14 ES)**: a with-values bulk pull requires the target environment ∈ the calling principal's scope (403 `InsufficientScope` — §9-2). **The metadata-only mode is allowed at reader or above regardless of scope** (CRYPTO_SPEC §6.3 — the line where plaintext meta is visible to all members. Lets `maruhi schema` work on out-of-scope environments). The environment list returns all environments. The response carries **no** advisory field of "is it in the calling principal's scope" (the client derives its own scope from the verified chain — a server declaration is never an input to verification rules)

- Cumulative ciphertext bytes is "the amount currently stored" and is freed by deletion (resource protection against DO SQLite's 10 GB)
- **Manifests have no row cap (2026-08-18 session 27. Pullfrog review handling — the original draft's "manifestVersion rows / environment" cap was withdrawn because, merged with the variable side's metaVersion budget, it would permanently block even delete operations, contradicting the PR #31 ruling [the deleted exclusion of the metaVersion cap below])**: since the server holds only the latest 1 (§12-5), rows don't accumulate, so the resource-protection target itself doesn't exist. The manifestVersion number just advances monotonically within §6.1's numeric representation; consuming a number consumes no resource
- **metaVersion rows / variable (environment) (2026-08-04 session 15 owner ruling — PR #31)**: rename / delete meta-statement rows (§12-5) are bound by none of this table's other caps and pile up without limit through repeated renames, so a cap equal to "versions / variable" is placed. **status = deleted statements are excluded**: a tombstone is the end of the prev chain with at most 1 additional row, and blocking deletion too would make a resource that reached the cap permanently undeletable at any role (colliding with this section's "freed by deletion" principle and violating the delete endpoint's wire contract — no cap-exceeded error is declared). The judgment is based on the stored state (does latest metaVersion + 1 exceed the cap) and doesn't misreport a stale declared metaVersion as cap-exceeded
- **DEK wrap rows / project (2026-08-02 session 07 review owner ruling)**: dek_wraps pile up one row per member per epoch, and a per-request cap alone can't bound accumulation through repeated requests, so a project-cumulative row cap is placed. The value is 3 orders of magnitude above realistic usage (member count × environment count × epoch count. Hundreds to thousands of rows). It's "the row count currently stored" and is freed by environment deletion / wrap deletion (§12-6). The check happens **on every wrap-insertion path — both §12-6's registration API (backfill / repair re-registration) and §12-4's composite requests (environment creation / rotation)** (2026-08-03: even after epoch-1 / new-epoch bulk insertion moved to composites — §12-4 — this cap applies regardless of path. The "DEK wraps / request" table cap likewise applies to composite requests' bundled sets)
- **The DO storage-total guard (2026-09-02 H2 — codifying the old "Phase 2 announcement". docs/notes/hosted-design.md §3-3 / §8 gap 3. The merge of the implementation PR containing this revision constitutes owner approval)**: in addition to the individual caps above, a 2-tier threshold of **warning at 8 GB / rejection at 9 GB** is placed on the project DO's measured SQLite size (`SqlStorage.databaseSize`) (drafted values. The unit is decimal GB = 10^9 bytes — a conservative interpretation putting the rejection threshold below the platform's "10 GB" floor whether that floor is decimal or binary). The 10 GB SQLITE_FULL is a "readable, unwritable" floor, and the aim is never to reach it. The platform passes raw DELETE statements even at the floor, but maruhi's delete operations accompany INSERTs of a tombstone, a delete statement, and an audit row in the same task (§12-4 / §12-5 / AUDIT_SPEC §3.3), so they fail at the floor — **the floor is unresolvable by the tenant themself**, and operations have no means of intervening on DO storage. It's the only defense line covering the audit log's (audit_events) indefinite retention (AUDIT_SPEC §5.3). The effectiveness of "freed by deletion" relies on DO SQLite shrinking `databaseSize` after a DELETE (workerd measurement — the equivalent of auto-vacuum. The app can't issue `VACUUM` and the `auto_vacuum` PRAGMA isn't allowed = reliance on platform behavior). The old announcement said "designed together with the audit-log aggregation policy's (AUDIT_SPEC §3.3) measured judgment", but H0 (hosted-design.md §3-3 — ruling CZ) fixed the ruling that separates aggregation to "after dogfooding measurement" and moves the guard forward to H2, so this provision stands on the guard alone (aggregation is the countermeasure for density [how row counts grow]; the guard is the countermeasure for total volume — they stand independently)

### 12-10. Strictness of security-critical acceptance schemas and the definition of mutation success (drafted 2026-08-19 session 32 — session-31 ruling 1)

PR-M1's audit (docs/notes/session-31.md §3 M1-A2) confirmed a fail-open path where the old server **silently dropped and accepted** the `manifest` field the new CLI sent (the acceptance schema's default is dropping unknown fields). On self-host the server and CLI are updated independently, so operational procedure (documenting update order) can't be the permanent fix. This section closes it structurally (design comparison / rejected options in session-31 §7 ruling 1).

1. **Rejecting unknown fields (strict acceptance)**: the acceptance schema of a security-critical mutation payload **must refuse unknown fields with a Schema-validation error (400)** (forbidding the default "silently drop"). The targets are **every mutation carrying signed structures / ciphertexts / key material**, and on **endpoints this spec provides** it means all of the following (regardless of implementation status — approved-but-unimplemented surfaces are also subject to this standard when implemented; new additions / revisions are judged by this standard and this enumeration is updated): chain append (§11-4. Including project creation = init carrying the genesis entry), the environment-creation / rotation composite (§12-4), value push / meta operations (§12-5 — incl. the declared-creation / activation composite [2026-08-30]), DEK wrap registration (§12-6), recovery-blob registration (§13-2), lease claim (§14), invite creation / acceptance (§15-2 — acceptance signature = the key-declaration class binding a public key to a user_id), head-declaration submission (§16-1 — unimplemented as of 2026-08-19. Subject to this standard when implemented). It's the API-acceptance-layer counterpart of the chain layer's consensus rule "unknown op = invalid chain" (CRYPTO_SPEC §6.2), and pre-publication it carries no backward-compatibility clause. It fixes the failure direction of "sending a new field to an old implementation" from silent acceptance (fail-open) to structural refusal (fail-closed). A composite request is 1 request = 1 decode, so an acceptance-time refusal is atomic and partial acceptance can't structurally occur. The implementation is done at a single implementation point wrapping every security-critical payload schema in `strictPayload`, with no per-handler manual checks. The wrapper's decode and encode pass `{ onExcessProperty: "error" }` to the inner schema (the whole parse including nests and unions). Since Effect v4 rc.113, the schema AST annotation `parseOptions` isn't read by the parser (a passed ParseOptions applies to the whole parse including nests and unions. The evidence up to rc.112 remains in docs/notes/session-32.md but isn't the current enforcement mechanism). `HttpApi.ParseOptions` passes the same options not only to the payload but also to the same endpoint's success / error encodings and path params / headers. `Schema.TaggedError` carries stack-derived non-enumerated fields, so encoding an error response under those options becomes an HttpApiSchemaError and falls to HTTP 500. For that reason strict sits only on payload schemas — not on success / error / params / headers. The header codec sees the whole received headers, so `onExcessProperty: "error"` isn't used API-wide either. Shared schemas themselves aren't wrapped (don't propagate to other endpoints' responses). An implementation PR must guarantee strict's effectiveness with pinned acceptance-path tests
2. **Design norm for wire-incompatible changes**: every subsequent security-critical wire change happens only **in a form the old implementation structurally refuses**. Field additions / removals are automatically caught by (1)'s strict acceptance. A semantics change with unchanged field composition is caught as a signature-verification mismatch on the old implementation by CRYPTO_SPEC §1 principle 6 (semantics lives inside the signed bytes) — no separate compatibility flag / version negotiation is provided
3. **The definition of mutation success**: a security-critical mutation's success is defined not as "a 2xx response was received" but as "**the effect was confirmed on a verifiable distributed object**" (a 2xx is only a transport-layer fact — applying the don't-trust-the-server principle to the mutation side, the same defense works against a malicious or buggy new server's false 2xx as against an old server's silent dropping). The confirmation material is fixed per mutation kind: chain appends / composites (environment creation / rotation) use **chain sync** (confirming one's own entry on the verified chain); meta operations (statements / manifests) use **metadata-only pull** (§12-7 — the path that records no `var.read`). **Value pushes are outside this definition's application**: the only distributed object usable for effect confirmation is a value pull, which would bring `var.read` audit onto the write path (no audit-clean path exists). A value push's success is carried as before by the server's CAS + value-signature verification and self-recording to the local floor; value-rollback detection is the territory of checkpoints (CRYPTO_SPEC §6.2 / §6.3). **Recording to the local floor (CRYPTO_SPEC §6.3) and reporting success to the user happen only for an effect that passed this confirmation**


### 12-11. Schema policy (a project setting — the activation gate and schema-locked. Drafted 2026-08-30 session 46)

CRYPTO_SPEC §4.2 layout v2's write gate (finding F — old-verifier protection) and the schema-locked acceptance (finding E) are unified as **a per-project server setting `schemaPolicy`** (design comparison / rejected options — making it a chain op, baking it into environment meta, per-environment settings — in docs/notes/session-46.md ruling CV). The value has 3 tiers:

| Value | Meaning |
|---|---|
| `disabled` (default) | Refuses acceptance of **new adoptions** of layout v2 (metaVersion-1 v2 creations and v2 re-issuances to v1 variables) (422 `schema-policy-disabled` — §12-5). **Continuation statements of variables already at v2 (deletion / activation / rename / schema re-issuance) are accepted** (same section — a downgrade doesn't freeze existing v2 variables' lifecycle). Existing v1 acceptance is unchanged |
| `enabled` | Accepts v2. Schema-field use is optional |
| `locked` | enabled + requires layoutVersion 2 and a non-empty varType on variable creation (metaVersion 1) (422 `schema-required` — §12-5). **A creation-time check**; a later explicit schema re-issuance lowering it isn't prevented (§12-5 — the blocked target is silent creation by typo) |

- **Not on the chain**: follows §6.2's "the chain is the ledger of key authenticity / authorization, not a ledger of mutable metadata" (CRYPTO_SPEC). This setting is **write-acceptance policy (hygiene under an honest server)**, and since a malicious server can always ignore its own acceptance policy, chaining / signing it adds no adversarial guarantee (same character as §12-8's acceptance policy. lease_policy rides the chain because it's an authorization for key disclosure — the server is the verified party — a different character). Meta is plaintext and server enforcement doesn't contradict E2EE (exploration-memo finding E)
- **Endpoints**: `GET /projects/:projectId/schema-policy` (200 = `{ schemaPolicy }`. read scope × chain role reader or above) / `PUT /projects/:projectId/schema-policy` (204. **admin scope × chain role admin or above**. Session principals are refused — outside §5's capability-restriction permission enumeration). Judgment order / existence concealment (non-member 404) are identical to §12-3. The payload carries no signed structure (outside §12-10 (1)'s strict target class — a 3-value Literal closes under Schema validation)
- **Distribution**: per §12-7, bundled into environment lists and pull responses as an advisory field (a server declaration — unsigned. The client's use is UX [guidance before `schema set` gets refused]; it's never an input to CRYPTO_SPEC §6.3's verification rules)
- **The acceptance judgment uses the acceptance-time policy** (read inside the project DO's serialization — no race window with a change)
- **Order of activation**: server update (S2) → all members' CLI update (S3) → per-project `enabled`-ification (**the addition to SELF_HOSTING "Updates" is on the implementation PR side** — the implementation split is docs/notes/value-free-schema-design.md §3). The consequence of an order violation (enabling on a project where an un-updated CLI remains): the un-updated CLI refuses a declared statement at decode stage (unknown status) and an active statement carrying schema fields at signature-verification stage (the former is an explicit error; the latter a warning indistinguishable from tampering — a residue of CRYPTO_SPEC §4.2's breakage mode, avoided by following the order)
- **Reversibility**: downgrading `enabled` → `disabled` only stops **new adoptions** of v2 — storage / distribution / verification of existing v2 statements and the lifecycle of variables already at v2 (deletion / activation / rename / schema re-issuance — the continuation-acceptance line is §12-5) are unchanged (verification doesn't consult the policy. The downgrade doesn't freeze declared variables — refined in the 2026-08-30 PR #112 review handling). `locked` → `enabled` likewise (removability — exploration memo 8th iteration)
- **Audit**: a change records `project.schema_policy_changed` (AUDIT_SPEC §3.3 — actor and the old / new values)

## 13. Connection to the reserve-key wrap ledger API (drafted session 18, 2026-08-09. 2026-09-12 KL3 revision — added §13-6 onward. 2026-09-19 DK revision — reserve-key-ification, removal of the old-device path, added §13-11)

The server storage / distribution side of CRYPTO_SPEC §8 (**reserve-key** wrap ledger — 2026-09-19 DK. Formerly "master-key wrap ledger"). The ledger's wrap target is the reserve key's blob; device keys don't ride the ledger (adding a device is §13-11's request row and CRYPTO_SPEC §6.2's `add_device`). Every wrap / segment on the ledger is **a ciphertext opaque to the server**, and no KEK material (the recovery code, the PRF output, segment plaintexts, the ephemeral private key) appears in any API payload — the server can't decrypt or interpret the blobs (maintaining zero-knowledge). Portability to another user or context fails at decryption via the AAD / info binding (CRYPTO_SPEC §8. No additional server-side check is needed). **§13-1–13-5 are the recovery-code path (invariant); §13-6 onward is the path added by KL3**.

### 13-1. Resource model

- The blob is **at most 1 per user** (D1 `recovery_wraps`, user_id primary key). Unrelated to projects / orgs / chains; the authorization doesn't involve the token-scope table (§12-3) or chain roles
- Re-issuance (CRYPTO_SPEC §8 "generate new code → re-wrap → delete the old wrap") is realized as **replacement**: an upsert on the same endpoint as registration, where the old wrap row disappears at the same time as the new blob's acceptance (v1 doesn't provide a standalone endpoint that only deletes — an operation that intentionally creates a wrap-less state is adequately served by re-issuance)
- 2026-09-19 DK: the blob's contents are the reserve key (CRYPTO_SPEC §3). Existing `recovery_wraps` rows (replicas of the master key) are **replaced** by wraps of the reserve key on migration (the same upsert as re-issuance — the migration procedure is in docs/SELF_HOSTING.md "Updates" [bundled into K3's PR])

### 13-2. Endpoints and authorization

| op | Endpoint | Authorization |
|---|---|---|
| Register / re-issue | `PUT /auth/recovery` (204) | Only a token containing `*` × admin scope (**session principals refused** — §5's capability restriction. 2026-08-28 W0 ruling. Before that sessions were allowed — inverted by the W2b implementation) |
| Fetch blob | `GET /auth/recovery` (200 / unregistered 404) | Same + rate limit (§13-3) |
| Registration state | `GET /auth/recovery/status` (200) | Any authenticated principal |

- **The token condition for key-material management operations**: registration / re-issuance / blob fetch touch user-wide key material, and aren't permitted to project-scoped or low-privilege tokens. A token principal is allowed only when it contains `{ project: "*", permission: "admin" }` scope (satisfied by the default CLI login token [§4]); otherwise 403 (insufficient-permission). Allowing replacement = re-issuance to a low-privilege token would enable the availability attack of swapping the wrap for an undecryptable blob with a stolen scoped token (same shape as §12-6's overwrite ban). Fetch is under the same condition (blob fetch is a watch-required event of AUDIT_SPEC §3.1, and there's no legitimate reason to call it from a scoped token in daily operation)
- Unauthenticated is always 401 (AuthMiddleware). 404 (unregistered) is returned only to the authenticated person themself, so no §11-2 existence-concealment issue arises (whether one's own registration exists is information disclosed to the person via status)
- **The blob fetch's CSRF header (session principals only)**: `GET /auth/recovery` is a GET but holds state in the form of fetch counting (§13-3), and a `SameSite=Lax` session cookie is also sent on cross-site top-level navigations, so session principals are required to send the same `x-maruhi-csrf: 1` as write-type requests (§5) (absence → 403). It blocks the availability harassment of a third-party site consuming the victim's fetch window. Bearer tokens can't be attached cross-site, so they're out of scope
- `status` carries no blob (registration presence + update time only). It's exempt from rate limits / scope conditions so the CLI's storage reminder and device-addition guidance can call it on every authentication

### 13-3. Rate limit (CRYPTO_SPEC §8's fetch-endpoint requirement)

- The target is only `GET /auth/recovery` (the blob body). **Fixed window: 5 per hour per user**. Excess is 429 and returns the window's remaining seconds (retryAfterSeconds)
- Its position is an auxiliary line of double defense (authentication + a high-entropy code is the main line): it slows online enumeration and blob exfiltration attempts after a session / token theft, buying detection time as a watch-required event. It's best-effort suppression whose count can be slightly exceeded by concurrent requests, not a crypto boundary
- The count sits beside the blob row (fetch_window_start / fetch_count); unregistered (404) isn't counted
- **2026-09-12 (KL3)**: this window is re-read as §13-8's "combined blob-fetch window" (summed per user with passkey / guardian-group wrap fetches. The cap of 5 per hour is unchanged. The count is a dedicated counter row)

### 13-4. Wire representation and acceptance policy

```
RecoveryWrap = {
  suite: "maruhi/v1",          // suite identifier (CRYPTO_SPEC §2 design principle 4)
  nonceHex,                    // 96-bit random nonce (lowercase hex, 24 chars)
  ciphertextHex                // AES-256-GCM ct || tag (lowercase hex)
}
```

- ciphertext is ≥16 bytes incl. tag and **≤16 KiB** (acceptance policy. The blob's substance is the JSON serialization of a reserve-key [formerly master-key — 2026-09-19 DK] record — a few hundred bytes — with ample headroom. The cap blocks fat-ciphertext accumulation into D1)
- Distribution (GET) returns the stored suite / nonceHex / ciphertextHex as-is (with updatedAtMs attached). The blob's serialization format is the client's (CLI's) contract; the server isn't concerned

### 13-5. Audit events

Blob fetch is `auth.recovery_blob_fetched`; registration / re-issuance is `auth.recovery_code_reissued` (AUDIT_SPEC §3.1. The D1 side). Implemented with the introduction of the D1-side audit-log base (same §5.2 option A) (2026-08-10 session 21): a fetch is recorded in the same batch as the count update only for a response that actually distributed the blob (200); rate-limit refusals and unregistered 404s aren't recorded (don't record as distributed what wasn't distributed — the same boundary as §13-3's count target). Registration / re-issuance is recorded in the same batch as the replacement upsert (the first registration is the same replacement acceptance, hence the same event).

## 14. Workload lease API (drafted session 22, 2026-08-12)

The API surface of CRYPTO_SPEC §9.1 (workload leases). A workload without long-term credentials (v1 = a GitHub Actions job) presents an OIDC token and an ephemeral public key, and in 1 request obtains the "chain + ciphertexts + statements + lease-wrapped DEKs" of an environment of a grant_server'd project. **No plaintext value or persistent credential appears anywhere**: zero secrets are stored on GitHub's side, the server doesn't decrypt values (only unwraps and re-wraps DEKs), and the response is ciphertexts and wraps only (§10 / CRYPTO_SPEC §10's invariants hold on the lease path too).

### 14-1. Authentication (OIDC) and authorization (the chain-bound policy)

- Authentication uses the OIDC token (JWT) bundled with the request. No maruhi token / session is used (outside §12-3's table). Verification: (1) the issuer is included in **the server implementation's supported-issuer list** (v1 = GitHub Actions `https://token.actions.githubusercontent.com` only) (a static configuration uniform across the deployment, carrying no project-existence or state information), (2) the signature is verified with the issuer's JWKS (fetched via OIDC discovery, TTL-cached), and only alg RS256 / ES256 is allowed (symmetric-key algs and `none` are refused), (2b) **a JOSE header declaring `crit` (RFC 7515 §4.1.11) is refused (added 2026-08-15)** — crit is the declaration of "extensions you must not accept if you don't understand", and since this spec defines zero extensions, every crit value is an un-understandable extension, (3) the time verification of `exp` / `iat` (clock-skew tolerance ±60 seconds).
- **JWKS freshness and availability (drafted 2026-08-15)**: if a re-fetch fails, **verification continues with a JWKS fetched within the grace window (drafted value: 6 hours) if one exists** (stale-while-revalidate). This doesn't contradict fail-closed — signature verification always runs, and refusal happens only when not a single usable key exists (that response is §14-3's 503 `oidc-jwks-unavailable`). Two reasons for this design: (a) a transient issuer / network failure (minutes to hours) mustn't directly stop every workload of every project; (b) **a re-fetch triggered by an unknown `kid` happens before signature verification = induceable by an unauthenticated caller**, so a design where a failed fetch discards the existing cache would let someone get legitimate tokens refused just by throwing a nonexistent kid. The implementation must both retain "the last successfully fetched JWKS" (a failure doesn't corrupt the existing value) and put a fixed-window cooldown on unknown-kid-forced re-fetches. Since the grace window is also "the bound on how long after the issuer revokes a key we keep accepting", it's placed as an explicit configuration value — a trade-off between availability and revocation tracking. **Authentication ends here and doesn't reference chain-derived state (grants / lease_policy) at all** — matching against the grant's policy belongs to authorization below (per §14-3, only authentication failures become 401)
- **First-come binding (replay mitigation. 2026-08-15 owner ruling — the design comparison, rejected options, and precedent are docs/notes/session-24.md)**: at lease issuance the server records, per project, a binding "**binding key → the presented ephemeral public key**", and on a re-claim with the same binding key, **permits idempotently if it's the same ephemeral public key** (a legitimate retry after a response loss. Keeps retries working even if an issuer that pre-issues tokens at job start and can't re-issue at runtime — GitLab etc. — is added later), and **refuses with 401 `token-replayed` if it's a different ephemeral public key**. This neutralizes "a copy of a used token", surfacing a theft as either a denial on the attacker's side (audit — §14-4) or a `token-replayed` failure on the legitimate job's side (see also CRYPTO_SPEC §9.1's narrowed non-guarantees). The rule's key points:
  - **The binding key is the SHA-256 of the JWS signing input (`header.payload`) — must not hash the raw token string (mandatory. 2026-08-15 pullfrog review)**. The raw token's third segment (the signature) is malleable outside the signature's protection: via the unused bits of the trailing base64url group (which WHATWG's forgiving-base64 decode discards — RS256's last character has 15 equivalents) and ES256's `s`-malleability, **the raw token string can be changed without changing the decoded bytes, signature verification, or `claims_digest` at all**. Keying on the raw token makes the binding match miss with this one-character edit, voiding the whole first-come binding. The signing input is the very byte sequence the issuer actually signed, invariant under validity-preserving mutation — closing this path (in the implementation the column name is also `binding_key`, not `token_hash`, preventing the mix-up at the name stage)
  - The binding key doesn't depend on the `jti` claim either. `jti`'s presence / semantics are issuer-dependent (Kubernetes is 1.32 GA, CircleCI unverified), while a signing-input hash requires nothing of the issuer
  - **Judgment / recording sit after authorization (lease_policy match / scope)** (§14-3's order) — don't create a path where observing binding state is reachable with a credential weaker than "valid signature from a supported issuer × lease_policy match". The binding's **recording happens in the same atomic block as issuance** (creating neither intermediate state: a binding left without an issuance, nor an issuance with no binding left)
  - **Retention consistency (mandatory)**: a binding row must be retained until at least "the last moment the time verification (§14-1's (3)) could accept that token" = `exp` + clock skew. Expiring a binding before the time verification's acceptance window lets replays through during the difference (a precedent — PyPI trusted publishing's 2026 audit pointed at the same-shape mismatch: JWT verification leeway 30 seconds > replay-cache lifetime 5 seconds. session-24)
  - The binding is per project (DO); the key contains no environment ID. It doesn't prevent cross-project first-come (CRYPTO_SPEC §9.1's non-guarantee (2). Making the binding global needs cross-DO state, not worth v1's complexity)
  - **Client (A3) obligation**: the lease endpoint is per environment but the binding crosses all environments in a project per token, so **a job leasing multiple environments with one OIDC token must present the same ephemeral key on every request** (one ephemeral key per token — don't rotate the key per request). Rotating the key gets the second and later requests refused with `token-replayed`. This is intended behavior (locking a token to the key that first used it is the substance of first-come binding; allowing a different key per environment would open the path of pulling an unbound different environment with a stolen token). On a runtime-issuing issuer (GitHub Actions) you may unify the key or issue a per-environment token, but on a pre-issuing issuer (GitLab / k8s projected volume) reusing 1 token with a fixed key is the only option
  - `token-replayed` isn't resolved by resending the same token. A runtime-issuing issuer (GitHub Actions) **may issue a fresh token and auto-retry once** (SHOULD). A retry with the same token + same key always passes idempotently, so recovery from a response loss needs no additional handling
- Authorization is judged by **existential quantification** (2026-08-12 review reflection — "selecting the matching element" would make the selection non-deterministic when multiple elements match): authorize if **at least one element exists** in the chain-derived valid grant_server's lease_policy (CRYPTO_SPEC §6.2) such that (1) its issuer_url matches the token's issuer, (2) its audience matches the token's `aud` (the audience's recommended value is the deployment's origin), and (3) **all** of its claim_constraints **exactly match** the token's claims. Only the claims enumerated in the constraints are evaluated; unenumerated claims aren't involved. Multiple elements with the same (issuer_url, audience) but different claim_constraints are **a legitimate representation** (e.g. per-branch CI restrictions as elements differing in a `sub` constraint's value — since v1 only supports exact match, permitting multiple branches is expressed in this form). Which element matched affects neither the authorization result nor the lease wrap (`claims_digest` — CRYPTO_SPEC §9.1 — is computed from the token's issuer / sub / aud and doesn't depend on identifying the element). Extensions of the evaluation semantics (prefixes etc.) happen by revising this chapter and don't affect the chain format (CRYPTO_SPEC §6.2's structure / semantics separation)
- **An empty claim_constraints doesn't match (fail-closed. Clarified 2026-08-24)**: since the issuer is shared across all GitHub Actions workloads and the audience is chosen by the token requester, treating 0 constraints as empty-product truth would authorize even a third party's workload. The policy-creation client requires ≥1 claim constraint per element, and the server-side evaluation likewise treats an empty element made by an old client etc. as a non-match. This minimum count is evaluation semantics and doesn't change CRYPTO_SPEC §6.2's chain shape / consensus rules
- The target environment must be in the disclosure scope (scope_environments)
- **Members' environment scope (CRYPTO_SPEC §6.2 — 2026-09-14 ES) isn't involved in the lease path**: a workload isn't a member, and a lease's environment restriction is carried by the grant's `scope_environments` (invariant). No composition rule is added
- **Existence concealment (§11-2 applies)**: unknown project, no grant, policy mismatch (a mismatch in issuer_url / audience / claim constraints, any of them), and out-of-scope environment are uniformly 404. Only OIDC-verification failures themselves (outside the supported-issuer list, signature, time, format) and **first-come binding violation (`token-replayed` — above)** are 401 — both are failures attributable to the presented credential. The latter is reachable only after authorization passes, so it's compatible with existence concealment (folding it into 404 would make the legitimate job's failure undiagnosable and defeat the first-come binding's purpose of visibility)

### 14-2. Endpoint and response

- `POST /projects/:projectId/environments/:environmentId/lease`. Request = `{ oidcToken, ephemeralPubHex }` (an ephemeral X25519 public key, 32 bytes hex. The workload generates it in memory and discards it when the job ends)
- Response = the whole chain + the current epoch + all active variables' latest versions (EncryptedPayload + writer info) + the latest meta statements (with author info) + **the latest `EnvironmentManifest` (with issuer info) + tombstone statements + the checkpoint-time value-snapshot enumeration (the same material as §12-7 — 2026-08-18)** + **lease-wrapped DEKs (for all epochs used by the latest values in the response + the current epoch)**. The same verification-material bundling discipline as the with-values bulk pull (§12-7), plus **the bundled chain** for a recipient that isn't a member (the chain-fetch API returns 404 to non-members per §11-2, so the lease response is the only distribution path). **Other members' head declarations (§16) aren't bundled** (CRYPTO_SPEC §6.6 — a malicious server can attach past declarations to an old view, so it adds no detection and only grows the misrecognition of "verified")
- The lease wrap follows CRYPTO_SPEC §9.1 (claims_digest bound in info). **Not stored** (doesn't enter dek_wraps — same §9.1)
- The receiving workload's verification obligation is CRYPTO_SPEC §9.1 (chain verification, repository anchor, commitment cross-check, value-signature verification, manifest and checkpoint-consistency verification — 2026-08-18)

### 14-3. Judgment order and errors

- OIDC verification = supported-issuer list / signature / time / format (401 — §14-1's authentication) → lease_policy match (issuer_url / audience / claim constraints) + scope (a mismatch is uniformly 404) → **first-come binding (401 `token-replayed` — §14-1. 2026-08-15 ruling)**: placed right after authorization and before the environment's existence judgment — a re-claim with a bound token + different key gets a uniform 401 regardless of the target environment's existence / deletion state, giving no environment-existence information to a holder of a policy-matching token's copy (the judgment is read-only and consumes no rate window) → environment existence → **rate limit (429 — below)** → the presence of server-key-directed wraps (missing = 503 typed `LeaseUnavailable`, reason: `server-wraps-missing` — don't leave the "granted but re-wrap incomplete" state [CRYPTO_SPEC §7] as an opaque failure) → issuance (recording the first-come binding is the same atomic block as issuance / audit / window consumption — §14-1)
- **The per-project rate limit (fixed window) sits after authorization (clarified 2026-08-15)**: placing it before authorization would return 429 even to an unauthorized caller, leaking "that project exists" (violating §11-2's existence concealment). Placing it after means 429 reaches only workloads that already matched the policy, and the principals who can consume the window are only those satisfying "a supported issuer's valid signature × an on-chain lease_policy match" (closing the path where a third party drains a legitimate workload's window)
- **Separately from this, a per-source-IP request-level rate limit sits at the head of the handler (before OIDC verification / DO resolution) (2026-08-24 — deepsec M5 handling)**: since a DO is implicitly created by naming a project ID, anyone holding a valid OIDC token could mass-produce DOs with many different project IDs (the constructor creates tables, and there's no collection path). The default deployment's Workers Rate Limiting binding (60/min/IP. Per-colo best-effort. Excess is 429 `LeaseRateLimited`) bounds the creation rate. The judgment depends only on IP and no project state, so a pre-authorization 429 leaks no existence information (the existence-concealment argument above concerns 429s tied to project state)
- **The response when JWKS can't be fetched (drafted 2026-08-15)**: when the issuer's JWKS can't be fetched and signature verification **couldn't be executed**, return 503 `LeaseUnavailable` (reason: `oidc-jwks-unavailable`) while maintaining fail-closed (§14-1). Every 401 target §14-1 enumerates (outside the supported-issuer list, signature mismatch, time, format) is a failure attributable to the presented token, but a transient issuer-side / network-side failure isn't — returning 401 would make the CI job treat it as "bad credentials", non-retryable, so it's separated as a retryable category. A deployment where the server key is unconfigured (CRYPTO_SPEC §9's keypair unconfigured) gets the same 503 with reason `server-key-unconfigured` (without the private key no unwrapping path exists, and that's a missing configuration, not a missing project)
- Acceptance policy (values are drafts — adjusted in review): leases are **a fixed window of 300 per hour per project** (excess 429). oidcToken ≤16 KiB, ephemeralPubHex strictly 32-byte hex

### 14-4. Audit

- Issuance: `server.dek_unwrapped` + `server.lease_issued` (1 row per environment — a lease is a per-environment distribution with no variable-granularity selection. AUDIT_SPEC §3.5). **The lease response doesn't record var.read** (var.read is evidence of a human actor's reads — AUDIT_SPEC §3.3. Disclosure to a workload is carried by the server.* family, and lease_issued feeds rotation-needed detection — same §4.1)
- Refusal: `server.lease_denied` (**only refusals after passing OIDC signature verification**, with a fixed-window cap — AUDIT_SPEC §3.5)
- No external identifiers (repository names etc.) are written into the audit payload: the matched policy element is held by the chain (the grant payload), and cross-checking works via `grant_chain_seq` + `claims_digest` (don't grow AUDIT_SPEC §1-2's forbidden information on the lease path either)

## 15. Invite API (drafted session 22, 2026-08-12 — resolving CRYPTO_SPEC open item #9. 2026-09-13 IV revision — link keys, issuance signatures, joint acceptance signatures, backing sources)

The resource / API surface of CRYPTO_SPEC §6.5 (link keys, issuance signatures, joint acceptance signatures, mutual confirmation). Member addition — whether the target is registered or unregistered — goes through the single mechanism of **invite → accept → add_member** (structurally eliminating additions without consent). No global public-key directory is built (same §6.5). **Invites predating this revision (token-bound acceptance blocks, `v=1` links) aren't accepted** (2026-09-13 owner ruling — no compatibility path. Existing pending rows become unacceptable and prompt expiry).

### 15-1. Resource model

```sql
invitations (
  id              TEXT PRIMARY KEY,   -- ULID (after the IV revision it's **client-numbered** — covered by the issuance signature. A collision is 409)
  project_id      TEXT NOT NULL,      -- genesis hash. Link-key possession is treated as a capability (consistent with §11-2)
  link_pub        TEXT NOT NULL,      -- the link public key (Ed25519, lowercase hex 64). Client-generated and declared at issuance (CRYPTO_SPEC §6.5). UNIQUE
  head_hash       TEXT NOT NULL,      -- the issue body: the inviter's verified head at issuance (hex 64) and seq (CRYPTO_SPEC §6.5). A public value
  head_seq        INTEGER NOT NULL,
  issue_signature TEXT NOT NULL,      -- the issuance signature (the inviter's chain sig key, hex 128). The server doesn't verify it, just stores and distributes
  role            TEXT NOT NULL,      -- 'reader' | 'member' | 'admin' (an invite never grants owner)
  scope_kind      TEXT NOT NULL,      -- 'all' | 'listed' (the scope to grant — CRYPTO_SPEC §6.2. 2026-09-14 ES)
  scope_environments TEXT NOT NULL,   -- a JSON array of environment_ids (the input list of the issue body's scope_environments_lp_hex. For display and add_member input)
  inviter_user_id TEXT NOT NULL,
  status          TEXT NOT NULL,      -- 'pending' | 'accepted' | 'completed' | 'revoked' (expiry is derived from expires_at)
  expires_at      INTEGER NOT NULL,   -- issuance + 7 days (drafted value)
  -- the acceptance block (status accepted and later):
  invitee_user_id TEXT, invitee_enc_pub TEXT, invitee_sig_pub TEXT,
  accept_signature TEXT,              -- CRYPTO_SPEC §6.5 acceptance signature (the acceptor's chain sig key)
  link_signature  TEXT,               -- CRYPTO_SPEC §6.5 link signature (the link key)
  accepted_at     INTEGER,
  created_at      INTEGER NOT NULL
)
```

- Storage is D1 (acceptance is an operation by a project non-member, so resolving link public key → project needs a global index). Audit events (invite.*) also sit in the same D1, appended in the same batch (AUDIT_SPEC §3.2 / §5.2)
- **The scope columns (2026-09-14 ES)**: `scope_kind` / `scope_environments` are added. The issue body (`head_hash` / `head_seq` / `role` / scope) + `issue_signature` is the material the inviter client verifies before `add_member`
- **The server holds / returns none of the invite's secrets**: the row carries the link **public** key, the issue body, and the issuance signature; the link key's seed never passes through the server (no token-equivalent value appears even in the issuance response). If a row leaks, acceptance can't be forged (the same "verifiable but not creatable" property as the old token_hash). The issue body + issuance signature is material the inviter client verifies with its own key before `add_member`, and the server can't forge or transplant it (CRYPTO_SPEC §6.5)
- **Single use**: acceptance is a pending → accepted CAS. Accepting an accepted / revoked / expired invite is 410
- The invitee-facing display-name snapshot and **the backing source's login** etc. are **not carried on the invite record**: what the pre-acceptance counterpart sees is only the role and the verifiable information the link carries (§15-3). No surface is created that would have them trust a server-declared display name. The backing source's login lives only in the link's fragment (inviter → invitee) and the inviter's local pin (the destination) (CRYPTO_SPEC §6.5's prohibitions)

### 15-2. Endpoints and authorization

| op | Endpoint | Authorization |
|---|---|---|
| Issue | `POST /projects/:projectId/invites` (body: `{ id, role, scopeKind, scopeEnvironmentIds, linkPubHex, headHashHex, headSeq, issueSignatureHex }` — scope is 2026-09-14 ES. Response: `{ expiresAtMs }`) | token scope admin × chain role admin or above (**issuing an invite with role = admin is owner-only**). **Session principals refused** (§5 — issuance requires generating a link key and an issuance signature, which can't be placed on keyless Web — ADR-0018 revision 2). `id` gets a **format check only** for ULID form, `linkPubHex` 32-byte hex, `headHashHex` 32-byte hex, `issueSignatureHex` 64-byte hex (the issuance signature isn't verified by the server — the verifiers are the inviter themself and the invitee). A UNIQUE violation on `id` / `linkPubHex` is 409 (the client re-numbers / re-generates) |
| Accept | `POST /invites/accept` (body: `{ linkPubHex, encPubHex, sigPubHex, acceptSignatureHex, linkSignatureHex }`) | **Only an all-projects-scope (`*`) × admin token** (same level as §13-2's key-material condition — an operation of the key-declaration class. **Session principals refused**. The reason is as before). Possession of the link key (= being able to make the link signature) is the capability to the target invite |
| List / revoke | `GET / DELETE /projects/:projectId/invites(/:id)` | token scope admin × chain role admin or above. **Session principals also allowed** (read + revocation-type) |

- **The server's acceptance verification (judgment order)**: Schema 400 → authentication 401 → CSRF / the key-material condition 403 → unknown `linkPubHex` 404 → unusable 410 → **link-signature verification** (`link_pub` from the stored row, `project_id` from the stored row, `invitee_user_id` reconstructed from the calling principal — never built from wire-declared values) 422 → **acceptance-signature verification** (with the presented sig key) 422 → CAS (a loss re-reads and gets 410). **The calling principal's internal user_id = the signed invitee_user_id** is enforced by both signatures. Keys get only the format check (32-byte hex); **no pre-judgment of member-key uniqueness (CRYPTO_SPEC §6.2) is made** (invariant). The server's signature verification is a front acceptance check, not the source of truth — the source of truth is the inviter client's issuance-pin matching + re-verification of both signatures (CRYPTO_SPEC §6.5)
- **Acceptance doesn't affect the chain** (invariant). The server updates the accepted invite whose target = invitee to completed when accepting add_member
- Acceptance policy (drafted values, invariant): pending invites cap at 100 per project, issuance is a fixed window of 30/hour/project. Excess is 429. Issuance / acceptance is strict acceptance (§12-10 (1) — already enumerated)
- **A list row** (`InvitationSummary`) replaces `tokenHashHex` with the issue body (`linkPubHex` / `headHashHex` / `headSeq` / `issueSignatureHex`) and adds `linkSignatureHex` to the acceptance block. The inviter client verifies the issue body + issuance signature with its own sig public key (failure = not its own issuance / a swapped row → don't add_member), cross-checks `linkPubHex` / role if it has an issuance pin, and re-verifies both signatures
- **Scope (2026-09-14 ES)**: the issuance body's `scopeKind` / `scopeEnvironmentIds` get format checks only (kind's closed set, an empty array if all, ≤256 elements, each id in §12-1 format. **No existence check** — the consensus rule is checked by verifyChain at add_member acceptance). List rows (`InvitationSummary`) and the acceptance response carry the scope. **Issuing an invite with role = admin is owner-only** (invariant). That the issuer's scope contains the invite's scope isn't checked at issuance (the final judgment is the containment rule at add_member acceptance — the issuance-time state may change), but the CLI checks and guides before communicating

### 15-3. The invite-link format (client spec)

```
https://<web-origin>/invite#v=2&i=<invite_id>&k=<link_seed_hex>&p=<project_id>&h=<head_hash_hex>&s=<head_seq>
  &iu=<inviter_user_id>&ie=<inviter_enc_pub_hex>&is=<inviter_sig_pub_hex>&r=<role>&sk=<scope_kind>&se=<environment_id comma-separated>&il=<inviter_github_login>&sig=<issue_signature_hex>
```

- **`v=2`** (2026-09-13 IV revision). `v=1` (`t=` token, `if=` FP) isn't accepted, and the acceptance client guides "ask the issuer to re-issue". **Acceptance by raw token (an input other than a link) is abolished** (don't keep a path that loses the anchor, issuance signature, and backing all at once)
- **The fragment (after `#`) is never sent to the server** (invariant): `i` is the invite id (a client-numbered ULID — covered by the issuance signature), `k` is the link key's seed (CRYPTO_SPEC §6.5 — the acceptance client derives `K_priv` to make the link signature. Never persisted), `p` / `h` / `s` are the invite-link anchor (CRYPTO_SPEC §6.3 (a)), `iu` / `ie` / `is` are the inviter's identity (the FP derives from `ie` ‖ `is` — the old `if` abolished), `r` is the role to grant, `sk` / `se` are the scope to grant (2026-09-14 ES — below), `sig` is the **issuance signature** (`invite_issue_signed_bytes` — covers `i / p / K_pub / h / s / r / iu / ie / is / sk / se`. Doesn't cover `k` or `il`). The acceptance client verifies `sig` with `is` before proceeding to anything else (failure = don't accept)
- **Since `r` is inside the issuance signature**, it's covered by tamper detection (promoted from the 2026-08-15 supplement's "display-only / warn"). The source of truth for the granted role is the invite record, and if it disagrees with the acceptance response's role the acceptance client treats it as **an error** (a swapped row or a tampered link)
- **`sk=<scope_kind>&se=<environment_id comma-separated>` (2026-09-14 ES)**: the scope to grant (`se` is empty if `sk=all`). Covered by the issuance signature (same status as `r=`). The acceptance client displays role and scope, and treats a disagreement with the acceptance response's scope as an error. CLI: `maruhi invite create --role <role> [--env <environment-id>]…` (`--env` repeatable. Omitted = all. role = owner can't be invited — invariant). `maruhi member add` signs `add_member` with the invite row's scope (it has no `--env`)
- **`il` is the inviter's GitHub login** (the inviter client builds it from `GET /auth/me`'s display login. The matching material of the backing source `github-signing-keys` — CRYPTO_SPEC §6.5). It's self-declared, but if `is` isn't in `il`'s signing-key list it just returns to the ceremony as unmatchable — a lie gains nothing. **The acceptance client doesn't persist `il`** (doesn't write it into the anchor pin). It's ignored in environments where the backing source is `none`
- CLI: `maruhi invite create [--role <role>] [--env <environment-id>]… [--github <login>]` (numbering the invite id → generating the link key → the issuance signature → issuance [sends the issue body + signature — includes the scope] → assembling and displaying the link → saving the issuance pin [`linkPubHex` / role / expiry / destination login]) / `maruhi invite accept '<link>' [--from <login>] [--inviter-fingerprint <fp>]` (verifying the issuance signature → mutual confirmation [CRYPTO_SPEC §6.5's fulfillment form] → key generation [if not yet generated] → joint signing → acceptance → pinning the anchor) / `maruhi member add [<invite-id>] [--github <login>] [--expect-fingerprint <fp>]` (issuance-pin matching → re-verifying both signatures → the fulfillment-form judgment → add_member) / `maruhi key publish [--gh]` (display your sig public key as an OpenSSH line, and `--gh` calls `gh ssh-key add --type signing`). The backing source is the CLI's non-secret setting `identityBacking` (`github-signing-keys` default / `none`)
- **The link's landing point (`<web-origin>/invite`) is a fully static guidance page** (invariant — 2026-08-28 W0 ruling / ADR-0018 revision 2・item 5. It holds no script and doesn't interpret the fragment. Per-path CSP `script-src 'none'`). Neither invite issuance nor acceptance is placed on the Web
- **The invite link is passed over a trusted person-to-person channel (normative)**: anyone who can read the link can accept before the legitimate counterpart (the backing source closes this — CRYPTO_SPEC §14.3-9), and anyone who can swap the link can lure them into their own project (the defense is the invitee reading `il`). To be moved into H5's threat-model document
- **Composition with signup control (§3)** (invariant): a signup invite code is passed over a separate channel
- **The issuance pin (the inviter side's non-secret local state — SHOULD)**: `issued[<invite id>] = { linkPubHex, role, expiresAtMs, expectedGithubLogin? }` in `invites/<projectId>.json`. The source of truth for IV1's verification is the inviter's own issuance signature over the server row's issue body (CRYPTO_SPEC §6.5); the pin carries the additional cross-check of `linkPubHex` / role and the retention of the destination login. The 4th form works even on a device without a pin (issued on another device), with only the destination login supplemented by `--github <login>` (no interactive input is provided — it would get mixed into the same path as the ceremony's re-entry prompts, and a typo would become a query for another person's login. Naming is limited to at issuance or an explicit flag action — 2026-09-13 K5 implementation ruling / owner approval). **The link key's seed / private key is never written into the pin**
- **The anchor is pinned only after acceptance succeeds** (invariant). The inviter's sig public key (`is`) is placed beside the anchor, and the first sync's mechanical matching (CRYPTO_SPEC §6.3 (a)) checks the sig public key match in addition to the FP. An anchor already mechanically matched (verified) isn't overwritten by a later acceptance

### 15-4. Audit events

Issuance = `invite.created`, acceptance = `invite.accepted`, revocation = `invite.revoked` (AUDIT_SPEC §3.2 — invariant. The 2026-09-13 IV revision doesn't change the payload: acceptance is always link-bound so no flag is needed; the backing source's login, link public key, and signatures aren't written)

## 16. Head-declaration / checkpoint-support APIs (drafted session 27, 2026-08-18)

The API surface of CRYPTO_SPEC §6.6 (head declarations) / §6.2 `checkpoint` / §6.3 (head gossip, checkpoint consistency). It follows the same discipline as §11 / §12: every endpoint is authentication-required, and responses to non-members / out-of-scope are uniformly 404 (§11-2).

### 16-1. Submitting and distributing head declarations

| op | Endpoint | Authorization |
|---|---|---|
| Submit a declaration | `PUT /projects/:projectId/head-attestation` (204) | token scope **read** × chain role reader or above |
| Distribute the declaration set | bundled as `attestations` into the chain-fetch (§11's get) response | same as get's authorization (read × reader or above) |

- **The basis for submitting at read scope**: a declaration accompanies read synchronization (CRYPTO_SPEC §6.3 — the submission trigger is after sync + verification success), and the only writable thing is "one's own signed declaration, 1 row", touching no secrets or shared state. Requiring write would exclude read-token sync clients from gossip under an authorization model where readers are resident (CRYPTO_SPEC §6.2), damaging split-view detection's completeness (every member's interest — same §6.6)
- Request = `{ suite, chainHeadHashHex, chainHeadSeq, signatureHex }` (the attester is the calling principal — same rule as §12-5's "calling principal = signer"). Acceptance verification is CRYPTO_SPEC §6.4 (signature / head existence / seq monotone advance). **A regressing declaration gets 409 (typed `AttestationRegression`. Returns the stored seq)**: the don't-silently-succeed discipline (same as §12-6) — an honest client's regression is a symptom of floor corruption or a concurrent CLI; quietly swallowing it would hide a client bug. Re-submitting the same seq passes idempotently with 204 (a resend of identical content — retry-safe)
- Distribution is **only current members' latest declarations** (with attesterUserId + attesterKeyFingerprintHex attached — same shape as §12-2's verification material). On `remove_member` acceptance the target's declaration rows are deleted (CRYPTO_SPEC §6.4). **Per-device declarations (2026-09-19 DK)**: storage / distribution is the latest 1 row per **(attester_user_id, attester_key_fingerprint_hex)**, not per member (devices sync independently, so seq monotonicity isn't imposed across devices — the regression 409 applies only against the same device's stored row). On `revoke_device` acceptance that device's declaration rows are deleted; on `remove_member` acceptance all of the target's devices' rows are. The acceptance-policy window (below, 60/hour) stays per member. **The server acceptance time of a declaration row may be stored but isn't distributed** (limits the behavioral information a declaration carries to "the reach point of chain sync" — CRYPTO_SPEC §6.6 / AUDIT_SPEC §6)
- Acceptance policy (drafted value — adjusted in review): **a fixed window of 60/hour per member** (excess 429). Storage is the latest 1 row per member (per device after 2026-09-19 DK — max 16 devices), so no storage bloat

### 16-2. Supporting checkpoint issuance

- **A standalone** `checkpoint` entry is **accepted via the generic chain-append API (§11's append)**. It accompanies no client-supplied ancillary data (the digest pre-image of the value snapshot is reconstructed by the server from acceptance-time state), and there's no other input a composite request would atomically bundle, so it uses the generic path. **A boundary checkpoint (2026-08-19 session 32 — a mandatory bundle of the environment-creation / rotation composites) is accepted via §12-4's composite path**. On either path the server upserts the reconstructed value-snapshot enumeration + the corresponding checkpoint seq / hash as the latest covering checkpoint for each environment contained in the payload, in the same project-DO transaction as the chain append (**the storage discipline is identical regardless of path**). Existing snapshots of environments not contained in the payload aren't changed (CRYPTO_SPEC §6.4)
- **Only when audit_head_hash is non-empty, effective-permission admin is required (token scope admin × chain role admin or above); insufficiency is 403** (a checkpoint of the data layer with an empty string is write × member or above. The chain-role-admin condition is also independently verified by CRYPTO_SPEC §6.2's consensus rule). Acceptance verification (consensus rules + cross-check against acceptance-time stored state) is CRYPTO_SPEC §6.2 / §6.4. A cross-check failure is refused with 422 (typed `CheckpointStateMismatch` — reasons: `manifest-mismatch` [a mismatch with the latest manifest = including the case where the issuer's view is stale] / `values-digest-mismatch` / `audit-head-unknown` / `audit-head-stale` [the position is below the immediately-preceding checkpoint's mirror row — CRYPTO_SPEC §6.4. Refusing an issuance that didn't re-fetch the audit-head declaration after a CAS conflict] / `environment-deleted` [an entry for a deleted environment — CRYPTO_SPEC §6.4]). The client re-fetches and re-verifies the data-layer view, re-signs, and retries; only an issuer with effective-permission admin notarizing an audit head also re-fetches the declaration (an issuer not notarizing doesn't fetch the audit head and doesn't hit the 403)
- **Fetching the audit head**: `GET /projects/:projectId/audit-head` (200 = `{ auditHeadHashHex }`). Authorization is **effective-permission admin (token scope admin × chain role admin or above — §9-2's min. 2026-08-18 security-review handling)** — opening it at member level would leak a timing side channel to below-admin via **polling the cumulative hash's changes** ("an audit-row append unaccompanied by a visible class-1 event = class-2's activity window") (admin is a principal who can browse all rows anyway; this response carries no new information). **The response carries no audit seq or row count** (the cumulative hash is random-looking and carries no ordinals — consistent with AUDIT_SPEC §7's "don't leak even the count" discipline and the C1 ruling. CRYPTO_SPEC §6.2). A project with zero audit rows returns the empty string. **Independent of a checkpoint's issuance permission (member or above)**: an issuer **without effective-permission admin** (including the case where the chain role is admin but the token scope stops at write — the client can judge beforehand from its scope and the chain-derived role, and doesn't fall back after hitting a 403) issues with audit_head_hash as the empty string (no audit-head notarization — CRYPTO_SPEC §6.2) (the data layer's notarization completes without an audit head)
- **Bounded extension of lazy materialization (2026-08-28 session 38 — the API surface of AUDIT_SPEC §5.1's supplement)**: when the cumulative hash column's lazy materialization reaches one call's extension cap (= the column hasn't reached MAX(seq)), every path that reads the audit head — this fetch endpoint and checkpoint acceptance (the non-empty notarization of standalone / boundary composites) — is refused with **503 (typed `AuditHeadNotReady`)**. The body is empty (doesn't carry the remaining amount or the audit row count — AUDIT_SPEC §7's non-leakage of counts). The refusal is returned only after the authorization judgment (consistent with §11-2's existence concealment). It's retryable: the extension's progress is stored server-side, and each call including the refused response advances it, so the client may retry immediately (the CLI retries in a bounded way and, on exhaustion, guides the occurrence condition [the first materialization of a huge existing log] and the resolution by re-running)
- The issuing client assembles the manifest reference (manifestVersion / signed_bytes hash) and values_digest **from its own verified view** (recomputed from §12-7's distributed material — never signing a server-declared value as-is). **Only an effective-permission-admin issuer** mirrors this endpoint's declared value for audit_head_hash alone as "an issuance-time unverified notarization" (empty string otherwise — above. CRYPTO_SPEC §6.3 / §6.4's semantics)

### 16-3. Audit events

- Accepting a `checkpoint` entry records the chain mirror `chain.checkpointed` (AUDIT_SPEC §3.4)
- **Head declarations don't become audit events** (AUDIT_SPEC §6 — high-frequency low-information, not contributing to rotation-needed detection, and don't newly create a persistent record of behavioral information like "when they synced". CRYPTO_SPEC §6.6's privacy minimization)
