## 1. Design principles

1. **Selective-disclosure E2EE**: the default is complete zero-knowledge (the server holds only ciphertexts). Server-side decryption becomes possible only when the user explicitly grants it per project (treating the server as "member N+1")
2. **Standard parts only**: do not invent custom protocols or custom primitives. Only WebCrypto, HPKE (RFC 9180), and audited libraries providing them are used
3. **Context binding**: every ciphertext is cryptographically bound via AAD / info to its usage context (project, epoch, recipient, etc.). Out-of-context reuse (a transplantation attack) fails at decryption
4. **Crypto agility**: every persistent data structure carries a suite identifier, allowing future algorithm migration
5. **Stating the limits of cryptography**: cryptography cannot un-read an "already-read value". The effectiveness of revocation is guaranteed by rotating the upstream credentials, supported as a product feature
6. **Semantics live inside the signed byte string** (2026-08-19 session 32 — codifying the existing architecture): security-critical semantics (values that are inputs to verification rules and information deciding verification branches) must always be placed inside the normalized LP signed byte string with a domain-separation string (§2.1). Transport fields outside the signed content are advisory and must not be used to branch verification rules. Consequently a change of semantics becomes a change of the LP field sequence, which old implementations structurally refuse as a signature-verification mismatch (doubling as the structural marker of a wire-incompatible change — AUTH_SPEC §12-10 (2)). The known residue is the acceptance side's verification-mode selection (which verification rule to apply doesn't enter the signed byte string — the target of session-31 §7 ruling 2); its resolution follows the consequences of that ruling
7. **Keys belong to devices, permissions belong to people** (2026-09-19 DK — design record docs/notes/dk-design.md ruling DK-A. Placed in §1 because, like principle 6, it cuts across multiple mechanisms — fulfilling the announcement in es-design.md §7 K1-1; the ruling is dk-design.md §6 K1-1): role, scope, and the distinctness of four-eyes votes are counted over people (user_id) on the chain, while key material and its revocation are handled per device (device key — §3). A signer is identified by (user_id, key fingerprint); the fingerprint selects the device. A device's effective permission = (min(the person's role, the device's role_cap), the person's scope ∩ the device's scope), never exceeding the person's permission. **Every check of a signer's (actor / writer / author / issuer / attester) role / scope in this specification is performed against the signing device's effective permission** (§5.1 / §6.2 / §6.3 / §6.6 / §7, AUTH_SPEC §12-6). The ledger (§8) guards a single reserve key that lives on no device. Individual rules are placed in §6.2 "Device keys" as derivations from this principle

## 2. Algorithm suite

Suite identifier: `maruhi/v1`

| Purpose | Algorithm |
|---|---|
| Data encryption (variable values) | AES-256-GCM (96-bit random nonce) |
| Key wrapping (DEK → recipient) | HPKE Base mode: DHKEM(X25519, HKDF-SHA256) + HKDF-SHA256 + AES-256-GCM |
| Signatures (membership log etc.) | Ed25519 |
| Hashing (chain, fingerprints) | SHA-256 |
| Key derivation (recovery code etc.) | HKDF-SHA256 |

- Implementation: AES-GCM / Ed25519 / HKDF come from WebCrypto. HPKE (incl. the X25519 KEM) uses the `hpke` (panva) 1.x library (**decided 2026-08-01**. Exact pin. Fallback path: hpke-js (dajiaji). The selection history is docs/notes/spike-c.md)
- HPKE Open(Decap) standardizes on an implementation that **passes the recipient's KeyPair (including the public key)**. Passing the bare private key is not used because it forces extractable=true (compatible with non-extractable-key operation. A verified finding of spike C)
- Reserve room to migrate the KEM to an X25519+ML-KEM-768 hybrid as `maruhi/v2` in the future (Phase 2 and later)

### 2.1 AAD / info encoding convention (mandatory)

An AAD / info / normalized byte string written `A || B || C` in this specification must not be implemented as plain string concatenation (the ambiguity of `("ab","c")` and `("a","bc")` yielding the same byte string destroys domain separation). Always use the following deterministic encoding:

- Each field becomes a UTF-8 byte string, concatenated as `uint32-BE length prefix + body`
- Numeric fields (epoch, version, seq) are decimalized to strings first, then treated the same way
- Only **non-negative safe integers (0 to 2^53 − 1)** are valid as numeric fields; non-integers (e.g. 1.5) and values ≥ 2^53 are refused as invalid input (fail-closed. Codified in 2026-08-28 session 34 — no behavior change to the existing implementation). Basis: in float64's precision-loss region, decimalization is no longer one-to-one with the value, which breaks the uniqueness of the normalized byte string for the same value — the point of this section. Boundary refusal is pinned by each runtime's harness check (test-vectors/README.md convention 21)
- Exactly one implementation of this encoder / decoder lives in `packages/crypto`, shared across every use (AAD, HPKE info, chain normalization). Pinned by test vectors

## 3. Key hierarchy

```
User (a member on the chain — user_id・role・scope)
├─ Device keys d1 … dn (one per device. Each has enc: X25519 [for receiving HPKE] + sig: Ed25519 [for signing the membership log])
│     cap = (role_cap, scope) — a device's effective permission = (min(role, role_cap), scope ∩ scope_d)
└─ Reserve key r (same form as a device key. Its private key lives only on the §8 ledger)
        │
        └─ Wrap target: Environment Epoch DEK (one per project × environment × epoch) — recipients are (user, device key)
                └─ Encryption target: variable values, and future secret metadata
```

- **Device key (2026-09-19 DK — formerly "User master keypair")**: generated client-side per device. The private key is never sent to the server; it lives only in that device's secure storage (CLI: the OS keychain, or `maruhi agent`'s memory). **A device key is never copied to another device**. A device has one key pair, and **the same device key is used across all projects** the person belongs to (a CLI discipline — device addition / revocation lands on every project's chain with the same FP. The chain doesn't enforce this: `add_device` is a per-project op, and registering a different key per project doesn't offend the consensus rules. AUTH_SPEC §13-11's registry cap assumes this operation). A member (user_id) on the chain holds a **set** of device keys: `add_member` / `genesis` put the first one on, and `add_device` / `revoke_device` (§6.2) record subsequent additions and removals. Signer identification stays (user_id, key fingerprint), with the fingerprint pointing at the device (§1 principle 7)
- **Reserve key (2026-09-19 DK)**: of the same form as a device key, a key pair whose private key **lives on no daily-use device and only on the §8 ledger**. On the chain it is an ordinary device key registered via `add_device` (cap = (owner, all)) and receives DEK wraps (so that restore after losing all devices can backfill even when no other device exists). After restoring (§8), `add_device` a new device key, then erase the reserve key's secret from the device
- **Key fingerprint**: the first 16 bytes of `SHA-256(enc public key || sig public key)`. Used for key identification in logs and the UI — **unchanged**. Since DK (2026-09-19), the fingerprint identifies the device
- **Fingerprint word display (drafted 2026-08-12)**: the display form used for human out-of-band cross-checks (the invite mutual confirmation = §6.5, the server-key check at grant_server execution = §9) is a mnemonic encoding of the 16-byte FP with the BIP39 English wordlist (12 words. 128-bit entropy + a 4-bit SHA-256 checksum). Regardless of display language or locale, **always the single English list** (verbal matching doesn't work if the two sides' displays differ). **No shortening to a shorter code**: since the attacker can freely choose one of the two keys being compared, trimming the display strength directly weakens the second-preimage search (2^N). This is a display encoding, not a new cryptographic primitive (SHA-256 + a fixed dictionary)
- **Environment** (decided 2026-08-01 — former open item #6): a namespace under a project (e.g. dev / staging / prod). An environment's **existence is chain-derived** (`create_environment` — §6.2. Revised 2026-08-03); the display name is plaintext metadata (authenticity is bound by the §4.2 statement). Cryptographic contexts (AAD / info) use `environment_id`, a stable identifier unaffected by renames (client-numbered at environment creation)
- **Environment Epoch DEK**: a 256-bit random value. One per environment × epoch of a project. Generated client-side, wrapped via HPKE to the enc public key of each recipient (each device key of each member, and the server when granted — 2026-09-19 DK), and stored
- Epochs advance independently per (project, environment) (a rotation of prod doesn't propagate to dev's epoch). An environment's initial epoch is 1, and `rotate_epoch` always advances the epoch by exactly 1 (the verification rule is §6.3. **Decided 2026-08-02**)
- ~~In v1 every member receives every environment's DEK (per-environment read restriction is a Phase 2 design task. **Open item #11**)~~ **2026-09-14 revision (ES — resolving open item #11)**: each member receives only the DEKs of the environments contained in their on-chain **scope** (the payload of `add_member` / `change_role` — §6.2). A scope is `all` (all environments — including those created later) or `listed` (a finite set of environment ids). Per-environment read restriction is realized by **key distribution, not a server policy**: no DEK wrap for an out-of-scope environment is ever generated or accepted (§6.3 / AUTH_SPEC §12-6), so even if the server is compromised, no out-of-scope DEK exists and none opens. The design record is docs/notes/es-design.md
- ~~v1 simplification: no per-device keys; the master keypair is placed on every device. Device addition happens by entering the recovery code (§8). Device-key separation and passkey PRF are future work (**open item #2**)~~ **2026-09-19 revision (DK — resolving open item #2)**: device-key separation is introduced as above. Adding a device is `add_device` by one of the person's other devices (no ceremony — §6.2); revocation is `revoke_device` (a rotate obligation of the same shape as `remove_member` — §7). The design record is docs/notes/dk-design.md

## 4. Encrypting variables

- A variable's value is encrypted with `AES-256-GCM(key = the DEK of that epoch)`
- AAD (mandatory): `suite || project_id || environment_id || epoch || variable_id || version`
- Variables hold an independent value set per environment (variable_id is unique within an environment. Cross-environment variable-name matching = the parity check is done over plaintext-metadata variable names)
- Variable names are plaintext metadata in v1 (for the parity check and UI search). Only values are encrypted. *Concealing variable names is a future option (**open item #3**). The authenticity of the name ↔ variable_id correspondence is carried by the signed statement of §4.2 (being plaintext and being unauthenticated are separate problems)
- The nonce is randomly generated and stored beside the ciphertext. Nonce reuse is absolutely forbidden (checked by a test)

### 4.1 Value write signatures (drafted 2026-08-03 session 12)

AES-GCM's authentication tag only proves possession of the shared key (the DEK); any DEK holder — all members, and key holders along the chain's history (removed former members and leaked old keys included) — can forge a "correctly decryptable" ciphertext for any coordinate. If a malicious server distributes these, recipients accept forged values as legitimate (a known residue of the session 11 review loop). To close this, **every version of every variable value carries a signature by the writer's chain signature key (Ed25519)**. Built only from existing parts (Ed25519 + SHA-256 + §2.1 LP); no new primitive is introduced.

- **The normalized byte string being signed** (§2.1 encoding):

  ```
  value_signed_bytes = LP("maruhi/v1/value-sig",
                          project_id, environment_id, epoch, variable_id, version,
                          nonce_hex, ciphertext_hex,
                          prev_value_sig_hash_hex,
                          writer_user_id, chain_head_hash_hex, chain_head_seq)
  ```

  - The domain-separation string is `<suite>/value-sig` (same shape as §5.1. The binding to the suite identifier is carried by the domain string, and a signature transplanted across suites fails verification)
  - Binary sequences (nonce, ciphertext, hashes) go into the LP as **lowercase hex strings**, following the precedent of §5.1 / §6.2. Numbers (epoch, version, chain_head_seq) are decimalized per §2.1
  - `prev_value_sig_hash_hex` = the SHA-256 (lowercase hex) of the immediately preceding version's `value_signed_bytes` for the same variable. At version 1, **the empty string**. This chains each variable's version history by hash, fixing a same-version fork (server equivocation) or a swapped history as **cryptographic evidence**: either a chain inconsistency against later versions or "two valid signatures carrying different signed_bytes at the same coordinate" (§14.3 — evidence-ification, not fork prevention)
  - **Epoch monotonicity along the version chain (a verification rule)**: version N's epoch must be **≥** version N−1's epoch (performed by a verifier who knows the preceding version — §6.3-6). The legitimate flow accepts pushes only at the current epoch (AUTH_SPEC §12-5), so the rule always holds (the current epoch is non-decreasing in acceptance order). Meanwhile, "injecting an old-epoch value into a forward version" signed by a removed member's key falls at verification as an epoch regression, provided the preceding version was already re-encrypted to a new epoch (the residue is §14.3-5). Note **declared-head seq monotonicity is NOT a rule** — honest concurrent writers whose sync timing differs may legitimately push declaring a head older than the preceding version (the exploration history is in the session 12 notes §12)
  - `writer_user_id` is the signer's own internal user_id (the same attribution binding as §5.1's signer_user_id. The signature itself refuses reattribution via key reuse)
  - `chain_head_hash_hex` / `chain_head_seq` are the entry_hash (§6.1) and seq of the chain head the writer last verified at signing time (**the binding of the authorization-time state**. Their verification rules are §6.3 / §6.4). The hash is the substance of the binding; the seq is the position specifier the verifier uses to fetch the entry (both are signed; a mismatch fails verification)
- **The AAD (§4) is unchanged**: the signature covers every AAD component (the suite via the domain string) + nonce + ciphertext. The AAD is independently maintained as the GCM layer's context binding (transplantation refused by decryption failure), and the existing variable-encryption test vectors don't change
- **The signature's semantics**: attribution, content authenticity, and authorization-time binding of "writer_user_id, having seen the chain state at (chain_head_hash, chain_head_seq), wrote this ciphertext at this coordinate (project / environment / epoch / variable / version)". **It does not prove the plaintext is correct** (a writer with legitimate permission can write a wrong value — §14.3). **It does not prove freshness either** (redistributing an old legitimate value passes signature verification. Freshness is handled by §6.3's local floor and §14.3)
- Re-encrypting current values at rotation (§7) is an ordinary push of a new version, and **the rotation executor signs as the writer**. The signature's attribution is "whoever wrote this ciphertext", not the provenance of the plaintext (the writer changing on re-encryption is the intended semantics)
- Server verification (at acceptance) / client verification (at distribution) are specified in §6.3 / §6.4, and the wire / acceptance-condition concretization is AUTH_SPEC §12
- Test vectors: `test-vectors/value-signature.json` (positive cases + negative cases for tampering, coordinate transplantation, signer swapping, head swapping, chain inconsistency, and forking)

### 4.2 Signed statements for variable / environment metadata (drafted 2026-08-03 session 12)

Variable / environment names are plaintext metadata (§4), but if the name ↔ ID correspondence is unauthenticated, a malicious server can swap the correspondence between names and ciphertexts (e.g. swap the names `DATABASE_URL` and `DEBUG_ENDPOINT`, injecting a different value into the app. A known residue of the session 11 review loop). An option putting the name into the value's AAD is not taken — a rename would force re-encryption of every version and verifying past versions would need the name history (the comparison is in the session 12 notes). Instead, we introduce **versioned signed statements that bind the name and status to a stable identifier unaffected by renames** (§3's environment_id / §4's variable_id):

```
var_meta_signed_bytes = LP("maruhi/v1/var-meta-sig",
                           project_id, environment_id, variable_id,
                           name, status, meta_version, prev_meta_sig_hash_hex,
                           author_user_id, chain_head_hash_hex, chain_head_seq)

env_meta_signed_bytes = LP("maruhi/v1/env-meta-sig",
                           project_id, environment_id,
                           name, status, meta_version, prev_meta_sig_hash_hex,
                           author_user_id, chain_head_hash_hex, chain_head_seq)
```

- The encoding is §2.1 (same convention as §4.1): numbers (`meta_version`, `chain_head_seq`) are decimalized; binary (hashes) go into the LP as lowercase hex strings
- `status` is `"active"` | `"deleted"` (**layout v2 of variables adds `"declared"` for a 3-value set** — "Layout v2" at the end of this section. Environment meta and the variable v1 layout keep the 2-value set). `meta_version` is a 1-based sequence (creation = 1; rename / deletion = +1). `prev_meta_sig_hash_hex` is the SHA-256 of the preceding statement's signed_bytes (lowercase hex; empty string at meta_version 1) — the same chaining convention as §4.1
- `name` is bound **as-is** as a UTF-8 byte string (signature verification is byte-exact). Unicode normalization (NFC) is done by the **client before signing**; neither the server nor verifiers normalize (putting normalization into the verification rules or post-acceptance processing turns divergence from the signed bytes or a normalization difference between implementations into a verification split). Refusing non-normalized forms, name uniqueness, and charset restrictions are API acceptance policy (AUTH_SPEC §12-1)
- A rename is a new statement incrementing meta_version. A deletion is a statement with `status = "deleted"` (its `name` keeps the last active name as-is — the name field is not emptied on deletion), and **re-activating after deletion is forbidden** (the statement-layer counterpart of ID-reuse prohibition — AUTH_SPEC §12-1). Signing the tombstone turns a server's unauthorized resurrection of a deleted variable into "hiding the deletion statement" = a rollback, within reach of §6.3's local floor and chain verification
- The author's required role (at declared-head time — the verification rule is §6.3): creating / renaming / deleting a variable and creating (meta_version 1) / renaming an environment = member or above; deleting an environment = admin or above (the same level as AUTH_SPEC §12-3's data-plane table. This revision changes no authorization level)
- **A meta statement itself has no epoch-equivalent freshness anchor**: no structural check corresponds to the value's (§4.1) epoch monotonicity, so "injecting a forged statement into a forward meta_version" by a removed member's key (with a declared head inside the membership interval) passes the statement's own signature and chain verification. This hole is **closed by the environment manifest's epoch baking (§4.3 — 2026-08-18. Resolving former open item #12)**: by requiring digest consistency with a verified manifest, statement verification inherits the manifest's epoch anchor (the residue is §14.3-5 — shrinking to a form symmetric with values). Fork evidence-ification (the prev chain) is unchanged as an independent defense layer
- A value (§4.1) is bound to variable_id, not to a name. Name → variable_id resolution (the CLI's push, `maruhi run`'s environment-variable names) must go through verified statements. When multiple active statements of the same name verify within one environment (server equivocation), the client refuses the resolution and warns
- Environment creation is a chain op (§6.2 `create_environment`), and the env meta statement (meta_version 1) is bundled into the creation composite request (AUTH_SPEC §12-4). Environment deletion is a data-plane admin operation + a `status = "deleted"` statement
- Test vectors: `test-vectors/metadata-signature.json` (positive cases + negative cases for tampering, name swapping, coordinate transplantation, signer swapping, head swapping, chain inconsistency, forking, rename-after-delete, and suite mismatch)

**Layout v2 of the variable meta statement — schema fields and the `declared` status (drafted 2026-08-30 session 46 — S0. Rulings CR, CS, CT are docs/notes/session-46.md)**

Defines the schema fields of the value-free schema (ADR-0014 Phase 3 ① — disclosing to agents only name / type / description / required) as a second layout of the variable meta statement. Why an extension rather than a parallel track (an independent schema-statement kind): because a §4.3 entry binds `meta_sig_hash`, schema fields placed on the statement body **automatically inherit manifest coverage** (completeness, epoch freshness, checkpoint binding, equivocation evidence-ification) **with no change to the manifest layer** (the design comparison and rejected options are session-46 ruling CR).

```
var_meta_signed_bytes_v2 = LP("maruhi/v1/var-meta-sig-v2",
                              project_id, environment_id, variable_id,
                              name, status, var_type, required, description,
                              meta_version, prev_meta_sig_hash_hex,
                              author_user_id, chain_head_hash_hex, chain_head_seq)
```

- **The encoding is §2.1 (same convention as v1)**. The domain-separation string is `maruhi/v1/var-meta-sig-v2` — the layout version is **statement-kind-local**, and the suite (`maruhi/v1`) is kept as-is (a suite is an identifier of the algorithm bundle; `maruhi/v2` is reserved for the PQ hybrid — §2, open item #5. AUTH_SPEC §12-2's "don't preempt v2" reservation concerns the algorithm version and this layout version doesn't conflict with it). Mutual interpretation of v1 and v2 fails structurally as a signature mismatch (§1 principle 6)
- **Schema fields**: `var_type` ∈ `"" | "string" | "number" | "boolean" | "url"` (`""` = unspecified. **A closed set** — no validation DSL, enum, or default-value mechanism is introduced. The reason enum is deferred is session-46 ruling CT). `required` ∈ `"true" | "false"` (**explicit and required in v2** — no empty string allowed. Fail-closed so that the default interpretation on omission isn't dispersed across client implementations). `description` is a free UTF-8 string (byte-exact binding like name; verifiers don't normalize. Length caps and charset are server acceptance policy — AUTH_SPEC §12-8. The display side's neutralization obligation is independent — same §12-8 and the design document)
- **The third value of `status`, `"declared"` (v2 only)**: "declared, value not yet set". Transition rules (the acceptance checks are AUTH_SPEC §12-5): creation (meta_version 1) is either active (with a value) or declared (no value). declared → active is a composite with the first value push (activation — meta_version + 1). declared → deleted is allowed. **active → declared is forbidden** (don't create a representation that rolls back the existence of a value — deletion is the only path that removes a value). The existing ban on re-activation after deleted applies to the transition to declared as well. The reason declared isn't allowed in the v1 layout is session-46 ruling CS (protecting the migration's core: "v1 is frozen")
- **The verifier's layout selection and the old verifier's breakage mode (ruling CR)**: which layout's signed_bytes to recompute is selected by the wire's `layoutVersion` (AUTH_SPEC §12-2 — omitted = 1). The verifier checks the supported range of layoutVersion **before signature verification**, and an excess is refused with a **typed error** "unsupported layout (client update required)" — an honest breakage mode that never appears as an invalid signature (a warning indistinguishable from tampering). layoutVersion sits outside the signed content (a transport field), but a false claim degenerates into a signature mismatch via recomputing signed_bytes under the other layout (same shape as §1 principle 6's known residue "verification-mode selection" — all the attacker gains is the quality of the error message; verification isn't broken)
- **The v1 layout stays valid**: no migration of existing statements is needed (no bulk migration). Statements that don't use schema fields / declared may keep being issued as v1 after v2 is introduced (a variable stays operated as v1). Natural re-issuance occasions (rename, setting a schema) move it to v2. A deletion statement keeps the schema fields and layout from the preceding statement as-is, under the same convention as name
- **Per-variable layout monotonicity (2026-08-30 — PR #112 pullfrog review handling)**: a variable whose preceding statement is v2 must have its subsequent statements (rename, schema re-issuance, deletion, activation) at **layoutVersion 2** (no regression to v1). Allowing the regression would make one rename silently drop the schema fields, breaking the premise of the presence guarantee (§14.2-8) — "a `required = true` declaration doesn't disappear without a signed explicit operation" — and schema-locked (AUTH_SPEC §12-11) could be bypassed via "create as v2 → rename down to v1". The schema fields' **values** themselves may be changed explicitly by a subsequent v2 statement (a schema re-issuance or the composite with a rename — the legitimate operation lowering required to false takes this form. Only the deletion statement requires full preservation of the preceding values — the same convention as name). The acceptance check is AUTH_SPEC §12-5; the client check is done by a verifier who knows prev (§6.3's rule 6 — the same known range as chain consistency)
- **The write enablement gate (finding F — old-verifier protection)**: acceptance of **new adoptions** of v2 — metaVersion-1 v2 creations and v2 re-issuances to v1 variables (the exact line is AUTH_SPEC §12-5) — is cut off by the per-project schema policy (AUTH_SPEC §12-11 — default disabled). **Continuation statements of a variable whose preceding statement is already v2 are accepted regardless of the policy** (2026-08-30 PR #112 review handling: the gate's purpose = preventing new v2 statements that un-updated clients can't read is already unachievable for variables that have distributed v2; stopping continuations adds no protection and only leaves the form where a policy downgrade freezes the lifecycle — deletion, activation — of existing v2 variables). The form where one upgraded member's write breaks an un-updated member's verification is prevented by the explicit enablement operation (the ordering server → all members' CLI → enablement — the addition to SELF_HOSTING "Updates" is on the implementation PR side). The v1 → v2 introduction itself happens before release (no applied external statements) and carries no backward-compat clause (the precedent of §6.2) — later layout bumps (v3~) surface in old clients as an explicit decode-stage error under the layout-selection rule above (layoutVersion's wire type is an integer with no fixed upper bound — AUTH_SPEC §12-2)
- **The semantics of required**: required is "**the environment's contract**" (this environment should hold a value of this variable), and satisfaction = the variable's status being active. Since a statement is per (environment, variable), per-environment required comes from the structure as-is. The verifiability of satisfaction (a strict guarantee not depending on a server declaration) is §14.2; that the type declaration is advisory (the prohibition of overclaim) is §14.3. The code side's requirement declaration is not the schema's responsibility (the code itself is the truth — `maruhi schema lint`. The design document)
- **The author's required role is the same as v1** (variable creation / schema setting / rename / deletion = member or above. This revision changes no authorization level). The environment meta statement (`env_meta_signed_bytes`) is outside this revision's scope (stays v1)
- Test vectors: the additive extension of `test-vectors/metadata-signature.json` (§11's 0.8-draft entry)

### 4.3 The environment manifest (drafted 2026-08-18 session 27 — resolving open item #12)

Because §4.2's meta statements "have no epoch-equivalent freshness anchor", the injection of a forward meta_version by a removed member or a leaked key is undetected even by a client holding a floor (§14.3-5 — the guarantee asymmetry versus values). And the omission of an entire variable set (dropping a whole statement from distribution — G6) is undetected by a client with no floor. To close these, we introduce **a signed per-environment manifest**: the executor of every operation that changes the meta state re-signs the environment's meta state (the digests of all variable statements + the environment meta statement), **baking in the current epoch at that moment**. Built only from existing parts (Ed25519 + SHA-256 + §2.1 LP); no new primitive is introduced.

- **The normalized byte string being signed** (§2.1 encoding):

  ```
  env_manifest_signed_bytes = LP("maruhi/v1/env-manifest-sig",
                                 project_id, environment_id,
                                 epoch, manifest_version,
                                 variables_digest_hex,
                                 env_meta_version, env_meta_sig_hash_hex,
                                 prev_manifest_sig_hash_hex,
                                 issuer_user_id, chain_head_hash_hex, chain_head_seq)

  variables_digest_hex = lower_hex(SHA-256(LP("maruhi/v1/env-manifest-vars",
                                              entry_1, …, entry_n)))
  entry_i = LP(variable_id, status, meta_version, meta_sig_hash_hex)
  ```

  - The encoding convention is the same as §4.1 / §4.2 (numbers decimalized, binary as lowercase hex; the domain-separation string binds the suite). The entry list is the latest form of **all** meta statements of that environment — including `status = "deleted"` tombstones — ordered by **byte ascending order of variable_id** (the ordering is part of the digest's canonical form). An environment with zero variables produces an LP of 0 elements (an empty set still has a valid digest)
  - `manifest_version` is a 1-based sequence (environment creation = 1). `prev_manifest_sig_hash_hex` is the SHA-256 of the preceding manifest's signed_bytes (empty string at manifest_version 1) — the same chaining convention as §4.1 / §4.2 (fork evidence-ification)
  - `epoch` is **the environment's current epoch at issuance time (at declared-head time)**. This baking is the core of the mechanism: the manifest layer supplies the freshness anchor the meta statements themselves lacked (the counterpart of the values' §4.1 epoch consistency)
- **Issuance triggers (all composite acceptances — AUTH_SPEC §12-4 / §12-5)**: environment creation (manifest_version 1, empty variable set), variable creation / rename / deletion, environment rename, and `rotate_epoch` (baking the new epoch — the meta set is unchanged but the epoch advance is reflected). **The composites for environment creation and `rotate_epoch` must mandatorily bundle a boundary `checkpoint` entry that binds the issued manifest (2026-08-19 session 32 — §6.3's issuance rule, AUTH_SPEC §12-4)**. **No manifest is issued on a value push** (the manifest contains no value version — avoiding the hot-path serialization where every push goes through a manifest CAS. Avoids rejection reason (i) of session 12's option C-2. Detecting value rollback is the checkpoint's responsibility — §6.2 / §6.3). No manifest is re-issued on environment deletion (the meta below it is cascade-deleted and the distribution channel disappears — AUTH_SPEC §12-4. The environment's own deleted statement is the terminal detection material)
- **The issuer = the executor of that operation**. The required role is the same as the operation itself (the §4.2 / AUTH_SPEC §12-3 table is unchanged). The semantics of `issuer_user_id` baking, key selection, and declared-head binding are the same as §4.1 / §4.2
- **Verification rules (client — merged into §6.3)**: (1) the same-shaped signature / head binding / authorization-time / coordinate / prev-chain (when a floor exists) verifications as §6.3's 1–3 and 5–6, (2) **epoch consistency (2026-08-19 session 32 revision — resolving session-31 M1-A6. The design comparison is session-32 §4–§5)**: when the verified chain contains a `checkpoint` entry carrying a tuple of that (environment_id, manifest_version), the tuple's (epoch, manifest_sig_hash_hex) must **match exactly** (boundary-checkpoint binding — agreement with the declared-head-time value is **not** an alternative path in this case. The manifest issued by the environment-creation / rotation composite is verified through this path of the boundary checkpoint the composite mandatorily bundles — §6.3 / AUTH_SPEC §12-4. When two tuples with different manifest_sig_hash coexist on the verified chain for the same (environment_id, manifest_version), refuse that environment's distribution and warn, as hard evidence of manifest equivocation). When no tuple exists, the manifest's epoch must match the environment's current epoch **at declared-head time** (strict — the manifest version of §6.3's rule 4. Since deletion, a demotion below member, or a scope shrinkage is accompanied by rotating all environments of the target's scope — §7, 2026-09-14 ES — a key that lost its write qualification cannot sign a manifest at the current epoch. **The old H+1 exception — unconditionally tolerating the composite form where the epoch comes into existence on the entry after the declared head — is abolished by this revision, and only checkpoint binding is the exception to strictness**), (3) **digest recomputation**: after individually verifying every distributed statement (tombstones included — AUTH_SPEC §12-7), recompute variables_digest and require agreement with the manifest. A mismatch detects a statement omission / injection and is refused, (4) **checkpoint consistency** (§6.3): the manifest_version / epoch must not regress against the latest checkpoint containing that environment (the lower bound supplied by the boundary checkpoint doubles as preventing the downward bypass of (2)'s comparison to a tuple-carrying version)
- **Server verification (at acceptance — AUTH_SPEC §12-5)**: meta is plaintext, so the server can verify up to and including **digest recomputation agreement**, on top of signature / head / authorization-time / prev chain / epoch consistency (unlike the values' AAD — no E2EE constraint). A forged manifest brought by a rogue client all falls at the acceptance stage
- **Semantics**: "the issuer declared that, at this chain position and this current epoch, this environment's meta state looks like this". It doesn't prove the plaintext is correct (G9) or the freshness of the chain head itself (G5) — the latter is carried by composition with the floor, out-of-band anchors, and checkpoints (§6.3). The prev chain converts a fork (different valid signatures at the same manifest_version) into undeniable evidence (§14.2-5). **Verification completes with a single latest manifest** (no distribution or chain verification of intermediate manifests needed — successor-hood is adequately verified by manifest_version monotonicity + epoch consistency. The design comparison is in the session 27 notes §5-1)
- **Coverage of the schema fields (2026-08-30 session 46 — the S0 confirmation. This section is unchanged)**: because entry_i binds `meta_sig_hash_hex` (the SHA-256 of the statement's signed_bytes), §4.2 layout v2's schema fields (type / required / description) and the `declared` status **automatically inherit this section's coverage** (completeness = detection of omission / injection, epoch freshness, checkpoint binding, equivocation evidence-ification) **with no change to the manifest layer** (a v2 statement's meta_sig_hash is computed from v2's signed_bytes — the entry structure and the digest encoder are unchanged). The `status` field of an entry merely gains `"declared"` as a new string value; the canonical form (byte ascending order of variable_id, a full enumeration including tombstones) is unchanged. The comparison with the parallel-track option (an independent schema-statement kind) falling outside this coverage is docs/notes/value-free-schema.md §4 and session-46 ruling CR
- Test vectors: `test-vectors/env-manifest.json` (§11)

## 5. Key wrapping (HPKE)

- Wrapping a DEK to each recipient is a one-shot Seal of HPKE Base mode
- `info` (mandatory): `"maruhi/v1/dek-wrap" || project_id || environment_id || epoch || recipient_user_id`
- A recipient obtains the DEK by Opening the wrapped DEK distributed by the server with their private key
- An info mismatch (transplantation to another project / epoch / recipient) fails decryption. This is the core of the transplantation-attack defense

### 5.1 Registration signatures on DEK wraps (owner ruling 2-E of 2026-08-02 session 07. Drafted in session 09)

A wrap's contents can't be verified by the server (E2EE), and resting the attribution of who registered an undecryptable poison wrap solely on server-managed data (the audit log) makes it forgeable under server distrust. To close this, **every DEK wrap carries a per-wrap registration signature by the wrapping executor's (§7) chain signature key (Ed25519)**. Built only from existing parts (Ed25519 + the §2.1 encoding); no new primitive is introduced.

- **The signature unit is per wrap** (one signature per wrap addressed to one recipient). A recipient can verify their own wrap standalone at distribution time (with a signature over the set, the repair path — AUTH_SPEC §12-6 — would change the signed set on individual delete / re-register and break verification)
- **The normalized byte string being signed** (§2.1 encoding):

  ```
  signed_bytes = LP("maruhi/v1/dek-wrap-sig",
                    project_id, environment_id, epoch, recipient_user_id,
                    recipient_enc_pub_hex, enc_hex, ciphertext_hex,
                    signer_user_id)
  ```

  - The domain-separation string is `<suite>/dek-wrap-sig` (like §5's HPKE info, the suite-identifier binding is carried by the domain string). A different suite produces different signed_bytes, and signature transplantation across suites fails verification
  - Binary sequences (recipient enc public key 32B, HPKE encapsulated key 32B, wrap ciphertext 48B) go into the LP as **lowercase hex strings**, following §6.2 grant_server's precedent (not raw bytes)
  - Including `recipient_enc_pub_hex` in the signed content is a proposal added to the ruling enumeration (suite / project / env / epoch / recipient / enc / ct): it binds every field of the wire WrappedDek (AUTH_SPEC §12-2) by the signature, leaving no unbound field. Standalone verifiability at distribution is preserved because a recipient knows their own public key
  - Including `signer_user_id` (the signer's own internal user_id) in the signed content is also a proposal added to the ruling enumeration (session 09 review loop 1): a signature alone only fixes "the holder of key K signed". Because the chain at drafting time allowed multiple members carrying the same public key (add_member back then didn't reject key duplication), **reattribution** via key reuse was possible (re-submitting someone's signed wrap into a deleted slot as a different member with the same key). Baking the signer user_id into the signature closes this. Standalone verifiability is preserved because the signer knows their own user_id and a recipient can reconstruct it from the distributed signer information (AUTH_SPEC §12-2) at verification time. Although §6.2's member-key uniqueness (a consensus rule) on 2026-08-03 banned duplicate-key members from coming into existence in the first place, this binding is kept as an independent defense layer (even if §6.2's rule breaks through an implementation bug or a future revision, the signature layer alone can still refuse reattribution)
- **The signature's semantics is attribution, not freshness proof**: the signature is bound to the context (project / environment / epoch / recipient / ciphertext / signer), and transplantation outside the context fails verification. Meanwhile, re-registering into the same context (re-registering identical content after the repair path's deletion) stays valid under the same signature. This is intended; timestamps / nonces are not part of the signed content (the slot-overwrite ban — AUTH_SPEC §12-6 — means re-registering the same context has no effect beyond "the same signer restoring the same content")
- **Server verification (at acceptance)**: acceptance requires the registration API's calling principal (the authenticated internal user_id) = the signer, and every wrap's signature is verified with that principal's sig public key in **the chain-derived current member set at acceptance time** (= "the key at registration time". Acceptance happens under the project DO's serialization, so the chain state at acceptance is the state at registration). Bringing a wrap signed by someone else (including a third party re-submitting into a deleted slot) is refused as a signer mismatch. This rule is compatible with every v1 registration path (bundling at environment creation, bulk registration after rotation, backfill for a new member, re-registration via the repair path) — each is "a client holding the DEK wraps it itself and registers it itself" (§7)
- **Client verification (at distribution)**: the server distributes the signature and the signer (user_id + key fingerprint) together with the wrap. The recipient verifies the signature with, among the sig public keys bound to that user_id in the verified chain history, **the one whose fingerprint matches the signer's** (the key recorded in the genesis / add_member payload). Even if the signer is later removed by `remove_member`, a wrap registered in the past verifies under the key of that time (the chain is append-only and keeps the key history). The implementation of v1's client verification logic is deferred to the CLI / Web implementation (together with §6.3's client sync); this specification requires that the wire and the stored form make it possible
- **Device keys (2026-09-19 DK)**: "the one whose fingerprint matches" is chosen among **the validity intervals of that user_id's device keys** (the keys from `add_member` / `genesis` cover the membership interval; a key registered via `add_device` covers from the `add_device` until before `revoke_device` — §6.2). The rule's shape is unchanged (key selection by fingerprint)
- The server's stored row carries the signature and the signer (user_id + key fingerprint) per wrap, and the audit event `dek.registered` copies the signer's fingerprint (AUDIT_SPEC §3.3 — enabling the cross-check of audit rows against off-chain signatures)
- Test vectors: `test-vectors/dek-wrap-signature.json` (positive cases + negative cases for tampering, coordinate transplantation, key mismatch, and suite mismatch)

### 5.2 Commitments on epoch DEKs (binding authenticity via the chain. Drafted 2026-08-03 session 12)

§5.1's registration signature is the attribution of "who brought this wrap"; it does not prove that the wrap contains **the legitimate** DEK of that epoch. If a malicious server colludes with a key holder along the chain's history, it can distribute a wrap of a self-made DEK for a real epoch in a form that passes §5.1 verification, enabling both (1) making recipients decrypt forged values under the fake DEK, and (2) making recipients encrypt / push new values under the fake DEK that the attacker can read (a known residue of session 11). To close this, **a SHA-256 commitment to the epoch DEK is placed on the membership chain, and a recipient must not use an opened DEK for any cryptographic operation until it cross-checks against the commitment**.

- **Computing the commitment** (§2.1 encoding. `dek_hex` is the DEK's 32 bytes as lowercase hex):

  ```
  dek_commitment_hex = lower_hex(SHA-256(LP("maruhi/v1/dek-commit",
                                            project_id, environment_id, epoch, dek_hex)))
  ```

  - The domain-separation string is `<suite>/dek-commit`. Including the coordinates (project / environment / epoch) in the pre-image means even an accidentally-reused identical DEK in another context won't match the commitment, and no DEK equality across contexts leaks from comparing commitment values
- **Where it is posted**: the environment-creation chain op `create_environment` (newly established in §6.2) carries the epoch-1 commitment in its payload, and `rotate_epoch` carries the new epoch's commitment. Since a chain entry is covered by the creator's / rotation executor's signature (= the client that generated the DEK — §7), the commitment is bound with attribution to "the DEK authorized by a member holding the required role in the chain-derived state at that time". **The epoch ↔ commitment correspondence is uniquely derived by every client and the server as part of chain verification (§6.3 / §6.4)**
- **Client verification (mandatory)**: recompute the commitment from the DEK obtained by Opening the wrap, and **the DEK must not be used for decryption or encryption until it matches** the commitment of that (environment_id, epoch) on the verified chain. A mismatching wrap is treated as a poison wrap (a target of the repair path — AUTH_SPEC §12-6) and warned. In particular, **the cross-check before push** cuts off the confidentiality attack of (2) (inducing encryption under a fake DEK whose key the attacker knows)
- **Secrecy**: the commitment is a public value (on the chain), but the DEK is a uniform-random 256-bit value, so SHA-256's pre-image resistance yields no DEK information from the commitment (the same premise as §8's "because it's a high-entropy random"). **Since this construction's secrecy depends on the input's entropy, applying the commitment to low-entropy values is forbidden** (§12)
- This is not a new primitive: built only from SHA-256 + §2.1 LP, it is the same "identification by public hash" as §3's key fingerprint (the confirmation that this isn't inventing a custom protocol is in the session 12 notes)
- **Independent of the recipient set**: the commitment's target is the DEK itself; it contains no wrap set or HPKE ciphertext. Therefore none of (a) backfilling past epochs after add_member (the inviter wraps the same DEK to the new member), (b) the repair path's delete → re-register, (c) variation of the wrap ciphertext for the same DEK via HPKE randomness, or (d) the post-hoc enlargement of the recipient set by add_member affects the commitment's generation or verification (the comparison with a wrap-set commitment, which breaks under all of these, is in the session 12 notes)
- **Separation of duties from §5.1**: the commitment is "what the legitimate DEK is" (authenticity); the registration signature is "who brought this wrap" (attribution). §5.1 is kept as the attribution / repair audit layer
- Test vectors: `test-vectors/dek-commitment.json` + the extension of `chain-entries.json` (§11)

## 6. The membership log (a signed hash chain)

Each project has an append-only signed chain. The server stores and distributes the chain but cannot tamper with or forge it (it cannot sign).

### 6.1 Entry format

```
{
  suite: "maruhi/v1",
  seq: <serial number>,
  prev_hash: <SHA-256(of the preceding entry's normalized byte string)>,
  op: <operation kind>,
  actor: { user_id, key_fingerprint },
  payload: <per-operation data>,
  timestamp,
  signature: <actor's Ed25519 signature (over the normalized byte string of all fields above)>
}
```

- **Identity rule (absolute)**: principals inside an entry are identified only by internal user_id and key fingerprint. No provider information such as a GitHub ID, and no email addresses, may be included (this structure is immutable and must be independent of authentication providers)
- Normalization: deterministic serialization (a canonical form with fixed field order). The implementation is pinned by test vectors
- **Field size limits (decided 2026-08-02)**: free-string fields in an entry (user_id, environment_id, reason, etc.) are **at most 1024 bytes in UTF-8**, and `grant_server`'s scope_environments is **at most 256 elements**. Entries exceeding this are invalid. This limit is a consensus rule of chain validity, identical across all implementations (client verification §6.3, server verification §6.4) (defense against resource consumption of a verifying client via a huge payload. Fixed-length hex fields have their own length checks. The limits on whole-entry and whole-chain sizes are specified as the server's acceptance policy in §6.4 — the only consensus rule is this field limit)

### 6.2 Roles and operation kinds (the authorization model. Decided 2026-08-01 — former open item #7)

On-chain roles have 4 tiers: **owner / admin / member / reader**:

| role | Can do |
|---|---|
| `reader` | Only fetch and decrypt values of environments within scope (receives DEK wraps for in-scope environments). Chain appends are **only `add_device` / `revoke_device` for one's own devices** (2026-09-19 DK) |
| `member` | + update values of in-scope environments (push new versions), `rotate_epoch`, `checkpoint`. With scope = all, `create_environment` |
| `admin` | + `add_member` / `remove_member` / `change_role` targeting readers / members — but only within the range where **the set of environments whose permissions the operation changes** (add = the new scope; change_role = old scope ∪ new scope if the role changes, or the symmetric difference if only the scope changes; remove = the current scope — principle 1) is contained in one's own scope |
| `owner` | + manage admins, `grant_server` / `revoke_server`, `set_approval_policy`, project deletion. **Scope is always all**. The last owner cannot be removed or demoted |

- **Org roles (AUTH_SPEC) play no part whatsoever in project access** (the chain is the only source of truth. §6.4)
- The server authorizes data operations such as push / pull by the chain-derived role as well (refusing a reader's push, etc.)
- **Normalizing grant_server's scope_environments (decided 2026-08-02)**: LP-encode the list of target environments' environment_ids with the §2.1 encoding, and place the resulting **lowercase hex string** as one payload field on the normalized byte string (nested LP). The list's order is part of the signed byte string. When generating, sorting in codepoint ascending order with no duplicates is recommended (SHOULD. Verification treats the scope as a set)
- **Environment scope (2026-09-14 ES revision — former open item #11)**: `genesis` / `add_member` / `change_role` establish a member's **scope**. A scope normalizes as two payload fields: `scope_kind` (`"all"` | `"listed"`) and `scope_environments_lp_hex` (a lowercase hex string of an environment_id list LP-encoded per §2.1 — the same nested LP as `grant_server`'s `scope_environments`. The list's order is part of the signed byte string; when generating, sorting in codepoint ascending order with no duplicates is recommended [SHOULD], and verification treats it as a set). `genesis` carries no scope in its payload — the creator's scope is structurally `all`. Consensus rules:
  - **Structure (the payload-structure-check stage — before the authorization judgment)**: when `scope_kind = "all"`, `scope_environments` must be the empty list (non-empty is `invalid-payload`). The list is at most 256 elements (the same cap as §6.1's `grant_server`). **A list containing duplicate environment_ids is invalid** (`invalid-payload` — the same line as `checkpoint`'s "nip non-determinism in the bud at the structure stage"). An **empty list under `scope_kind = "listed"` is valid** (= a member who receives no environment's DEK. Plaintext meta remains visible per §6.3)
  - **Environment existence (the authorization stage)**: each environment_id in `listed` must have a `create_environment` preceding it on the chain at that entry's position (rejection reason `unknown-environment` — the same reason code as `rotate_epoch` / `checkpoint`. Makes a typo fail-closed; no pre-scoping a not-yet-existing environment). A deleted environment may be enumerated because the chain doesn't observe deletions (harmless)
  - **Owner is all (the authorization stage)**: an `add_member` / `change_role` establishing `role = owner` is invalid unless `scope_kind = "all"` (rejection reason `scope-role-mismatch`). The owner is the fulfiller of the "last owner" protection, `grant_server` (disclosure of all environments), and the rotate obligation for all environments, and cannot hold a scope. admin / member / reader may hold `listed` (a dev-only admin can write — design record ruling C)
  - **Principle 1 — modifiability of permissions (the authorization stage. 2026-09-14 — design record 3-ter, pullfrog round-9 revision)**: when an entry changes a member's permission in environment E (whether they can read / write values, `rotate_epoch`, `checkpoint` — the role table), **the actor's scope must contain E**. That is, the actor's scope must contain the op's **set of environments undergoing a permission change** (rejection reason `scope-not-contained`. `all` contains everything, and `listed` contains only subsets of `listed` — `listed` does not contain `all`). The permission-change environment set is derived from the role table (not an enumeration): `add_member` = the new scope / `change_role` = old scope ∪ new scope when new role ≠ old role (all environments where the role changes), or (new \ old) ∪ (old \ new) when new role = old role (only the scope's entrances and exits change permissions) / `remove_member` = the current scope. **The set algebra (the treatment of `all` — 2026-09-14 Cursor Bugbot report handling)**: in the containment judgment, `all` is treated as **the set U of all environments (including ones created in the future)** and `listed{X}` as the finite set X. Therefore `all ⊇ anything` is true, `listed{X} ⊇ all` is false, `listed{X} ⊇ listed{Y}` iff Y ⊆ X. `all ∪ listed{X} = all`, `all \ listed{X} = U \ X` (contains un-created environments, so a `listed` actor cannot contain it), `listed{X} \ all = ∅`, `all △ listed{X} = U \ X`. As a consequence, **a `change_role` where the old scope or the new scope is `all`, and an `add_member` granting `all`, can be performed only by an actor with scope = all**, because the permission-change environment set includes U \ X (or U) (a `listed` admin can neither make a target `all` nor make an `all` target `listed` — they cannot bear the obligation of handing over / collecting the DEKs of future environments). **Corollary — the obligations' fulfillability**: since §7 / AUTH_SPEC §12-6's obligations (backfill / rotate) arise only for environments whose permission changes, the obligation environment set (`add_member` = the new scope [backfill] / `change_role` = (new \ old) [backfill] ∪ (old \ new) [rotate] ∪ (the new scope if demoting below member) [rotate] / `remove_member` = the current scope [rotate]) is a subset of the permission-change environment set, so the actor bearing an obligation always holds that environment's DEK (wrapping a DEK is done by a DEK holder [§7] — matching the cryptographic necessity that only someone holding E's DEK can put a person into E or take them out of E). The form containing only the obligation environment set (a temporary formulation of 2026-09-14) is merely a necessary condition for authorization and is not adopted, since it would pass a scope-invariant promotion (a dev-only admin raising a prod reader to member). A dev-only admin can perform a `change_role` that changes only the scope within the symmetric difference. The owner always passes because of all
  - **Environment-targeted ops**: the target environment_id of `rotate_epoch` and the environment_id of every tuple of `checkpoint` must be contained in the actor's scope (rejection reason `environment-out-of-scope`). The new environment_id of `create_environment` is judged by the same predicate — since a `listed` scope cannot contain a not-yet-existing environment, **only an actor with scope = all can create an environment** (never create the form of making an environment the creator can't receive — an implicit scope change not in the signed content)
  - **Check order (pinned per reason code by test vectors. The scope-family checks are placed after the existing check sequence, preserving the expected reasons of existing negatives)**: `add_member` = role rule → `duplicate-member` → `duplicate-member-key` → `unknown-environment` (for each id in scope) → `scope-role-mismatch` → `scope-not-contained`. `change_role` = role rule → `approval-required` (direct append only — below) → `unknown-target` → `last-owner-protected` → `unknown-environment` → `scope-role-mismatch` → `scope-not-contained` → `approval-quorum-unreachable` (when four-eyes is in effect — below). `remove_member` = role rule → `approval-required` → `unknown-target` → `last-owner-protected` → `scope-not-contained` → `approval-quorum-unreachable`. The `approval-required` of `add_member` / `grant_server` / `revoke_server` is at the same position (right after the role rule). `rotate_epoch` = role rule → `unknown-environment` → `environment-out-of-scope` → epoch ordering. `create_environment` = role rule → `duplicate-environment` → `environment-out-of-scope`. `checkpoint` = role rule → the admin role for a non-empty audit head → `unknown-environment` → `environment-out-of-scope` → `checkpoint-epoch-mismatch` → `checkpoint-regression` (scanning all tuples stage by stage — stage-wise)
  - **The verification state** derives each current member's scope (an input to §6.3's wrap-destination match check, the declared-head-time scope check, and AUTH_SPEC §12-3's authorization). The history index holds the (role, scope) change points (seq) per membership interval of each member
  - **The recipient set R(E)** (the single definition for §6.3 / §7 / AUTH_SPEC §12-4 / §12-6): the complete set of DEK-wrap destinations of environment E = { current member m | E ∈ scope(m) } ∪ { valid `grant_server` g | E ∈ scope_environments(g) }. A `grant_server`'s server key carries its own `scope_environments`, so it is outside ES's target; the judgment applies identically across recipient classes
  - **A shrinkage counts as a removal (§7)**: when old scope \ new scope is non-empty in `change_role`, each environment in the shrunk part carries the same `rotate_epoch` obligation as `remove_member` (not a consensus rule but a §7 obligation — in contrast to `grant_server` where a re-grant refuses a scope shrinkage at the consensus level, a member shrinkage is accepted and incurs the obligation. To avoid redoing invitations and splitting membership intervals — design record ruling F). For the enlarged part, the actor backfills the DEKs of all epochs (AUTH_SPEC §12-6)

- **Device keys (2026-09-19 DK — former open item #2. Design record docs/notes/dk-design.md)**: a member holds a **set** of device keys. `genesis` / `add_member` register the first device key (the payload is unchanged. That key's cap is structurally (owner, all)); `add_device` / `revoke_device` add and remove. **Principle D1 — keys belong to devices, permissions belong to people (§1 principle 7)**: role, scope, and the distinctness of four-eyes votes are counted over user_id, while key material and its revocation are handled per device. A signer is identified by (user_id, key FP); the FP selects the device. **A device's effective permission** = (min(the person's role, the device's role_cap), the person's scope ∩ the device's scope), and **every check of "the actor / writer / author / issuer / attester's role / scope" in this specification is performed against the signing device's effective permission** (the role rules, principle 1's containment, environment-targeted ops, §6.3's rules 1 / 3 / 3′, §6.6, and four-eyes votes). A cap is an **upper bound** on the person's permission, not the permission itself (`owner` = no bound). The individual rules below are derived from this principle
  - **Payload and structure (the structure-check stage)**: `add_device` = `[enc_pub_hex, sig_pub_hex, role_cap, scope_kind, scope_environments_lp_hex]` (public keys are lowercase hex, 64 chars. `role_cap` ∈ {`reader`, `member`, `admin`, `owner`} — `owner` is "no bound". The scope's two fields use the same encoding and the same structural rules as "environment scope" [`all` ⇒ the empty list, ≤256 elements, duplicates invalid, `listed`'s empty list is valid = a device that receives no DEK]). `revoke_device` = `[target_user_id, device_fingerprints_lp_hex]` (a lowercase hex of the list of FPs [lowercase hex, 32 chars] LP-nested per §2.1. ≥1 and ≤256 elements, duplicates invalid. Order is signed. Generation SHOULD sort ascending; verification treats it as a set)
  - **`add_device` authorization**: the actor is a current member (any role — a reader may). The target is the actor themself (the payload carries no target). Each of the new device's public keys must not duplicate a same-kind public key of **any device key** of the current member set (extending `duplicate-member-key`'s target to the device set — "Member-key uniqueness" below. Collisions with a valid `grant_server`'s server key are outside this rule, same as `add_member`). Each environment_id in `listed` must have a preceding `create_environment` (`unknown-environment`). **Monotonicity (principle D2)**: the new device's cap must not exceed **the signing device's own cap** (the bound written in the payload. The key from `add_member` / `genesis` is structurally (owner, all)) — role_cap_new ≤ role_cap_signer, and device scope_new ⊆ device scope_signer (the set algebra is the same as "environment scope": `all` = U. Rejection reason `device-cap-exceeded`). **The comparison is cap-to-cap — do not compare the effective permission with the person's role folded in** (under effective permission, a member couldn't register a reserve key with cap (owner, all) — a cap is "an upper bound on the person's permission", not a permission, and `owner` means "no bound". A member's reserve key's effective permission stays min(member, owner) = member — 2026-09-19 Cursor Bugbot report handling). The rule exists so a stolen device cannot create a device with a stronger bound than itself; the reserve key (cap (owner, all)) is registered by the first device key (cap (owner, all))
  - **`revoke_device` authorization**: if the target is the actor themself, any role. If someone else, the same role rule as `remove_member` (determined by the target's role) plus principle 1's containment (the target **person**'s scope ⊆ the actor's effective scope — judged by the person's scope, not the revoked device's effective scope [with a votes-only device the containment would hold vacuously]. Only someone who can fulfill the revocation's rotate obligation [§7] may revoke. Rejection reason `scope-not-contained`). Each FP must be a **currently valid** device of the target (`unknown-device`). An entry that would leave the target with zero devices is invalid (`last-device-protected` — a memberless-device member cannot return; that shape is expressed by `remove_member`). One may revoke the very device currently signing (valid at the entry's position; signatures thereafter are invalid)
  - **A device's validity interval**: a device key is valid from the seq of `add_device` (or `add_member` / `genesis`) until **just before** the seq of `revoke_device` (inclusive convention — the post-application state of the `revoke_device` entry doesn't contain the device). The verification state derives, per current member, the device set (FP → public keys, cap); the history index derives each device's validity interval and cap (inputs to §5.1 / §6.3's key selection, 3′, and AUTH_SPEC §12-6's recipient judgment). `remove_member` ends all of the target's devices at once. Re-adding the same user_id (`add_member`) starts again from a single first device
  - **The recipient set R(E) (the device axis)**: the complete set of DEK-wrap destinations of environment E = { (m, d) | m ∈ current members, d ∈ devices(m), E ∈ scope(m) ∩ scope(d) } ∪ { valid `grant_server` g | E ∈ scope_environments(g) } (the device expansion of R(E) from "Environment scope" above — §6.3 / §7 / AUTH_SPEC §12-4 / §12-6 read this definition). The judgment is the single predicate "identify (id + key) ∧ E ∈ effective scope", applied across recipient classes
  - **Relation to four-eyes**: `add_device` / `revoke_device` cannot be included in `set_approval_policy`'s `ops` (structure check — `invalid-payload`) and cannot be proposed either (`approval-not-required`) — adding a device doesn't add a user_id and doesn't affect quorum, and revocation is a safe-side operation (the same line as `rotate_epoch`). The element (user_id, key FP) of principle 2's S is unchanged; the FP points at the signing device (see "four-eyes" below for `approve`'s device vocabulary)
  - **Check order (pinned per reason code by vectors)**: `add_device` = the actor rule (`actor-not-member` / `actor-key-mismatch`) → `duplicate-member-key` → `unknown-environment` → `device-cap-exceeded`. `revoke_device` = `unknown-target` → `unknown-device` → the target-dependent role rule (self passes; others get `insufficient-role`) → `last-device-protected` → `scope-not-contained` (others only) — the same shape as `remove_member` / `change_role`'s existing order (`resolveTargetedOp`), which resolves the target's existence before judging the target-dependent role rule (2026-09-19 pullfrog report handling). The check order of existing ops is unchanged (the effective-permission substitution only changes each check's input)
  - The introduction of this rule adds new ops and touches no existing op's payload format. Existing chains accepted before the introduction stay **valid** under the new rules (each member's device = the initial single key). `chain-entries.json` is extended by addition (§11)

- **Four-eyes (2026-09-14 PF1 — multi-signature approval. Design record docs/notes/es-design.md §3)**: dangerous operations are accepted as a two-stage "propose → approve" entry pair, and the inner op applies **only when the signatures of distinct owners reach the required count**. No threshold signatures or aggregate signatures are introduced (just counting existing Ed25519 signatures over two entries). Consensus rules:
  - **The policy**: `set_approval_policy` establishes a policy { ops, required_approvals }. A state with no policy ever established (or `required_approvals = 0`) is **off** (the default — a single-owner project sees no change). `required_approvals` is 0 (off) or ≥2. **Enabling or changing it is invalid unless the current owner count at that point ≥ required_approvals** (rejection reason `approval-quorum-unreachable`). `ops` must be a subset of the following set (structure check — `invalid-payload`): `grant_server` / `revoke_server` / `remove_member` / `change_role` / `add_member` / `set_approval_policy`. `create_environment` / `rotate_epoch` / `checkpoint` (don't stop data-plane / safe-side operations — a rotate is incident response and mustn't be delayed), `genesis` / `propose` / `approve` / `withdraw` cannot be targets. **While a policy is in effect, `set_approval_policy` itself and `add_member` / `change_role` establishing the owner role are always targets regardless of the `ops` enumeration** (turning it off also needs four-eyes — otherwise four-eyes is meaningless. Leaving an owner-adding op outside four-eyes would let a single owner directly append their own second key pair as an owner, reaching quorum with their own second owner — 2026-09-14 pullfrog review handling. Since `distinct` counts on-chain identity, not personhood, the identity-adding path itself goes into four-eyes)
  - **The reachability invariant**: while a policy is in effect, an op that would bring the current owner count below `required_approvals` (a `remove_member` of an owner, a `change_role` from owner to another role) is invalid (`approval-quorum-unreachable` — a generalization of `last-owner-protected`. Its check position is the tail of each op)
  - **Principle 2 — authorization by the signer set (2026-09-14 — design record 3-ter)**: every entry is authorized by a **signer set S**. For a direct append, S = {actor}; via a proposal, S = {the proposer **who proposed as owner**} ∪ {every `approve`'s actor}. **An element of S is identified by (user_id, the key FP at signing time)** (the owner-delegated ruling of 2026-09-15 — design record docs/notes/es-design.md §8 K2-11: a vote is a signature made at owner role; if a voter is removed → re-added with a different key, the old key's vote lapses. The proposal signature of a proposer who proposed as admin is not a vote, but after being promoted to owner they can append `approve` and that vote counts — each quorum vote corresponds to a signature at owner role, and the audit can follow quorum by signatures alone). The approval count required by an op `required(op)` is `required_approvals` when the policy is in effect and the op is a target, and 1 otherwise. An entry (direct append) or a proposal's application is invalid, when `required(op) ≥ 2`, unless **at application time, the number of distinct user_ids among S's elements who are owners as current members holding the same key FP as at signing time ≥ required(op)** (principle 2 is an additional condition that applies only when `required(op) ≥ 2`; an op with `required = 1` is judged only by the ordinary role rule [S = {actor} holds the op's role] — it doesn't deny a non-owner member / admin's direct append). **The invariant (policy monotonicity — two consequences)**: while a policy is in effect, (a) the policy-changing op (`set_approval_policy`) and owner-identity-adding ops (`add_member` / `change_role` establishing the owner role) are always targets regardless of the `ops` enumeration, and (b) an op that brings the owner count below `required_approvals` ("reachability" above) is invalid — no path exists to weaken or bypass the policy with fewer than a quorum of signers. Owner-decreasing ops are handled by (b) and aren't always-on targets (they can be directly appended if not in `ops` — the same set as "The policy" above / §14.2-10). The individual rules below are derived from this principle and the invariant
  - **Refusing a direct append of a target op (derived)**: while a policy is in effect, an entry **directly** appending a target op has S = {actor}, so |S ∩ owners| ≤ 1 < required — invalid (rejection reason `approval-required`. The check is **immediately after** the role rule). In contexts where `propose` / `approve` evaluates the inner op, the inner op is still gathering S, so this check **does not occur** (it is the same judgment of principle 2, not an exception)
  - **`propose`**: the actor holds a role able to execute the inner op under the ordinary rules, and the inner op must satisfy the consensus rules (structure, authorization, containment, last-owner, reachability, … — except `approval-required`) in the state at that time (a proposal that doesn't satisfy them is invalid — not stacked as pending. The reason code is the inner op's own reason). `inner_op` must be a target of the policy (`ops` + the always-target ops) (`approval-not-required` — proposing a non-target op means nothing). `expires_at_ms` is a non-negative safe integer. The proposal goes onto the verification state as pending (identifier = the proposal entry's entry_hash). **A `propose` while the policy is off is invalid** (`approval-not-required`)
  - **`approve`**: the actor is an owner at that point, and the signing device's effective role is owner (`insufficient-role` — a device with cap < owner cannot cast a vote. 2026-09-19 DK). The referent must be a pending proposal (`unknown-proposal` — applied / withdrawn / nonexistent). The actor's user_id must not already hold a **live vote** in S (a signature by that person's valid device at application time — 2026-09-19 DK, "device vocabulary" below) (a self-approval by a proposer who proposed as owner, a second vote from the same device, a second vote from another device of the same person — `duplicate-approval`. One person, one vote. A voter re-added under a different key has their old vote lapsed and may vote again. **Revocation is not monotonic**: a vote is bound to (user_id, key FP), so remove → re-add under a different key → remove → **re-register with the original key** revives the old vote cast by that key [a consequence of the rules. The paths leading from re-registering the same key to owner — `add_member` as owner, or re-registration as non-owner followed by a `change_role` promotion — are all ops that establish an owner = always four-eyes targets [invariant (a)] and thus require quorum signatures; not re-registering a compromised-known key is an operational discipline — 2026-09-16 owner ruling, design record §11 K5-J]. A proposer who proposed as admin is not an element of S, so after promotion to owner they may approve their own proposal — 2026-09-15). **The `approve` entry's `timestamp_ms` must be ≤ the proposal's `expires_at_ms` (`proposal-expired`)** — the **only place** this specification uses timestamp in a consensus rule. Because `timestamp_ms` is the approver's self-declaration (the chain has neither monotonicity nor an upper bound), **the expiry is a UX safeguard protecting an honest approver from a context-lost approval, not a guarantee against a malicious approver**: an approver who backdates their time can approve an expired proposal (that approver is a principal legitimately holding a four-eyes vote as an owner — not what the expiry protects. 2026-09-14 pullfrog review handling — the old "refuse-direction only = fail-closed" claim is retracted). §14.2-10's guarantee doesn't depend on the expiry. Vote count = |S ∩ owners at application time| (derived from principle 2): **this `approve` entry's own actor** (an owner — already checked by the role rule) **who, also at this `approve` entry's point, has a signing key FP that is a current member's valid device whose effective role is owner** (2026-09-19 DK — the device vocabulary of the old "owner as a current member holding the same key FP as at signing time"), plus the distinct user_id count of past voters (S's elements = past `approve` actors and a proposer who proposed as owner). A past voter who was demoted / removed after the proposal doesn't count (and isn't revived even if re-added under a different key — 2026-09-15. For re-registration with the same key, see this item's "revocation is not monotonic") (the state in which a past voter's owner qualification is judged is "the pre-application state of this `approve` entry" — 2026-09-14 Cursor Bugbot report handling: if a voter's owner qualification were checked only at vote time, a remaining single owner could complete a quorum using a departed voter's vote. With 2 owners and `required_approvals = 2`, completion is "an owner's proposal + another owner's approve" or "a non-owner's proposal + 2 owners' approves"). When the vote count reaches `required_approvals`, **the inner op applies at this `approve` entry's seq** (inclusive convention — `remove_member`'s end of membership and `change_role`'s new role / scope take effect at this seq. §7's rotate obligation and the rotation-needed detection also start at this seq). At application, the inner op's consensus rules are re-checked **in the state at application time**, and additionally **the proposer must be a current member at that point, hold the same key FP as at proposal time, and hold the role the inner op requires** (the device vocabulary — 2026-09-19 DK: the proposing device is still valid at application time and its effective role suffices for the inner op. Rejection reason `proposal-void` — a proposal whose proposer was removed, demoted, or key-changed after proposing cannot complete). An `approve` entry that fails the application-time check is an invalid entry, and the proposal stays pending (closed by `withdraw` — an approval signature is not given a "close" effect). The actor of an applied inner op is treated as **the proposer** (the record of membership and attribution). **The relation to principle 1**: the fulfiller of the inner op's obligations (rotate / backfill) is the approver who completed the application (owner — scope = all, so they hold every environment's DEK and can fulfill it under the containment rule), so principle 1 is structurally satisfied. The principle-1 checks made at proposal time and application time against the proposer's scope confirm "this is an op the proposer could directly append" — not a guarantee of fulfillability (if the proposer's scope shrank after proposing, application fails with `scope-not-contained` and the proposal stays pending — closed by `withdraw`)
  - **The device vocabulary of `approve` votes (2026-09-19 DK)**: S's element (user_id, key FP) is unchanged; the FP points at the signing device. A vote counts = "at this `approve`'s point, that FP is a valid device of a current owner, and that device's effective role is owner". distinct is over user_id (another device of the same person is still 1 vote). **A revoked device's vote lapses** (`revoke_device` is a declaration that "this key may be compromised" — the same as the 2026-09-15 ruling that a key update lapses the old key's votes). If the same person re-registers a revoked device key via `add_device`, the old votes revive (the device form of "revocation is not monotonic" — a consequence. The CLI warns on re-registering a revoked FP). `add_device` / `revoke_device` themselves can't be four-eyes targets ("Device keys" above)
  - **The relation between a policy change and pending proposals (2026-09-14 pullfrog review handling)**: a pending proposal doesn't snapshot the policy at proposal time — it is judged under **the current policy at each `approve` entry's point** — the required count is the current policy's `required_approvals`; if the inner op is no longer a **target** of the current policy (`ops` + the always-target ops — the same predicate as `propose` / the direct-append refusal. An always-target op doesn't leave the target set while the policy is in effect) (the policy turned off, or a non-always-target op removed from `ops`), that `approve` is invalid as `approval-not-required` and the proposal stays pending (closed by `withdraw`. An op that left the target set can be executed by direct append — an always-target op has no such path. 2026-09-14 Cursor Bugbot report handling). Lowering `required_approvals` takes effect on pending proposals immediately (the next `approve` completes with the already-sufficient count)
  - **`withdraw`**: the actor is the proposer or an owner. The referent is pending (`unknown-proposal`). Closes the proposal (a state change, nothing else)
  - **Check order** (pinned per reason code by vectors): `set_approval_policy` = role rule (owner) → `approval-required` (if a policy is in effect, no direct append) → `approval-quorum-unreachable`. `propose` = role rule (judged by the inner op's rules) → `approval-not-required` → the inner op's consensus rules (except `approval-required` — the inner op's reason codes). `approve` = role rule → `unknown-proposal` → `duplicate-approval` → `approval-not-required` (left-target after a policy change — above) → `proposal-expired` → (at quorum) `proposal-void` → the inner op's consensus rules. `withdraw` = role rule → `unknown-proposal`
  - The verification state derives the policy (ops, required) and the pending-proposal set (proposal hash → proposer, inner op, expiry, voter set). **No consensus-rule cap on the number of pending proposals** (server acceptance policy — §6.4 / AUTH_SPEC §12-8)
  - Introducing the 4 ops requires simultaneous updates of every implementation under "unknown op = invalid chain", but it touches no existing op's payload format (independent of ES's add_member / change_role change). Test vectors are bundled into the same regeneration as ES (§11)
- **Member-key uniqueness (decided 2026-08-03 — the outcome of session 09's handoff discussion)**: `add_member` (and `add_device` — 2026-09-19 DK) is invalid when **any** of the target's enc / sig public keys matches the **same-kind** public key of **any device key** of any member of the current member set (including the genesis-derived owner, in the verified state at that point) (rejection reason `duplicate-member-key`). The rule's nature:
  - **The unit of the judgment is the individual enc / sig key** (not the key fingerprint = enc‖sig match). The comparison target is **all device keys** of the current member set (2026-09-19 DK — a person has multiple device keys, and sharing one of the two keys produces the same ambiguity across devices. The old premise "v1 has no device-key separation; 1 user = 1 master keypair" is gone). There is no legitimate use case for a member / device reusing only one of the two keys; sharing a sig key creates the ambiguity "multiple principals whose signatures verify", and sharing an enc key creates "multiple wraps to the same key" plus murky delete / rotation semantics — so the stronger side is taken. No cross-kind comparison between enc and sig (X25519 and Ed25519 uses never intersect; no attack can be built from confusing them)
  - **The prohibition range is only the current member set** (not the whole chain history). Re-adding a `remove_member`'d member under the same user_id and same keys (the same person returning) is not forbidden. Re-registering a removed member's key under a different user_id is also not forbidden — it is equivalent to an act within admin / owner's power to "add a member with an arbitrary public key"; the key fingerprint remains on the chain so it is mechanically traceable, and wrap attribution is independently guarded by §5.1's signer_user_id binding
  - **Check order**: role rule (admin or above; granting admin/owner is owner only) → target user_id duplication (`duplicate-member`) → key duplication (`duplicate-member-key`) (2026-09-14 ES: after this come the scope-family checks `unknown-environment` → `scope-role-mismatch` → `scope-not-contained` — the "Environment scope" check order above. `add_device`'s order is "Device keys" above — 2026-09-19 DK). Reason codes are part of the consensus rules; the order is pinned by composite-violation-entry vectors (role → key is negative `authz-add-member-role-precedes-duplicate-key`, user_id → key is negative `authz-add-member-duplicate-user-precedes-key`)
  - This is a **consensus rule** of chain validity, identical across all implementations (client verification §6.3, server verification §6.4). It is defense in depth that eliminates, at the chain layer, the root cause of the reattribution (key-reuse sock-puppet) that §5.1's signer_user_id binding closed — making "key → principal" reverse-lookup uniqueness (relied on by §5.1's client verification, the audit UI, and §6.3's wrap-destination match check) an invariant
  - Since no existing chains were accepted before this rule's introduction (2026-08-03) (introduced under the premise of pre-release, no applied chains), it carries no backward-compat exception
  - `genesis` is the first member and the member set is empty, so duplication structurally cannot arise (the rule is consistently "a check against the current member set" across every key-registration path, and the genesis-derived owner key also becomes a comparison target of later add_member). A collision between a `grant_server` server enc key and a member key is outside this rule (the recipient class and the fingerprint definition differ — §9. An owner-only operation, and server-destined wraps are unimplemented until Phase 2). **Caution**: since grant_server itself is a live consensus rule, banning this collision as a consensus rule in Phase 2 would need a backward-compat clause (grandfathering) for chains accepted until then — the same argument that let this rule skip the exception clause on the ground that "no chains accepted before introduction exist" cannot be used (recorded as the cost of deferral. 2026-08-03)
- **The chain binding of the environment lifecycle (drafted 2026-08-03 session 12 — consensus rules)**: environment creation is the chain op `create_environment` (amending the former "environment creation is not a chain op". To secure the posting place of §5.2's epoch-1 commitment and make an environment's existence itself chain-derived). Consensus rules:
  - `create_environment`'s environment_id is **unique across the whole chain history** (rejection reason `duplicate-environment`). The ban on reusing a deleted environment's ID (AUTH_SPEC §12-1) is **promoted from a server-tombstone acceptance policy to a consensus rule clients can verify too** (environment deletion itself stays a data-plane operation and the chain doesn't observe it — whole-history uniqueness suffices)
  - `rotate_epoch` is **invalid unless** the target environment_id's `create_environment` **precedes** it on the chain (rejection reason `unknown-environment`). The former rule "chain acceptance doesn't cross-check environment metadata" (AUTH_SPEC §12-4) is replaced — still client-verifiable — because environment existence changed from mutable server-local state to a chain-derived value (the former behavior where a rotate_epoch to a nonexistent ID merely burned the ID is abolished)
  - `create_environment` / `rotate_epoch`'s `dek_commitment_hex` is lowercase hex, 64 chars (the format check is a consensus rule. The commitment's **content** cannot be verified by chain verification — the recipient's cross-check, §5.2, carries it). The format check belongs to the existing payload-structure-check stage (individual checks of fixed-length hex fields — §6.1's precedent) and **precedes the authorization judgment** (the existing implementation's / vectors' verification-stage order "structure → actor → signature → authorization" is unchanged)
  - The payload's normalized field order (pinned by chain-normalization vectors): `create_environment` = `[environment_id, dek_commitment_hex]`, `rotate_epoch` = `[environment_id, new_epoch, reason, dek_commitment_hex]` (appended to the **tail** of the existing 3 fields)
  - The authorization-stage check order: role rule → `duplicate-environment` / `unknown-environment` → `environment-out-of-scope` (2026-09-14 ES — "Environment scope" above) → epoch ordering (§6.3). The order is pinned per reason code by test vectors
  - An environment's **display name and deletion are not put on the chain** (names are §4.2's signed statements; deletion is a data-plane admin operation). The chain is the ledger of key authenticity / authorization, not a ledger of mutable metadata (restraining chain bloat. Making a name rename a chain op would let display edits consume §6.4's entry limit)
  - Effect on chain capacity: `create_environment` is 1 entry per environment (the environment cap is 1,000 incl. tombstones — AUTH_SPEC §12-8); `rotate_epoch`'s addition is 1 entry +64 bytes. Well under §6.4's 10,000 entries / 32 MiB
  - Since no existing chains were accepted before this rule's introduction (pre-release, no applied chains), it carries no backward-compat exception (the same premise as §6.2 member-key uniqueness). The initial epoch = 1 and `rotate_epoch`'s +1 rule (§3 / §6.3) are unchanged, and the start point of epoch 1 becomes observable as `create_environment`'s seq
- **The lease-policy extension of the grant_server payload (drafted 2026-08-12 — the source of truth for §9.1 workload-lease authorization)**: the normalized field order of `grant_server`'s payload is `[server_enc_pub_hex, server_key_fingerprint_hex, scope_environments_lp_hex, lease_policy_lp_hex]`. `lease_policy` is an **issuer-generic** list of workload-identity federation constraints — each element = `(issuer_url, audience, claim_constraints)`, where `claim_constraints` = a list of exact-match constraints `(claim_name, claim_value)`. Normalization is the same nested LP as scope_environments (§2.1. List order is part of the signed byte string; generation SHOULD sort in codepoint ascending order with no duplicates). An empty list (0 elements) means "no lease path" (the grant only permits registering server-key-destined wraps)
  - **The consensus rules pin only the structure**: field order and size limits (issuer elements ≤8, claim constraints per issuer ≤8, each string under §6.1's 1024-byte limit. The element-count limits are chosen so that the normalized size of a spec-conforming `grant_server` entry stays mathematically below §6.4's 1 MiB acceptance-policy limit — the premise of that section's size bound). The constraints' **evaluation semantics** (v1 = exact match only; enabled issuer = GitHub Actions only) live in AUTH_SPEC §14, so future extension of the evaluation rules / supported issuers doesn't touch the chain format (= requires no grandfathering). No policy language is brought into the consensus rules
  - **Relation to the identity rule (§6.1)**: an external-namespace identifier appearing in claim_value (e.g. `owner/repo`) is **a description of the authorization target, not a principal identification**, and doesn't offend the rule "an actor = internal user_id + key FP only" (actor identification is unchanged)
  - This extension happens before release, when no chain containing a grant_server entry has been accepted (no backward-compat clause under the same premise as §6.2 member-key uniqueness). The deferral cost recorded on 2026-08-03 — "a Phase 2 revision needs grandfathering" — is dissolved without paying it, by fixing the payload format before release. Existing grant_server / revoke_server test vectors are fully regenerated under this revision (§11)
- **Server-key uniqueness (drafted 2026-08-12 — resolving the item deferred on 2026-08-03)**: `grant_server` is invalid when the payload's server enc public key matches any member's enc public key in the current member set (rejection reason `duplicate-server-key`). The recipient-class-crossing version of §6.2 member-key uniqueness's motivation ("key → principal" reverse-lookup uniqueness). The check order is role rule → the re-grant rule (§6.3) → key duplication, pinned per reason code by test vectors. Introduced before release, so no backward-compat clause
- **The `checkpoint` op (drafted 2026-08-18 session 27 — resolving open items #4 and #12, merged with AUDIT_SPEC open item #2)**: an op by which a client (member or above) notarizes onto the chain a digest of the data state of their own verified view. Only an issuer with effective-permission admin also notarizes the server-declared audit head in the same entry (anyone else writes the empty string). The chain is already "an authenticated broadcast everyone verifies" (the same argument as §5.2's posting-place judgment), and a checkpoint's freshness reduces to the chain head's freshness (floor, out-of-band anchors, head declarations — §6.3 / §6.6) — which stops the recursion "the rollback-detection mechanism itself gets rolled back" (the whole verification chain is in the session 27 notes §6). Consensus rules:
  - The payload's normalized field order: `[environments_lp_hex, audit_head_hash_hex]`. `environments_lp_hex` is a lowercase hex string of the list of environment entries LP-nested per §2.1 (the same nested LP as scope_environments). Each entry = `LP(environment_id, epoch, manifest_version, manifest_sig_hash_hex, values_digest_hex)`. **A payload containing duplicate environment_ids is invalid (MUST — the consensus rules' payload-structure check below)**: unlike scope_environments (whose elements are bare IDs where duplication carries no information), this entry carries tuples, so allowing 2 entries for the same environment would make §6.3's baseline and `checkpoint-regression`'s comparison target non-deterministic (2026-08-18 pullfrog review handling — duplication is not a SHOULD). The list is generated in byte ascending order of environment_id (SHOULD — verification doesn't make order normative). 0 elements (a project with zero environments) is valid
  - `values_digest_hex = lower_hex(SHA-256(LP("maruhi/v1/env-values-digest", v_1, …, v_m)))`, `v_j = LP(variable_id, version, value_sig_hash_hex)` (byte ascending order of variable_id. **Active variables only** — tombstones are captured by the manifest side — §4.3. **Variables with status = declared — §4.2 layout v2, value not yet set — are also excluded (2026-08-30)**: no value exists and there is no coordinate to notarize. The statement itself is captured by the manifest side, and the verification rule that "a declared receiving no value distribution is legitimate" is §6.3). `value_sig_hash_hex` = the SHA-256 of that version's `value_signed_bytes` (§4.1)
  - `audit_head_hash_hex` = the server-declared cumulative hash of the audit log (defined in AUDIT_SPEC §5.1), or **the empty string = no audit-head notarization** (covering both the case where the issuer's effective permission [min(token scope, chain role) — AUTH_SPEC §9-2] isn't admin and the audit-head declaration couldn't be fetched — AUTH_SPEC §16-2's timing side-channel handling — and the case of zero audit rows. The data-layer notarization — environments — is valid independent of the audit head). **The audit row count (seq) must not be put in the payload**: the chain is distributed to all members including readers, and the audit seq is a gapless shared numbering, so including it would let anyone below admin decisively infer the row count / activity level of visibility class 2 (AUDIT_SPEC §6) (colliding with that §7's discipline of "don't leak even the count"). The cumulative hash is random-looking, carries no ordinal, and the cross-check (AUDIT_SPEC §6) needs no seq
  - The consensus rules verify **form, the actor's chain role, and coordinate consistency**: the payload structure (hex lengths, element count, refusal of duplicate environment_ids), **when audit_head_hash is non-empty, the actor being admin or above at that entry's point** (rejection reason `checkpoint-audit-role-insufficient`. The API acceptance surface additionally requires token-scope admin — AUTH_SPEC §16-2), each environment_id having a preceding `create_environment` (rejection reason `unknown-environment` — same as rotate_epoch), each environment entry's epoch **exactly matching the chain-derived current epoch at the entry's point (before its own application)** (rejection reason `checkpoint-epoch-mismatch`. Since the append CAS — §6.4 — eliminates races with a concurrent rotate, every legitimate issuance satisfies this), and **each environment entry's manifest_version being ≥ the value of the most recent preceding `checkpoint` entry containing the same environment** (rejection reason `checkpoint-regression` — cuts off, at the chain layer, the form where a malicious or careless member notarizes an old state and rolls back a floorless client's detection baseline. manifest_version is a public payload value so the cross-check is possible within chain verification alone. Epoch non-regression follows automatically from the exact-match rule above. **To satisfy this rule, an issuing client refreshes its data-layer view before issuing a checkpoint** — issuing from a verified view holding only manifests older than the most recent checkpoint makes an invalid entry). **The environment set may be a subset** (a cover of all active environments is not made a consensus rule — avoids racing environment creation, and per-environment issuance is valid. Interpreting the baseline is §6.3). The **contents** of `manifest_sig_hash_hex` / `values_digest_hex` / `audit_head_hash_hex` can't be verified by chain verification (manifests, values, and audit rows live off-chain); content verification is carried by the server's acceptance verification (§6.4) and the client's distribution-time cross-check (§6.3) — the same split as §5.2's "form is a consensus rule; content belongs to the cross-checking side"
  - The authorization-stage check order: role rule (member or above) → the admin role for a non-empty audit head (`checkpoint-audit-role-insufficient`) → `unknown-environment` → `environment-out-of-scope` (2026-09-14 ES — "Environment scope" above) → `checkpoint-epoch-mismatch` → `checkpoint-regression`. The order is pinned per reason code by test vectors
  - **A boundary checkpoint (2026-08-19 session 32 — the mandatory bundle on the environment-creation / rotation composite. AUTH_SPEC §12-4) needs no exception to these consensus rules**: the bundled checkpoint sits at the seq right after the composite entries (create / rotate), and epoch exact match — judged "at the entry's point (before its own application)" — naturally equals the current epoch after the bundled entries apply (create = 1 / rotate = new_epoch). `unknown-environment` is satisfied by create's precedence (the immediately preceding seq). On the consensus-rule side it is completely identical to M2's periodic checkpoint
  - The verification state derives the **latest checkpoint** (seq; per-environment (epoch, manifest_version, manifest_sig_hash, values_digest); audit_head_hash) (the input to §6.3's checkpoint-consistency verification)
  - Size limits: a spec-conforming server refuses entries for deleted environments (§6.4) and caps the active-environment count at 100 (AUTH_SPEC §12-8). Therefore a checkpoint passing **the server's acceptance policy** carries at most 100 environment entries, and the largest form is about 50 KiB / entry (100 environments × ~450 bytes + the 64-byte audit head. Including nested-LP hex encoding) — well below §6.4's 1 MiB limit. Under the expected cadence (§6.3 — every 7 days + after completing a rotate and its re-encryption), roughly 50–100 entries per year, or ~2.5–5 MiB/year at the largest form — comfortably small against §6.4's 32 MiB / 10,000 entries (the estimates are in the session 27 notes §8). This is an operational estimate, not a hard limit. Since environment deletion can't be derived from the chain, "100 active" is a server acceptance-policy bound, not a consensus-rule element limit
  - **Issuers are clients only (structural necessity)**: a chain op requires the actor's Ed25519 signature, and the server can't sign. A "periodic" checkpoint is client-driven, not a server cron (issuance triggers are §6.3)
  - Introducing this op is a breaking change requiring simultaneous updates of every implementation under the "unknown op = invalid chain" consensus rule, but being pre-release it carries no backward-compat clause (the same premise as §6.2's precedent). **Because it touches no existing op's payload format, existing test vectors' canonical chains stay valid and it extends them by addition** (unlike the grant_server lease-policy extension — a payload format change = full regeneration. §11)

### 6.3 Client verification rules

- At sync, the client verifies the whole chain (or the diff from a verified position): prev_hash continuity, signatures, and operation permissions
- **Epoch ordering rule (decided 2026-08-02. Following the 2026-08-03 environment lifecycle binding — §6.2)**: `rotate_epoch`'s `new_epoch` must exactly equal "that environment's current epoch (initial value 1 right after `create_environment`) + 1". It refuses rollback (old-epoch DEKs held by removed members encrypting new values), duplication, and jumps (a DoS where one member-permission signature consumes the epoch space to its limit and makes future rotations impossible). Beyond each epoch's current value, the verification state derives **each epoch's validity interval (the starting seq)** (an input to §4.1's value verification)
- **The re-grant rule (decided 2026-08-02. Made two-tiered 2026-08-12)**: a `grant_server` to the same server key as a valid `grant_server` is accepted **only as an enlargement of the disclosure scope (scope_environments) (old ⊆ new)**. A shrinkage must go through `revoke_server` (with §7's all-environment rotation obligation) — a shrinkage without rotation would be a sham shrinkage making a DEK the server already knows look "undisclosed". Meanwhile, **the lease policy (lease_policy — §6.2) may be freely revised by a re-grant (including shrinkage and full deletion)**: the policy is the lease path's (§9.1) ACL and doesn't change the server's known-DEK set. Charging a full-environment rotation for a tightening would unjustly raise the cost of legitimate policy fixes (correcting a misconfiguration, transferring a repository) and push toward not fixing them. The two-tier judgment is made independently per field
- **The DEK wrap destinations must exactly equal the chain-derived recipient set R(E) (§6.2 — current members in scope + valid grant_servers within the disclosure scope) (2026-09-14 ES revision — the environment-axis version of the old "current members on the chain (+ valid grant_servers)")**. Generating / accepting a wrap to a public key not on the chain is forbidden (defense against ghost-member attacks). Generating / accepting a wrap addressed to an out-of-scope member is forbidden (the environment-axis version of ghost-member defense). **The device axis (2026-09-19 DK)**: "current members in scope" reads "each device of a current in-scope member whose effective scope contains E" (the device expansion of §6.2's R(E) — wraps to revoked devices or devices outside their device scope are forbidden to be generated / accepted). **The receiving side**: a wrap addressed to oneself for an environment ∉ **this device's effective scope** is **not used even though it opens; warn** (evidence that the server isn't enforcing AUTH_SPEC §12-6's acceptance rules. The actual harm is limited to "readable" since every verifier refuses writes to that environment as out-of-scope, but normatively it is not used). The registration path and the exact-match judgment for server-key-destined wraps are AUTH_SPEC §12-4 / §12-6 (2026-08-12 revision — dissolving the old "v1 has no registration path" boundary. The exact-match target is the current member set + valid grant_server server keys within the disclosure scope). Response-scope lease wraps are outside this rule (§9.1's boundary)
- **DEK commitment cross-check (2026-08-03 — §5.2)**: after Opening a wrap and before using the DEK, cross-check against the chain-derived (environment_id, epoch) commitment (mandatory)
- **Verification of value / metadata statements (2026-08-03 — §4.1 / §4.2)**: the client verifies each distributed value / metadata statement as follows. "The state at declared-head time" means the chain-derived state with entries **applied up through** seq = `chain_head_seq` (inclusive) (a push right after a `create_environment` / `rotate_epoch` entry that is itself the declared head arises necessarily in the legitimate flow — an off-by-one implementation difference would become a verification split on legitimate data, so this is pinned by vectors. The same inclusive convention applies to membership-interval boundaries — signatures headed by an add / remove entry itself):
  1. **Signature**: from the distributed writer / author's user_id and key fingerprint, select — among the sig public keys bound to that user_id in the verified chain history — the one whose fingerprint matches **and that was validly bound to that user_id at declared-head time** (a key of the membership interval containing the declared head), and verify the signature (refusing a key-and-head combination straddling intervals for a user_id who was removed → re-added under a different key. §5.1's selection rule plus the head-time binding condition). Even if the signer is later removed, a past legitimate write verifies under the key of that time
  2. **Head binding**: `chain_head_hash_hex` must match the entry hash at seq = `chain_head_seq` on one's own verified chain. Two kinds of mismatch are distinguished (specifying chain-fork behavior): (a) `chain_head_seq` ≤ one's own head yet the hash mismatches = **hard evidence of chain forking (equivocation) or forgery** — refuse immediately + warn. (b) `chain_head_seq` is ahead of one's own head = possibly just one's own chain being stale (even under an honest server, another member's append can land between sync and fetch) — first re-sync and re-verify the chain; if it matches as an extension of one's own chain, accept normally; if it still doesn't match after re-syncing, treat as (a)
  3. **Authorization time**: in the chain-derived state at declared-head time, the writer / author held the required role for that operation (the §4.2 / AUTH_SPEC §12-3 table). A signature by a removed member's key passes only when the declared head lies inside the membership interval — this is the grounds on which a client can verify "membership at registration time" (the residue is §14.3)
  4. **Epoch consistency (values only)**: the signed epoch must equal that environment's current epoch at declared-head time (since pushes are accepted only at the current epoch — AUTH_SPEC §12-5 — a legitimate write always satisfies this. It cuts off the path of forging a current-epoch value with a removed member's key: removal accompanies a rotation of every environment of the target's scope — §7. And an out-of-scope environment has no signature coordinate for the target in the first place [3′] — so within a removed member's membership interval, no head exists whose current epoch at that time equals the present current epoch). A value signature whose declared-head seq is **before** the environment's `create_environment` seq is invalid (the epoch is undefined for a nonexistent environment — forbidding a fallback-to-default implementation)
  5. **Coordinate consistency**: the signed coordinates (project / environment / variable / version / epoch — and for values, nonce / ciphertext too) must match the requested context, the declared AAD, and the received payload (recomputing from expected coordinates rather than reconstructing server-declared values — the same posture as the session 11 CLI verification)
  6. **Chain consistency**: `prev_*_hash` matches the signed_bytes hash of the known preceding version / meta_version, and for values the epoch is **non-decreasing** from the preceding version (§4.1's epoch monotonicity). On first sync or a latest-only fetch with no stored predecessor, no check target exists (what isn't guaranteed in that case is §14.3)
- **The scope authorization-time check (2026-09-14 ES)**: add a **scope authorization-time check** to the verification of values / metadata statements / manifests (1–6): **3′. Scope (environment-targeted signatures)**: in the chain-derived state at declared-head time, the writer / author / issuer's scope must contain that environment_id (rejection reasons `writer-environment-out-of-scope-at-head` / `author-environment-out-of-scope-at-head` / `issuer-environment-out-of-scope-at-head` — immediately after rule 3's role check). Environment meta statements (rename / delete), variable meta statements, and manifests are all environment-targeted and in scope. The bundled statement / manifest of the environment-creation composite — whose declared head is the pre-append head (AUTH_SPEC §12-4) and whose environment doesn't yet exist — holds vacuously because the creator's scope = all (§6.2)
- **Device-key selection and effective permission (2026-09-19 DK)**: rule 1's "the key validly bound to that user_id at declared-head time" means a key whose device-key validity interval (§6.2) contains the declared head. A signature where a revoked device declares a head at or after the revocation seq gets `*-key-mismatch-at-head` (an existing reason code — the same shape as straddling a membership interval). Rules 3's role and 3′'s scope are judged by **the signing device's effective permission** (a value signature from a device with cap < member gets `*-role-insufficient-at-head`; outside the device scope gets `*-environment-out-of-scope-at-head` — both existing codes; only the input changes to the effective permission)
- **Treating out-of-scope environments (2026-09-14 ES revision — design record ruling G)**: for out-of-scope environments, a member still receives and verifies the chain (all entries — including that environment's `checkpoint` tuples), the environment's existence, display name, variable names, schema fields, manifest, and tombstones (plaintext meta = the open-item-#3 line) (a metadata-only pull — AUTH_SPEC §12-7). They don't receive ciphertexts or DEK wraps addressed to themselves, and can't write / rotate / checkpoint. **Cross-environment verification**: (i) tuples of out-of-scope environments in a `checkpoint` are verified as consensus rules (§6.2) but are **not used as baselines** for checkpoint consistency — a baseline is needed only for environments where one pulls with values, (ii) manifest verification covers only pulled environments (unchanged), (iii) head declarations and invite-link anchors carry no environment and are unchanged. A repository anchor's per-environment epochs are chain-derived values, so it can be written for out-of-scope environments too (unchanged), (iv) the local floor is "the join of facts verified successfully" — an out-of-scope environment's floor is simply never established (not a target of refusal or warning). **Device scope (2026-09-19 DK)**: in addition to the person's scope, environments outside the device scope are treated identically (meta visible, no DEK received). Since the device scope is a subset of the person's scope, it never exceeds the person's visible range (ruling G)

### 6.4 The server's role: verification, serialization, and the source of truth for authorization

- **The chain is verified by the server too**: the chain is public data (signatures, hashes); the server verifies prev_hash continuity, signatures, and operation permissions when accepting an append, and refuses an invalid entry. Client verification (§6.3) is defense against a distrusted server; server verification is defense against rogue clients — both are mandatory
- **The chain is the source of truth for authorization**: the server-side judgment of "who may fetch this project's data (wrapped DEKs, ciphertexts)" is based on the current member set derived from the chain (and each member's scope — 2026-09-14 ES. AUTH_SPEC §9-2 / §12-3). Its role differs from D1's memberships (org); no independent permission table contradicting the chain is built for project access (the two-sources-of-truth prohibition)
- **Serializing concurrent appends**: chain appends are serialized by the project DO. An append request carries "the hash of the head to parent"; if it mismatches the current head it is refused (compare-and-swap). The client fetches the latest chain, re-verifies, and retries
- **Size limits (server acceptance policy. Added 2026-08-02 — the item §6.1 deferred)**: at append acceptance the server applies: (1) a whole entry's normalized byte string (§6.1's entry_bytes) is **at most 1 MiB**, (2) the whole chain is **at most 10,000 entries** and **at most 32 MiB of cumulative normalized bytes**. These are **not consensus rules of chain validity but the server's acceptance policy**. Since §6.1 / §6.2's field size limits (consensus rules) mathematically bound a spec-conforming entry's normalized size to at most ~810 KiB (the largest `grant_server` form: scope_environments = 1024-byte environment IDs × 256 elements ≈ 512 KiB + lease_policy = 8 elements × 8 claim constraints × 1024-byte strings — §6.2 — ≈ 288 KiB. Both including nested-LP hex encoding), this policy never refuses a spec-conforming entry, and no chain split arises from implementation disagreement. The cumulative limits are resource protection guarding the append-time whole-chain re-verification (this section) and every client's sync / verification cost (§6.3) from chain-bloat DoS by append flooding under member permission (`rotate_epoch` etc.). Because it is an acceptance policy, raising the values doesn't affect past chains' validity, and self-host-side adjustment doesn't break consensus either. An excess is refused with a typed error (front defenses such as an HTTP-boundary raw-body limit are implementation details; this spec defines only the normalized-byte-string-based values)
- **Project ID = the genesis entry hash (added 2026-08-02)**: a project's identifier is the genesis entry's entry hash (§6.1's entry_hash, lowercase hex, 64 chars), and the server resolves the project DO by this ID. Chain initialization numbers the ID by the server verifying and hashing genesis (the client can foresee the ID by the same computation). Under this binding, a server's swap of "distributing a different chain under the same project ID" is mechanically detectable by the client's genesis-hash recomputation (part of §6.3's sync verification). Re-submitting the same genesis resolves to the same ID, so it is refused as a duplicate genesis on an initialized project
- **Server verification of value / metadata signatures (2026-08-03 — §4.1 / §4.2)**: signature verification is added to the acceptance conditions of push / variable / environment meta operations (the concretization of the acceptance conditions is AUTH_SPEC §12): exact match of the API calling principal = the writer / author (the same rule as §5.1 — bringing values / statements signed by someone else is refused), signature verification by the chain-derived current member's sig key at acceptance time, the declared head existing on the server's own chain, agreement of the declared-head-time role and the key binding (the same judgment as §6.3's rules 1 and 3 — the acceptance-time key must have been bound to the same user_id at declared-head time too. Eliminates at the acceptance stage the declarations of old-membership-interval heads by a principal who was removed → re-added under a different key, which clients uniformly refuse), and **values only**, epoch consistency (§6.3's rule 4 — meta statements carry no epoch and are out of scope). Server verification is defense against rogue clients / misimplementations; the guarantees under server distrust are carried by client verification (§6.3) (the same two-wheel picture as this section's opening)
- **Composite acceptance (2026-08-03. The manifest bundling added 2026-08-18 — §4.3)**: environment creation is accepted as one request "`create_environment` entry + env meta statement (meta_version 1) + the epoch-1 wrap complete set + the environment manifest (manifest_version 1)"; rotation is "`rotate_epoch` entry + the new epoch's wrap complete set + the environment manifest baking the new epoch", each accepted atomically by the project DO (AUTH_SPEC §12-4). No intermediate state is created where the chain append (CAS) and the data registration are separated ("an epoch exists but no wraps")
- **Acceptance verification of `checkpoint` (2026-08-18 — §6.2)**: on top of the consensus rules (form, the actor's chain role admin for a non-empty audit head, unknown-environment, epoch exact match, checkpoint-regression), the acceptance policy cross-checks the payload's contents against **the server's stored state at acceptance time**. **The cross-check baseline of a boundary checkpoint bundled in a composite (2026-08-19 session 32 — AUTH_SPEC §12-4) is "the stored state after the composite's application"**: the bound manifest is registered by the same transaction's bundled part, and at environment creation the environment itself didn't exist beforehand — so the "pre"-acceptance state has nothing to cross-check (a standalone checkpoint cross-checks the stored state at acceptance time = pre-application as before. The same-request bundle-internal coordinate / hash agreement checks are carried by AUTH_SPEC §12-4's consistency checks, and the non-overlapping scope with this cross-check is unified in the implementation PR):
  - **Manifest reference**: each environment entry's (manifest_version, manifest_sig_hash) must match that environment's **latest** manifest at acceptance time
  - **Value snapshot**: each environment entry's values_digest must match the value recomputed from the acceptance-time stored state (every active variable's latest version and its stored value_signed_bytes hash). **The digest's pre-image doesn't ride the wire** (the server can uniquely reconstruct it from acceptance-time state — an agreement check suffices)
  - These two checks require "the issuer's verified view = the data state at acceptance time". If a concurrent data-layer write (a push, a meta operation) lands between issuance and acceptance, it is refused with a typed error and the client re-fetches, re-verifies, re-signs, and retries (the same retry structure as the chain-append CAS's 409). What dominates the collision probability is **issuance duration × the project-wide write frequency** (because the cover is all environments — §6.3 — a write to any environment invalidates an in-flight checkpoint. Secrets writes are low-frequency and rare in practice. The fallback when it never converges is §6.3's subset issuance). Notarizing a past state is not accepted (simplifying to acceptance-time agreement makes the per-variable baseline monotonicity follow automatically from the state's time monotonicity)
  - **The audit head (only when audit_head_hash is non-empty — empty = no notarization is out of scope)**: the API calling principal's effective permission is admin (AUTH_SPEC §16-2. The chain role admin is also verified as §6.2's consensus rule); audit_head_hash **exists** in the stored cumulative-hash sequence (AUDIT_SPEC §5.1), and **its position of occurrence is ≥ the position of the immediately preceding `checkpoint` entry's mirror row (`chain.checkpointed` — AUDIT_SPEC §3.4)** (**when no preceding `checkpoint` entry exists — the project's first checkpoint — no position floor is imposed [vacuously true]**. That the acceptance check and the admin cross-check [AUDIT_SPEC §6] are the same predicate is the basis of soundness, and the base-case treatment is identical between the two — 2026-08-18 pullfrog review handling) (2026-08-18 pullfrog / Bugbot review handling — without the position floor, the path remains where an honest issuer who lost the CAS race re-signs with the stale audit-head declaration and gets accepted, and the admin cross-check's position check [AUDIT_SPEC §6] misreads a benign race as a tampering accusation. **Under this acceptance check, under an honest server the cross-check's position check structurally always holds**). Latest-agreement is **not** required (the audit head can advance between the issuer's fetch and the append's acceptance — the chain append itself writes a mirror row — requiring latest-agreement would self-race). Insufficient effective permission is 403; a declaration not meeting the position floor is refused with the same typed error as other cross-check failures, and the client refetches the audit-head declaration and retries (§6.3)
  - **Entries for deleted (tombstone) environments are refused (acceptance policy — 2026-08-18 pullfrog review handling)**: a deleted environment has no manifest or values (AUTH_SPEC §12-4's cascade), so "agreement with the acceptance-time state" can't be defined. **This cannot be a consensus rule** (the chain doesn't observe environment deletions — per §6.2's environment-lifecycle binding, deletion is a data-plane operation and active / deleted can't be judged by chain verification alone), so it is a separate acceptance-stage refusal from `unknown-environment` (a typed error — AUTH_SPEC §16-2). A legitimate issuer doesn't include an environment that has a verified deletion statement (§6.3)
  - **Bringing a notarization of a false state (a nonexistent state, a tampered digest, a fake audit head) is eliminated at the acceptance stage** (defense against rogue clients — this section's two wheels. An attacker colluding with the server can ignore this acceptance verification, but even then the client-side §6.3 checkpoint consistency and the consensus rule `checkpoint-regression` operate independently. **The per-variable non-regression inside values_digest cannot be cross-checked by chain verification** — the digest is opaque, so a colluding server + a current member lowering the value baseline remains a residue. That class, however, has legitimate push permission and can write legitimately without lowering the baseline = reduces to G9)
  - **Atomic storage of the value snapshot**: in the same project-DO transaction as acceptance, for each environment contained in the payload, "the checkpoint-time value-snapshot enumeration" (the acceptance-time state itself) + the corresponding checkpoint seq / hash is stored (upserted) as the latest covering checkpoint; existing snapshots of environments not contained in the payload are left unchanged. This keeps B's baseline even when only A is re-checkpointed while both A / B baselines exist, and lets AUTH_SPEC §12-7 distribute each environment's chain-derived "latest checkpoint containing that environment" and its corresponding enumeration
- **Acceptance and distribution of head declarations (2026-08-18 — §6.6)**: the server stores the latest declaration as 1 row per member (per device after 2026-09-19 DK — §6.6 / AUTH_SPEC §16-1) (not put on the chain — a declaration is mutable data updated on every sync; making it a chain op would let sync activity consume the entry limit. The same line as §6.2's "the chain is not a ledger of mutable metadata"), and verifies at acceptance: exact match of calling principal = attester, signature verification by the sig key of a current member (reader or above) at acceptance time, the declared head matching the entry hash at that seq on the server's own chain, and seq monotonic advance from the stored declaration (a regression is refused with a typed error — don't let it silently succeed). On accepting `remove_member`, the target member's declaration rows are deleted; on accepting `revoke_device`, that device's declaration rows are deleted (only valid devices of current members are distributed — storage convergence to the chain-derived truth. The same shape as AUTH_SPEC §12-6's old-key wrap cleanup)
- **Acceptance of scope and four-eyes (2026-09-14)**: §6.2's consensus rules (scope structure, containment, environment-targeted ops, the four-eyes proposal / approval / policy) are verified by verifyChain at chain acceptance (the 4 acceptance steps are unchanged). **The acceptance side effects of a completed four-eyes application** (the `approve` entry reaching quorum) — rotation-needed detection, declaration-row deletion, old-key wrap cleanup, invite completion — run identically to accepting the inner op directly, inside that `approve` entry's acceptance task (AUDIT_SPEC §3.4's mirror likewise). **Acceptance policy**: pending proposals are capped at **32** per project (excess → a typed error — AUTH_SPEC §12-8. Not a consensus rule). **Expired proposals aren't counted** (a pending proposal past `expires_at_ms` by the server's clock is excluded from the cap computation). **The upper bound of `expires_at_ms`** (acceptance policy — 2026-09-14 pullfrog round-9 handling): at `propose` acceptance, a proposal whose `expires_at_ms` exceeds the acceptance-time server clock + **30 days** is not accepted (a typed error — AUTH_SPEC §12-8. Not a consensus rule: `expires_at_ms` is the proposer's chosen value and §6.2's structure check only requires a non-negative safe integer, so without an upper bound a proposal bearing a far-future expiry could occupy the cap, defeating the expiry exclusion). To state the effect precisely: the expiry exclusion releases **abandoned proposals** (ones the well-meaning proposer neither completed nor withdrew) without waiting for `withdraw`, and the upper bound extends that to every proposal — a deliberate occupation resolves in at most 30 days, and the immediate-release provision is an owner's `withdraw` (the CLI's bulk withdrawal). It's an acceptance policy, not a consensus rule, so the server clock suffices. No per-proposer secondary cap (if needed at K5, it can be added additively as an acceptance policy). `propose` / `approve` / `withdraw` / `set_approval_policy` are accepted via the generic chain-append API (AUTH_SPEC §11)
- **Device count and device-op acceptance (2026-09-19 DK)**: valid devices per member are capped at **16** (acceptance policy — not a consensus rule. An `add_device` exceeding it gets a typed error — AUTH_SPEC §12-8). `revoke_device`'s acceptance side effects: deleting the target device's declaration rows (AUTH_SPEC §16-1), rotation-needed detection (the `revoke_device` variant of AUDIT_SPEC §4.1), and the mirror (AUDIT_SPEC §3.4). `add_device`'s acceptance side effect: the mirror only (DEK backfill is the client — §7). `add_device` / `revoke_device` are accepted via the generic chain-append API (AUTH_SPEC §11)
- **The recipient set for DEK-wrap acceptance** is §6.2's R(E) (AUTH_SPEC §12-6 — both exact match and the recipient judgment include scope)

### 6.5 The cryptographic side of invites: link keys, issuance signatures, the joint acceptance signature, and mutual confirmation (drafted 2026-08-12 — resolving open item #9. 2026-09-13 IV revision)

The cryptographic side of inviting an unregistered user (and adding a registered user — the two are the same mechanism). The resource / API side is AUTH_SPEC §15. Design principle: **an invite carries no key material (device keys, reserve key — 2026-09-19 DK) and no DEKs** (a leaked invite link doesn't become a key leak — the only secret the link carries is **the link-key seed**, effective for that single invite; the leak's radius is one invite). The counterpart key's authenticity is carried by (1) the joint acceptance signature via the link key (this section — **IV1**), (2) the issuance signature (this section — IV1), (3) key matching via the backing source (this section — **IV2**), (4) the invite-link anchor (§6.3), and (5) as a fallback, out-of-band mutual confirmation of key FPs (word display — §3). **No global public-key directory is built** — avoiding both a structure where knowing a user_id enables add_member without the counterpart's consent (unconsented addition) and a new trust object called a directory; keys always travel with context as "an acceptance of this invite". A backing source (the IdP's public-key list) is not a directory: acceptance requires holding the link and the acceptor's active signature, and the backing source **only post-hoc matches the key of that acceptance** — it is neither a key source nor an input to add_member.

- **The link key**: the inviter client numbers an invite id (ULID) per invite, generates a 32-byte uniform random `k` (the seed), and derives the Ed25519 key pair `(K_priv, K_pub)` (the same derivation as §3's signature key — the seed = the private key's seed). `K_pub` goes to the issuance API as part of the issue body (below) (AUTH_SPEC §15-2); `k` rides only the link's fragment. **The server never once receives `k` / `K_priv`**. The inviter client doesn't persist `k` (display = discards the reference right after assembling the link)
- **The issue body and the issuance signature**: the inviter signs the issue body (the invite id, the link public key, the verified head, role, **scope**, their own identity) with their chain signature key (Ed25519), and places it **on both the server row and the link**:

  ```
  invite_issue_signed_bytes = LP("maruhi/v1/invite-issue",
                                 invite_id, project_id, link_pub_hex, head_hash_hex, head_seq, role,
                                 inviter_user_id, inviter_enc_pub_hex, inviter_sig_pub_hex,
                                 scope_kind, scope_environments_lp_hex)
  ```

  - **Scope (2026-09-14 ES revision)**: the scope to be granted (same encoding as §6.2) is appended to the **tail** of the issue body. Like role it is a tamper-detection target, and the acceptor reads "which environments I'm entering" before accepting. `add_member` signs with the invite row's role / scope (AUTH_SPEC §15-2 — the inviter cannot attach a different scope after acceptance: the consent's extent is fixed at issuance). `invite-link.json` is regenerated (§11)
  - The encoding is §2.1 (binary as lowercase hex, numbers decimalized). The verification key is `inviter_sig_pub_hex` inside the signed content (self-bound — the same shape as §5.1's / the old §6.5's acceptance signature); a successful verification is the attribution that "the holder of `inviter_sig_pub`'s private key issued this invite (this id, this link_pub, this head, this role, this scope)". **Who** the inviter is is shown by the backing source (below) or the out-of-band check
  - Semantics (the acceptor's side): drops path tampering of the link (swapping the anchor / role / scope / inviter keys) into verification failure. A third party who ghost-added the inviter's public key to their own chain cannot build an inviter-named link (a mechanical cut of reverse-direction phishing — supplement 21 ruling E). The accepting client treats an issuance-signature verification failure as a reason **not to accept** (not overridden by an out-of-band check)
  - Semantics (the inviter's side): being able to verify the server row's issue body + issuance signature **with one's own sig public key** is the source of truth that "this row (this link_pub) is one's own issuance". The server can't forge the issuance signature, and transplanting it to another row falls on the `invite_id` / `link_pub_hex` binding. This lets the inviter verify an acceptance **without depending on an issuance pin** (even from another device) (supplement 21 ruling A ⑦). The issuance pin (AUTH_SPEC §15-3) remains a SHOULD-level material carrying the additional cross-check and the retention of the destination login
  - The server doesn't verify the issuance signature (the verifiers are the inviter themself and the acceptor — don't create a second source of truth)
- **The joint acceptance signature**: accepting an invite carries **an acceptance signature** by the acceptor's chain signature key (Ed25519) and **a link signature** by the link key `K_priv`, over **the same byte string**:

  ```
  invite_accept_signed_bytes = LP("maruhi/v1/invite-accept-v2",
                                  project_id, link_pub_hex,
                                  invitee_user_id, invitee_enc_pub_hex, invitee_sig_pub_hex)
  accept_signature = Ed25519(invitee_sig_priv, invite_accept_signed_bytes)
  link_signature   = Ed25519(K_priv,           invite_accept_signed_bytes)
  ```

  - The domain string is `-v2` (the old `invite-accept` bound `invite_token_hash_hex` — the old form isn't accepted. AUTH_SPEC §12-10 (2)'s "the form old implementations structurally refuse"). The encoding is §2.1. The acceptance signature's verification key is `invitee_sig_pub_hex` inside the signed content; the link signature's verification key is `link_pub_hex` inside the signed content (both self-bound)
  - Semantics: the acceptance signature = attribution and context binding of "the holder of this key pair expressed the intent to join this invite under this key" (unchanged). The link signature = "**the holder of the link** approved accepting under this key". Since the server doesn't hold `K_priv`, **it is cryptographically impossible to make a valid link signature with the acceptance block's keys swapped for different ones**. Because an invite is **single-use** (AUTH_SPEC §15), an attacker who snatches the link and accepts first under their own key (the attacker can make the link signature) **surfaces** as an acceptance collision against the legitimate counterpart on the same invite — this residue (reading the link path + first-come) is closed beforehand by the backing source's match (IV2), or by the out-of-band mutual confirmation when no backing source exists
  - The server verifies both signatures at acceptance (AUTH_SPEC §15-2). Before `add_member`, the inviter client verifies the list row's issue body + issuance signature with its own sig public key (failure = not its own issuance / a swapped row → refuse), cross-checks `link_pub_hex` / role if an issuance pin exists, and then re-verifies both signatures independently
- **The backing source (IV2 — a client spec)**: the source that mechanically matches, via the IdP's published key list, whether the acceptance key (on the inviter's side) / the inviter key (on the acceptor's side) belongs to "the named counterpart". As swappable abstractions it offers `github-signing-keys` / `org-directory` (reserved — an org's key book, the equivalent when SSO is introduced) / `none` (no matching = the ceremony), and v1's implementation is `github-signing-keys` only:
  - Each user registers their maruhi **sig public key (Ed25519)** on GitHub as an **SSH signing key** (the kind for commit signing; unusable for SSH authentication) (`maruhi key publish`). The representation is an OpenSSH public-key line `ssh-ed25519 <base64(the SSH wire format: uint32-BE length ‖ "ssh-ed25519" ‖ uint32-BE length ‖ the 32-byte key)>` (RFC 4253 §6.6 / RFC 8709). **This is an interoperability encoding, not a new cryptographic primitive** (the same positioning as §3's FP words and §8.4's handoff code. The encoding / parsing lives in `packages/crypto` as a single implementation, pinned by test vectors)
  - A client performing the match fetches that login's signing-key list from GitHub's public API (`GET /users/{login}/ssh_signing_keys`, no authentication) and checks whether the target sig public key is contained **byte-exactly** among the `ssh-ed25519`-kind keys. Matching **only the sig key** suffices: the enc key is inside the signed content of the acceptance / issuance signatures, bound by the sig key's holder
  - The only information sent to the backing source is **the login** (no project, keys, values, or usage state). The host is fixed (`api.github.com`). The response is treated as public information; whether the match **fails** (no such key) or is **impossible** (can't fetch, rate limit, offline), fall back to fulfillment forms 1–3 below (fail-closed: a backing source can only ever be grounds to **omit** the ceremony — it never works in the direction of **exempting** it). When the key is absent, the client may offer, before entering the ceremony, the choice "ask the counterpart to register (`maruhi key publish`) and re-run" (a postponement of the ceremony, not a replacement — supplement 21 ruling D ④)
  - The registration conduit (a client spec): the accepting client guides registration at the completion of acceptance, and proposes registration (or re-registration) right after key generation / regeneration / restoration (supplement 21 ruling G ⑥). Registration requires the user's explicit consent (yes) and is never done without it
  - A future backing-source candidate: having an SSH **authentication** key the user already registered with the IdP SSHSIG-sign the acceptance body (`github-ssh-keys` — removes the registration step) will be proposed separately as a revision adding SSH public-key / SSHSIG parsing and verification to this specification (supplement 21 ruling G ⑦)
  - The byproduct that the same key can also sign commits is tolerated (the uses are separated by SSHSIG's namespace and this specification's LP domain strings)
- **The relation to device keys (2026-09-19 DK)**: the key accepting an invite and the key issuing an invite are each **the device key of the device performing that operation**. What is registered to the backing source (`github-signing-keys`) (`maruhi key publish`) is the sig public key of the device used for accepting (per-device registration is fine — GitHub holds multiple signing keys). The path for a person adding their own other device is not the invite but `add_device` (§6.2 — neither third-party guarantee nor mutual confirmation is needed: it's the person's own operation adding their own key, and what travels is only the FP [public information] — if the server swaps the public key, the FP check fails). The verified fingerprint book's (fulfillment form 3) records are a **set** of (origin, user_id) → FP, and a known counterpart's unknown FP is treated the same as a key change (warning + the ceremony)
- **Mutual confirmation (mandatory UX)**: the confirmation is **bidirectional**. On the inviter's side: before executing `add_member`. On the acceptor's side: before executing the acceptance. One-directional confirmation alone leaves **reverse-direction phishing**: luring the victim with a fake invite into joining an attacker-owned project and pushing real secrets (the attacker is the legitimate owner of their project; chain verification raises no alarm) — so mutuality is mandatory
- **Fulfillment forms of explicit confirmation (2026-09-12 revision — normalizing the interpretation of the verified fingerprint book. 2026-09-13 IV revision — adding form 4 and making it the default)**: the preceding item's confirmation is fulfilled, on both the inviter's and the acceptor's side, by one of the following. **The default is 4.**, falling back to 1–3 when 4 can't be established:
  1. **The read-aloud ceremony**: cross-check the FP word sequence out-of-band (a call etc.) at that execution, and re-enter the final word
  2. **Flag-based mechanical matching** (`--expect-fingerprint` / `--inviter-fingerprint`): explicit specification at execution time of an FP recorded out-of-band. Because it is explicit agency for that single acceptance, the out-of-band record is treated as already cross-checked (the form allowed in non-interactive environments that don't use the backing source)
  3. **A verified-fingerprint-book hit + per-acceptance explicit confirmation**: if the same (origin, user_id, FP) was confirmed before via 1. or 2. (the CLI records it as a non-secret setting), only **re-performing** the read-aloud check is exempted. The explicit confirmation (a yes input) naming the target (the counterpart, role / project) is not exempted. This form is usable only when stdin / stdout is an interactive terminal; it is not used in AI-agent environments (the same allow-list as ADR-0016 decision 7's primary boundary)
  4. **Link binding + backing-source matching (the default — IV1 + IV2)**:
     - The inviter's side: when (i) the list row's issue body + issuance signature verifies under one's own sig public key (and if an issuance pin exists, the `link_pub` / role cross-check holds too), (ii) the link signature / acceptance signature verifications succeed, and (iii) the backing source matches that "the acceptance's sig key is the key of the counterpart named at issuance (`invite create --github <login>` — kept in the issuance pin; absent that, `--github <login>` at execution time. No interactive input is provided — AUTH_SPEC §15-3)" — then **without a confirmation input** the client may proceed to `add_member`. The naming was explicit agency made at invite issuance; the per-acceptance consent was already expressed there
     - The acceptor's side: when (i) the issuance-signature verification succeeds and (ii) the backing source matches that "the inviter's sig key (the link's `is`) is a key of the login the link names (`il`)" — then no read-aloud check is needed, and fulfillment is **the acceptor's declaration that "I was expecting an invite from that login"** (non-interactive: a match of `--from <login>` / interactive: a yes input naming the login). Acceptance is the acceptor's declaration of active intent to participate, and this single declaration is not omitted (the last defense distinguishing a **valid** link of a different person swapped on the path is "reading the login")
     - A cryptographic-verification **failure** of (i)(ii) (an issuance-signature / link-signature / acceptance-signature failure, a mismatch with the pin) is **refused rather than falling back** to forms 1–3 (a broken signature is never overridden by a human read-aloud). An **impossibility** of (iii) (backing source `none`, no destination login, unregistered, un-fetchable) falls back to 1–3
  - **Never allow an unconfirmed automatic pass on a book hit alone** (unchanged): the invite link doesn't carry the acceptor's identity, and the book is merely a verification record of a past, different context — it cannot substitute for human consent to this grant / acceptance. The form-4 confirmation-less path exists only when **both** the cryptographic verification (link binding) and the issuance-time naming (backing-source match) hold
- The `add_member` entry's (§6.2) format and semantics are unchanged by this section (the IV revision) (the scope-field addition is §6.2's ES revision — 2026-09-14): the public keys on the chain are the ones the inviter confirmed, and onward authenticity is carried by chain signatures. The issuance signature, the acceptance signature, and the link signature are additional off-chain evidence (server verification + inviter / acceptor client verification — AUTH_SPEC §15) and are not included in the consensus rules of chain validity
- **Prohibitions (this section's scope)**: never emit the link-key seed `k` / `K_priv` to disk, logs, error messages, or audit (it is displayed once, as the link). Build no API where the server receives `k` / `K_priv`. Never report the backing source's match result to the server (the match completes inside the client). Never write the backing source's login into the chain, audit, the server-stored invite row, or the signed structure (it lives only in the link's fragment and the inviter's local pin)
- Test vectors: `test-vectors/invite-accept-signature.json` (v2 — regenerated) / `test-vectors/invite-link.json` (new — §11)

### 6.6 Head declarations (drafted 2026-08-18 session 27 — the declaration form of §6.3's head gossip)

Off-chain data by which a reading-side client declares with a signature "I have verified up to this chain head". Built only from existing parts (Ed25519 + §2.1 LP).

- **The normalized byte string being signed** (§2.1 encoding):

  ```
  head_attestation_signed_bytes = LP("maruhi/v1/head-attestation",
                                     project_id, attester_user_id,
                                     chain_head_hash_hex, chain_head_seq)
  ```

  - Baking `attester_user_id` is the same reattribution countermeasure as §5.1's signer_user_id. project_id binds the context, and transplanting a declaration to another project fails verification
  - **The signature is mandatory**: an unsigned declaration can be synthesized by the server and used in both directions — warning-inducing DoS (fake contradicting declarations) and fake reassurance (fake agreeing declarations). A signed declaration becomes, the moment it contradicts one's own view, **undeniable evidence** of "server equivocation or the attester's key leak" (the same standing as §14.2-5)
  - **No timestamp / nonce is included**: the signature's semantics is the attribution of "verified up to this head", not a freshness proof (the same line as §5.1's semantics). A declaration's recency is ordered by chain_head_seq; redistributing an old declaration is equivalent to server omission (making declarations look stale) and can't be prevented by cryptography (G8). A timestamp only adds the behavioral information "when they synced" without adding detection capability (the privacy consideration is in the session 27 notes §7)
- **Client verification (when receiving a distributed declaration)**: (1) the attester (user_id + key FP) is a current member in one's own view, and was still a member at the declared-head time (inclusive — §6.3's convention), (2) the signature verifies under the sig public key bound to that user_id in the chain history whose FP matches and that was valid at the declared-head time (the same key selection as §6.3's rule 1), (3) cross-checking the declared head against one's own view (the two-way distinction of §6.3's head-gossip paragraph). A declaration failing verification is not used as cross-check material (eliminating warning induction by fake declarations)
- **Device keys (2026-09-19 DK)**: the attester's key is the signing device's device key. "The key valid at the declared-head time" in client verification (1)(2) is judged by the device's validity interval (§6.2). A declaration is stored / distributed as the latest 1 row per **device**, not per member (AUTH_SPEC §16-1 — devices sync independently, so seq monotonicity across devices is not required)
- **Semantics**: "attester_user_id accepted this project's chain as verified up to this position". It doesn't prove the chain head's authenticity (verification is done by the receiving side against its own view — §6.3). **It carries nothing about whether plaintext values / variables were accessed** (the only behavioral information a declaration discloses is "the reach point of chain sync" — small in increment against the chain itself, which has every member distribute and verify every operation and every actor; and since split-view detection is in every member's interest including readers, declarations are distributed to all members. It is not made an audit event — AUDIT_SPEC §6)
- Wire / storage / acceptance / distribution are specified in AUTH_SPEC §16; server verification is §6.4. The client's submission triggers, cross-check rules, and on-detection behavior are §6.3's head-gossip paragraph
- **Workloads (§9.1) don't participate in declarations**: a workload holds no Ed25519 signing key (only the ephemeral X25519), so a forgeable unsigned declaration has no evidential value. Other members' declarations aren't bundled into the lease response either — a malicious server can attach past declarations to an old consistent view, so it adds no detection and only grows the misrecognition of "verified". The workload's defense is carried by the repository anchor (§6.3 (b)) and checkpoint consistency (§6.3)
- Test vectors: `test-vectors/head-attestation.json` (§11)

## 7. Epochs and membership changes

- Member removal and server revocation are always accompanied by `rotate_epoch`. **The target environment set (2026-09-14 ES revision)**: `remove_member` targets **the environments of the target's current scope** (scope = all means all environments); `revoke_server` targets all environments (unchanged — the revision is outside ES's scope, design record §6). Per environment a new DEK is generated, current values are re-encrypted under the new DEK, and the new DEK is wrapped to the recipient set R(E) (§6.2). **Out-of-scope environments must not be included in the rotate targets** (the target doesn't hold their DEK and no obligation exists — and the executor can't rotate outside scope either. By the containment rule — §6.2 — a remove's actor contains the target's scope, so it can fulfill it). The definition of "all environments" and the interruption discipline on 404 are unchanged: the `rotate_epoch` entry carries the new DEK's commitment (§5.2), and each re-encrypted value is signed by the executor as writer (§4.1). **"All environments" means those of the chain-derived environment set (`create_environment` — §6.2) not deleted by a verified deletion statement (§4.2's status = deleted)** (a deleted environment's ciphertexts and wraps are gone; a rotate has nothing to protect. The server doesn't accept a rotate to a deleted environment — AUTH_SPEC §12-4). If a rotate to an environment believed active is refused with 404, **don't silently skip** — interrupt and warn unless a verified deletion statement can be confirmed (don't make selective rotation-blocking by a malicious server invisible)
- **A demotion below member (turning reader via `change_role`) is accompanied by `rotate_epoch` of the target's scope's environments (drafted 2026-08-03 session 12. 2026-09-14 ES revision — the motivation stays epoch-anchor soundness; only the range shrinks to scope)**: the removal obligation's (above) motivation is confidentiality (revoking known DEKs), but the demotion obligation's motivation is **epoch-anchor soundness** — the demoted keeps receiving new DEKs as a reader, so there is no confidentiality effect, but without an intervening rotation the signature coordinate "a head inside the demoted's member interval × the current epoch" remains valid **indefinitely until the next rotation**, letting a forward injection at the current epoch (§14.3-5) keep working under collusion with a malicious server. Once the epoch advances, the demoted's forgeable coordinates shrink to the same "only the epochs of that time" as a removed member's. The re-encryption / re-wrap procedure is identical to removal
- **Scope shrinkage (2026-09-14 ES revision)**: when old scope \ new scope is non-empty in `change_role`, each environment in the shrunk part carries the same `rotate_epoch` obligation as `remove_member` (confidentiality — revoking the DEKs of the shrunk part held by the target). The obligation's origin is that `change_role`'s seq. Rotation-needed detection runs only on the shrunk environments (AUDIT_SPEC §4.1). **For a scope enlargement**, the actor (a DEK holder via the containment rule) wraps the DEKs of all epochs of the enlarged environments to the target and registers them (AUTH_SPEC §12-6's additive path — same shape as the post-add_member backfill. Not made a composite)
- **Who wraps**: a DEK wrap is always made by "a client holding the DEK" (unchanged). At member addition, the inviter's client wraps all-epoch DEKs of **the target's scope's** environments to the new member's (accepted device's — 2026-09-19 DK) public key. At rotation, the executor's client wraps the new DEK to R(E) (2026-09-14 ES revision)
- **Rotating a project with a valid grant_server**: the rotation executor also re-wraps the new-epoch DEK to the server public key (without re-wrapping, the lease path — §9.1 — stops. The UI makes this explicit). The registration paths are the composite request's wrap complete set (including the server key) and the post-grant backfill — AUTH_SPEC §12-4 / §12-6 (2026-08-12 revision — dissolving the old "v1 has no registration path" boundary)
- Past versions' values stay under the epoch DEK of their time. **All-epoch DEKs of each in-scope environment** are wrapped to R(E) (2026-09-14 ES revision — the old "all-epoch DEKs of all environments to current members". A new member can also read history within scope. Unlike messages, secrets don't aim to hide history)
- A removed member can't decrypt values after the new epoch. Neither can a revoked device (2026-09-19 DK — "Device revocation" below)
- **The obligations' origin and fulfiller under four-eyes (2026-09-14 PF1)**: the rotate obligation of a proposal-routed `remove_member` / demotion / shrinkage / `revoke_server`, the member-destined backfill obligation of `add_member` / scope enlargement, and the server-destined backfill obligation of `grant_server` (all environments × all epochs within the disclosure scope — AUTH_SPEC §12-6) each start at **application time** (the seq of the `approve` entry reaching quorum). At proposal time the target is still a member, there is no DEK to revoke, and no wrap can be registered for the pre-application target (not yet in the recipient set R(E) — AUTH_SPEC §12-6 refuses). **The fulfiller is the approver who completed the application** (an owner — scope = all, so holding every environment's DEK, fulfillable under the containment rule), and after application the approving client executes the sweep (rotate obligations) and the backfill (member-destined / server-destined all-epoch wrap registration — AUTH_SPEC §12-6's fifth path). The rule "the wrap's executor = the inviter / the actor who signed the enlargement / the grant executor" is for direct appends; via four-eyes it moves to the approver **regardless of the inner op's kind** (2026-09-14 pullfrog / Cursor Bugbot review handling). A state left unfulfilled is the same existing "member exists but no wrap" (AUTH_SPEC §12-4's asymmetry), and `project verify`'s un-converged-obligation warning (rotation-sweep's standing warning) displays unmet backfill too
- **Device revocation (2026-09-19 DK)**: `revoke_device` carries, for every environment of each revoked device's **effective scope** (the person's scope ∩ the device's scope), the same `rotate_epoch` obligation as `remove_member` (confidentiality — revoking the DEKs that device held. Revoking an empty-scope device [a votes-only device] carries no obligation). The obligation's origin is that `revoke_device`'s seq. The fulfiller is the actor who signed the revocation (another device of the same person, or an admin / owner who revoked someone else's device — holds the DEK by principle 1's containment). **When a reader revokes their own device**, the actor can't fulfill it because they lack `rotate_epoch` permission — this revocation is not refused by the consensus rule (a revocation is a safe-side operation, the same line as not delaying `rotate_epoch` via four-eyes); instead the obligation is surfaced to members-or-above of that environment via rotation-needed detection (AUDIT_SPEC §4.1's `revoke_device` variant) and `project verify`'s un-converged-obligation warning, and the CLI shows the person "who to ask to rotate"
- **Backfill on device addition (2026-09-19 DK)**: `add_device`'s actor (a device of the same person) wraps, for each environment of the new device's effective scope, the DEKs of **all epochs** to the new device's enc public key and registers them (AUTH_SPEC §12-6's additive path — same shape as the post-`add_member` backfill. Including the reserve key [cap (owner, all)]). The actor is a device of the same person and holds those DEKs ("the wrap's executor = a DEK holder"). Even a reader's device can register its own backfill (AUTH_SPEC §12-3 — when every recipient is the person's own device key). When an approver performs the backfill of a four-eyes-routed application (`add_member` / scope enlargement), the destinations are the target's **all devices** (per R(E))
- **Rotation-needed detection (a product feature)**: on member removal, compute from the audit log the variables that member could read, raise an "upstream-credential rotation recommended" flag, and display it in the UI / CLI. A workflow compensates for the limit that cryptography cannot un-read an already-read value

## 8. The reserve-key wrap ledger (recovery code, passkey PRF, guardians, handoff)

**2026-09-12 revision (KL3)**: the former §8 "Recovery code" is generalized into **the set of per-recipient wraps of the same master-key blob (a ledger)**. The recovery-code path's structure, byte strings, and test vectors (`recovery-wrap.json`) are **unchanged**; this revision only adds paths (no re-wrapping or migration of existing blobs). The design record is docs/notes/integration-options.md supplement 19.

**2026-09-19 revision (DK — former title "master-key wrap ledger")**: the ledger's wrap target B is a blob of the **reserve key** (§3 — a device key whose private key lives only on the ledger). The old "master key" split into the device key (placed on a daily-use device) and the reserve key (placed on the ledger), and the ledger guards only the latter. The ledger's structure (classes S / G / H), the AAD (including the domain string `master-wrap` — byte-compatible), the shares, the handoff request / approval payloads, and `recovery-wrap.json`'s byte strings are unchanged. What changes is (1) B's meaning, (2) the **removal** of the handoff's old-device path (`kind = "device"` / `source = "device"`) (it cannot exist since daily-use devices don't hold B — device addition is carried by §6.2's `add_device`), (3) guardian shares being sealed to **each device key** of a guardian, and (4) **the reserve key being required to be opened** for any ledger change (adding a wrap, re-issuing, naming guardians) (since the reserve key lives on no device, the client first opens B via the code or a passkey, then builds the new wraps. At the first key generation, the device key and the reserve key are generated together and the recovery-code wrap plus any passkey wraps are built on the spot). The design record is docs/notes/dk-design.md ruling DK-G.

### 8.1 Shared provisions

- **The wrap target B**: an opaque blob of the reserve key (enc / sig) (2026-09-19 DK — formerly: the user master private key). Its serialization format is the client's (CLI's) contract; the server isn't concerned (currently = the keychain record's JSON. On top of a device-key record's fields, a B the client generated as a reserve key carries `"kind": "reserve"` (2026-09-26 K16 — recording the fact of generation. Being inside the AEAD, the server can't create, erase, or swap it. A client doesn't record or revoke a B lacking it — e.g. a pre-DK device-key duplication — as a reserve key; it separates reserve keys. A device's store [the keychain] doesn't accept a record carrying this field. Cryptographic operations, the AAD, and wire formats are unchanged. The design record is docs/notes/dk-design.md §21). The restoring side uses it **only to issue device keys** after passing self-verification — never placing it into a daily-use store)
- **Recipient classes**: (S) symmetric KEKs — `recovery-code` / `passkey-prf`. (G) guardian groups — `guardian`. (H) handoff — the ephemeral recipient (a response scope carrying a guardian's approval to the requester — holds no persistent ledger row. Same as §9.1 lease wraps)
- **The wrap** (shared by classes S / G. The old "H's device migration" was removed in 2026-09-19 DK — 8.4): AES-256-GCM, 96-bit random nonce (stored beside the ciphertext). The AAD, in §2.1 encoding:

  ```
  master_wrap_aad = LP("maruhi/v1/master-wrap", user_id, kind, wrap_ref, mode)
  ```

  `kind` ∈ {`passkey-prf`, `guardian`} (`device` was removed in 2026-09-19 DK — 8.4). `wrap_ref` = passkey-prf: `wrap_id` / guardian: `group_id`. `mode` = guardian only, `any` | `all`; the empty string otherwise. **Exception: `recovery-code` keeps former §8's AAD `LP("maruhi/v1/recovery-wrap", user_id)`** (preserving byte compatibility. Not used for the new paths)
- Every wrap / share is opaque to the server, and no KEK material (the recovery code, the PRF output, share plaintexts, the ephemeral private key) appears in any API payload. Portability to another user or context fails at decryption via the AAD / info binding (design principle 3)
- **The prerequisite of fetching**: in every class, fetching a wrap / share is limited to the authenticated person themself (or a handoff approver) (the double defense of authentication + key material — same as former §8). Fetch endpoints are rate-limited (AUTH_SPEC §13-8)

### 8.2 Symmetric-KEK recipients (class S)

- **recovery-code** (former §8 unchanged): a 256-bit random value generated at signup. The display form is a grouped human-readable Base32 string, which the user stores safely. `KEK = HKDF-SHA256(recovery_secret, salt = empty (length 0), info = "maruhi/v1/recovery")`. The grounds for the empty salt (RFC 5869 §3.1 — when the IKM is already uniform-random, salt may be omitted; use separation is carried by info), no stretching needed because it's a high-entropy random, the Argon2id clause (if a passphrase-derived key is ever introduced, Argon2id is mandatory = requires revising this specification), and re-issuance = generate a new code → re-wrap → delete the old wrap, are all unchanged. The key-loss flow is unchanged too (device addition is §6.2's `add_device` after 2026-09-19 DK and outside this section): **first establish a session on the new device via GitHub authentication**, then on that authenticated session fetch the wrapped reserve key → enter the recovery code → derive the KEK → decrypt (→ per §3, `add_device` a new device key and erase the reserve key's secret from the device). **No passphrase-derived KEK is introduced even in KL3** (supplement 12 L4-a)
- **passkey-prf** (new): takes `prf_out` (32 bytes. The authenticator's HMAC-SHA-256 output, uniform-random) of the WebAuthn PRF extension (CTAP2 hmac-secret) as the IKM:

  ```
  prf_out = PRF(credential, eval.first = prf_salt)
  KEK     = HKDF-SHA256(prf_out, salt = empty (length 0), info = "maruhi/v1/passkey-prf")
  ```

  - `prf_salt` is **a 32-byte random generated per registration**, placed beside the ledger row as a public parameter (same treatment as credential_id / rpId). Why not a fixed string: a fixed salt would make the KEK a fixed function of the credential, so a once-leaked KEK would open wraps re-registered later. With a random, re-registration = a new KEK — the same semantics as recovery-code's "re-issue → delete the old wrap"
  - The grounds for the empty salt are the same as recovery-code's (prf_out is a uniform-random 256-bit). Use separation is carried by info. No stretching needed
  - PRF is **obtainable only in a browser**. It is obtained on a localhost page distributed by the CLI (`127.0.0.1`, rpId = `localhost`), and the PRF output is handed to the CLI process via a single loopback POST (ADR-0018: the hosted Web has no code path for keys / wraps). Never obtain the PRF on the production-served Web. Authentication between the page and the CLI (a one-time token + an Origin check) follows ADR-0018 decision 2's requirements
  - A user may hold multiple passkey-prf wraps (multiple authenticators). Each row is independent (identified by wrap_id)

### 8.3 Guardian groups (class G)

B is sealed to the public keys of guardians the ward (the person) named. A path where "even after losing both the key and the recovery code, restore works via a guardian + the person's account authentication".

- **A group**: `group_id` (a random ULID), `mode` ∈ {`any` (1-of-n: any one suffices), `all` (n-of-n: everyone needed)}, a group KEK = a 256-bit random. B is wrapped by 8.1's AES-GCM binding `kind = "guardian"`, `wrap_ref = group_id`, and `mode` into the AAD
- **Shares** (share_index = 1..n):
  - `mode = any`: every `s_i = KEK`
  - `mode = all` (n ≥ 2): `s_1 … s_{n-1}` are independent 32-byte randoms and `s_n = KEK ⊕ s_1 ⊕ … ⊕ s_{n-1}`. Restore XORs all shares. Any n−1 shares are independent of KEK (the standard form of information-theoretic n-of-n secret sharing). **No k-of-n (Shamir etc.) is introduced** (a new primitive). Nested HPKE (sealing under A then under B) isn't taken because it's sequentially dependent and approvals can't run in parallel
- **Sealing a share**: HPKE Base mode one-shot Seal (the same primitive as §5). The recipients = the guardian's **currently valid device keys'** enc public keys (the same keys that receive DEK wraps — 2026-09-19 DK, the chain-derived device set of §6.2. The same `s_i` is sealed once per guardian's device: info doesn't include the device, but the recipient keys differ so they can't be opened crosswise). The plaintext = `s_i` (32 bytes). aad is empty; info is

  ```
  guardian_wrap_info = LP("maruhi/v1/guardian-wrap", user_id, group_id, mode, share_index, guardian_user_id)
  ```

  The domain string makes it mutually non-transplantable with §5 `dek-wrap` / §9.1 `lease-wrap` / 8.4 `handoff-wrap`. Including `mode` in both the AAD and info drops a server's `any` ↔ `all` swap (making the requester compute an n-share XOR / misleading them that 1 share suffices) into a decryption failure
- **The authenticity of guardian keys**: a guardian is chosen from the ward's shared-project **chain-derived current members**, and their enc public key is taken from the chain (the payloads of add_member / genesis / add_device — §6.2's device set). Key confirmation follows §6.5's "fulfillment forms of explicit confirmation" (the read-aloud ceremony / flags / a verified-fingerprint-book hit + yes). No global public-key directory is built (§6.5). The ledger keeps the guardian's user_id and the device's key FP beside each share, and the client cross-checks them against the guardian's current device set (chain-derived) — if every sealed-to device has been revoked / renewed, it warns of the mismatch (STALE) (2026-09-19 DK) — under `all`, one person's mismatch makes the group unrestorable. A guardian adding a device doesn't carry existing shares along (the ward re-creates). **When a guardian's device is revoked (`revoke_device`)**: the sealed `s_i` remains on that device (§7's revocation obligation is rotating DEKs and doesn't include shares). A single share can't open B — the group's wrap is fetchable only by the ward themself (AUTH_SPEC §13-7), and an approval requires the ward's handoff request and the ward's account authentication — so the residue folds into the same line as §14.3-8's collusion (an intentional residue; without threshold sharing, share whereabouts aren't collected at device revocation). The ward's client warns if even one sealed-to device is revoked (SHOULD — not waiting for all devices' revocation) and **proposes** re-creating the group (not an obligation — re-creation is opening the reserve key = requires the ceremony. 2026-09-20 K1 review handling, design record §6 K1-13)
- **No guardian consent procedure in v1**: naming is the ward's sole operation. Since a restore requires the guardian's active approval (8.4), the only thing an unconsented naming causes for the guardian is "a ward appears in their own ledger". A consent signature (an invite-style handshake) is a candidate for a future revision
- Deleting a group = the ward's sole operation (deleting the row. Old shares vanish). Replacing a guardian is delete → re-create

### 8.4 Handoff (class H — guardian approval)

A response-scope mechanism that "re-seals a share to the requester's ephemeral public key and hands it over". The approver is **only a guardian** (2026-09-19 DK — the device-migration item of the former "a shared mechanism for device migration (the old device approves) and guardian recovery" was removed: since a daily-use device doesn't hold B, an old-device approval can't exist. The request / approval payload forms are unchanged). **Device addition is outside this section** (§6.2 `add_device` — carries no secret). A restore from total device loss is: a device that obtained the reserve key B through this section's path signs `add_device` with the reserve key to register its own new device key, then erases the reserve key's secret from the device (§3).

- **The ephemeral key E**: an X25519 keypair the requester (the restoring device) generates in memory. Never persisted. Dies with the requester process
- **request_id**: `lower_hex(SHA-256(LP("maruhi/v1/handoff-id", E_pub_hex)))`. Requester and approver can independently compute the same value
- **The handoff code (a client spec)**: `E_pub (32 bytes) ‖ the first 4 bytes of SHA-256(E_pub)` Base32-encoded (RFC 4648 alphabet, no padding) (displayed grouped. The display form is pinned by a test vector). **The code is carried by a human** (copy-paste between the same person's devices; out-of-band to a guardian). **The server neither relays nor stores E.pub**: the approver obtains E.pub and request_id from the carried code. This makes a server's swap of the receiving key structurally impossible and removes the need for a 12-word check ceremony (§3's "no shortening to a shorter code" — the situation where the attacker chooses one of the keys — doesn't arise). The code is public information (a public key), not key material
- **Approval**: the approver Seals a 32-byte value `v` to E.pub via HPKE Base mode one-shot (empty aad; info below). **One approval per request_id per (approver, source)**

  ```
  handoff_wrap_info = LP("maruhi/v1/handoff-wrap", user_id, request_id, source, share_index, approver_user_id)
  ```

  - **A guardian's approval**: `v = s_i` (fetch their own share from the ledger → Open it with their device key's enc key → **on the spot** Seal it to E.pub. The share / B is never stored). `source = group_id`, `share_index` = their share number, `approver_user_id` = the guardian's user_id (the FP of the device key used to approve is placed beside the approval row — AUTH_SPEC §13-6)
  - **Revision note (2026-09-19 DK)**: the old "old-device approval (device migration)" — `source = "device"`, `share_index = 0`, co-sending a `kind = "device"` wrap of B under `KEK_h` — was removed. There is no `source = "device"` and no blob column on the approval row (AUTH_SPEC §13-7 doesn't accept it)
- **The requester's assembly**: for each received approval, obtain the KEK per that group's `mode` (any: any one share; all: the XOR of all n shares), and open the group's wrap fetched from the ledger (the single form — 2026-09-19 DK). The obtained B is used **only to issue device keys** after passing self-verification (key consistency) (§3 / 8.1 — never placed into a daily-use store)
- **Identity confirmation before approving (normative)**: before approving, a guardian confirms **out-of-band** (a call etc.) that the requester is the ward themself. The server shows the approver the request's ward (the user_id and a display snapshot), but that is a display, not a proof (even if the server shows a false ward, the info's user_id binding keeps anyone but the legitimate requester from opening it — fail-closed). Approvals, PRF fetching, and restores are ceremonies, and are refused in AI-agent environments / non-interactive terminals (ADR-0016 decision 7's existing gate)
- **Validity**: a request expires at the drafted value of 15 minutes; approvals disappear from the server together with the request (response scope — never entering the persistent ledger). The requester may delete the request after success

### 8.5 Prohibitions (this section's scope)

- Never emit a KEK, a share, an ephemeral private key, or B's plaintext to disk, logs, or error messages
- Passphrase-derived KEKs (the Argon2id clause — 8.2)
- k-of-n threshold sharing, custom key-agreement / confirmation protocols (incl. SAS shortening)
- An implementation distributing a handoff's E.pub to the approver via the server (the code is carried by a human)
- **Keeping** the reserve key's private key in a daily-use device's store (the keychain, agent memory) (2026-09-19 DK — it lives in memory only during a restore or a ledger change; erase it when done)
- Sealing the reserve key with a device-bound sealer (SE / TPM etc.) (2026-09-19 DK — a restore must be possible from any device: the ledger only)

## 9. Selective disclosure (the server key)

- The server (deployment) holds its own X25519 keypair. The private key is stored in Workers Secret (self-hosted: inside the user's own account)
- **The server-key fingerprint (decided 2026-08-02)**: the first 16 bytes of `SHA-256(the server's enc public key (32B))`. Since the server holds only an enc key, §3's user FP definition (enc ‖ sig) doesn't apply. Chain verification checks this FP against the in-payload public key
- By default, no project's DEK is wrapped to the server (= pure E2EE)
- When a project owner enables a server-driven feature (e.g. GitHub Actions sync), the client records `grant_server` on the chain and wraps the required epoch DEKs — per the grant scope (which may include a subset of environments) — to the server public key
- Disabling is `revoke_server` + `rotate_epoch`
- The UI / CLI constantly displays "this project is disclosed to the server"
- **The server-key check at grant execution (drafted 2026-08-12)**: the grant_server execution UI / CLI word-displays (§3) the fingerprint of the server-distributed enc public key and requires an explicit confirmation of its agreement with the deployment's public config (AUTH_SPEC §4 — `/auth/config`'s `serverKeyFingerprintHex`). The authenticity confirmation required of member keys (§6.5) is not exempted only for the server key — a grant is the operation making the server "member N+1"
- **The HPKE info for server-destined wraps (drafted 2026-08-12)**: for persistent wraps addressed to the server (§7's rotation, the post-grant backfill), §5's info uses **the server-key fingerprint (lowercase hex)** in the recipient_user_id position (the server has no user_id. Pinned by §11's vectors)
- In the MVP (Phase 1) this feature itself isn't implemented (only the data structures are reserved as spec) — **implemented in Phase 2 together with §9.1 (drafted 2026-08-12. The acceptance surface is AUTH_SPEC §12-4 / §12-6 / §14)**

### 9.1 Workload leases (drafted 2026-08-12 session 22)

A mechanism distributing a grant_server'd project's DEKs to a workload without long-term credentials (v1 = a GitHub Actions CI job) as **response-scope ephemeral-key wraps**. The API surface and OIDC verification rules are AUTH_SPEC §14. **The server's role is not "the decryptor of values" but "the DEK broker"** — on the lease path the server never decrypts variable values (only unwraps and re-wraps DEKs addressed to itself).

- **The lease wrap**: an HPKE Base mode one-shot Seal (the same primitive as §5). The recipient is the ephemeral X25519 public key the workload generates in memory and discards when the job ends
- `info` (mandatory): `"maruhi/v1/lease-wrap" || project_id || environment_id || epoch || claims_digest_hex` (§2.1 encoding)
- `claims_digest_hex = lower_hex(SHA-256(LP("maruhi/v1/lease-claims", issuer_url, subject, audience)))` — the verified OIDC token's issuer / sub / aud. The server and the workload independently compute the same value, and reusing a lease response in another workload's context fails decryption (the consistent application of design principle 3)
- **A lease wrap is never persisted**: it doesn't enter dek_wraps (AUTH_SPEC §12-6) and exists only inside the lease response. §6.3's "DEK wrap destinations must exactly equal the chain's current members + valid grant_servers" (the ghost-member ban) is **a rule for the persistent wrap store and client-generated wraps**, and lease wraps (server-generated, response-scoped, within the grant's range) are outside it — under this boundary the two rules coexist without contradiction
- **The chain is the source of truth for authorization**: which workloads may obtain a lease (issuer / audience / claim constraints) is the grant_server payload's lease_policy (§6.2) — owner-signed, append-only, verifiable by every member. Not a server-mutable setting
- **The receiving workload's verification obligations (mandatory)**: before using a lease response, (1) chain verification (§6.3. project_id = the genesis hash is pre-fixed in the workload's configuration), (2) the repository anchor's containment / non-regression check (§6.3 out-of-band anchor (b) — SHOULD), (3) the DEK commitment cross-check (§5.2), (4) value-signature and meta-statement verification (§4.1 / §4.2 / §6.3), (5) **environment-manifest and checkpoint-consistency verification (§4.3 / §6.3 — 2026-08-18)**: the manifest's digest recomputation and epoch consistency, and the non-regression checks of manifest / value snapshot against the chain-derived latest checkpoint. A workload is a floorless first-sync class (§14.3-3); (2) carries the chain head's freshness and (5) the data layer's completeness / currency (up to checkpoint time) under that head
- **Replaying an OIDC token within its validity (added 2026-08-15, owner ruling the same day — the design comparison and rejected options are docs/notes/session-24.md)**. What `claims_digest` binds is issuer / subject / audience; neither the workload's ephemeral public key nor a nonce is included. So at the cryptographic layer alone, **someone who obtained a copy of a still-valid OIDC token** (network capture, a malicious workflow step, a log leak) can request a lease **under their own ephemeral key** and receive a legitimately re-wrapped DEK — the lease wrap itself has no means to distinguish "the legitimate job" from "a holder of the token's copy" (what this section guarantees is that "a lease response can't be **transposed to another workload identity**", not preventing bearer replay under the same identity). This residue is closed by **the server's first-come binding** (AUTH_SPEC §14-1: at issuance, recording "binding key → the presented ephemeral public key" and refusing a re-claim with the same token + a different key) — the cryptographic construction (the lease wrap, claims_digest) doesn't change. **The binding key is the hash of the JWS signing input (`header.payload`), not of the raw token**: the raw token's signature segment is malleable outside the signature's protection (base64url trailing bits / ES256 s-malleability), and keying on the raw token would void the binding via a one-character edit that changes only the hash without changing signature verification or claims_digest (2026-08-15 pullfrog review. Details in AUTH_SPEC §14-1). And since the binding crosses all environments of a project per token, a workload leasing multiple environments with one OIDC token must present the same ephemeral key on every request (AUTH_SPEC §14-1). The proof-of-possession the ruling didn't take (mixing the ephemeral public key's hash into the requested `aud`; the same shape as IETF WIMSE's WIT/WPT now in standardization) was deferred because it structurally doesn't work with issuers that fix the audience at token-issuance time (GitLab etc.) (preserving issuer generality — session-22 §2 R1. Re-ruled when issuers can issue key-bound tokens). **The shrunken non-guarantees (v1)**: (1) first-come use of a token stolen **before its first use** (the legitimate job detects it as a `token-replayed` failure — exposure is "until first use", not the full `exp - iat` width), (2) cross-project first-come when **multiple projects' lease_policies permit the same workload identity**, due to the binding state being per-project. Same character of description as §14.3's non-guarantee list
- **Guarantee implications**: §14.2's guarantees are unchanged after the lease path's introduction — a compromised / malicious server can lose **confidentiality** within the grant scope (the grant's definition itself), but **cannot inject forged values into a workload** (a value signature's writer is a member on the chain, and the server can't sign). Compared to the "copy plaintext secrets into CI" sync pattern, no attack surface exists in the write direction (poisoning the CI environment)
- Variable-granularity leases ("only this variable") can't be expressed under v1's key hierarchy (DEKs per environment × epoch) and are left as a Phase 3 task (ROADMAP: DO-based leases)
- Test vectors: `test-vectors/lease-wrap.json` (§11)

## 10. API-boundary invariants

- No plaintext secret value, DEK, or device-key / reserve-key private key (2026-09-19 DK — formerly "master private key") appears in any API payload
- On the API schema, a secret value is expressed only as the `EncryptedPayload` type (the fields' normative definition is AUTH_SPEC §12-2 — on top of suite / AAD components / nonce / ciphertext, it includes §4.1's signature block since 2026-08-03)
- The server only stores / distributes ciphertexts, enforces access control, and stores the chain (except the sync processing of grant_server'd projects)

## 12. Prohibitions

- Inventing custom crypto protocols or custom modes
- ECB, CBC (unauthenticated), static nonces, key reuse (across purposes)
- Logging private keys, DEKs, or plaintext values (incl. in error messages)
- Recording provider IDs or email addresses on the chain / audit log
- Applying the §5.2-style hash commitment to low-entropy values (its secrecy depends on the input entropy. A commitment's target is only uniform-random 256-bit key material)

## 14. Guarantees and non-guarantees of data authenticity (drafted 2026-08-03 session 12)

The normative summary of "what each mechanism of §4.1 / §4.2 / §5.1 / §5.2 / §6 proves and what it doesn't". The detailed threat analysis, design comparison, and rejected options are docs/notes/session-12.md. Phase 2's pre-release threat-model document (ROADMAP) builds on this section.

### 14.1 Decomposing the security goals

The following properties are independent and must not be conflated:

| # | Goal | Meaning | The mechanism carrying it |
|---|---|---|---|
| G1 | Attribution | Whose key signed this data | The signatures of §4.1 / §4.2 / §5.1 + the user_id baking |
| G2 | Authorization time | In which chain state the signer held the required role | §4.1 / §4.2's head binding + §6.3's declared-head-time role verification |
| G3 | Content authenticity | Whether the ciphertext / DEK / metadata was altered after signing (commitment) | §4.1 / §4.2's full enumeration of the signed content, §5.2's commitment |
| G4 | Context binding | Non-transplantability outside project / environment / epoch / variable / version / recipient | The AAD (§4), HPKE info (§5), the coordinate enumeration of every signed content, §5.2's coordinate-bearing pre-image |
| G5 | Freshness | Detection of rollback to old legitimate data | §6.3's local floor (SHOULD) + out-of-band anchors (the chain head) + checkpoint consistency (§6.2 / §6.3 — the data layer. 2026-08-18). A client holding neither anchor nor floor has no mechanized guarantee (14.3-3) |
| G6 | Completeness | Detection of omissions of values / updates / chain entries | The chain: prev_hash + seq continuity. Values / meta: the prev chain (the known range) + the local floor + **the environment manifest's digest (§4.3 — set-omission detection) + the checkpoint's value snapshot (§6.3. 2026-08-18)** |
| G7 | Fork resistance | Detecting a split view distributing a different "legitimate" history per member | Evidence-ification (the prev chains, head bindings, **signed head declarations §6.6**) + head gossip's mutual cross-check (§6.3 — avoidable via the server's omission, so **not guaranteed**. 2026-08-18). Composition with an out-of-band anchor (an external agreement point) narrows the residue (14.3-4) |
| G8 | Availability | Resilience to the server refusing responses / deleting / delaying | **Not guaranteed** (even when detectable, it can't be prevented) |
| G9 | Plaintext correctness | That a writer wrote the "correct" value | **Not guaranteed**. Provable only up to "a writer holding legitimate permission wrote this ciphertext" |

### 14.2 Guarantees (assuming the client performs every §5.2 / §6.3 verification)

All relative to "the chain view the client verified" (that view's own freshness is G5/G7's territory):

1. **The impossibility of injecting a fake DEK**: a DEK not matching the commitment of (environment, epoch) on the verified chain is refused before use. Even a server colluding with any key holder along the chain's history can't inject a self-made DEK into a real epoch (SHA-256 collision resistance). Wrap tampering / poison wraps degenerate into an availability problem (G8)
2. **The boundedness and attribution of value / metadata forgery**: a value passing verification is limited to one signed by the holder of "a sig key of a member who held the required role at some point on the chain", against a declared head within that key's membership interval and a coordinate of the then-current epoch. A metadata statement passing verification is likewise limited to a signature against a declared head inside a membership interval (carrying no epoch coordinate — §4.2). In both, the attribution (user_id + key FP) is fixed unforgeably. The server alone can forge neither values, names, nor DEKs
3. **The soundness of the current epoch**: under operation where member removal, demotion below member, and scope shrinkage are accompanied by rotating all environments of the target's scope (§7 — the 2026-09-14 ES revision), a key that lost its write qualification (a removed member, a demoted member, a leaked old key) cannot forge a current-epoch value or a current-epoch DEK (G2 + epoch consistency §6.3-4 + §5.2)
4. **The authenticity of name ↔ ID correspondences**: rewriting the name ↔ variable_id / environment_id correspondence is possible only within the range of signed statements by a key holder holding (or having held) the required role, and attribution remains. Server-side correspondence swapping or unsigned renames are refused at verification. **The meta layer's freshness is supplied by the environment manifest's (§4.3) epoch baking (2026-08-18)**: a key that lost its write qualification (removed, demoted, a leaked old key) cannot sign a current-epoch manifest (§7's rotation obligation [all environments of the target's scope — 2026-09-14 ES] + the manifest's epoch-consistency verification), so the meta forward-injection residue shrinks to a form symmetric with values (14.2-3) — 14.3-5's (i)(ii)(iii) (resolving the old asymmetry "meta has no epoch anchor")
5. **Evidence-ification of forks and swaps**: two valid signatures with different content at the same coordinate (variable × version, meta_version, or manifest_version), a binding to a head not present in one's own view, and a signed head declaration (§6.6) contradicting one's own view become cryptographic evidence of server equivocation or key leakage (undeniable)
6. **Data-layer completeness and currency up to checkpoint time (2026-08-18 — §6.2 / §6.3)**: when the verified chain contains a `checkpoint`, a distribution passing the checkpoint-consistency verification hasn't rolled back from the meta state (manifest) / value state (snapshot) at checkpoint-issuance time. **This guarantee is relative to "the chain view the client verified"** (per this section's opening): the chain head's own freshness is carried by the floor / out-of-band anchors, and a client without them retains 14.3-3
7. **Detection material for post-hoc audit-log tampering (2026-08-18 — §6.2, AUDIT_SPEC §6)**: the audit cumulative hash notarized in a checkpoint makes a post-hoc tampering / deletion of the audit rows within the notarized prefix detectable as a contradiction with the recomputation by an admin who can read all rows (undeniable, being signed and on-chain). An admin's cross-check verifies, on top of membership, **the monotonic advance of the notarized position** (≥ the position of the preceding checkpoint's mirror row — AUDIT_SPEC §6), also detecting a stale-replay that keeps returning an existing old cumulative hash (freezing the protected prefix). Falsehood at record time (the server writing fake rows from the start, or not writing them) is a non-guarantee as before (the audit log is server-managed data — AUDIT_SPEC §6's threat model is unchanged)
8. **The verifiability of required satisfaction (presence) (2026-08-30 session 46 — §4.2 layout v2)**: since the schema fields (type / required / description) and the `declared` status ride on signed statements and automatically inherit manifest coverage (§4.3), "are all of this environment's required variables set (active)" is decidable by **every** verifier — including clients that can't decrypt values — from the verified statement set alone, **without depending on a server declaration**. The server's room to falsely claim "a value exists" is squeezed by the active-statement value-distribution requirement (§6.3), and its room to falsely claim "no value" by omission detection (the manifest's digest + checkpoints)
9. **The key-distribution guarantee of environment scope (2026-09-14 — ES)**: for an environment E not contained in member m's scope on the verified chain, no DEK wrap of E addressed to m is generated by a spec-conforming client or accepted by a spec-conforming server (§6.3 / AUTH_SPEC §12-6). Even if the server is compromised, no material exists that hands E's DEK to m. **Not guaranteed**: revoking the DEKs / plaintexts acquired while in scope (§1 principle 5 — compensated by the rotate obligation at shrinkage / removal and rotation-needed detection), and the concealment of plaintext meta (existence, names, schema fields) (open item #3)
10. **The four-eyes application guarantee (2026-09-14 — PF1)**: in a project with the policy in effect, a target op applies only on an entry sequence whose distinct-owner signatures (proposal + approvals) reach the required count (§6.2). A leak or rampage of one owner's key doesn't apply a target op. **Not guaranteed**: collusion of owners at or above the required count, a project with the policy off (the default), and non-target ops. Owner-identity addition (`add_member` / `change_role` establishing an owner) and policy changes are always four-eyes targets regardless of the `ops` enumeration (§6.2), so the path where a single owner adds identities to reach quorum is closed — however, the same-personhood of owner identities existing before the policy's enablement is not verified (a person already holding 2 identities at enablement is outside four-eyes). **Availability (2026-09-14 pullfrog review handling)**: while the policy is in effect, the on-chain current-owner count never falls below `required_approvals` thanks to the reachability invariant (§6.2), but if the number of **owners able to sign** (owners holding keys and cooperating) falls below `required_approvals` (permanent key loss, departure — still owners on-chain), the remaining owners can complete none of adding an owner, removing / demoting the missing owner, or changing the policy, and **target ops and the policy change become unrecoverable** (the data plane — push / rotate / create_environment — keeps running. No break-glass time lock is placed because it would conflict with principle 6 and the treatment of timestamps). Mitigation is an operational premise: enabling is recommended at current owner count ≥ `required_approvals` **+ 1** (a spare owner), and the CLI guides this condition and each owner's recovery registration (§8) at enablement (the consensus-rule enablement condition stays ≥ — owner ruling under approval item 17)
11. **The guarantee of per-device revocation (2026-09-19 — DK)**: for a device key d revoked by `revoke_device` (seq s) on the verified chain, no DEK wrap of an epoch after s is generated addressed to d by a spec-conforming client or accepted by a spec-conforming server (§6.2's R(E) / AUTH_SPEC §12-6). Signatures by d of values / meta / manifests / declarations declaring heads after s, and chain entries / four-eyes votes by d after s, are refused by every verifier. The person's (user_id's) membership, role, scope, and other devices are unaffected (no re-invite or re-vote needed). **Not guaranteed**: revoking DEKs / plaintexts d acquired before revocation (§1 principle 5 — compensated by §7's rotate obligation and rotation-needed detection), automatic revocation of devices d registered via `add_device` before revocation (visible on the chain as "added by d" — a revoker revokes them in bulk in the same entry), anything beyond **pre**vention of creating devices above cap monotonicity (a stolen device can create devices at or below itself), and **the revocation of that device's API tokens** (a token is a credential independent of chain facts — AUTH_SPEC §6. `revoke_device` alone leaves the revoked device able to authenticate with its token until the token's expiry [default 90 days, up to 365 at issuance, changeable on self-host — AUTH_SPEC §6], reading ciphertexts, plaintext meta, and self-information [it can't open values since post-revocation epoch DEKs don't reach it]. The client proposes targeted revocation of that device's tokens at revocation [SHOULD], and immediate cutoff from the Web is carried by token revocation — 2026-09-20 K1 security-review handling, design record §6 K1-15)

### 14.3 Explicit non-guarantees (v1)

1. **Availability (G8)**: a malicious server can refuse responses, delete data, or selectively delay. Repair paths and warnings exist, but prevention isn't possible
2. **Plaintext correctness (G9)**: a malicious (or mistaken) legitimate writer's wrong value can't be prevented. Under E2EE the server can't verify values, and this is a design consequence
3. **Freshness / completeness toward a first-sync client holding neither floor nor anchor (G5/G6. The residue class was narrowed on 2026-08-18)**: to a client with no local floor, the server can distribute "an internally consistent old view" (a shortened chain + the values, statements, manifests, and checkpoints of that time). **Since a view rolled back with the chain makes a removed member look current**, 14.2's guarantees hold only in the sense of that view's point in time. Since the out-of-band anchors (§6.3 — invite links for new members, the repository anchor for workloads) provide the chain head's freshness and checkpoint consistency (§6.3) provides the data layer's completeness / currency under that head (**up to checkpoint time** — 14.2-6), **the residue shrinks to "a client holding neither floor nor out-of-band anchor"** — this class has no trust anchor and mechanized freshness guarantees are in principle impossible (head gossip's declaration cross-check adds detectability but is avoidable by the server's omission — 14.3-4). The full picture of the mitigations and the verification chain is in the session 27 notes §2 / §6
4. **Split view (G7)**: distributing a different internally-consistent view per member is **not guaranteed to be detected** (updated 2026-08-18): head gossip (§6.3 / §6.6) gives detectability via mutual cross-check of declarations and undeniable evidence-ification, but the server can selectively omit or stall declaration distribution (omission reduces to G8), so an actively malicious server can distribute per view "only declarations on the shared pre-fork prefix" and make the cross-check come up empty. Narrowing the residue is carried by composition with out-of-band agreement points (the repository anchor — every member / workload sees the same git history) and checkpoints; complete closure isn't a v1 goal
5. **The collusion residue**: the holder of a key whose chain history contains "a membership interval with role member or above" (a removed former member, a member demoted below member, a leaked old signing key) + the server can inject attributed fake values / fake statements **limited to coordinates inside that interval (values: the epochs of that time × the heads of that time. Meta: the heads of that time)**. There are two injection directions with different detectability:
   - **The backward direction** (swapping existing coordinates, combined with rollback): detected as a version / meta_version / epoch regression on the local floor, or a signed_bytes difference at the same version
   - **The forward direction** (an "append" injection forging the next version / meta_version / manifest_version after the real latest under old coordinates): needs no rollback or omission, and **isn't detected by signature / chain verification plus a naive floor (serial monotonicity) alone**. For values it is detected for a floor-holding client via epoch monotonicity (§4.1) + the floor's extended rule (§6.3's (c)). **For meta it is likewise detected for a floor-holding client via the environment manifest's (§4.3 — 2026-08-18) epoch baking + the epoch-consistency verification + the floor's manifest-version rule** (a fake meta statement alone falls on the manifest's digest mismatch; an injection with a fake manifest can only claim an old epoch): the old asymmetry "meta has no epoch anchor and isn't detected even by the floor" is resolved, and the meta residue shrinks to the same 3 as values — (i) a first-sync client without a floor (reduces to non-guarantee 3. With an out-of-band anchor, checkpoint consistency — §6.3 — even provides forward-injection detection via the epoch-baseline check [the checkpoint version of floor rule (c)]: only coarser than a returning client's floor in that the baseline is checkpoint time; the shape is the same), (ii) the window between remove / demotion and the completion of all-environment rotate (§7 makes it an obligation so it's short, but not a mechanized guarantee — a mechanism candidate is the session 12 notes §10-7. Kept as an independent task — session 27 notes §11), (iii) **a returning client whose epoch floor for that environment is older than the attacker's membership interval (= hasn't once pulled that environment since the interval ended)** (rule (c)'s baseline doesn't fire because it is ≤ the attack coordinate's epoch — the manifest-version rule has the same shape)
   - Note **a key holder not knowing the DEK (a signing-key-only leak) can't forge a decryptable fake value** (AES-GCM tag unforgeability degenerates a value injection into a decryption failure = an availability problem). Forging a meta statement / manifest needs no DEK, so this class can also forward-inject meta — with the same detectability as above (the manifest's epoch consistency + the floor)
6. **Leakage / un-revocation**: a member (readers included) can leak the DEKs / plaintexts they hold. Cryptography can't un-read an already-read value (a restatement of §1 principle 5)
7. **Declaration-to-value agreement (type / format. 2026-08-30 session 46 — §4.2 layout v2)**: agreement between the schema fields' var_type / description and the actual value is not guaranteed — under E2EE the server fundamentally can't verify it, and verification is only **an advisory check** by clients in contexts handling plaintext values (at push, at `maruhi run`). It is a subspecies of G9 (plaintext correctness); a signature proves only up to "the author declared this type". **Display discipline (normative)**: the UI / CLI displays a type as "declared", and must not display "verified" in a context other than the principal that performed the type check — required satisfaction (presence — 14.2-8) may be displayed as "verified from signed statements", and this asymmetry is exactly the guarantee's split (exploration-memo finding B, session-46 ruling CU)
8. **Collusion in guardian recovery and handoff (2026-09-12 — §8.3 / §8.4. 2026-09-19 DK revision: the approver is only a guardian — the old-device approval path was removed)**: if one guardian under `mode = any` (all of them under `all`) colludes with someone who obtained the ward's account authentication, they can restore the ward's reserve key (a restored reserve key can sign `add_device` as a cap-(owner, all) device key — post-exposure recovery is non-guarantee 10). A share left on a revoked guardian's device (§8.3) is on the same line — a share can't open B without the ward's account authentication. A guardian is a person the ward trusts as "that counterpart", and cryptography doesn't prevent this (one can also choose not to name guardians). An attack where the ward's account hijacker impersonates a guardian to obtain an approval is prevented only by the guardian's out-of-band identity confirmation (the server can't prove it). If the path carrying the handoff code is actively tampered with, the approval goes to the attacker's ephemeral key, but approval / wrap fetching requires the ward's account authentication (the condition is code tampering + account hijack combined)
9. **The invite-link path's residue (2026-09-13 — the §6.5 IV revision)**: the link key keeps the server from swapping the acceptance key, but **an attacker who can read the path the link is passed over** (a Slack DM etc.) can accept under their own key before the legitimate counterpart (it surfaces on the legitimate counterpart's side as an acceptance collision). The backing source (`github-signing-keys`) closes this beforehand, but not when the attacker can place their key on the counterpart's GitHub account (account takeover) or when the inviter misnames the destination login. Under backing source `none`, the fallback out-of-band mutual confirmation closes it. If the path is **actively** swapped (a valid link to the attacker's own project), the acceptor-side defense is the acceptor reading the inviter login the backing source shows (`--from` / yes). **An invite link is passed over a trusted person-to-person channel** (normative — AUTH_SPEC §15-3). This item moves to the threat-model document in H5
10. **Reserve-key exposure (2026-09-19 — §8 / DK)**: on a restore from total device loss, the reserve key B sits in the memory of the device performing the restore. If that device is compromised, so is the reserve key (cryptography doesn't prevent it — the recovery means is the post-restore `key reserve rotate` [registering a new reserve key + revoking the old one = the rotate obligation]). Not keeping the reserve key on daily-use devices (§8.5) limits the exposure opportunity to the moments of restore and ledger change
