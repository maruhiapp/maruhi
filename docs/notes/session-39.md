## 1. 裁定 AM: 鍵なし Web の全体形(静的最小 / 許可リスト全部 / 中間)

### 第 1 周

- **案 AM-a: 静的案内ページ最小形**(管理も `maruhi ui` へ。ADR-0018
  Consequences が要求した比較対象)— 運営の配信面が最小になり、認証済み面の
  XSS 爆発半径がゼロになる。しかしペルソナ分析(設計文書 §1)で P5
  (CLI を入れない関係者 — session-29 §4 の「鍵なしの管理画面を渡す」の相手)が
  構造的に切り捨てられ、ROADMAP Phase 2 の監査 UI(W2)の置き場も消える。
  `maruhi ui` は各人のローカルであり「CLI を入れない人」には届かない —
  (a) は P5 の需要を「CLI を入れさせる」に変換するが、それは reader role +
  読み取り画面で足りる相手に鍵と儀式を課す過剰要求
- **案 AM-b: 鍵なし管理画面(決定 1 の許可リスト全部)** — 招待リンク発行・
  トークン管理(発行含む)まで。発行系 2 種がいずれも credential の生成
  (改訂 1・5 項の指摘)であり、招待発行は加えてアンカー欠落問題(裁定 AN)を
  持つ。「復号不要」と「低リスク」の混同が残る
- **案 AM-c: 中間形 — 静的 + 認証済み読み取り + 失効系 mutation のみ** —
  発行系を除外し、mutation を「資格・可視性を減らす方向」に限定する

### 第 2 周(上位互換探索)

- AM-c の境界を場当たりの画面列挙でなく**原則**に昇格できるか: 「Web に置く
  mutation は失効・ログアウト(資格を減らす)のみ。資格の生成(招待発行・
  トークン発行)、警告の消去(rotation dismiss)、チェーン書き込みは置かない」。
  rotation dismiss をどちらに入れるかがこの原則の試金石 — dismiss は復号不要・
  credential 非生成だが、**クラス 1 の警告を全メンバーから消すガバナンス操作**
  (AUDIT_SPEC §3.3)であり、XSS が warning を黙らせる面になる。原則を
  「減らす方向のみ」と立てると dismiss は自然に CLI 側に落ちる — 例外リストが
  不要になり、将来の画面追加の判定も一意になる。採用
- **案 AM-d: (c) + 書き込み系を「確認つきなら可」に緩める** — 棄却:
  確認 UI は同じバンドルが描く(UI 契約の署名オラクル問題 — session-30 §1 —
  と同型の自己確認)。確認の有無は境界にならない

### 第 3 周(再点検)

- XSS 爆発半径の再評価(設計文書 §6): (c) の全損 = メタデータ閲覧 + 失効 DoS
  (回復可能)。**補正(PR #103 pullfrog レビュー指摘)**: 当初稿は「発行系・
  dismiss は構造的に不能」と書いたが、これは誤り — バンドル省略は同一オリジン
  XSS への境界にならず(XSS はセッション + 自前 CSRF ヘッダーで任意 fetch
  可能)、構造的に不能なのは値・鍵の復号 / 署名を要する操作(チェーン書き込み・
  push・メタ操作)/ maruhi トークン発行(device flow が GitHub トークンを
  要求)まで。招待発行・受諾・dismiss・リカバリーブロブ・DEK 削除・値付き
  pull は現行サーバーが**セッション主体に許している**。この評価の成立には
  サーバー側のセッション能力制限が必要 → 裁定 AT で設計に組み込む
- 縮退可能性: (c) は画面単位で (a) へ縮退可能(W1 のみで止めれば (a) そのもの —
  設計文書 §7)。ADR-0018 の「各段は独立に停止可能」の型を画面レベルでも保つ
- (a) を選ばない判断の可逆性: 認証済み画面の需要(P3〜P5)が実測で出なければ
  W2 以降を止めるだけで (a) に戻る。逆((a) から (c))は API gap の解消を
  伴い高い — 迷う場合は縮退可能な側に置くのが正しい

**選択: 案 AM-c**(境界原則込み)。ADR-0018 改訂 2・1 項に固定。

## 2. 裁定 AN: 招待リンク発行を Web から除外する(決定 1 許可リストの改訂)

### 第 1 周

- **案 AN-a: Web でも発行(アンカーなしリンク)** — 棄却: 招待リンクの
  フラグメント(AUTH_SPEC §15-3)は帯域外アンカー `h` / `s`(発行者の検証済み
  ヘッド)と相互確認材料 `if`(発行者鍵 FP)を運ぶ。鍵なし Web は検証済み
  チェーン状態も鍵も持たず、これらを埋められない。アンカーなしリンクを正規
  経路にすると、新メンバー(床なし初回同期 = CRYPTO_SPEC §14.3-3 の支配的
  残余)への巻き戻し・fork 配布の検出材料(§6.3 帯域外アンカー (a))を欠く
  第二級リンクが常態化し、受諾側 CLI も欠落を警告なしで受理する分岐を持つ
  ことになる(fail-closed の逆行)
- **案 AN-b: Web 発行 + サーバー申告ヘッドをフラグメントに埋める** — 棄却:
  アンカーの意味は「サーバーを経由しない検証済み値」であり、サーバー申告値を
  埋めた瞬間に検出機構として死ぬ(悪意サーバーが古いヘッドを申告すれば
  アンカーがそれを追認する — 毒化)
- **案 AN-c: 発行は CLI / `maruhi ui` のみ。Web は一覧・失効まで** — 発行は
  invite token(bearer capability)の生成でもあり、トークン境界(裁定 AO)と
  同じ「credential を生成しない」側に揃う

### 第 2 周(上位互換探索)

- **案 AN-d: AN-c + Web の招待管理画面に発行手順の案内(`maruhi invite create`)を
  静的に置く** — 導線の断絶(「発行ボタンがない」)を案内で埋める。コード
  パス追加ゼロ。AN-c の上位互換として採用

### 第 3 周(再点検)

- 一覧・失効の据え置きを確認: 招待の一覧・失効(AUTH_SPEC §15-2 — admin)は
  棚卸しと資格削減であり、AM の境界原則に適合。改訂 1 も「一覧・失効は
  据え置き」をトークン側で既に確立しており、招待側も同型に揃う
- ADR-0018 決定 1 の許可リストは「招待リンクの発行」を明示的に含むため、
  これは**決定の改訂**である — ADR 改訂 2 として提示する(蒸し返しではなく、
  改訂 1・5 項が開けた「credential 生成の再裁定」の招待版。アンカー欠落は
  改訂 1 時点で未指摘の新事実)

**選択: 案 AN-c + AN-d**。ADR-0018 改訂 2・2 項。

## 3. 裁定 AO: トークン境界(改訂 1・5 項の解消)+ L-2 の扱い

### 第 1 周

- **案 AO-a: Web に発行 UI(生値を発行応答で一度だけ表示)** — 棄却: 現状
  トークンは既定で全プロジェクト admin・無期限(AUTH_SPEC §6 / SECURITY_REVIEW
  L-2)。XSS が「自分で高権限トークンを発行して持ち出す」を 1 手にする —
  鍵なし Web が値を守っても、credential 生成面があれば攻撃者は値へ CLI /
  API 経由で到達する(境界の迂回)。生値が DOM に出る点も改訂 1・4 項
  (拡張混入)の面
- **案 AO-b: Web は一覧・失効のみ。発行は device flow(端末)のみ据え置き** —
  発行 API を**そもそも追加しない**(現状の唯一の発行経路 = device flow を
  維持)ため、attack surface の増分がゼロ。生値の存在場所が「発行時の端末
  表示 1 箇所」に固定される
- **案 AO-c: `maruhi ui` に発行 + DOM 生値表示** — 棄却: localhost でも
  ブラウザ拡張の content script は DOM に触れる(session-30 §2 — LNA は拡張に
  適用されない)。ターミナルの発行表示には拡張が触れない — この差が生値を
  DOM に出した瞬間に消える(session-29 §7-2 と同じ構図)

### 第 2 周(上位互換探索)

- **案 AO-d: AO-b + 生値の端末限定を `maruhi ui` にも明文化** — 第 2 段の
  設計に先回りして「トークン生値は ui の DOM に出さない(発行・表示は端末)」を
  ADR に固定する。改訂 1・5 項が明示的に裁定材料として要求した点であり、
  ここで決めないと第 2 段の設計に同じ未裁定が持ち越される。採用
- **案 AO-e: 発行 API を作った上で操作別契約(改訂 1・1 項)で ui からの発行を
  許す** — 棄却(今回は): 需要が未実測(ドッグフーディングは device flow で
  回っている)。必要になれば第 2 段の UI 契約設計で「発行を依頼し、生値は
  鍵保持プロセスの端末に表示」という儀式型の操作として追加できる(AO-d は
  これを妨げない — DOM に出さない規律だけを固定している)

### 第 3 周(再点検)

- **L-2(無期限)の扱い**: SECURITY_REVIEW の申し送りは「トークン管理 UI
  設計・仕様改訂と同時に」— 本裁定がその時点である。一覧 UI を設計する以上、
  一覧に並ぶ「無期限」の列を仕様が既定のまま放置する選択はない。AUTH_SPEC §6
  改訂に**既定 TTL(起草値 90 日)+ 再ログイン更新(同名ローテーション)**を
  含める。既存トークンへの遡及は実装 PR(W3a)の移行規則に委ねる(仕様は
  新規発行の既定を定める)。**補正(PR #103 pullfrog レビュー指摘)**: 当初稿の
  「CI 等の無人ワークロードはリースを使うため TTL は無人運用と衝突しない」は
  過大主張 — リース対応 issuer は v1 = GitHub Actions のみ(§14-1)で、
  GitLab CI / k8s / cron 等は PAT しか使えず 90 日ごとの人間介在が必要になる。
  §6 にこの限定を明記し、扱い(明示 TTL 指定〔上限つき〕か issuer 拡張か —
  無期限既定へは戻さない)を W3a へ申し送り
- 不足 API の確認: 現行 `POST /auth/token/revoke` は**提示トークン自身の失効・
  トークン主体限定**(CLI logout 用 — handlers-auth.ts)であり、セッション
  主体の Web からは使えない。一覧 API(生値・ハッシュを返さない)+ 指定失効
  (セッション主体または `*` × admin トークン — §13-2 の鍵素材条件と同水準)を
  §6 改訂で設計する(実装は W3a)。名前変更 API は作らない(同名再発行 =
  ローテーションで足り、追加の書き込み面を増やさない)
- 指定失効の権限水準の確認: 失効は資格を減らす方向だが、スコープ限定トークン
  からの「他トークンの失効」は可用性攻撃(CI 用トークンの窃取で作業用トークンを
  消す)になりうるため、§13-2 と同じ「セッションまたは `*` × admin」に置く

**選択: 案 AO-b + AO-d + L-2 の §6 改訂同時実施**。ADR-0018 改訂 2・3 項、
AUTH_SPEC §6 改訂。

## 4. 裁定 AP: 鍵なし Web でのチェーン検証の要否と表示規律

### 第 1 周

- **案 AP-a: Web バンドルに検証コード(@maruhi/crypto の verify サブセット)を
  入れ「検証済み」表示** — 署名検証は公開データのみで可能であり技術的には
  成立する。棄却: 検証者(Web の JS)とデータ配布者(サーバー)が**同一の
  運営配信ドメイン**にあり、悪意・侵害された運営はデータとバッジを同時に
  偽装できる — ADR-0018 Context の「配る側が悪意を持てる構造自体は消えない」と
  同じ論法で、バッジは検証の演出にしかならない。加えて crypto コードの
  バンドル同梱は供給網と監査対象を増やす(検証だけでも「crypto を含む Web」に
  なり、決定 1 の「復号・ラップのコードパスを含めない」の検査が
  「復号だけ除外した crypto サブセット」の検査に複雑化する)
- **案 AP-b: 検証を実装せず、全表示を「サーバー申告」として明示** — Web の
  信頼上の位置づけ(サーバーと同一ドメイン)を表示がそのまま語る形

### 第 2 周(上位互換探索)

- **案 AP-c: AP-b + 検証済み表示が要る場面は CLI へ誘導**(`maruhi project
  verify` / `audit verify` / `reconcile`)— 検証の需要自体は否定せず、検証が
  意味を持つ場所(ユーザーの機械・署名検証済みチェーン)へ導線を張る。採用
- **案 AP-d: サーバー申告表示 + 別チャネル検証(CLI が出すダイジェストと目視
  照合)** — 棄却: 目視照合の儀式を Web に増やすのは改訂 1・2 項(儀式は TTY)と
  逆行。照合するなら最初から CLI で見ればよい

### 第 3 周(再点検)

- FP 表示の規律を追加: Web に出る鍵 FP は監査・チェーン表示との突合用の
  **参照値**であり、相互確認(儀式)の照合材料ではない — 「この画面と照合せよ」と
  読める文言を禁止する(儀式の完全性は「表示された語 = 鍵保持プロセスが計算
  した語」に依存し、Web はそれを保証できない — 改訂 1・2 項の適用)
- セルフホスト(運営 = 自分)でも例外を作らないことを確認: バンドルは同一で
  あり、「セルフホストなら verified 表示」の分岐はホステッドとの挙動分裂 +
  決定 1 の「フラグで隠すだけの形は禁止」と同型の禁止形になる
- CLI の TCB 規律との整合: CLI は検証済みステートメント経由でしか名前を
  信用しない(AUTH_SPEC §12-2)。Web は同じデータを「未検証」と明示して
  表示する — 規律の**緩和**ではなく、検証者の不在を表示に正直に写す形

**選択: 案 AP-b + AP-c(+ FP 規律)**。ADR-0018 改訂 2・4 項、設計文書 §4。

## 5. 裁定 AQ: 監査 UI の可視性クラスと admin 限定 `seq` の表示

### 第 1 周

- **案 AQ-a: Web 側でも可視性クラスをフィルタ実装** — 棄却: 可視性の真実源は
  サーバー認可段(AUDIT_SPEC §7 — クラス 2 は admin 未満に存在しないかのように
  振る舞う)。クライアント側の二重実装は乖離のリスクだけを足す(隠すだけの
  形の逆パターン: サーバーが返したものを Web が隠す必要はない)
- **案 AQ-b: API の応答をそのまま写す。admin 応答の `seq` は表示する** —
  `seq` は C1 裁定で admin 応答限定になっており(row_id との使い分け —
  AUDIT_SPEC §7)、admin に見せるのは新情報ゼロ。`maruhi audit reconcile` の
  報告が seq を語るため、突合結果と画面の照合に有用
- **案 AQ-c: `seq` を Web では表示しない** — 棄却: reconcile との照合手段を
  消す割に得るものがない(admin はどのみち API・CLI で seq を見られる)

### 第 2 周(上位互換探索)

- **案 AQ-d: AQ-b + 完全性の非主張を明文化** — Web は欠番検査・ミラー突合・
  累積ハッシュ照合を**行わず**、「gaps なし」等の完全性表示もしない(検証は
  CLI の verify / reconcile — 裁定 AP と同じ線)。seq は生データの列として
  出すだけ。採用
- admin 未満向けの文言規律: 一覧の見出しは「あなたの role で可視のイベント」
  とし、不可視クラスの件数・存在を示唆しない(件数非漏洩 — AUDIT_SPEC §7 —
  の表示層での維持)

### 第 3 周(再点検)

- 監査 API の消費が Web セッションで CSRF・監査汚染を生まないことを確認:
  読み取りは監査行を書かない(var.read は暗号文配布のみ — AUDIT_SPEC §3.3)。
  メタデータのみ pull も記録なし。Web の閲覧がフォレンジクスを汚さない
- 本人軸(`GET /auth/audit/events` — S6 の本人ビュー)はクラス概念の外
  (本人行は常に可視)であり、規律の追加は不要

**選択: 案 AQ-b + AQ-d**。設計文書 §3 S6・§4。

## 6. 裁定 AR: 招待リンクを開いた人への静的案内ページ(AUTH_SPEC §15-3 改訂)

### 第 1 周

- **案 AR-a: フラグメントを解釈して role(`r`)等を表示する動的ページ** —
  棄却: (1) 解釈コードは「Web 受諾画面」への漂流の入り口(§15-3 の旧文
  「Web ダッシュボード実装時に同じ形式を解釈する」の縮小再生産)。(2) invite
  token(bearer capability)が自前コードの script 文脈に載る — location.hash は
  ページ上の任意スクリプトから読める事実は変わらないが、自前コードが触らな
  ければ自前コードの侵害・バグで漏れる経路は消える。(3) 受諾前の相手に
  見せるべき情報(role)は受諾クライアント(CLI)が儀式の中で表示する —
  ページ表示は儀式外の二重表示で、不一致時の優先が曖昧になる
- **案 AR-b: 完全静的(フラグメント非解釈)の案内のみ** — 「このリンクは
  maruhi CLI で受諾する: `maruhi invite accept '<このページの URL>'`」の
  静的テキスト。リンクの URL をそのままコマンドへ渡す案内は location 非依存で
  書ける

### 第 2 周(上位互換探索)

- **案 AR-c: AR-b + CLI 未導入者向けのインストール導線(docs へのリンク)** —
  静的リンクの追加のみ。P2(未登録・CLI 未導入)の実際の次の一歩を埋める。
  採用
- **案 AR-d: フラグメントを解釈しないことの検査可能化(ページに JS を置かない
  ことを CSP / ビルドで固定)** — 検討の上で W1 実装時の検査項目へ送る(静的
  ページに script タグ自体を置かない構成は spike-a の静的配信で成立済み。

## 8. 裁定 AT: セッション主体の能力制限(PR #103 pullfrog レビュー指摘の解消)

pullfrog の初回レビュー(review 5052658273)が、裁定 AM の全損評価の前提誤り
(§1 第 3 周の補正)と実装側の事実 — `ensureTokenScopeForProject` はセッション
主体を素通りし、`ensureKeyMaterialAccess` はセッションを常時許可、招待発行・
rotation dismiss はチェーン role のみでセッションから到達可能 — を指摘した。
検証の上、正当と判定(コード確認済み)。境界原則(裁定 AM)を実際に強制する
機構の裁定を追加する。

### 第 1 周

- **案 AT-a: 文書上の残余として明記するのみ(サーバー変更なし)** — 棄却:
  ADR-0018 改訂 2 の境界原則が「UI に置かない」という強制力のない宣言に
  なり、マージ = 規範確定の重みに耐えない。「隠すだけの形は禁止」(決定 1)の
  精神にも反する — バンドル省略は UI で隠すことの上位互換でしかなく、能力の
  所在(サーバーがセッションに許す集合)が変わっていない
- **案 AT-b: サーバー側でセッション主体の呼べる API を肯定列挙(allowlist)に
  制限する** — セッションクッキーは XSS に最も晒される資格情報であり、Web の
  画面集合が要る API(読み取り + 失効系 + 認証系)だけを許し、それ以外を
  403 で拒否する。deny-list でなく肯定列挙にするのは ADR-0016(fail-open →
  fail-closed への反転)と同じ型 — 新エンドポイント追加時の既定が「セッション
  不可」になる
- **案 AT-c: Web を別 origin に分離し CORS で制限** — 棄却: 同一オリジン
  XSS には CORS もヘッダー allowlist も無力(制限は cross-origin にしか
  効かない)。配信面が 2 origin に増えるだけで、問題の層(サーバーが
  セッションに許す集合)に触れていない

### 第 2 周(上位互換探索)

- **案 AT-d: AT-b + 署名必須操作(チェーン追記・push・メタ操作)も明示拒否に
  含める** — これらは鍵を持たない XSS には署名検証で元々成立しないが、明示
  拒否に含めることで防御を署名検証の実装詳細(および将来の検証変更)に依存
  させない。肯定列挙の実装上は自然に含まれる(列挙外 = 拒否)。採用
- **案 AT-e: セッションに可変スコープ(トークンと同じ scopes 列)を持たせる** —
  棄却: 必要なのは固定の 1 プロファイル(Web の画面集合)だけであり、可変化は
  発行面(誰がスコープを選ぶか)という新しい設計問題を生む。将来必要になれば
  AT-b の列挙を土台に拡張できる

### 第 3 周(再点検)

- 正当なセッション消費者の不在を確認: 制限対象(招待の発行・**受諾**・
  rotation dismiss・リカバリーブロブ登録取得・DEK 削除・値付き一括 pull)の
  いずれにも、採用形 (c) の Web 画面からの正当な導線がない。受諾は §15-3 改訂
  (静的案内ページ — Web 受諾画面は作らない)により正当導線が消えた —
  セッション XSS + 漏洩招待リンクで攻撃者鍵を被害者 user_id に束縛する面
  (§15-2 がスコープ限定トークンに対して塞いだ面と同型)を FP 相互確認の
  手前で塞げる。値付き pull の除外は SECURITY_REVIEW L-1(セッション pull の
  監査証跡汚染)の発生面自体を消す方向
- CLI / `maruhi ui` への影響なし(どちらもトークン主体)。既存 Web は
  セッションを張る画面を持たないため利用者影響ゼロ — W1 / W2a と独立に
  いつでも入れられ、**W2(セッションを持つ画面の初出)の前提**とする
  (順序制約は設計文書 §6・§7)
- 判定順の整合: 403 の位置は §11-2(存在秘匿)・§12-3(判定順)と整合させる
  必要がある — 実装 PR(W2b)で §14-3 の先例(認可段の後の位置決め)に倣い
  固定テストを課す。仕様は「セッション主体は拒否」の規範のみを規定する
- 置き場: AUTH_SPEC §5(セッションの章)に能力制限を規定し、§13-2・§15-2 の
  認可表からセッションを除去する追随を同時に行う(表の単独読みで誤らない
  ように)

**選択: 案 AT-b + AT-d**。AUTH_SPEC §5 追記 + §13-2 / §15-2 追随、ADR-0018
改訂 2・1 項の強制手段の明記、設計文書 §6 / §7(PR-W2b)。

## 10. 第 4 周(オーナー指示による再点検 — 2026-08-28)

オーナーの指示「決まった内容をもう一度見て、さらに良い案がないか考える」を
受けた追加の 1 周。前回の教訓(裁定 AT — 仕様文書ベースの再点検が実装の
現行挙動を素通しした)を踏まえ、**api-schema の全エンドポイント目録と §5 の
許可列挙の全件突合**を検査手順に含めた。結論: 中核の裁定(AM〜AT)は
覆らない。欠陥修正 1 件 + 検査可能化の強化 3 件を適用し、根本代替案 3 件を
検討の上で棄却した。

### 10-1. 欠陥修正: §5 許可列挙に W2a プロジェクト一覧 API が無かった

- 全件突合で発見。S4(プロジェクト一覧)はセッション画面だが、§5 の読み取り
  列挙に W2a で設計する一覧 API が含まれていなかった — fail-closed の既定
  (列挙外 = 拒否)の下で、文言どおりに W2b を実装すると **S4 が 403 になる**。
  pullfrog が §15-2 の一覧・失効行で指摘したのと同型の「表・列挙の単独読みの
  罠」の自作分であり、私の第 3 周が素通ししていた
- 修正: §5 の読み取り列挙に「プロジェクト一覧(W2a で設計 — 本人の
  membership のみ)」を追加し、「セッションに開く新設 API は本列挙への追加を
  同じ改訂で行う」を fail-closed 既定の但し書きとして明文化。設計文書 S4 /
  §7 W2b にも相互参照を追記

### 10-2. 強化: `/invite` の不変条件を構成で強制(裁定 AR の検査可能化)

- 実装確認: 現行 web は funstack のインラインブートストラップ script を
  index.html に持ち、CSP はそのハッシュ許可(`write-headers.ts`)。SPA の
  1 ページとして `/invite` を作ると「静的・スクリプトなし」が規約どまりになる
- 採用: `/invite` は **SPA 外の独立静的 HTML アセット**として配信し、
  per-path の CSP **`script-src 'none'`** を `_headers` に置く(規約 →
  検査可能な構成へ。AUTH_SPEC §15-3 に明文化、実装は W1)。第 3 周の
  AR-d(検査手段は実装の領分)を、実装形が確認できたため規範側へ引き上げた

### 10-3. 強化: W2b の実装形と優先度

- 実装形: セッション拒否をハンドラごとの手動検査でなく**エンドポイント契約
  への宣言焼き込み(単一実装点)**とする推奨を §5 に追記 — §12-10 (1) の
  strict 受理(AST 注釈の焼き込み + 固定テスト)と同じ型で、書き忘れの
  余地を構造的に消す
- 優先度: W2b を **W 系列の最初の実装 PR として先行させる推奨**を設計文書
  §7 に追記(依存ゼロ・利用者影響ゼロの純粋な防御強化で、待つ理由がない)
- あわせて §12-7 の値付き pull CSRF 段に「§5 は本経路自体をセッションに
  拒否する。CSRF 要求はそれ以前の防御 + 将来緩和への保険として撤去しない」の
  相互参照を追記(単独読みの罠の残り 1 箇所)

### 10-4. 検討の上で棄却した根本代替案

- **Web 専用 BFF(`/web/*` の別 API 面)** — 棄却: 同一オリジン XSS には
  BFF でも「セッションで呼べる集合」が境界のすべてであり、§5 の肯定列挙と
  防御水準が同じ。新しい API 面 + ハンドラ重複だけが増える(§5 が支配)
- **失効ゼロ形 (c′)(Web を純読み取りにし、失効も CLI へ)** — 棄却:
  XSS 残余は「失効 DoS(回復可能)」の分しか縮まない一方、**「どのブラウザ
  からでも漏洩トークン・招待を即失効できる」というインシデント対応の
  緊急経路**を失う。資格を減らす方向の操作は失っても攻撃者が得をしない
  操作であり、置いておく価値が上回る(AM の境界原則の再確認)
- **AUDIT_SPEC §7(dismiss)へのセッション拒否の追記** — 不要と判定:
  §3.3 の記録細則は元々「チェーン role admin 以上 × トークンスコープ admin」
  であり、スコープを持たないセッションは**厳密に読めば最初から条件を満たさ
  ない**(現行実装のセッション素通りの方が仕様からの逸脱)。W2b は AUDIT_SPEC
  の文言に追いつく方向であり、二重の規範を増やさない
- 維持確認: TTL 90 日(起草値 — レビューで調整可)、セッション可変スコープ
  (AT-e)の再棄却、監査 auditHead の列挙外(Web に消費者なし — 列挙外 =
  拒否で足りる)、S10 の v1 外
