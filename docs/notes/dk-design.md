# DK 設計録 — デバイス鍵分離(端末単位の失効)(2026-09-19 フェーズ 1 設計セッション・所有者承認待ち)

**位置づけ**: ROADMAP H 系列「仕様改訂群」の 3 つ目 = **DK: デバイス鍵分離 — 端末単位の失効**(CRYPTO_SPEC 未決 #2 の残り半分。順序は ES → PF1 → **DK** → PF2 → PF3 — 2026-09-14 所有者裁定)のフェーズ 1 成果物。設計の全体像・裁定の反復記録(巡数と棄却案を含む)・実装分割・承認依頼項目を持つ。仕様改訂の起草は docs/notes/dk-spec-drafts.md(CRYPTO_SPEC §3 / §5.1 / §6.2 / §6.3 / §6.4 / §6.5 / §7 / §8 / §11 / §13 / §14、AUTH_SPEC §5 / §6 / §11-1 / §12-3 / §12-6 / §12-8 / §13 / §16-1、AUDIT_SPEC §2 / §3.4 / §4.1 / §4.2 / §6)。**正本 3 文書・コード・テストベクターは本セッションでは触らない**(所有者が §4 の承認項目に答えた後、K1 以降を別セッションで行う — ES / KL3 と同じ手順)。様式は docs/notes/es-design.md に合わせる。

**前提**: (1) ES / PF1 は 2026-09-19 の K7(PR #183)で完了しており、本設計は ES の scope(`all` / `listed`・受信者集合 R(E)・原則 1)と PF1 の四眼(原則 2・票の (user_id, 鍵 FP) 束縛)を**前提として継承する**(蒸し返さない。帰結として既存規則の字面を変える必要が出た点は承認項目として提示する)。(2) KL3 の master 鍵ラップ台帳(CRYPTO_SPEC §8 — クラス S / G / H)と IV(§6.5 — リンク束縛 + 裏付け元)は実装済みで、DK はその上に載る。(3) **利用者がいないうちは古い実装をすべて削除してよい**(2026-09-14 所有者裁定)— 互換経路は持たず、旧クライアントは新 op に対して fail-closed になればよい。(4) 委任モデル(KL4)の据え置き(補足 19 19-3 (10))は蒸し返さず、DK の帰結として委任が構造的に安くなるかだけを見る。(5) ハードウェア封印(device-key-sealing.md 案 3)は DK の上に載る別項目で、本設計は「封印を妨げないこと」の確認だけを行う。

**用語(本設計録・ドラフト共通)**: **端末鍵(device key)** = 端末ごとに生成する enc(X25519)+ sig(Ed25519)の鍵対。チェーン上の鍵の単位であり、鍵フィンガープリント(§3 — `SHA-256(enc ‖ sig)` の先頭 16 バイト)で識別する。**予備鍵(reserve key)** = 端末鍵と同じ形の鍵対のうち、秘密鍵が **§8 の台帳にだけ住み、日常の端末には置かない**もの。全端末を失ったときに台帳から復元し、新しい端末鍵を登録するためだけに使う。チェーン上では普通の端末鍵と区別されない(区別は台帳側の事実)。**端末の上限(device cap)** = 端末鍵に付与する (role 上限, scope) の組。端末の**実効権限** = (min(人の role, 端末の role 上限), 人の scope ∩ 端末の scope)。旧「master keypair」の語は退役する(移行は裁定 DK-J)。

## 1. 全体像

### 1-1. 問題の再定義

現行(CRYPTO_SPEC §3 の v1 簡略化)は **1 ユーザー = 1 master keypair を全端末に複製する**。KL3 の台帳(§8)はこの複製を安全に運ぶ機構(リカバリーコード / パスキー PRF / 保護者 / 旧端末のハンドオフ)であり、複製そのものは変えていない。帰結:

- 「ノート PC を紛失した」に対して、その端末**だけ**を失効できない。紛失端末は master 鍵の平文をキーチェーンに持つため、台帳のラップを消しても API トークンを失効しても、鍵そのものは攻撃者の手元に残る。取れる手段は**鍵の再生成 = アイデンティティの作り直し**(`key generate` → 全プロジェクトで `remove_member` + 再招待 → 各プロジェクトの scope 全環境で rotate 義務 → リカバリー台帳の再構築)であり、ES で細かくした scope の意味論も四眼の票の束縛も、その作り直しの前では一律に「全部やり直し」に潰れる
- 端末を「他人に貸す」形の運用(CI 箱・Codespaces・電話)に、その端末の権限を人より狭くする手段がない。ES は**人**の scope を細かくしたが、同じ人の端末はすべて同じ鍵を持つため、端末を区別できない
- KL3 のハンドオフ(旧端末が B を新端末へ渡す)は master 鍵の**平文の移動**であり、移動のたびに全プロジェクトの全 DEK を開ける鍵が新しい端末に増える。増えた端末を後から減らす手段がない

DK が答える形: **鍵を端末に属させ、権限は人に属させたまま**にする。チェーンのメンバー(user_id・role・scope)は人であり、その人が持つ**端末鍵の集合**をチェーンが管理する。端末 1 台の失効 = その端末鍵を受信者集合 R(E) から外し(以後の DEK はその鍵へ包まれない)、その鍵による以後の署名を無効にし(値・メタ・チェーン op・票)、その端末が開けた DEK の rotate 義務を導出する — つまり **`remove_member` の端末版**である。人は残るので再招待も四眼の票の作り直しも要らない。

同時に「端末 = 鍵の単位」から自動的に従うもの:

- **義務の範囲**: 端末が開けた DEK は「その人の scope(∩ 端末の scope)の全環境」であり、失効の rotate 義務はそれと一致する(ES の帰結 — 端末は人の scope を超えない)
- **失効の履行者**: 端末を失効させる actor は同じ人の別端末(または本人を remove できる admin / owner)であり、いずれも当該環境の DEK を持つ(原則 1 の系)
- **予備鍵の必然**: 端末鍵しか無いと「全端末を失った人」は鍵をすべて失い、単独 owner のプロジェクトは死ぬ。よって**日常の端末に置かない鍵を 1 本、台帳にだけ置く**必要がある。これは KL3 の B(台帳のラップ対象)の意味を「複製の元」から「予備鍵」に変えるだけで、台帳の構造・バイト列は変えない

### 1-2. 機構の絵

```
人 U(チェーンのメンバー: user_id・role・scope — ES のまま)
├─ 端末鍵 D1(ラップトップ)     cap = (owner, all)            ← add_member / genesis で載る最初の鍵(payload 不変)
├─ 端末鍵 D2(電話)             cap = (owner, listed{})       ← add_device(D1 が署名)。DEK は受け取らない = 「票だけの端末」
├─ 端末鍵 D3(Codespace)        cap = (member, listed{dev})   ← add_device(D1 が署名)。dev だけ読める・書ける
└─ 予備鍵 R                     cap = (owner, all)            ← add_device(D1 が署名)。秘密鍵は §8 台帳にだけ住む

チェーン(1 プロジェクトに 1 本 — 不変)
  genesis      U   D1 の enc / sig                          scope = all
  add_device   U → R    [enc, sig, role_cap=owner, scope=all]           ← actor = (U, FP(D1))。本人だけが自分の端末を足せる
  add_device   U → D2   [enc, sig, role_cap=owner, scope=listed{}]      ← 新端末の cap ≤ 署名した端末の cap(単調性)
  add_device   U → D3   [enc, sig, role_cap=member, scope=listed{dev}]
  revoke_device U  [FP(D1)]                                            ← actor = (U, FP(D2)) — 電話から紛失ラップトップを失効。R(E) から D1 が外れ、
                                                                          D1 の以後の署名は無効。義務 = D1 の実効 scope(= all)の rotate

R(E) = { (m, d) | m ∈ 現メンバー, d ∈ devices(m), E ∈ scope(m) ∩ scope(d) } ∪ { g ∈ 有効 grant_server | E ∈ scope_environments(g) }
  R(prod) = { (U,D1), (U,R), … }        ← D2(scope 空)・D3(dev のみ)宛の prod ラップは生成も受理もされない
  R(dev)  = { (U,D1), (U,R), (U,D3), … }

署名者の同定 = (user_id, 鍵 FP) — 不変。FP が端末を指す。既存の「FP が一致し、その時点で user_id に束縛されていた鍵で検証する」(§5.1 / §6.3-1 / §6.6)は、
「その時点で有効(add_device 以後・revoke_device より前)だった端末鍵」と読めばそのまま成立する。
四眼の票 S の要素 (user_id, 鍵 FP) も不変。distinct は user_id で数える(同じ人の別端末は 1 票)。失効した端末の票は失効し、別端末で入れ直せる。

§8 台帳(KL3 — 構造・AAD・分片・ハンドオフの要求 / 承認 payload は不変)
  B = 予備鍵 R のブロブ(旧: master 鍵のブロブ — 同じ JSON 形)
  受信者: recovery-code / passkey-prf / guardian(保護者の**各端末鍵**へ分片を封印)
  ハンドオフ: 要求者 = 本人、承認者 = 保護者のみ(旧端末の承認 `kind = "device"` / `source = "device"` は不要になり削除 — 日常の端末は B を持たない)

端末の追加(儀式なし・秘密の移動なし)
  新端末: login → `device add`  → 端末鍵を生成 → 公開鍵を要求行として登録 → FP(12 語 / hex)を表示
  既存端末: `device approve <FP>` → 要求行の公開鍵を FP で照合 → 全プロジェクトへ add_device + 全エポックの DEK を新端末へバックフィル
  (運ぶのは FP = 公開情報。サーバーが公開鍵をすり替えても FP 照合で落ちる — §3 の FP 強度の前提どおり)
```

端末を失った人の導線(1 本): 別端末で `maruhi device revoke "MacBook"` → 全プロジェクトへ `revoke_device` → 履行できる rotate はその場で(sweep)→ 履行できないもの(reader のプロジェクト)は誰が rotate すべきかを表示 → 紛失端末の API トークンも失効。CLI の端末が無ければ Web でトークン失効(即時の遮断)→ `key recover` で予備鍵を復元 → 上の導線。

### 1-4. 変えないもの(制約の確認)

- **暗号プリミティブ・HPKE info・AAD は不変**: DEK ラップの info(§5 — `recipient_user_id` まで)は端末を含めない。同じ人の 2 端末は鍵が違うので、A 宛のラップを B が開くことは HPKE が既に拒む。登録署名(§5.1)は `recipient_enc_pub_hex` を束縛済みで、端末はそこで固定される。§8 の AAD / info・XOR 分片・ハンドオフの `handoff-wrap` info も不変(`kind` の値集合から `device` が消えるだけ)
- **「署名するのは人間だけ」**: 端末鍵の保持者は人。機械メンバー(サーバー鍵・ワークロード)の扱いは不変(裁定 DK-K)
- **チェーン・監査にプロバイダ ID を書かない**: 端末の表示名(「MacBook」)はチェーンに載せない。actor は (user_id, 鍵 FP) のまま — FP が端末を指す
- **意味論は署名バイト列の中(§1 原則 6)**: 端末の cap(role 上限・scope)は `add_device` payload の LP フィールド。端末の表示名・トークンの対応は署名の外(登録簿 — advisory)に置き、検証規則に用いない
- **ES の scope・原則 1・PF1 の原則 2 は前提のまま**: 端末の実効権限は人の権限との min / ∩ であり、人の権限を超えない。四眼の distinct は user_id、票は (user_id, FP)
- **`add_member` / `change_role` / `genesis` の payload は不変**: ES の `chain-entries.json` 正規チェーン(seq 1〜24)のバイト列は変わらない。新 op は末尾に追記する(§6.2 `checkpoint` op 追加時と同じ「追記で拡張」の型)
- **招待の形(IV1 / IV2)は不変**: 受諾する鍵 = 受諾した端末の鍵。裏付け元(GitHub 署名鍵)へは端末ごとに `key publish` する(GitHub は複数の署名鍵を持てる)。発行文・受諾文の LP は触らない
- **Web は鍵を持たない(ADR-0018)**: 端末の一覧は読み取り(サーバー申告)、端末の追加・失効はチェーン op なので CLI のみ。紛失時に Web でできるのは既存のトークン失効(資格を減らす方向 — 改訂 2 の境界内)
- **旧クライアントは fail-closed**: `add_device` / `revoke_device` は未知 op としてチェーン検証で拒否される(`invalid-payload`)。互換経路なし

## 2. 裁定の反復記録

各裁定点で §5 の手続き(候補 3 案以上 → 上位互換 / 銀の弾丸の巡 → 新案が出た巡の次にもう 1 巡・空巡が連続 2 で打ち止め → 原則の抽出と既存裁定の導出確認 → UX の点検 → 採用)を回した。巡の記録は「何を試みて、何が出て、何が出なかったか」を 1 行ずつ残す(es-design.md §12-bis の訂正に従う — 候補表を作って「空巡」と書くだけでは探索にならない)。巡数は正直に記す。採用案が正本の規則を変える点は、その裁定の直後に docs/notes/dk-spec-drafts.md へ起草した(裁定番号を併記)。

### 裁定 DK-A: 鍵の単位と置き場 — 何を失効したいのか(列挙 1 巡 + 問題の立て方の巡 + 内容のある第 3 巡 + 空巡 2・打ち止め)

| 案 | 内容 | 評価(何を得て何を失うか) |
|---|---|---|
| A-1 台帳の受信者クラス「端末」(ROADMAP の軸 (i)) | master 鍵を端末ごとの鍵で包んで §8 台帳に置く。失効 = そのラップの削除 | **失効が空文**: 現行の端末は master 鍵の**平文**をキーチェーンに持つ(ラップは取得経路であって保管形ではない)。ラップを消しても鍵は紛失端末に残り、以後の DEK も master 鍵宛に包まれるので開ける。得られる遮断は API トークンの失効(`DELETE /auth/tokens/:id` — 既存)と同値。「端末が master 鍵の平文を持たない」形は封印(device-key-sealing.md 案 3)だが、それは**保護**であって失効ではなく、開封中のメモリ・生きた侵害には効かない。棄却 |
| A-2 **端末ごとの鍵をチェーンに載せる — メンバー = 人、鍵 = 端末の集合**(軸 (ii) の「人」版) | チェーンのメンバー(user_id・role・scope)は不変。メンバーが持つ鍵を**集合**にし、`add_device` / `revoke_device` で増減する。署名者の同定 (user_id, 鍵 FP) の FP が端末を選ぶ。R(E) は (人, 端末) の対 | 「その端末が持っていた鍵だけを無効化」が暗号で言える(以後の DEK はその鍵へ包まれず、以後の署名は無効)。義務は remove と同型。既存規則の大半は「FP で鍵を選ぶ」形で書かれており無変更で一般化する。対価: ファンアウト(受信者 = 端末数)、端末の追加・失効がプロジェクトごとのチェーン op(N プロジェクト = N エントリ)、`ChainMember` の型変更が全消費者に及ぶ |
| A-3 端末 = メンバー行(軸 (ii) の「端末」版) | (user_id, 鍵) をメンバー行とし、同じ user_id の行を複数許す。role / scope は行ごと | 「人」の単位が消える: `duplicate-member`・最後の owner・四眼の distinct・招待の受諾・要ローテーション検出の在籍区間・ES の包含規則がすべて「人」を前提にしており、行ごとの role / scope の分裂を各規則で扱い直すことになる。端末は「人の scope を超えない」(ES §6 申し送り)ので人が先にある。棄却 |
| A-4 アイデンティティ鍵(root)を台帳にだけ置き、端末追加は root の署名を必須にする 2 層 | root(sig)がチェーン上の人の鍵、端末鍵は root が署名した証明書で載る。root は日常の端末に置かない | 得るもの: 盗まれた端末では端末を増やせない(失効を掻い潜る「不正な端末の温存」を防ぐ)。失うもの: 端末追加のたびに台帳を開く(コード入力 / パスキー / 保護者)= KL3 ハンドオフの利得(旧端末での承認 1 回)を捨てる。生きた侵害(マルウェア)では root を開封する瞬間を攻撃者が待てるため利得は「盗難(T2)」に限られ、その利得は第 3 巡の単調な cap と一括失効で大半を回収できる。棄却 |
| A-5 ユーザー単位の端末チェーン(署名付き鍵ログ)をプロジェクトチェーンから参照(銀の弾丸候補) | 端末の追加・失効を人ごとの別チェーンに 1 回書けば全プロジェクトに効く | 各プロジェクトの検証者が**全メンバーの端末チェーン**を取得・検証する(クロスチェーン依存)。split view の面が人数分に増え、可用性が結合し、アンカー・チェックポイントも人ごとに要る。鍵の透明性ログ(補足 17)と同じ規模で、KT が「不要」と裁定された論法(プロジェクトチェーンが既に鍵の台帳)がそのまま当たる。棄却(将来の組織の鍵台帳 / 公開証人と同じ棚) |

**第 1 巡(列挙)**: A-1〜A-3。A-1 は「失効」の定義で落ち、A-3 は「人」の単位を壊す。A-2 が残る。**第 2 巡(問題の立て方を問う — 何を失効したいのか)**: 端末が持つ能力を分解した — (a) DEK を開ける(enc)、(b) 署名する(sig — 値・メタ・チェーン op・票)、(c) リカバリーを開ける(台帳)。案 (α) 端末鍵に enc / sig を常に両方持たせる(現行と同形)、案 (β) 端末ごとに片方だけ持たせる(enc-only の「読む端末」/ sig-only の「承認する端末」— 鍵一意性は種別ごとなので構造的には可能)、案 (γ) **端末に (role の上限, scope) の cap を持たせ、実効権限 = (min(人の role, 上限), 人の scope ∩ 端末の scope) で表す**。(γ) は (β) の上位互換: sig-only の承認端末 ≒ cap (owner, listed{})(DEK を一切受け取らず票だけ入れる電話)、enc-only の CI 箱 ≒ cap (reader, listed{dev})。鍵の形は 1 種類のままで能力の分離が得られ、「鍵の欠けた端末」を全検査で特別扱いせずに済む。(c) は**予備鍵**(台帳にだけ住む端末鍵 — B の意味の読み替え)で、端末鍵と別の鍵種を作らずに済む。新案 (γ) + 予備鍵が出た。**第 3 巡(上位互換 — A-4 の利点を A-2 で得る)**: 「盗まれた端末が端末を増やせない」を、(i) **単調性**(新端末の cap ≤ 署名した端末の実効 cap)と (ii) **一括失効**(`revoke_device` の payload に FP のリスト — 紛失端末が失効前に作った端末を、失効者が一覧から選んで同じエントリで失効できる)で回収する。盗まれた電話(cap (owner, listed{}))は scope 空の端末しか作れず、盗まれたラップトップが作った端末はチェーン上に「誰が追加したか」(actor FP)つきで見える。新案(単調性・一括失効)。**第 4 巡(銀の弾丸)**: A-5 端末チェーン → 棄却(上表)。「予備鍵を持たず、全端末喪失 = 各プロジェクトで再招待」→ 単独 owner のプロジェクトが死に、KL3 の保護者経路が守るものを失う。棄却。「予備鍵 = 既存 master 鍵を台帳にだけ残す」→ 採用構造の言い換え(新案でない)。**空巡**。**第 5 巡**: 「端末に履歴エポックを渡さない(現エポックのみ)」→ 失効の義務(現エポックの rotate)は変わらず、履歴を読めない端末の用途が薄い(§7「secrets は履歴の秘匿を目的としない」)。棄却。「cap を後から変える op(`set_device_cap`)」→ 新 op は追記で後から足せる(payload 形式の変更を伴わない)ので今は持たない — 申し送り。「端末追加を招待型(リンク)にする」→ DK-D で扱う。新案なし → **空巡**。連続 2 空巡で打ち止め。

**原則の抽出**: **「鍵は端末に属し、権限は人に属する」** — 権限(role・scope・票の distinct)は user_id で数え、鍵素材とその失効は端末で扱う。署名者は (user_id, 鍵 FP) で同定し、FP が端末を選ぶ。端末の実効権限は人の権限を超えない(min / ∩)。置き換え前・既存の裁定がこの原則から導出できることの確認: ES 裁定 A〜N(scope は人の属性 ✓ / R(E) は「人 × scope」を「(人, 端末) × 実効 scope」に置換 ✓ / 包含規則は actor **端末**の実効 scope で判定 ✓ / G の可視範囲は人の scope ✓)、PF1 P1〜P8(distinct owner = user_id ✓ / 票の (user_id, FP) 束縛 = 端末束縛 ✓ / `proposal-void` の鍵 FP = 端末 ✓ / 常時対象 = owner **身元**の追加であり端末追加は含まれない ✓)、K2-11 ②⑤ / K5-J(票は owner role で作られた署名・失効は単調でない ✓ — 端末語彙でも同じ)、KL3 19-2 A(台帳 = 同一 B への受信者ごとのラップ — B の意味が予備鍵に変わるだけ ✓)/ D・E(ハンドオフ = 保護者経路に残る ✓)/ G(「旧端末 = 事前登録は無意味」— DK では旧端末の承認自体が不要 ✓)、IV 補足 21(受諾鍵 = 受諾端末の鍵 ✓)、ADR-0018(Web は鍵を持たない ✓)、§5.1 の signer FP 選択 ✓、§6.2 鍵一意性(種別ごと・現メンバー集合 → 現メンバーの全端末 ✓)、§6.3-1 の「在籍区間の鍵」(→ 端末の有効区間 ✓)。✗ なし。

**UX の点検**: 新端末 = 新端末で `device add`(FP を表示)+ 手元の端末で `device approve <FP>`(照合 + yes)の 2 コマンド・12 語の読み上げなし(FP は自分の端末間で運ぶ)・秘密の移動なし。紛失 = `device revoke <名前>` 1 コマンド。owner の招待・承認の手順は不変。エージェント環境: approve は儀式(拒否)、add(要求側)はゲートなし。**採用: A-2 + cap + 予備鍵 + 単調性 + 一括失効**。cap を v1 の CLI で露出するか(`device approve --cap / --env`)は所有者選択(承認項目 2)。→ ドラフト A-1 / A-3。

### 裁定 DK-B: 失効の意味論・§7 の義務・履行者・全端末喪失(列挙 1 巡 + 空巡 2・打ち止め)

| 案 | 内容 | 評価 |
|---|---|---|
| B-1 **失効 = remove の端末版** | `revoke_device` で失効した各端末について、その**実効 scope**(人の scope ∩ 端末の scope)の全環境に `rotate_epoch` 義務(§7 の MUST の書式)。履行者 = 失効を署名した actor(同じ人の別端末、または他人の端末を失効させた admin / owner)。**reader の自己失効**だけは actor が rotate できない(role 不足)— 義務は「未割当」として要ローテーション検出(`rotation.recommended` trigger = `revoke_device`)と `project verify` の未収束警告で scope を覆う全 member 以上に見せ、CLI は失効した本人に「誰かに rotate を頼め」と表示する | 義務の形が remove(§7)・降格・縮小(F-1)・revoke_server と同一。端末は人の scope を超えない(ES §6 申し送り)ので、端末が開けた DEK の環境集合 = 実効 scope で閉じる |
| B-2 理由依存(`retired` = 義務なし / `lost` = 義務あり) | 破棄した端末の失効は rotate を免除する | 破棄の証明が無く fail-open(「破棄した」と書けば義務が消える)。ephemeral 環境(Codespaces の再作成)の運用コストは下がるが、それは委任 / 転送 agent(DK-H)の領分。棄却 — 所有者選択として承認項目 4 に併記 |
| B-3 reader の自己失効を合意規則で拒否(admin に頼め) | 履行不能な義務を作らない | 安全側の操作(失効)を止める — ES 裁定 E「rotate はインシデント対応であり遅らせてはならない」と同じ論法で棄却。失効は即時に R(E) から外す価値がある |
| B-4 その端末が**実際に読んだ**環境だけ rotate(監査 `var.read` の actor 鍵 FP から導出) | 義務を最小化 | 「読んだ記録が無い」≠「読めなかった」(取得済み DEK でのオフライン復号・サーバー不信下の監査は改竄可能)。検出のランク付け (a)/(b)(AUDIT §4.1)には使う(端末単位で「確実に取得した」が言えるようになる — DK-F)が、義務の**範囲**には使わない。棄却 |

**全端末喪失の経路**: `key recover`(リカバリーコード / パスキー / 保護者 — KL3 の 3 経路。旧端末の承認経路は不要になる — DK-G)で予備鍵を復元 → 予備鍵(cap (owner, all))で新端末鍵を `add_device`(単調性から任意の cap を作れる)→ 予備鍵が自分の DEK ラップを開いてバックフィル → 予備鍵の秘密を端末から消す(台帳は据え置き)→ 紛失端末を `revoke_device`(rotate)。予備鍵が登録されていないプロジェクト(その端末の加入時に予備鍵の登録が済まなかった — DK-D の初回同期の登録が担う)は再招待。

**第 2 巡(上位互換)**: 「失効を 2 段にする(soft = R(E) から外すだけ / hard = 義務つき)」→ soft は「サーバーが既に知る DEK を開示されていないように見せる」見せかけの縮小と同型(§6.3 の再 grant 規則が縮小を拒否する理由)。棄却。「失効端末が取得しなかったエポックを rotate 対象から除く」→ B-4 と同じ理由。棄却。**空巡**。**第 3 巡(銀の弾丸)**: 「予備鍵を復元した端末で予備鍵をそのまま日常鍵にし、新しい予備鍵を作る」→ 台帳(コード・パスキー・保護者グループ)の全再構築が要る。棄却 — 復元後は予備鍵の秘密を消し台帳を据え置く(残余: 復元に使った端末が侵害されていれば予備鍵も侵害されうる → `key reserve rotate`〔新予備鍵の登録 + 旧予備鍵の失効 = rotate〕を用意する。DK-L)。「失効の代わりに端末の cap を空に縮める」→ 縮小 = remove 相当(F-1)で義務は同じ。新案でない。**空巡**。打ち止め。

**原則の抽出**: 「失効 = R(E) からの受信者の除去。義務 = 除去された受信者の実効 scope の rotate。履行者 = 除去を署名した actor」— remove(§7)✓、降格(§7 — 動機はアンカーの健全性だが範囲は同じ)✓、縮小(F-1)✓、revoke_server(全環境 — サーバー鍵の実効 scope は開示スコープだが改訂は ES の対象外のまま)✓、四眼経由の履行者 = 承認者(P8)✓。reader の自己失効は「actor が履行できない唯一の失効」で、ここは E(rotate を止めない)の系として「止めずに見せる」。✗ なし。

**UX の点検**: `maruhi device revoke MacBook` → `Revoked in 4 projects. Rotated: alpha (dev, prod), beta (dev). Needs a member or owner to rotate: gamma (you are a reader there) — ask them to run maruhi env rotate.` 非対話で可(失効は儀式ではない — 値も鍵素材も表示しない。エージェント環境でも通す)。**採用: B-1**。→ ドラフト A-8 / C-3。

### 裁定 DK-C: 四眼(PF1)との交差 — 票・重複・void(列挙 1 巡 + 空巡 2・打ち止め)

| 案 | 内容 | 評価 |
|---|---|---|
| C-1 **原則 2 を端末語彙で読む** | S の要素 (user_id, 鍵 FP) は不変(FP = 署名した端末)。票が数えられる条件 = 「適用時点で、その FP が現 owner の**有効な端末**で、端末の実効 role が owner」。distinct は user_id(同じ人の別端末は 1 票)。`duplicate-approval` = actor の user_id が S に**生きている票**(有効な端末による票)を既に持つ(同じ端末でも別端末でも)。失効した端末の票は失効し、別端末で入れ直せる。`proposal-void` = 提案した端末が有効・提案者が現メンバー・実効 role が内側 op に足りる。「失効は単調ではない」(K5-J)は端末でも同じ: 失効した端末鍵を同じ人が `add_device` で再登録すれば旧票は復活する(帰結 — CLI は失効済み FP の再登録に警告 = K6-I の親戚)。`add_device` / `revoke_device` は四眼の**対象にできない**(端末追加は user_id を増やさず定足数に影響しない・失効は安全側) | 原則 2 の字面のうち「同じ鍵 FP を持つ現メンバー」が「その FP を有効な端末として持つ現メンバー」に一般化されるだけで、規則の構造は不変。cap (owner, listed{}) の電話は DEK を持たずに票を入れられる(能力分離の実益) |
| C-2 同じ人の別端末からの 2 票目を重複扱いせず、数えもしない | 規則が単純 | 監査に「票にならない approve」が増え、「1 人 1 票」の字面が濁る。K6 の pending 表示(「あなたは approve できます」)が別端末で誤案内になる。棄却 |
| C-3 失効した端末の票を残す(端末失効 ≠ 鍵の侵害と見る) | 失効の後始末が減る | 失効は「この鍵は侵害されたかもしれない」の宣言であり、K2-11 ⑤(鍵更新で旧鍵の票は失効する)の論法と矛盾する。棄却 |
| C-4 `add_device` を owner 確立 op として常時四眼の対象にする | owner の鍵の増加を 2 owner で見る | 不変条件 (a) が守るのは「定足数を満たす身元の追加」であり、端末は user_id を増やさない(票は distinct user_id)。owner の端末追加に 2 owner を要求すると、単独 owner が四眼を有効化した後で自分の端末を足せない(方針オフにも四眼が要る — 復帰不能)。棄却 |

**第 2 巡(上位互換)**: 「cap < owner の端末からの approve を `insufficient-role`」→ 実効 role の置換規則(DK-A)の帰結であり新案でない。「他人の端末を owner が失効させる `revoke_device` を四眼の対象にする」→ 失効は安全側(rotate と同列 — 遅らせない)。棄却。「S の要素に端末の追加 seq を足して同一鍵再登録の復活を閉じる」→ K2-11-bis ⑤ d と同じ(閉じるのは運用失敗の後始末だけ・状態が増える)。棄却。**空巡**。**第 3 巡**: 新案なし。**空巡**。打ち止め。

**原則の抽出**: 「S の要素は署名した端末で同定し、票は適用時点でその端末が現 owner の有効な端末であるときだけ数える。distinct は人」— P4(承認者 = owner・distinct)✓、P5(票の再計算・現在性)✓、K2-11 ②(owner role で作られた署名)✓、⑤(鍵更新で失効・同一鍵で存続)✓、K5-J(非単調の注記)✓、P3 の常時対象(身元の追加のみ)✓。✗ なし。

**UX の点検**: 初回: `key generate` → 端末鍵 + 予備鍵 → コード表示(+ passkey の案内)。後日 `guardian add` → 「予備鍵を開封します: コードを入力 or パスキー」→ 指名。Codespaces(`/docs/linux-keychain`)の手順は「`agent -- bash` → `login` → `device add`(コード表示)→ 手元で `device approve`」に変わり、コードもリカバリーコードも打たない(KL3 と同じ手数)。**採用: G-1**。→ ドラフト A-9 / B-7。§8 の表題は「master 鍵ラップ台帳」→「予備鍵ラップ台帳」を提案(所有者選択 — 承認項目 8)。

### 裁定 DK-H: 委任モデル(KL4)への帰結(列挙 1 巡 + 空巡 2・打ち止め)

問い(§3 8): DK の帰結として agent が端末鍵だけを持つ形になり、委任が構造的に安くなるか。

| 案 | 内容 | 評価 |
|---|---|---|
| H-1 **安くならない(据え置き維持)— 動機が「盗難」から「ephemeral」へ移る** | agent が持つ鍵は master 鍵から端末鍵に変わるが、鍵を使う箇所(約 30)と `MasterKeyOps` 化の費用は不変。委任の主目的「永続的な master 鍵窃取が消える」の価値は、端末鍵の失効可能性で**一部先取り**される(agent の侵害 = 端末 1 台の失効 + rotate で収束し、アイデンティティの作り直しにならない)。一方 ephemeral 環境(コンテナ再作成のたびに端末が消える)では「端末を登録 → 破棄のたびに失効 + 実効 scope の rotate」が重く、転送 agent(鍵を手元から出さない)の価値はむしろ上がる | 裁定変更なし。承認項目にはせず情報として記す |
| H-2 DK と同時に委任化する | 端末鍵 = 委任の単位で一石二鳥 | KL3 19-3 (a) の見積り(約 30 + 3 箇所・1 週)は DK で変わらず、ベータゲートを伸ばす。据え置きの蒸し返し。棄却 |
| H-3 ephemeral 端末の失効を義務なしにする(B-2) | Codespaces の摩擦を消す | fail-open。棄却(所有者選択に併記) |

**第 2 巡**: 「ephemeral 端末に `--key-ttl` 相当の**チェーン上の期限**を持たせ、期限で自動失効」→ 期限は timestamp を合意規則に持ち込む(P6 の例外を増やす)。棄却。「Codespaces は KL1 の永続キーリングで端末鍵を持ち越し、1 codespace = 1 端末にする」→ 運用の案内(docs)であり新案でない。**空巡**。**第 3 巡**: 新案なし。**空巡**。打ち止め。

**採用: H-1**。申し送り: KL4 の再評価時に「転送 agent の主用途 = ephemeral 環境」と書き直す。

### 裁定 DK-I: 封印(device-key-sealing.md 案 3)との関係(単巡 — 事実確認)

端末鍵レコードは `StoredMasterKey` の JSON 形(suite / encPub / encSk / sigPub / sigSkSeed)で不変であり、封印バックエンド(FIDO2 hmac-secret / SE / TPM / パスフレーズ)はこのブロブを包む保存層。DK は形を変えず、端末ごとの鍵は端末ごとの封印と自然に対応する(封印器 1 つの喪失 = その端末の失効で済む)。**予備鍵は端末束縛の封印器で封印してはならない**(どの端末でも復元できる必要 — 台帳のみ)。端末鍵の失効はチェーン側の事実で封印器の状態に依存しない。妨げなし。→ §5 申し送り。単巡(探索の対象ではなく確認)。

### 裁定 DK-J: 移行 — 既存の 1 鍵モデルから(列挙 1 巡 + 空巡 2・打ち止め)

| 案 | 内容 | 評価 |
|---|---|---|
| J-1 **チェーンは据え置き・既存 master 鍵 = 最初の端末鍵・台帳と複製端末だけ手当** | `add_member` / `genesis` の payload が不変なので既存チェーンは新規則で**有効**(各メンバーは端末 1 つ)。既存 master 鍵 K は端末鍵 D1 と読み替える。台帳の B(= K の複製)は予備鍵へ差し替える: 新 K_r を生成 → 全プロジェクトへ `add_device(K_r)` → 台帳を K_r で再封印(コード再発行 / パスキー再封印 / 保護者グループ再作成)。K を複製していた他端末は、各端末で `device add` → 承認 → その端末の K の複製を削除(K 自体は D1 として有効)。CLI は初回起動で「この端末の鍵は予備鍵と同一です。予備鍵を分けます」と案内する(`key generate --split-reserve` 相当 — K4 の CLI 裁量) | 破壊的変更なし。ES A-1 の「再作成」の帰結を DK では避けられる(ES §6 申し送りの懸念〔再生成 2 回〕は生じない) |
| J-2 検証デプロイを再作成(ES A-1 と同じ帰結) | 手当が要らない | 必要のない破壊。棄却(所有者が「作り直す方が早い」と判断する場合の代替として承認項目 9 に併記) |
| J-3 既存 K を予備鍵として読み替え、端末には新鍵 | 端末鍵が最初から「新しい」 | K は全端末に複製済みで「台帳にだけ住む」前提を満たさない(消したつもりの複製が残る)。棄却 |

**第 2 巡**: 「移行を合意規則で強制する(端末 1 つのメンバーを無効に)」→ 端末 1 つは正当な状態(予備鍵未登録のプロジェクトもありうる)。棄却。「旧 CLI の K を自動で予備鍵に分けない(利用者の明示操作のみ)」→ 案内 + 明示操作は J-1 に含む(自動で鍵を作らない)。新案でない。**空巡**。**第 3 巡**: 新案なし。**空巡**。打ち止め。

**採用: J-1**。移行順序: サーバー(K3)→ 全メンバーの CLI(K4)→ 各人の予備鍵の分離と複製端末の登録。旧 CLI は新 op を含むチェーンを `invalid-payload` で拒否する(fail-closed)。→ SELF_HOSTING "Updates" は K3 の PR に同梱(ES K2 の先例)。

### 裁定 DK-K: 端末を持たない主体・Web(単巡 — 事実確認)

- **サーバー鍵(`grant_server`)**: 受信者クラス server は不変(FP 定義・開示スコープ・リースポリシー・再 grant 規則)。R(E) の grant 側は変わらない
- **CI リース(§9.1)**: ワークロードの一時鍵は応答スコープで、端末でもメンバーでもない。不変
- **Web(ADR-0018)**: 鍵を持たないので端末の追加・失効(チェーン op)は置けない。置けるのは端末一覧の**読み取り**(登録簿 = サーバー申告 — `GET /auth/devices` をセッション許可列挙へ追加)と、既存のトークン失効(資格を減らす方向 — 改訂 2 の境界内)。紛失時に手元に CLI が無い人の最初の一手はここ(トークン失効で API 経由の新規取得を即時に止める。その後 `key recover` → `device revoke`)
- **`maruhi ui`(第 2 段)**: 端末の承認(儀式)は TTY に残す(ADR-0018 改訂 1・2 項)

→ §1-4「変えないもの」に明記済み。単巡。

### 裁定 DK-L: CLI の命名と導線(列挙 1 巡 + 空巡 2・打ち止め)

| 案 | 内容 | 評価 |
|---|---|---|
| L-1 **新グループ `maruhi device`** | `device add [--label]`(新端末で。鍵生成 + 要求行 + FP 表示 + 待機)/ `device approve <fp|words> [--cap <role>] [--env …]`(既存端末で。照合 + yes + 全プロジェクトへ追記 + バックフィル)/ `device list [--project]`(チェーン上の自分の端末とプロジェクトごとの登録状況 + 表示名。値ゼロ = agent-gate 非適用)/ `device revoke <fp-prefix|label> [--user <id>] [--project]`(全プロジェクトへ失効 + sweep + 履行不能の表示 + 紐付いたトークンの失効の提案)。`key` は「自分の鍵」に留める: `key generate`(端末鍵。初回は予備鍵も)/ `key show`(端末 FP と予備鍵 FP)/ `key publish`(この端末の sig 鍵)/ `key recover [--passkey|--handoff]`(予備鍵の復元 → 端末鍵の発行 → 予備鍵の秘密の破棄)/ `key recovery`(コード再発行 = 予備鍵の再封印)/ `key seal …`(予備鍵のパスキー封印)/ **`key reserve rotate`**(新予備鍵の登録 + 旧予備鍵の失効)。`key approve <code>`(KL3 — 旧端末 / 保護者の共通承認)は旧端末経路の削除に伴い **`guardian approve <code>`** へ改名(保護者承認だけが残るため)。`agent` は不変 | 端末は「自分の資源」で、`member`(他人の管理)とも `key`(自分の鍵 1 本)とも違う語彙。help の一覧に 1 行増える |
| L-2 `key` の拡張(`key add-device` / `key devices` …) | グループを増やさない | `key` が「自分の鍵」から「自分の端末群」まで膨らみ、`key approve` / `key recover --handoff` の意味も混ざる。棄却 |
| L-3 `member` の下(`member device …`) | メンバー管理の一部と見る | 端末は本人が管理し admin は失効しかできない — member グループ(admin の操作)に置くと権限の絵が逆になる。棄却 |

**第 2 巡**: 「`device revoke` にトークン失効を常に同梱(フラグでなく既定)」→ 端末 = トークンの対応は advisory(登録簿の任意リンク)で、既定で他のトークンを消すと誤失効の面が増える。提案 + yes に留める(既定の名前 `cli:<hostname>` が一致すれば候補に出す)。新案でない。「紛失時の導線を 1 コマンド(`maruhi lost <label>`)に畳む」→ `device revoke` が同じことをする(別名を増やさない)。棄却。**空巡**。**第 3 巡**: 新案なし。**空巡**。打ち止め。

**導線の点検(3 人)**: (1) 端末を失った人: `device revoke "MacBook"`(+ 提案されたトークン失効に yes)→ 表示された「rotate を頼む相手」に連絡。CLI が無ければ Web でトークン失効 → 別端末で `key recover` → 同上。(2) 新端末を足す人: 新端末で `login` → `device add`、手元で `device approve <fp>`。儀式 0。(3) チームの owner: 他人の端末を失効させるのは `device revoke --user <id> <fp>`(remove と同じ role 規則・rotate は自分が履行)。招待・承認の手順は不変。**採用: L-1**(名称は承認項目 10 の所有者選択)。
