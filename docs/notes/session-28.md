## 2. Implementation decisions (the body of the handoff)

### 2-1. Choice of migration tool: `maruhi env rotate --init-manifest`

session-27 §14 said "a dedicated init command, or rotate"; **the rotate path**
was adopted. Reasons:

- AUTH_SPEC §12-5's manifest acceptance is **bundling into meta ops only** —
  no standalone init endpoint exists in the spec. A dedicated endpoint would
  need a spec revision (adding an acceptance path) and would permanently grow
  the attack surface just for migration
- A rotate composite always re-issues a manifest (§12-4), so adding "tolerate
  missing" to the existing command makes initialization work. And since the
  epoch advances, cleaning the pre-migration environment's old-epoch keys
  (§7's re-encryption) runs at the same time

`--init-manifest` semantics (the fail-closed boundary):

- What it loosens is **only tolerating absence when the server distributes no
  manifest**. When a manifest is distributed, all verification (signature,
  head binding, authorization, epoch consistency, digest recomputation) runs
  regardless of the flag
- **Absence on an environment whose floor already has a manifest record is
  rejected even under the flag** (no legitimate path makes an initialized
  manifest disappear = evidence of suppression)
- On an already-initialized environment the flag is a warned no-op (a normal
  next-version issuance)

CAS initial value: for an environment with no stored manifest, "latest = 0" is
assumed and manifestVersion 1 (empty prev) is accepted (clarification added to
AUTH_SPEC §12-5 (6) — see §3). Separate from the create composite where
`CreateEnvironmentManifestSchema` pins v1, the rotate / meta-op
`EnvironmentManifestSchema` also accepts v1 (the migration's first operation
issues v1).

A run where initialization is actually needed (absence confirmed) **forces
sending a rotate composite** (same path selection as `--new-epoch`): taking
interrupted-resume (restart without the composite) or a "just checking" early
return would look successful while never issuing v1 (a fix for the PR #81
review bot's finding).

**Dependency caution (PR #81 pullfrog review)**: this path depends on
`env rotate` using a valued pull (`pullVerifiedEnvironment` — which honors
`allowMissingManifest`). `pullVerifiedEnvironmentMetadata` has no migration
tolerance (the metadata-only pull has no missing-tolerance branch), so
**swapping rotate's front stage to a metadata-only pull in the future would
break the migration path**.

### 2-2. Migration procedure for existing dogfooding environments (finalized)

For each environment created before the manifest was introduced, a member or
above runs once:

```
maruhi env rotate <environmentId> --init-manifest --reason "manifest initialization"
```

- On success, manifestVersion 1 is issued and stored, and subsequent
  distributions go through manifest verification (absence joins = rejection).
  `--init-manifest` is not needed afterward
- Order is arbitrary; environments are independent. pull / run / push /
  ci run against an uninitialized environment fail on missing-manifest
  rejection until it is initialized (the error message guides to the command
  above), so **run it on all environments promptly after deploying this PR**
- **Order requirement (PR #81 pullfrog review)**: ① deploy the server →
  ② run `--init-manifest` initialization on all environments → ③ update CI
  (the CLI picked up by actions/setup-maruhi), in that order. Consequence of
  reversing: an old server × new CLI can't receive a manifest at the rotate
  endpoint, so **the guided initialization procedure itself fails** (no
  server-version negotiation exists). If CI picks up the new CLI before the
  environments migrate, `verifyLeaseDistribution` — which has no migration
  tolerance (a workload can't self-initialize) — fails existing jobs on
  missing-manifest rejection (the wording is self-explanatory — it won't be a
  silent lockout)
- Not written in SELF_HOSTING.md (a pre-release internal migration — a
  post-release self-host structurally can't have an uninitialized state since
  the create composite mandates bundling v1). However, **the pre-release
  checklist (ROADMAP) got "add this migration's item to SELF_HOSTING.md's
  'Updates' section" linked** (because on a self-host where server and CLI
  update independently, the same shape happens post-release — same home as
  the 2026-08-11 client_id migration precedent)

### 2-3. Floor-file compatibility policy (settling trap 8)

The floor (`floor/<projectId>.json`) is strictly decoded (schema mismatch =
whole-file corruption), but the `EnvironmentFloor.manifest` field is
**optional, and absence is tolerated as "no manifest floor"**:

- v1 floor files written before the manifest was introduced lack this field;
  treating absence as whole-file corruption (a fail-open rebuild) would also
  discard the detection material in the existing value / meta floor. The floor
  version (`v: 1`) is not bumped
- If the field **exists but is malformed**, it's whole-file corruption like
  any other field (strict-decode principle preserved)
- Merging is monotonic (the larger manifestVersion wins; the side missing the
  field doesn't lose). The variable-creation composite's floor commit
  (`commitPush`) also rides the manifest forward

### 2-4. One verification implementation in packages/crypto

`verifyDistributedEnvManifest` (manifest-verify.ts) is the single
implementation for both server acceptance (§6.4) and client distribution-time
verification (§6.3). Same shape as value-verify / meta-verify (shares
chain-history.ts's declared-head-point lookup and headAuthorizationReason).

- **The composite-issuance epoch special case** (the verification-side shape
  of §12-5 (4)): even on a mismatch at declared head H, accept when "the H+1
  entry establishes exactly that epoch on that environment" (create composite
  = epoch 1, rotate composite = new_epoch). Since epochs move at most +1 per
  entry, the two conditions are equivalent. The soundness argument (a key that
  lost write standing can't take the special case) is in manifest-verify.ts's
  module comment and pinned by the `composite_epoch_rule` vector family
- prev-linkage actual-match and epoch non-decrease are checked only when a
  predecessor is passed (latest-only distribution — same shape as ruling B).
  Cross-session regression, same-version difference, and forward injection
  are carried by the floor's manifest extension

### 2-5. Re-signing on CAS retry (§12-5 (6))

- A rotate chain-CAS (ChainHeadConflict) retry re-signs **both** the entry and
  the manifest on each attempt (the declared head advances)
- `ManifestVersionConflict` (409) is handled differently per command:
  - **rotate**: can't be resolved by an in-run re-sign (a concurrent meta op
    may have changed the meta set itself, and without restarting from pull the
    digest's material is stale), so it guides a re-run and aborts
  - **push (variable creation)**: joins the existing name-resolution loop (the
    same entry as MetaVersionConflict), re-reads the meta state, and re-signs
    both the statement and the manifest
- Bulk variable submission runs sequentially (§12-5's implementation note —
  sweep-rotate was already sequential)

### 2-6. Server retention and distribution

- `environment_manifests` is 1 row per environment (UPSERT) — it does not
  store every manifestVersion (§12-5 / §12-8. The history of session-27 §16
  withdrawing the row-cap option)
- Environment deletion cascade (`retireEnvironment`) removes the row.
  Environment deletion does not re-issue a manifest (§12-4)
- Bundled into both pull modes (valued / metadata-only) and the lease
  response (§14-2). Optional on the wire only during the transition until
  migration completes (the server always bundles it if a stored row exists)

## 3. Spec divergence (report on trap 1)

**No semantic divergence**. During implementation, 3 places where "the spec
didn't pin it down" were appended to the spec as clarifications (each with a
Status line in the existing format — this PR's "to-be-ruled"):

1. **AUTH_SPEC §12-5 (6)**: the manifestVersion CAS initial value — no stored
   manifest = latest 0 → manifestVersion 1 accepted (migration path. No
   dedicated init endpoint is created). **Supplement (PR #81 pullfrog
   review)**: accepting v1 on a non-composite meta op requires the declared
   head = the current head at acceptance time — v1 is accepted from latest 0,
   and the CAS can't detect a rotation after the declared head (the argument
   "don't add an independent acceptance-time epoch check" fails precisely for
   v1), so this blocks baking a stale epoch by the same kind of requirement as
   the composite path's pinning. The implementation is a single place:
   `acceptManifestForMetaOp` (the single entry for the 4 paths)
2. **CRYPTO_SPEC §6.3**: the boundary of the explicit migration init
   (`--init-manifest`) — what is loosened is tolerating absence only; absence
   after floor establishment is rejected even under the migration op
3. **CRYPTO_SPEC §6.3**: the basis for applying floor rule (c) to manifests —
   the larger of "the pull-time epoch floor" and "the floor manifest's own
   epoch" (review-bot finding: in the window right after a rotate is accepted
   where the pull basis lags in bounded re-sync form, a forward
   manifestVersion baking in an old epoch would slip through. It's the
   transitive form of the manifest chain's epoch non-decrease — §4.3
   epoch-regressed — so the strengthening produces no false positives)

## 5. Handoff

1. **Connecting to M2 (checkpoints)**: `latestCheckpoint` derivation and
   checkpoint-consistency verification (§6.3) are not in this PR. The shape
   where the manifest's `signedBytesHashHex` (floor record,
   `VerifiedManifest`) becomes material for the checkpoint's manifest
   reference is already secured
2. **The residue of meta forward injection** (after §14.3-5's shrink): even
   with the floor's manifest rules, injection into "a client that hasn't
   pulled once since the attack key's membership interval ended" is not
   detected (the same-kind limit as the value's rule (c)). The non-guarantee
   is pinned by a test (floor-detection.test.ts — in the form advancing
   together with the manifest). More generally, **detection in the rollback
   direction depends entirely on the local floor at M1** (distribution-time
   verification doesn't pass a predecessor, so prev actual-match and epoch
   non-decrease don't fire, and a declared head need only exist on the
   verified chain, not be the tip — the same convention as values and meta).
   The 2 places where §4.3's "freshness anchor" is genuinely needed
   (first contact with no floor, disposable CI runners) are not protected in
   M1 — distributing an internally-consistent old manifest + old statement
   set passes. That closure is M2 (checkpoint consistency) / M4 (head gossip)
   territory (a confirmation item in the PR #81 pullfrog review — don't read
   it as more than it is in later PRs)
3. **The CLI's variable rename / delete and environment rename / delete
   commands stay unimplemented** (outside this PR's scope — the API paths are
   pinned by server tests). When adding them, don't forget manifest bundling
   (signNextManifest) — api-schema's payload types make manifest required, so
   forgetting is caught by a type error
4. **Sequential execution of bulk submission**: when implementing batch
   creation from CI in the future, manifestVersion CAS serializes it per
   environment (§12-5's implementation note)
