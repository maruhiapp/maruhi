# 検討メモ: デバイス鍵のハードウェア裏付け — 封印(sealing)方式の比較

日付: 2026-08-10。CRYPTO_SPEC 未決事項 #2(デバイス鍵分離・パスキー PRF)の将来設計に向けた検討メモ。
**本メモは仕様変更ではない**。採否・詳細設計は Phase 2 以降のデバイス鍵分離の設計時に所有者が裁定する(CRYPTO_SPEC の改訂 → 人間承認 → 実装、の順は不変)。

## 1. 背景ときっかけ

きっかけは mizdra 氏の記事「Secure Enclave を使用した Git コミット署名鍵管理」(<https://www.mizdra.net/entry/2026/08/07/101542>)。要点:

- macOS の Secure Enclave(SE)内に non-exportable な ECDSA P-256 鍵を生成し(`sc_auth create-ctk-identity`)、SSH 署名として Git コミット署名に使う
- 動機は「コーディングエージェントに作業を委託中、1Password の生体認証タイムアウトでコミットが中断される」問題。SE 常駐鍵なら対話的認証なしで署名でき、かつ秘密鍵はチップ外に出ない
- 記事自身が明示する限界: 同一端末内のマルウェアは SE に署名を「依頼」できる(鍵は盗めないが使える)

maruhi 側の現状と接点:

- CLI は master 秘密鍵を OS キーチェーンに生バイトで保存し、使用時に都度インポートする。spike-c.md の知見 4 の通り「メモリ上に生鍵がある時点で extractable=true と等価」であり、ここがクライアント TCB の実質的な最弱点
- v1 は 1 ユーザー = 1 master keypair を各デバイスへコピーするモデル(CRYPTO_SPEC §3)。端末 1 台の紛失 = アイデンティティ全体の危殆化であり、デバイス単位の失効ができない
- エージェント検出(`gunshi/agent`)の問題意識は記事の動機と同一線上にある

この記事から maruhi が持ち帰るべきなのは「Secure Enclave という道具」ではなく、**「長期鍵を端末から持ち出せなくする」という性質**である。

## 2. 前提: どの案もデバイス鍵分離が先

以下の全案は、デバイス鍵分離(未決事項 #2)を前提とする。セキュリティ価値の本体はハードウェアそのものではなく**失効可能性**にある(端末紛失 → その端末の鍵だけをチェーンで失効し、エポックをローテーションする)。デバイス鍵分離自体が §3(鍵階層)・§5(ラップのファンアウト = メンバー × デバイス)・§6(チェーン op: デバイス追加・失効)・§8(リカバリー)・AUTH_SPEC(デバイス登録 API)に波及する大きめの仕様改訂であり、ハードウェア裏付けはその上に載る強化である。

## 3. 案の比較

### 案 1: ハードウェア常駐鍵(記事の直訳)

デバイス鍵そのものを SE / TPM 内に non-exportable で生成し、署名・鍵合意をハードウェアに依頼する。

- 利点: 秘密鍵がプロセスメモリにすら現れない(最強の保管)
- 欠点:
  - SE は P-256 のみ。`maruhi/v1` の X25519 / Ed25519 は載らず、**スイート変更が必須**になる
  - **PQ 移行との構造的衝突**: `maruhi/v2`(X25519+ML-KEM-768 ハイブリッド)の KEM はハードウェアに載らない。鍵をハードウェアに縛ることは、アルゴリズムをハードウェアの更新サイクルに縛ること
  - WebCrypto では到達できず、OS ごとのネイティブバインディング(Security.framework / CNG / TPM2-TSS)が暗号プロトコル実装に入り込む(絶対規則との衝突)
  - CI ランナー・コンテナには SE / TPM がなく、必須化できない(ソフト鍵経路が恒久的に併存し、テストマトリクスが倍増)
- 判定: enc(HPKE)鍵には不適。「sig 鍵だけ SE に置く」変種は筋が良いが、案 3 の封印バックエンドとしてほぼ同じ利得をスイート変更なしで回収できるため、単独では採らない

### 案 2: PRF 封印(sealed device keys)

デバイス鍵はソフトウェア鍵(X25519 / Ed25519 のまま)とし、WebAuthn PRF 拡張 / CTAP2 hmac-secret でハードウェアから導出した秘密を KEK として**封印(暗号化)して保存**する。使用時のみメモリ上で開封する。

- スイート変更ゼロ(封印はローカル保存層であり、ワイヤプロトコルに現れない)
- PQ 移行に無影響(封印対象の鍵を差し替えるだけ)
- Web(WebAuthn PRF)と CLI(CTAP2 hmac-secret)で同一機構・二つのトランスポート
- ADR-0014 の封印バックアップ・ROADMAP の「パスキー PRF によるデバイス鍵」と同系統(既定路線の具体化)
- 失うもの: 開封中はメモリに鍵が露出する。ただし maruhi は実行時に平文値を子プロセスの環境変数へ注入するため、同一端末マルウェアに対する「メモリにすら出ない」の実効差分はもともと小さい(案 1 も記事の通り依頼攻撃には勝てない)。封印が守るのは**静止時の持ち出し**(ディスク・バックアップ・キーチェーンダンプ経由の長期鍵流出)であり、そこは案 1 と同等

### 案 3: 封印バックエンドの抽象化(案 2 の一般形。**本メモの推奨**)

「デバイス鍵は封印されて保存される」を規約とし、封印器(sealer)を差し替え可能なバックエンドにする:

| 封印バックエンド | 対応環境 | 特性 |
|---|---|---|
| FIDO2 hmac-secret(YubiKey 等ローミング認証器) | 全 OS(CLI は libfido2 系経由) | リファレンス実装。ポータブル、Web と機構共有 |
| Secure Enclave(`kSecAttrAccessControl` 保護のラップ鍵) | macOS | ドングル不要。**封印にのみ使うため P-256 でもスイート変更不要**(案 1 の欠点をすべて回避しつつ記事の利点を回収) |
| TPM2 | Windows / Linux | 同上の platform 版 |
| パスフレーズ(KDF は要選定。Argon2id 等) | 全環境 | フォールバック。ハードウェアなし環境・非常用 |

- SE / TPM がここで**封印器として再登場**する点が案 1 との本質的な違い: ハードウェア鍵は maruhi の暗号プロトコルに一切現れず、OS のセキュアストレージ機能の利用(現行の OS キーチェーン信頼と同じ層)に留まる
- 同一デバイス鍵を複数の封印器で**多重封印**できる(例: YubiKey + パスフレーズ)。封印器 1 つの喪失・故障がロックアウトに直結しない — 案 1 の non-exportable では原理的に不可能な冗長化
- 封印済みブロブは暗号文なのでサーバー保管も選択肢に入り、封印バックアップ(ADR-0014)・デバイス追加フローと同一機構に統合できる余地がある

## 4. 検討して却下した代替案・補完に回した案

- **PRF 直接導出**(封印ブロブを持たず、PRF 出力から鍵を決定論的に導出): 保存物ゼロは魅力だが、認証器ごとに PRF 出力が異なるため複数封印器の重ね掛けができず、アイデンティティが単一ハードウェアに不可逆に縛られる。リカバリー設計も壊れる。**却下**(封印方式が上位互換)
- **サーバー補助アンロック**(KEK を端末シェアとサーバーシェアの 2-of-2 に分割し、認証時のみサーバーが放出): 「エポックローテーション不要の即時リモートキル」「封印ブロブ + PIN 窃取に対するオフライン攻撃の無効化」という固有価値がある。ただし開封のたびにオンライン必須・サーバー可用性 = ロックアウトリスクという代償があり、かつ封印と**合成可能**(KEK = KDF(ハードウェア秘密, サーバーシェア))。よって置換案ではなく、**案 3 の上に将来積めるオプション層**に分類
- **ssh-agent / age プラグインへの委譲**: 署名は委譲できるが HPKE Open(Decap)が通らず、maruhi の中核操作を賄えない。外部エージェントのセキュリティへの依存も増える。**却下**

## 5. 要検証(採用検討時のスパイク項目)

1. CTAP2 hmac-secret を**タッチなし**(up=false のアサーション)で取得できるかは認証器の実装・設定に依存する。エージェント運用の成立条件は「セッション開始時に 1 回開封 → プロセスメモリ内キャッシュ(ディスクレス不変条件と整合)」で足りるか、それとも無タッチ開封が必須か
2. CLI からプラットフォーム認証器(Touch ID 等)へは CTAP では到達できない(OS ネイティブ API が必要)。CLI の現実的な既定構成 = ローミングキー + SE/TPM バックエンド、の妥当性
3. libfido2 等ネイティブ依存の供給網評価(最小依存規則との折り合い)。封印はワイヤ暗号ではなくローカル保存層だが、鍵取り扱いに触れるため `packages/crypto` 同等の人間レビューを必須とする
4. Bun からの CTAP アクセス経路(FFI / サブプロセス)の実現性と、Bun.secrets(現行キーチェーン保存)との併存設計

## 6. 採用時に必要な改訂(影響範囲の見取り図)

- CRYPTO_SPEC: §3(デバイス鍵の鍵階層)、§5(ラップ先のデバイス粒度化)、§6.2(デバイス追加・失効のチェーン op)、§8(リカバリーとの関係整理)。いずれも所有者承認フロー
- AUTH_SPEC: デバイス登録・失効 API
- ROADMAP: 将来項目「パスキー PRF によるデバイス鍵」の本メモによる具体化

## 7. 推奨まとめ

| 項目 | 推奨度 |
|---|---|
| デバイス鍵分離(前提アーキテクチャ) | **強く推奨**(失効可能性が価値の本体。未決事項 #2 の本線) |
| 案 3: 封印バックエンド抽象(リファレンス = FIDO2 PRF) | **推奨**(既定路線とする) |
| 案 1: ハードウェア常駐鍵 | 単独では非推奨(sig 鍵限定でも、案 3 の SE 封印でほぼ同じ利得をスイート変更なしで得られる) |
| サーバー補助アンロック | 将来のオプション層(案 3 と合成可能。単体では採らない) |
