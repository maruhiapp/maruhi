# セッション 42: W2a — プロジェクト一覧 API の設計裁定(BI〜BL)

日付: 2026-08-29。目的: PR-W2a(web-dashboard-design.md §7)の設計裁定の記録。
対象は S4(プロジェクト一覧)の不足 API「自分がチェーン導出メンバーである
プロジェクトの一覧」のサーバー側導出形・エンドポイント仕様・投影の維持規律。
規範の置き場は AUTH_SPEC §11-5(本 PR で起草 — 本改訂を含む実装 PR のマージを

各裁定は「複数案 → 上位互換探索 → 3 周比較 → 自律選択」(session-27 §14 の様式。
記号は session-41 の BH の続きで BI〜)。

前提資料: AUTH_SPEC §5・§9-2・§11-2・§11-3、CRYPTO_SPEC §6.4(認可の真実源は

## 1. 裁定 BI: 一覧の導出形(D1 投影 vs ファンアウト vs 複合形)

設計文書 S4 が列挙した 2 案(D1 投影 / org 経由候補列挙 + DO 確認ファンアウト)に
上位互換候補を加えて比較した。必須条件: §11-2(存在秘匿)と両立し「返すのは
本人の membership のみ」。

### 第 1 周

- **案 BI-a: org 経由の候補列挙 + DO への確認ファンアウト** — `/auth/me` の
  orgs → D1 `projects`(org 帰属)→ 各プロジェクト DO へ membership 確認。
  **棄却(性能でなく正しさ)**: チェーン membership は org 非依存である
  (AUTH_SPEC §9-2「org 加入はいかなるプロジェクトアクセスも自動付与しない」の
  対偶として、**org 外プロジェクトのチェーンメンバーは正当に存在する** —
  招待 §15 は invitee の org を一切見ない)。org 経由の候補列挙は招待経由の
  cross-org メンバー(まさに P5 — CLI を入れない利害関係者 — の主用途)を
  構造的に取りこぼす。全プロジェクト走査への拡張は O(全プロジェクト) の
  ファンアウトで論外
- **案 BI-b: membership の D1 投影(チェーン受理時に維持する導出キャッシュ)を
  新設し、一覧は純 D1 読み** — 横断索引が 1 クエリで引ける。ただし DO(チェーン
  受理)と D1(投影)は別トランザクションであり、dual-write の失効窓が両方向に
  残る: add_member 受理 + 投影 insert 失敗 = 一覧に出ない(missing)、
  remove_member 受理 + 投影 delete 失敗 = 除名済みメンバーの一覧に残る
  (ghost)。ghost 側は自己修復経路がなく、「返すのは本人の(現)membership
  のみ」が D1 障害の窓だけ破れる
- **案 BI-c(採用形の原型): D1 投影を候補索引に格下げし、一覧時に各候補を
  DO へ確認(既存 RPC `memberRoleFor` — 招待 API の認可入力と同じもの)** —
  応答は常に受理時点のチェーン導出真実(role 込み)。DO が非メンバーと答えた
  候補行はその場で削除(ghost の自己修復)。ファンアウトの範囲は「本人の
  投影行」に有界で、BI-a の候補列挙の不完全性(org 依存)を持たない

### 第 2 周(上位互換探索)

- **BI-c の投影スキーマ最小化**: role・状態列を持たない **(project_id,
  user_id) の集合のみ**とする。role は確認 RPC が返す現在値を使うため、
  `change_role` の投影追随コードが丸ごと不要になり、投影の維持点は
  「集合に入れる(genesis / add_member)・集合から消す(remove_member)」の
  2 種に縮む。採用
- **D1 `invitations` の流用(新テーブルなし)**: completed 招待の
  invitee_user_id から候補を引く案 — 棄却: genesis actor(自分で作った
  プロジェクトの owner)に招待行が存在せず、最頻ケースが最初から欠ける。
  補完に org 経由列挙を足すと BI-a の不完全性が戻り、招待行の失効・掃除と
  membership の寿命が偶発結合する(第 2 の真実源の悪い形)
- **CLI ローカルピン(非機密ローカル状態)のみで一覧**: サーバー API を
  作らない案 — 棄却: W2(web S4)が成立しない(ブラウザにローカル床はない)。
  CLI 単体の需要にはピン由来の表示を将来足せるが、本タスクの目的(S4 の
  前提 API + CLI を第一消費者にした検証)を満たさない
- **投影の置き場を DO(シングルトン逆引き DO)にする**: 棄却: プロジェクト DO →
  逆引き DO の cross-DO 書き込みで dual-write 問題は D1 と同じまま、
  シングルトン DO というホットスポットと新しい実体だけが増える。user 軸の
  クエリは D1(認証・セッションと同居)が既存の置き場

### 第 3 周(再点検)

- **存在秘匿(§11-2)との整合**: エンドポイントはプロジェクト ID を受け取らず
  (パス・クエリに対象指定がない)、応答は本人行のみ — 非メンバーが任意 ID の
  存在を探る面が構造的に存在しない。トークンスコープ外のプロジェクトは応答から
  単に不出現(他所の「スコープ外 = 404」と同じ情報量)
- **2 つの真実源の禁止(CRYPTO_SPEC §6.4)との整合**: 投影は**発見(discovery)
  専用の導出キャッシュ**であり、いかなる認可判定にも使わない(認可・role は
  従来どおり各 DO のチェーン導出状態。一覧応答の role も DO 確認の戻り値)。
  「プロジェクトアクセスについてチェーンと矛盾する独立の権限テーブル」には
  該当しない — 矛盾した行は読取時に DO 側が勝ち、行が削除される
- **DO 実体化の懸念(AUTH_SPEC §14-3 の DO 量産と同型か)**: 投影行は受理済み
  チェーン(init / add_member)からのみ生まれるため、確認ファンアウトが未知 ID の
  DO を実体化する経路はない
- **コスト有界性**: 確認ファンアウトは 1 リクエストあたり候補ページ上限
  (BK — 100)× DO RPC。候補は本人の membership 行のみで、他人が膨らませる
  ことはできない(自分で膨らませても自分のページングが増えるだけ)。Workers の
  サブリクエスト上限(1,000)に対してもページ上限が防波堤になる

**選択: BI-c(role なし D1 投影 = 候補索引 + 読取時 DO 確認)**。BI-b の
「投影 = 真実」形はどの読みでも確認を省けない(除名の ghost が自己修復しない)
ため下位互換、BI-a は正しさで不成立。採用形は「D1 投影の新設」と「DO への確認
ファンアウト」の**合成**であり、S4 の二択のどちらか単独よりも失効窓が狭い。

## 2. 裁定 BJ: 投影の維持点・修復・移行

### 第 1 周

投影(`project_members(project_id, user_id, created_at)`)の維持点:

- **init(genesis 受理)**: worker の `projects.insertIfAbsent` と同一 D1 batch で
  genesis actor(owner)の行を挿入する(projects 行と投影行の原子性 — §11-3 の
  冪等修復の再挿入経路でも同じ batch)
- **append の add_member 受理後**: upsert(INSERT OR IGNORE)。invite completed
  突合(handlers-membership.ts の既存例外)と同じ位置・同じ理由で **defect を
  握って前進する**: チェーンは確定済みで、D1 障害を応答へ伝播すると成功した
  追記が 500 に見え再試行が ChainHeadConflict になる。失敗の帰結は「一覧に
  出ない」という可視・可修復な表示欠落のみ(アクセス自体はチェーン truth で
  成立)で、修復経路(下記)が閉じる
- **append の remove_member 受理後**: delete(同じ defect 握りの位置)。失敗の
  帰結は ghost 行だが、BI-c の読取時 DO 確認が応答から排除 + 行削除するため、
  **一覧の正しさはこの delete の成否に依存しない**(delete は衛生・候補集合の
  縮小)

### 第 2 周(上位互換探索 — 修復・移行経路)

- **missing 方向の自己修復 + 既存プロジェクトの移行**: チェーン取得
  (`membership.get`)成功時に投影行を lazy upsert(INSERT OR IGNORE 1 文・
  defect 握り)する。get 成功 = DO がチェーン導出メンバーと確認済みなので
  ghost を作る方向には働かない。これにより (a) add_member 時の D1 障害の
  missing は対象者の次回同期で自己修復し、(b) **投影導入前に作成された既存
  プロジェクト(ドッグフーディング環境)は、各メンバーの次回チェーン同期で
  無人バックフィルされる**(専用の移行スクリプト・明示初期化操作を持たない —
  §12-5 (6) のマニフェスト v1 移行が明示操作を要したのは署名付き構造の発行が
  必要だったからで、投影は非署名の導出キャッシュなので自動で足りる)
- スコープ注記: タスクのスコープ外規定は「既存エンドポイントの挙動変更
  (…D1 投影採用時のチェーン受理経路への投影維持の追加を除く)」。get への
  lazy upsert は受理経路ではないが、**ワイヤ挙動(応答・エラー・判定順)を
  一切変えない投影維持そのもの**であり、これを欠くと移行が手作業になるため
  除外規定の趣旨(投影維持の追加は許す)の側で採る — PR 説明に明記する
- **一括バックフィルスクリプト(全プロジェクト走査)**: 棄却 — lazy upsert が
  恒久の自己修復を兼ねるのに対し、スクリプトは一回性の運用手順が増えるだけで
  以後の失効窓を狭めない
- **受理側 upsert を DO 内から D1 へ書く(単一トランザクション化)**: 棄却 —
  DO SQLite と D1 は別ストアで原子化は元々不可能。DO に D1 依存を持ち込むと
  チェーン受理の失敗面が D1 可用性に広がる(受理の権威を汚す)。worker 側の
  after-commit 位置(invite completed と同じ)が正しい

### 第 3 周(再点検)

- 失敗方向の総括: missing = 表示欠落(次回同期で自己修復)、ghost = 読取時
  排除(応答には現れない)+ 行削除。**どちらの窓でも「本人の現 membership
  のみ」の応答不変条件は破れない**(破れうるのは網羅性のみ、かつ自己修復)
- 投影行に FK を張らない(invitations と同じ理由: 導出キャッシュは参照整合で
  受理・修復を阻害しない)。projects 行との join も応答に要しない(BK の
  最小応答が projects 行のカラムを使わない)ため、§11-3 の部分失敗窓とも干渉
  しない
- 監査: 投影の upsert / delete は監査イベントを書かない(チェーン受理の証跡は
  `chain.member_added` / `chain.member_removed` ミラーが既に担う。導出キャッシュの
  収束は §12-6 の旧鍵ラップ掃除同様、それ自体は行動情報でない — ただし掃除と
  違い削除対象が「定義上不可視の行」なので dek.deleted のような可視イベントも
  要しない)

**選択: BJ = 受理経路 3 点(init 同一 batch / add upsert / remove delete)+
get 成功時 lazy upsert(移行・自己修復)**。

## 3. 裁定 BK: エンドポイント形・応答・認可・受理ポリシー

### 第 1 周

- **配置**: `GET /projects`(membership グループ、endpoint 名 `list`)。init
  (`POST /projects`)と同じリソースの GET で REST 的に自然、かつチェーン導出
  membership の面なので membership グループが意味的に正しい。`/auth/projects`
  (auth グループ)案は棄却 — §6 の `/auth/tokens` は認証リソース(トークン)
  自体の一覧であるのに対し、これはチェーン由来のプロジェクト面
- **応答(最小形)**: `{ projects: [{ projectId, role }], nextAfter? }`。
  role は DO 確認の戻り値(受理時点のチェーン導出 role)。**org 情報・作成
  時刻・ヘッド情報は載せない** — cross-org メンバー(BI-a の棄却理由の主体)へ
  他 org の帰属情報を新規開示しない・S5(概要)以降が持つ情報を一覧に重複
  させない、の両方から最小に固定する。拡張は加法(optionalKey)で行える
- **認可**: セッション主体 = 可(§5 の許可列挙 — SESSION_ALLOWED_ENDPOINTS へ
  同一 PR で追加。session-39 §10-1 / session-40 申し送り 1)。トークン主体 =
  スコープとの交差 — 候補のうち `tokenScopeAllowsForProject(id, read)` を
  満たすものだけを応答する(`*` スコープは全件、プロジェクト限定スコープは
  当該プロジェクトのみ)。スコープ外は**不出現**であり、他所の「スコープ外 =
  404」(§11-2)と同じ情報量

### 第 2 周(上位互換探索)

- **ページング**: `after`(省略可のクエリ、projectId 排他カーソル)+ サーバー
  固定ページ 100 件(candidates 基準・project_id 昇順)。D1 ページが満杯の
  ときのみ `nextAfter`(= ページ末尾の projectId)を返す。1 呼び出しの DO
  確認を 100 に有界化する(Workers サブリクエスト上限への防波堤を契約側に
  持つ)。クライアント指定の limit は持たない(受理ポリシーの値を増やす方向の
  ノブを作らない)。並び順は project_id 昇順(安定・一意)で、表示順の加工は
  クライアントの領分
- **レート制限**: 置かない。列挙攻撃面がない(応答は本人行のみ・対象指定
  なし)、コストは本人の投影行数に有界(他人が膨らませられない)、1 呼び出しの
  上限はページ 100 が縛る — §13-3(要監視のブロブ)や §15-2(発行)と違い、
  守るべき希少資源・秘匿対象がない。導入は将来の加法で可能
- **CSRF ヘッダー(セッション主体)**: 要求しない。§11-4 の「状態を持つ GET」の
  「状態」は監査行・計数への書き込みを指し、本エンドポイントはどちらも書かない。
  ghost 行の読取時削除は導出キャッシュのチェーン truth への収束(§12-6 の旧鍵
  ラップ掃除・§16-1 の申告行削除と同じクラス)であり、クロスサイトに誘発されても
  正当な一覧と同じ収束が起きるだけで攻撃利得がない
- **404 系エラーを一切持たない**: 対象指定がないため ProjectNotFound が構造的に
  発生しない。宣言エラーは AuthMiddleware 由来(401 / 403)のみ

### 第 3 周(再点検)

- DO 確認の拒否語彙: `memberRoleFor` の拒否は not-member / not-initialized のみ
  (下限 reader = メンバーであること。全メンバーは reader 以上なので
  insufficient-role は出ない)。両者とも「候補行が stale」を意味するため
  行削除 + 不出現に畳む。他の拒否 kind は不変条件違反 = defect
- 並行性: DO 確認は並行度を絞って発行する(実装値 10 — 1 ユーザーの一覧が
  瞬間的に 100 DO を同時実体化しない)。確認は読み取り RPC であり、DO 側は
  既存の permit 直列化に従う
- §12-10 (1) の strict 対象か: 否 — GET でありセキュリティクリティカルな
  mutation payload を持たない(strictPayload 不要)
- W2b マトリクステストとの接続: SESSION_ALLOWED_ENDPOINTS への追加により
  機械導出マトリクスの許可面(session-not-allowed が返らない・401 でない)に
  自動編入される。パスパラメータを持たないため concreteUrl の置換表の追記も
  不要

**選択: BK = `GET /projects`(membership.list)+ 最小応答 + スコープ交差 +
カーソルページング(100 固定)+ レート制限・CSRF なし**。

## 4. 裁定 BL: 固定テストの形

- **本人 membership のみ / 存在秘匿**: 2 ユーザー × 2 プロジェクトの交差
  フィクスチャで、各主体の一覧が自分の membership のみを返すことを固定
  (他人のプロジェクトは status を含め一切現れない)
- **除名の追随**: add_member 受理 → 一覧に出現(role 込み)→ change_role 受理 →
  role が追随(投影に role 列がないことの検証を兼ねる)→ remove_member 受理 →
  一覧から消える(タスク指定の固定テスト)
- **ghost の読取時排除**: 投影行だけを残して DO 側が非メンバーの状態を作り
  (remove_member 受理後に投影行を直接再挿入)、一覧が排除 + 行削除で収束する
  ことを固定(BI-c の要 — D1 delete の成否に正しさが依存しないことの実挙動証明)
- **lazy upsert(移行経路)**: 投影行を直接削除 → 一覧が空(missing 窓の再現)→
  チェーン取得成功 → 一覧に復帰(既存プロジェクトの無人バックフィルと同じ経路)
- **トークンスコープ交差**: プロジェクト限定スコープのトークンは当該
  プロジェクトのみ・`*` は全件。水準は read で足りる(どのスコープも read 以上)
- **ページング**: ページ上限を跨ぐ件数での nextAfter 連鎖と全件到達・順序
  (project_id 昇順)— ただし実プロジェクト 100+ 件の生成は重いので、
  ページ定数を注入可能にはせず(受理ポリシーの焼き込みを尊重)、投影行の直接
  挿入 + ghost 排除の合成で「満杯ページ + nextAfter」を作る
- **セッション許可**: session-capability.test.ts の機械導出マトリクスが
  SESSION_ALLOWED_ENDPOINTS の追加行を自動で拾う(許可面数の期待は列挙長と
  同値なので手書きの追随は発生しない)。positive control に一覧の 200 を追加

## 5. 実装後の再点検(上位互換の一巡再探索 — タスク手順 7)

実装完了後(server 7 テスト + CLI 3 テスト全通過後)の一巡。中核の裁定
(BI-c / BJ / BK)は覆らない。棄却込みの候補:

### 5-1. 探索 1: 一覧応答へのヘッド情報同梱(棄却)

各行に headSeq / headHashHex を載せれば CLI が「同期が古い」を一覧で警告できる
という候補。棄却: memberRoleFor の戻りにヘッドを足す変更が要り、応答の
「サーバー申告ヘッド」は検証なしでは分岐攻撃の検出を足さない(CRYPTO_SPEC §6.6 の
リース同梱棄却と同じ論法 — 「検証済み」の誤認だけが増える)。CLI の鮮度検査は
既存の `project verify` / 床の領分。

### 5-2. 探索 2: 確認ファンアウトの省略(投影 = 真実への回帰。棄却)

一覧の支配コストは DO 確認だが、実測(vitest-pool-workers)では最悪形 —
満杯ページ 100 候補全部が未初期化 DO(コールドスタート + 即拒否)+ 追加 1
ページ — を含むテスト本体が約 1.1 秒で完走しており、正しさ(ghost 窓の排除)と
引き換えにする水準のコストではない。一覧は低頻度(ダッシュボード表示・CLI
明示操作)。ページ 100 × 並行 10 の形を維持。

### 5-3. 探索 3: `me` 応答への件数同梱・一覧の `/auth/me` への統合(棄却)

`/auth/me` に projects を吸収する案は、me(認証自己情報 — 毎呼び出し)へ DO
ファンアウトのコストを恒常付加し、W2b の許可列挙の粒度(me は認証系・一覧は
読み取り系)も混ざる。分離を維持。

### 5-4. 探索 4: lazy upsert の条件書き込み化(棄却)

チェーン取得ごとの投影 upsert(INSERT OR IGNORE 1 文)を「行が無いときだけ
書く」(先読み + 条件分岐)にする案。棄却: D1 の read + conditional write は
文数が増える方向であり、INSERT OR IGNORE は既に no-op 側が最小コスト。取得
経路の支配コストは DO RPC(チェーン全体の運搬)で、1 文の D1 upsert は
オーダーを変えない。

### 5-5. 探索 5(レビュー反映): nextAfter のスコープ外 ID 漏れ(欠陥修正)

PR #106 の Cursor Security Agent 指摘(MEDIUM)。初版は `nextAfter` を
スコープ交差・DO 確認**前**の候補ページ末尾から出しており、スコープ限定
トークンへ「本人の投影にあるがスコープ外の project_id」(ID = genesis
ハッシュ = 実質 capability)がカーソル経由で漏れた — §11-5 の「スコープ外 =
不出現」に対する自作の違反(裁定 BK 第 2 周が「ページは候補基準」を先に決め、
第 3 周がカーソルの中身を情報開示面として点検しなかった)。

修正の比較:
- **確認済み行基準のカーソル + サーバー内スキャン継続** — 棄却: ghost /
  スコープ外の長い尾部で 1 呼び出しの走査が有界にならず、有界化するとカーソルが
  進まなくなる(打ち切り位置のカーソルは同じ漏れを持つ)
- **不透明カーソル(暗号化)** — 棄却: 鍵管理・実装面の追加に対し、漏れの根は
  「候補空間がスコープより広い」ことであり、隠蔽は根治でない
- **候補列挙の SQL レベル交差(採用)**: トークンのスコープが名指しする
  プロジェクト ID 列(スキーマ上限 100 エントリ)を候補クエリの `IN` に渡し、
  候補空間自体をスコープ内に閉じる。`nextAfter` は構成上スコープ内 ID しか
  運ばない。`*` スコープ・セッションは制限なし(全件が本人資格の視界)。
  応答行への従来の述語適用は深層防御として維持

残余(受容・§11-5 に明記): セッション・`*` スコープの主体の `nextAfter` に
本人の stale ghost 行の ID が載りうるが、本人の membership 履歴由来で新情報を
運ばない。回帰テスト(スコープ外候補 100 件 + スコープ限定トークン → 応答の
全フィールドにスコープ外 ID 不出現)を追加した。

### 5-6. 探索 6: 投影を不要にするプラットフォーム機構(棄却)

Durable Objects に「名前空間内の実体列挙」「タグ・逆引き索引」の類の
プリミティブは存在せず(名前指定の解決のみ)、user 軸の横断クエリは D1 に
置くのが唯一の実装可能形。KV / R2 への投影も D1 に対して原子性(init の
同一 batch — BJ (1))と索引クエリの両方で劣後する。銀の弾丸なし。
