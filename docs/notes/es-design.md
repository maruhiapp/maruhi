## 1. Overview

### 1-1. Restating the problem

The current v1 simplification (CRYPTO_SPEC §3) is "**every member receives every environment's DEK**". Anyone let into the project can decrypt prod even with the reader role. Competitors' RBAC hides prod behind "server policy", but if the server is compromised the policy is gone. To extend maruhi's differentiator (ADR-0014 decision 1: "a wider set of parties you don't have to trust") onto the environment axis, restriction must happen **by key distribution, not by policy** — a DEK wrap for prod simply **does not exist** for an out-of-scope member, so it cannot be opened even if the server is compromised.

At the same time, restricting by key distribution automatically entails:

- **The performer of a wrap is a DEK holder** (§7), so the operation "put someone into an environment" can only be done by someone holding that environment's DEK (cryptographic necessity — cannot be loosened by policy)
- **The rotate obligation on member removal** (§7's "all environments") shrinks to "the environments that member held DEKs for" — a dev-only member's departure no longer forces a prod rotation (an operational difference from competitors)
- **Narrowing** a scope is equivalent to removal from those environments and carries the same rotate obligation (the member-side version of the logic — §6.3 — where `grant_server` re-granting rejects a scope narrowing and forces `revoke_server` + rotate)

Four-eyes (PF1) answers a different problem: today a single owner's signature passes `grant_server` (handing a key to the server) or `remove_member`. One hijacked owner account, one rogue insider, moves everything. **Requiring two owners' signatures cryptographically guarantees "one person cannot do the dangerous operations"** (rather than noticing in audit afterward, they simply do not pass — supplement 17). Changing the §6.2 consensus rules = changing every client's verification rules, which is why it is bundled into the same revision as ES.

### 1-2. Picture of the mechanism (key distribution)

```
Chain (signed · distributed to all members · verified by every client)
  genesis                 owner  A   scope = all (structurally fixed)
  add_member  B  role=member scope=all
  add_member  C  role=member scope=listed{dev, staging}   ← actor A's scope ⊇ {dev, staging} (containment rule)
  add_member  D  role=reader scope=listed{prod}
  change_role C  role=member scope=listed{dev}            ← narrowing = equivalent to removal from staging → §7 obligation (rotate staging only)

Wrap recipient set of environment E: R(E) = { m ∈ current members | E ∈ scope(m) } ∪ { g ∈ active grant_server | E ∈ scope_environments(g) }
  R(prod)    = { A, B, D }        ← creating or accepting a prod wrap for C is forbidden (the environment-axis version of §6.3's "wrap targets = exactly the current members")
  R(dev)     = { A, B, C }
  R(staging) = { A, B } (after C's narrowing)
  Creating a new environment E': E' ∈ actor's scope = only actors with scope = all (a not-yet-existing environment cannot be inside a listed scope). R(E') = all-scope members (+ disclosure grants)

What an out-of-scope member (e.g. prod as seen by C) receives (ruling G):
  ○ the chain (every entry — including prod checkpoint tuples; verified but not used as the basis)
  ○ environment existence · display name · variable names · schema fields · manifest · tombstones (plaintext meta — the same line as open item #3; meta-only pull is allowed)
  ✕ ciphertexts · own DEK wraps (pulls with values are rejected) · push / meta writes / rotate / checkpoint (environment-targeting ops only inside scope)
```

The four-eyes (PF1) picture:

```
  set_approval_policy  ops={grant_server, remove_member, change_role, set_approval_policy} required=2   ← can only be enabled while owner ≥ 2
  propose   #p1  op=grant_server payload=<canonicalized payload> expires_at_ms=…   ← proposer = a role that can execute that op (if an owner proposes, that is 1 vote)
  approve   #p1                                                            ← another owner; the inner op is applied at the seq of the approve entry on which distinct-owner votes reach required
  (on application, the inner op's consensus rules are re-checked against "the state at application time"; remove_member's §7 obligation runs from the application seq)
  withdraw  #p2                                                            ← the proposer or any owner closes a pending proposal
```

### 1-4. What does not change (constraint check)

- Crypto primitives unchanged (Ed25519 signatures · SHA-256 · §2.1 LP only; scope reuses the same nested LP as `grant_server`'s `scope_environments_lp_hex`; four-eyes merely counts two existing signatures in two entries — no threshold or aggregate signatures)
- "Only humans sign" (no machine members). Approvers are human owners too
- No provider IDs are written to the chain or audit
- Semantics live inside the signed byte string (§1 principle 6): scope · proposal content · expiry · quorum are all LP fields
- Old clients are fail-closed: the payload format change (add_member / change_role) fails under the old implementation as `bad-signature` (the canonicalized byte string differs) or as Schema's strict rejection; the new ops fail as `invalid-payload` (unknown op). No compatibility path

## 2. Iterated record of rulings (ES)

Round counts are recorded honestly (items decided in a single round say so). **Note (appended 2026-09-14)**: the "2 rounds · called" and "single round" labels in this section's and §3's headings are the wording at drafting time; they did not satisfy the stopping condition. ### Ruling A: where the scope lives (2 rounds · called)

| Option | Content | Where is the plaintext | Signer | Revision range | Cost | Consistency |
|---|---|---|---|---|---|---|
| A-1 **payload extension** | Add a scope field to the `add_member` / `change_role` payloads (format change = full chain regeneration) | The chain (public) | The operation's actor | §6.2 / §6.3 / §6.4 / §7 | Medium (regenerate all existing vectors · existing chains invalidated) | As ROADMAP directs. §6.2 explicitly notes "reserved room" |
| A-2 extra op `set_member_scope` | add_member / change_role unchanged (= scope all). A separate op sets the scope. A scoped add is accepted as an **atomic pair** (add_member, set_member_scope) | Same as above | Same as above | Same as above + new op + pair composite endpoint | Medium (existing vectors unchanged as pure appends · existing chains stay valid) | The in-between state (scope=all for 1 seq) is a semantic seam. Non-atomic, a concurrent rotate wraps all environments for the new member — a leak window |
| A-3 data-plane policy | Leave the chain unchanged; the inviter "doesn't wrap out-of-scope DEKs" + the server relaxes the full-set rule | Server configuration | None (unsigned) | §12-6 only | Low | **Infeasible**: §6.3's "wrap targets = exactly the current members" (the anti-ghost-member measure) breaks; scope becomes unverifiable and unattributed. Contradicts the very requirement "by key distribution, not by policy" |
| A-4 embedding in the role string | `role = "member@prod,staging"` | The chain | actor | §6.2 | Low | String hack. Breaks role's closed set and comparisons (ROLE_RANK). Rejected |

Round 1's candidates were A-1 / A-2. **Search for a strictly-better option**: there is no way to get A-2's advantage (preserving existing chains · vectors) in A-1 — once the signed bytes change, old entries can only be verified under the old rules. The only way to get A-1's advantage (1 entry = 1 fact, simple containment rule) in A-2 is to force the pair on add_member — that is A-1's verification rules rewritten across 2 entries. **Silver bullet**: searched for "a structure that takes scope outside the role" — an independent chain per environment (project × environment membership) would mean re-splitting the whole per-project design of owner / admin · grant_server · checkpoints · anchors into per-environment units; the scale is an order of magnitude larger (rejected). No new option in round 2 → called.

**Adopted: A-1**. Reasons for rejection: A-2 needs the pair composite (a new endpoint) and an explanation of the seam, and all it buys is "preserving existing pre-public chains". Per the 2026-09-14 ruling "old implementations may be deleted" and the §11 precedent (grant_server lease-policy extension = full regeneration), the format is fixed before publication. **As a consequence, the projects on the existing validation deployment (existing chains containing add_member) become invalid under the new rules and must be recreated** (stated in approval item 1. The possibility that DK touches the add_member format again is a supplement — §6 handoff).

### Ruling B: scope encoding and structural rules (2 rounds · called)

| Option | Content | Assessment |
|---|---|---|
| B-1 **kind + list** | `scope_kind` ∈ {`all`, `listed`} + `scope_environments_lp_hex` (same nested LP as `grant_server` · lowercase hex). `all` ⇒ the list must be empty (non-empty is `invalid-payload`) | Makes "all environments" an explicit signed field. Reuses the grant_server precedent (≤ 256 elements · order is signed · generation ascending SHOULD · verification treats it as a set) |
| B-2 list only, empty = all | One field | **Fail-open shape**: a tampering that drops the list, or an implementation bug, turns into "all environments". Rejected |
| B-3 list only, sentinel `"*"` | Reserved value in the environment_id namespace | ID format is a free string (§11-1), so a consensus rule forbidding `*` would be needed. Rejected |
| B-4 list only, no way to express all | Everyone enumerated | Every environment creation would require change_role for every all-scope member (the creator signs for everyone = the creation composite balloons). Rejected |

Structural rules (fixed in round 2): (1) each id in `listed` must have a **`create_environment` preceding it on the chain at that point** (`unknown-environment` — the same reason code as rotate / checkpoint. Typos fail closed, and no ahead-of-time scopes to nonexistent environments). A deleted (tombstoned) environment may still be listed since the chain does not observe the deletion (harmless). (2) Duplicate ids are `invalid-payload` (the checkpoint precedent — duplicates carry no information in set semantics, but the seed of nondeterminism is culled at the structure stage). (3) an **empty `listed` list is valid** (= a member who receives no environment's DEK; meta still visible; expresses "will be admitted later" or "an admin who only administers". `all` and `listed{}` are distinct states, no ambiguity). **Silver bullet**: grouping the environment namespace (tags) and writing scope in tags — tags become mutable off-chain meta, violating principle 6 (rejected). Called.

**Adopted: B-1 + structural rules (1)(2)(3)**.

### Ruling C: the relationship between role and scope — do owner / admin also carry a scope? (3 rounds · called)

| Option | Content | Assessment |
|---|---|---|
| C-1 reader / member only | admin / owner are always all. Entries with role ≥ admin must have `scope_kind = all` | Simple. "prod only for owner / admin" can be written. A dedicated dev-team admin cannot be expressed |
| C-2 **only owner is fixed to all; admin and below may be listed** | Works in combination with the containment rule (ruling D) | Strictly better than C-1: setting admin to all reproduces C-1's behavior. A dev-only admin (can only manage dev's membership) can be expressed |
| C-3 owner may also be listed | — | Loses the "last owner" protection, grant_server (disclosure of all environments), and the performer of the all-environment rotate obligation. Rejected |

Round 1: C-1. Round 2: C-2 turned out to be strictly better (covers every C-1 case; the rule is just "owner is all" + containment). Round 3: C-2's drawback = the current implicit expectation "an admin can see every environment" breaks in some scenes (an admin also declares a scope) — with the CLI default at `all`, the experience is unchanged. No new option → called.

**Adopted: C-2**. Consensus rule `scope-role-mismatch`: an entry with `role = owner` (including genesis's owner — genesis is structurally all) whose `scope_kind ≠ all` is invalid.

### Ruling D: (d) can an admin put people into environments outside their own scope? (2 rounds · called)

The physical constraint comes first: **the performer of a wrap is a DEK holder** (§7). An admin who does not hold prod's DEK cannot create a prod wrap for a new member.

| Option | Content | Assessment |
|---|---|---|
| D-1 **containment rule** | Derived from principle 1 "ability to change permissions" (3-ter — revised from "feasibility of discharging obligations" in pullfrog round 9 on 2026-09-14): if an entry changes a member's permissions in environment E (ability to read / write values, rotate, checkpoint), then actor's scope ∋ E. **The environment set of the permission change** = `add_member`: the new scope / `change_role`: old ∪ new if the role changes, old △ new (symmetric difference) if only the scope changes / `remove_member`: the current scope. **Invalid unless actor's scope ⊇ the environment set of the permission change** (`scope-not-contained`). Set algebra is defined with `all` = the set of all environments U (including future ones) and `listed{X}` = the finite set X (`all △ listed{X} = U \ X` — a `change_role` where old or new is `all` is only possible for an `all` actor. 2026-09-14 Cursor Bugbot fix: if `all` were expanded into the ids of existing environments, a listed admin could set a target to `all`). The obligation's environment set (add = new scope, change_role = symmetric difference ∪ demotion part, remove = current scope) is a subset of the permission change's environment set, so feasibility of discharging the obligation follows as a **corollary**. An owner is all, so always passes. (History: initially "new scope" only, which missed the rotate obligation of the narrowed part; corrected to "old ∪ new"; in 3-ter it was re-derived from "feasibility of discharging obligations", but that is only a necessary condition for authorization, and a scope-unchanged promotion [a dev-only admin raising a prod reader to member — the obligation's environment set = ∅] still passed. Closed by making the ability to change permissions the principle and demoting feasibility of obligations to a corollary.) | "Can be admitted = can hand over the DEK" and "can be removed = can discharge the rotate obligation (re-encryption needs the old DEK)" line up structurally. Never creates a dangling state (a member exists but nobody can build their wraps) |
| D-2 no containment + delegated backfill | An admin may grant any scope; another in-scope member (member or above) backfills the DEK | The state "member exists but no wrap" becomes the norm (§12-4's asymmetry made permanent). The rotate obligation on remove is also left to others. Rejected |
| D-3 unneeded under C-1 (admin = all) | — | Since C-2 was adopted as the strictly-better option in ruling C, the containment rule is needed |

**Silver-bullet search**: "a shape where the fact of holding the DEK structurally enforces the rule without checking the actor's scope" = bundling the backfill into the add_member composite. §12-4's reason for rejecting the composite still stands ("all environments × all epochs can exceed the 1-request cap") (rejected). No new option in round 2 → called.

**Adopted: D-1**. The application to remove_member is by the symmetry "can remove = can rotate" (a dev-only admin cannot remove a prod member). Check order (fixed in vectors): **the scope checks go after the existing check sequence** (preserving every existing negative case's expected reason) — add_member = role rules → `duplicate-member` → `duplicate-member-key` → `unknown-environment` → `scope-role-mismatch` → `scope-not-contained`. change_role = role rules → `unknown-target` → `last-owner-protected` → `unknown-environment` → `scope-role-mismatch` → `scope-not-contained`. remove_member = role rules → `unknown-target` → `last-owner-protected` → `scope-not-contained`. Four-eyes' `approval-quorum-unreachable` sits at the end of each sequence.

### Ruling E: environment-targeting ops (create / rotate / checkpoint) and scope (2 rounds · called)

| op | Rule | Reason |
|---|---|---|
| `rotate_epoch` | Target environment_id ∈ actor scope (`environment-out-of-scope`) | Re-encryption needs the old DEK. A rotate outside scope cannot be discharged |
| `checkpoint` | Every tuple's environment_id ∈ actor scope (same as above) | The preimage of values_digest (value_sig_hash) can only be obtained via a pull with values, which is unavailable outside scope. It is a consensus rule so that §6.3's basis never depends on "a tuple notarized by an out-of-scope member" in any implementation |
| `create_environment` | New environment_id ∈ actor scope = **only `all` actors** (same as above) | A not-yet-existing environment cannot be in a listed scope (ruling B-(1)), so it falls under the same single predicate with no dedicated rule. Avoids the shape "creating an environment the creator cannot receive" (= losing the DEK right after creating it) |

**Strictly-better search**: the "implicitly add the creator to the scope on create" option — a scope change not in the signed bytes (violates principle 6). "When a listed actor creates, the new environment is auto-added to the listed set" is rejected for the same reason. No new option in round 2 → called.

**Adopted: the table above**. Check order: role rules → `unknown-environment` (rotate / checkpoint) → `environment-out-of-scope` → the existing subsequent checks (epoch ordering / checkpoint-epoch-mismatch …). create = role rules → `duplicate-environment` → `environment-out-of-scope`.

### Ruling F: (a) is scope narrowing equivalent to remove? (2 rounds · called)

| Option | Content | Assessment |
|---|---|---|
| F-1 **accept narrowing and impose the §7 obligation** | In `change_role`, environments in old scope \ new scope ≠ ∅ count as "removal from that environment" = that environment's `rotate_epoch` obligation. The obligation starts at the entry's seq | Just adds a fourth kind `scope-narrowed` to the same interruption-recovery structure (rotation-sweep) as remove / demotion / revoke |
| F-2 reject narrowing in consensus rules (the grant_server shape) | Narrowing is done as remove + re-add | Restarts the invitation (acceptance · backing · anchor), splits tenure, and breaks audit's membership intervals. grant_server rejects narrowing to prevent "cosmetic narrowing without rotate"; imposing the obligation achieves the same end. Rejected |

**Rotation-needed detection** (AUDIT_SPEC §4.1) derives its candidate set from "per-environment access windows" — the same shape as the structure the revoke_server variant already has for re-grant on widening (`scopeStarts` of `grantIntervals`). Detection on narrowing is limited to the narrowed environments, and `rotation.recommended`'s origin is the seq of that `change_role`. For **widening**, the obligation is a backfill by the actor (a DEK holder — the containment rule) (same shape as after add_member — the appended path of §12-6). The obligation for **demotion** (below member) is "the environments of the target's scope". The obligation for **remove** is "the environments of the target's current scope" — the part that was wider in the past already has its narrowing-time obligation tracked separately (the sweep follows it independently), so the current scope suffices. No new option in round 2 → called.

**Adopted: F-1**.

### Ruling G: (b) what an out-of-scope member sees · cross-environment verification (2 rounds · called)

| Option | Content | Assessment |
|---|---|---|
| G-1 hide existence too | Exclude from the environment list | **Impossible**: an environment's existence is on the chain as `create_environment` and every member verifies it |
| G-2 **meta visible · only values and DEKs not received** | Environment existence · display name · variable names · schema fields · manifest · tombstones are distributed (meta-only pull allowed). Pull with values · own DEKs · push · meta writes · rotate · checkpoint are refused | Consistent with the line of open item #3 (variable-name secrecy) — extends the current policy "names are visible to the operator" to between members. `maruhi schema` (no values) working outside scope is desirable for agent use |
| G-3 distribute ciphertexts too | Undecryptable without the DEK | Pointless to distribute; only widens the surface of "server compromised + DEK leaked later". Also muddies the semantics of `var.read` (pull with values = recorded). Rejected |

**Cross-environment verification**: (i) `checkpoint` can notarize a subset of environments (§6.2), so tuples of out-of-scope environments are "verified (they are a consensus-rule target — the issuer is checked to be in scope) but not used as one's basis". The §6.3 checkpoint-consistency basis is only needed for **environments one pulls**. (ii) Manifest verification is only for pulled environments (unchanged). (iii) Head attestations · invitation-link anchors carry no environment — unchanged. Repository anchors (per-environment epochs) are chain-derived values, so they can be written for out-of-scope environments too (unchanged). (iv) The floor (§6.3 local floor) is "the join of facts that verified", so a floor for out-of-scope environments simply never gets established. **Silver bullet**: none (G-2 extends an existing line). No new option in round 2 → called.

**Adopted: G-2**. Rejection shape: pull with values / fetching own DEKs / writes targeting an environment where the target environment ∉ the caller's scope is **403 typed `InsufficientScope`** (environment existence is already known from chain derivation, so it is not folded into 404; the same layer as role-insufficient 403).

### Ruling H: (c) the environment axis of effective permission and composition with the CI lease policy (2 rounds · called)

A general n (≥ 2) has the same verification cost (distinct-owner vote count ≥ n), and the owner count ≥ n condition generalizes naturally. ### Ruling P3: the set of target ops (2 rounds · called)

Ops that can be targeted: `grant_server` / `revoke_server` / `remove_member` / `change_role` / `add_member` / `set_approval_policy`. Ops that cannot: `genesis` (structure) / `create_environment` / `rotate_epoch` / `checkpoint` (do not stall data / safety-side operations — rotate is incident response and must not be delayed by four-eyes) / `propose` / `approve` / `withdraw` (recursion). `set_approval_policy` is always a target while on, regardless of the enumeration (P2). `revoke_server` can be targeted because even the "stop disclosure" direction admits mistakes (stopping a lease path = stopping CI) — it is not in the recommended default set. Recommended default set (when CLI `--ops` is omitted) = `{grant_server, remove_member, change_role, set_approval_policy}` (approval item 17). No new option in round 2. **Round 3 (2026-09-14 pullfrog review — a hole in the default config)**: without `add_member` in the default set, a single owner can directly append their own second keypair as an owner and meet quorum with a second owner of their own making (`distinct` is a chain identity, not a person). Option 1 = make `add_member` / `change_role` that establish the owner role **always-targeted**, by the same argument as `set_approval_policy` / option 2 = add `add_member` to the default set (every invitation path becomes four-eyes, and the hole returns in deployments that drop it) / option 3 = state it as out of guarantee + CLI warning. **Option 1 adopted** (the ability to add owners is the very premise of four-eyes. Strictly better than option 2 — the default set is unchanged and the hole stays closed even when dropped). Residual: multiple owner identities held by the same person before enablement cannot be detected (stated in §14.2-10). The relationship between policy change and pending proposals was fixed as "judged under the policy current at each approve" (nit fix — A-2). **Round 4 (pullfrog review — the cost of always-targeting)**: when there are exactly `required` owners and one is permanently lost, the remaining owner can neither add an owner (always four-eyes), remove / demote the lost owner (`approval-quorum-unreachable`), nor turn the policy off (always four-eyes) — the admin plane locks out (the data plane keeps working; a lost key without a registered recovery wrap and a "person never returns" case have no detour). Options = (i) state as residual + on enablement the CLI guides "owner ≥ required + 1" and recovery registration for every owner (operational precondition), (ii) strengthen the enablement condition in consensus rules to `>` (spare owner mandatory), (iii) timelocked break-glass (conflicts with principle 6 and P6's timestamp ruling — rejected). **(i) adopted; (ii) is left to the owner's choice as approval item 17** (strengthening it in consensus rules would stop 2-owner teams from using four-eyes at all)

### Ruling P4: approvers and proposers (2 rounds · called)

- Approvers are **owners only** (distinct user_id). An option to include admins as approvers would let "2 admins remove an admin" = a bypass of the owner's admin authority (§6.2); rejected
- The proposer is **anyone who can execute the inner op under the normal role rules** (an admin can propose a reader's removal). If the proposer is an owner, the proposal counts as 1 vote (the 2-owner flow = proposal + 1 approval)
- A proposer cannot stack an approval entry on top (distinct). There is no approval revocation (each proposal is closed via `withdraw`)

### Ruling P5: the application point and re-checking (2 rounds · called)

- The inner op is **applied at the seq of the `approve` entry on which votes reach `required`** (inclusive convention — a remove's tenure end, a change_role's new role, take effect at that seq)
- On application, the inner op's consensus rules are re-checked against **the state at application time** (target existence · role rules · containment rule · last owner · key duplication · reachability …). In addition, **the proposer must still be a current member holding the same key FP and the role the inner op needs** (`proposal-void` — a proposal whose proposer was removed, demoted, or rekeyed after proposing cannot complete)
- **A vote = the actor of the current `approve` itself + "past voters who are still owners at the moment of the current `approve` entry"** (2026-09-14 Cursor Bugbot fix · round 2 made the current approver's inclusion explicit): if only owner status at voting time were checked, a vote by a voter later demoted or removed would remain, letting a single remaining owner complete (a four-eyes breach). The vote count is recomputed in the pre-application state at each approval; the current approver is already confirmed owner by the role rules and is always counted
- The same checks run at proposal time too (an op invalid at the proposal stage is not stacked as pending — the `propose` itself is an invalid entry). The double-check cost is negligible at one entry each
- An approval entry whose application fails is an **invalid entry** (it does not go on the chain). The pending proposal stays (closed via withdraw). The shape "a proposal auto-closes when application fails" was rejected — it gives an approver's signature the ambiguous side effect of "closing"

### Ruling P6: proposal expiry (3 rounds · called)

| Option | Content | Assessment |
|---|---|---|
| P6-1 no expiry + withdraw | Pending is closed explicitly | Old proposals get forgotten, and a context-lost owner risks approving them later |
| P6-2 seq distance | Expire after N entries from the proposal | seq is activity, not time (in a quiet project it stays valid forever). Rejected |
| P6-3 **`expires_at_ms` + the approver's timestamp** | `expires_at_ms` in the proposal payload. Consensus rule: `approve` entry's `timestamp_ms ≤ expires_at_ms` (`proposal-expired`) | The first use of timestamp in chain verification. Since `timestamp_ms` is the approver's own declaration, **the expiry is a UX safety device protecting honest approvers from context-lost approvals, not a guarantee against a malicious approver** (faking it backwards approves an expired one — but that approver is the legitimate holder of 1 vote anyway). §14.2-10's guarantee does not depend on expiry |

Round 3: whether P6-3's timestamp use contradicts chain-history.ts's discipline "timestamps are never used for authorization decisions" — the discipline's intent is "do not judge tenure / role by time" (seq is authoritative); P6-3 does not change the seq-based application point and merely uses the approver's own signed time as an additional rejection condition called expiry. The spec explicitly says "the only place timestamp is used in a consensus rule". Default expiry = 7 days (the same drafting value as invitation expiry). No new option → called. **Supplement (2026-09-14 pullfrog review)**: the drafting-time claim "the effect only runs toward rejection = fail-closed" held on only one side (an approver can fake `timestamp_ms` backwards; the chain has neither monotonicity nor an upper bound), so it was retracted and the wording "not a guarantee against a malicious approver" was stated as above. Adding a lower bound (≥ the proposal entry's timestamp) cannot stop in-window fakery and adds no guarantee, so it was not taken.

**Adopted: P6-3 + `withdraw` op**.

### Ruling P7: the origin of `remove_member`'s rotate obligation (single round)

**The application point** (the seq at which approval completes). At proposal time the member is still enrolled; the obligation's object (DEK revocation) does not exist yet. rotation-sweep derives obligations from "applied removes" (the seq of the approve entry that completed the application, not the proposal entry). Rotation-needed detection (AUDIT §4.1) also runs at the same seq. Single round (uniquely determined by application semantics).

### Ruling P8: server acceptance (§6.4) · audit mirrors (§3.4) · CLI (2 rounds · called)

- Acceptance: `propose` / `approve` / `withdraw` / `set_approval_policy` are **generic appends** (§11 — no accompanying data). Token level is the same as the inner op's (admin). Acceptance policy: pending proposals per project capped at **32** (typed 422 `ProposalLimit` — not a consensus rule; expired proposals are not counted; `expires_at_ms` is upper-bounded by server clock at acceptance + 30 days — 2026-09-14 pullfrog round 9)
- Side effects on application completion (`applyAcceptanceSideEffectsSync` in `chain-accept.ts`): for the approve entry that completes, run the inner op's side effects (remove → rotation-needed detection · delete attestation rows; add → old-key wrap cleanup · mark invitation completed)
- Mirrors: `chain.proposed` / `chain.approved` / `chain.proposal_withdrawn` / `chain.approval_policy_changed` (1 entry 1 row — the bijection invariant). **A completing approve entry additionally writes the inner op's mirror row** (`chain.member_removed` etc.) **at the same chain_seq**, with `{ viaProposalSeq }` in the payload (does not change the structure by which rotation-needed detection's membership interval Q1 reads `chain.member_removed`). `audit verify`'s bijection check is revised to "1 entry ↔ 1 row + the completing approve's application row"
- **The discharger of an obligation that went through four-eyes is the approver, regardless of the inner op's kind (2026-09-14 pullfrog / Cursor Bugbot review fix)**: application happens at the seq of the approver's approve entry, and the proposer's client is usually not running. Symmetric to remove's sweep, **the client of the approver who completed the application runs the backfill (add_member / scope widening = to the member, for every environment in the target's scope × every epoch; grant_server = to the server, for every environment in the disclosure scope × every epoch) and the rotate (remove / demotion / narrowing / revoke_server)**. The approver = owner = all, holds the DEKs, and can discharge per the containment rule. Stated as a fifth route on AUTH_SPEC §12-6's standalone registration path (spec-drafts B-6 / A-6). `add_member` is not in the recommended default set but `change_role` is, and widening happens via `change_role`, so this route is reachable under the default config
- CLI: new group **`maruhi approval`** (`list` / `show <id>` / `approve <id>` / `withdraw <id>` — a separate group from `maruhi key approve <code>` [KL3 handoff], no collision. id = the proposal entry's hash [hex 64; accepts a unique prefix of the first 8 characters]), **`maruhi project policy approvals --required N [--ops …]`** (on / change / `--off`). The existing `member remove` / `member change-role` / `server grant` / `server revoke` / `member add` emit a `propose` when the policy targets them and exit displaying "needs N−1 more owner approval(s)" (the rotate obligation converges after application by re-running `member remove` or by a sweep on the `approval approve` side — the approver runs the rotate). **The approver's CLI runs the sweep after approving** (the completer of a remove = the approver is the §7 discharger. Under the containment rule an owner is all, so it can be discharged)
- Web: listing of pending proposals only (no signatures on Web — ADR-0018)

No new option in round 2 → called.

## 3-ter. Re-examining the premise — replacing enumeration with principles (2026-09-14, answering the owner's question "can this be avoided by re-examining the premise?")

**Cause analysis**: all 4 late-found holes share the same shape — because the rules were written as "an enumeration of per-op special cases", each forgotten combination became a hole.

| Hole | What was forgotten in the enumeration |
|---|---|
| `change_role` containment covered only the "new scope" | The narrowed part's rotate obligation |
| A closed path where `approval-required` also applies to a proposal's inner op | The context "via proposal" |
| Votes by departed voters persist | The point in time at which votes are counted |
| Quorum satisfiable by a self-made owner identity | That "ops that add owners" are part of the policy |
| Scope-unchanged promotion passing outside the actor's scope (after the principle replacement — pullfrog round 9) | (Not enumeration) insufficient coverage of the principle: "feasibility of discharging obligations" is a necessary condition of authorization and did not cover permission changes that spawn no obligation |

Since adding to the enumeration just recurs on the next combination, **the rules were replaced by two principles, with per-op rules written as their consequences** (spec-drafts A-2 already revised).

- **Principle 1 — ability to change permissions** (revised from "feasibility of discharging obligations" in pullfrog round 9 on 2026-09-14): if an entry changes a member's permissions in environment E (ability to read / write values, rotate, checkpoint), the actor's scope contains E. The per-op **environment set of the permission change** is derived from the role table (add = new scope; change_role = old ∪ new if the role changes, symmetric difference if only the scope; remove = current scope). In set algebra `all` is treated as the set of all environments U (including future ones) — since `all △ listed{X} = U \ X` is not contained in `listed`, a scope change crossing `all` is only possible for an all actor (Cursor Bugbot fix). **Corollary — feasibility of discharging obligations**: the §7 / §12-6 obligations (rotate · backfill) arise only on environments whose permissions change, so obligation's environment set (add = new scope, change_role = symmetric difference ∪ demotion part, remove = current scope) ⊆ permission change's environment set ⊆ actor scope always holds, and only DEK holders carry obligations. The first version of 3-ter made "feasibility of discharging obligations" the principle, but that is a necessary — not sufficient — condition of authorization, and a scope-unchanged promotion (a dev-only admin raising a prod reader to member) whose obligation set is empty still passed (pullfrog round 9). The "gain" of letting a dev-only admin change the role of a {dev, prod} member without touching prod is synonymous with being able to grow or shrink prod's writer set — it was not a gain. A `change_role` that only changes scope still works for a dev-only admin via the symmetric-difference test
- **Principle 2 — authorization by signer set S**: for a direct append, S = {actor}; via proposal, S = proposer ∪ approvers. When required(op) ≥ 2: the distinct count of S that are owners at application time ≥ required(op) (an op with required = 1 is judged by the normal role rule = S = {actor} holds the op's role — principle 2 is an additional condition applying only when required ≥ 2, and does not deny direct appends by non-owners). **Invariant "policy monotonicity"** (two consequences — separated in pullfrog round 9): (a) while a policy is in effect, the policy-changing op (`set_approval_policy`) and owner-identity-adding ops (`add_member` / `change_role` that establish an owner) are always targeted regardless of the `ops` enumeration; (b) ops that take the owner count below required (`remove_member` of an owner / `change_role` away from owner) are invalid (reachability). Owner-reducing ops are handled by (b) and are **not** always-targeted (they can be appended directly if not in `ops` — per the premise of approval item 17 / §14.2-10). The `approval-required` exemption provision, vote recomputation, and always-targeted set are all consequences of this principle and invariant, and no longer need enumerating as exceptions

**Effect and limits**: the failure shape changes from "forgotten enumeration" to "misapplied principle" and "**insufficient coverage of the principle** (the principle drops part of what the old rules covered — row 5 above; actually happened right after the replacement)". Insufficient coverage can be detected by checking, one by one, whether each pre-replacement rule is derivable from the principle (round 9 skipped this check and dismissed `old ∪ new` as "a coarse approximation"). The latter is verifiable against the principle (K2's negative cases are enumerated per principle: principle 1 = each element of the permission change's environment set outside actor scope [including scope-unchanged promotion]; principle 2 = each element of S being non-owner / duplicate / wrong point in time). Not a zero-guarantee, but a shape where the review net works. Reason codes and check order are unchanged (needed to fix the vectors).

**Final re-read (2026-09-14 — answering the owner's "are there any other defects?")**: approval items 1–24 were re-read under 5 considerations (whether obligations have a discharger · reachability to states that break invariants · agreement between client verification and server acceptance · point-in-time skew · ES × four-eyes interactions). No ruling-changing defect was found; 2 reinforcements were appended to A-2: (i) the pending-proposal acceptance cap (32) does not count expired ones — abandoned proposals resolve by time without waiting for `withdraw` (an acceptance policy, so the server clock is fine. Pullfrog round 9: deliberate squatting only yields if `expires_at_ms` has an upper bound, so the acceptance policy carries a 30-day bound. The remedy for immediate resolution is an owner's `withdraw`); (ii) for ops via four-eyes, principle 1's discharger is the approver (owner = all) and is structurally satisfied — the principle-1 check on the proposer is a confirmation of "can this op be appended directly". Intersections confirmed as fine: an owner → admin demotion carries the scope all → listed narrowing obligation, and the actor (owner) can discharge it / a listed{} admin can only add listed{} targets (administration-only admin) / a proposer can propose their own remove (enrolled until application) / two competing proposals: the later application fails on the inner op's rules and stays pending / an undischarged narrowing obligation belongs to the narrowing's actor, not to the actor of a later remove (current scope only). **What could not be verified**: check-order interactions and the details of `audit verify`'s bijection rule can only be fixed by K2's vectors and K5's implementation tests.

**Procedure for when the owner cannot produce an option (general)**: (1) rephrase the hole as "what was forgotten in the enumeration"; (2) write in one sentence the higher purpose generating that enumeration (here: "only those who can discharge an obligation may create one" and "the policy cannot be weakened below quorum"); (3) make that sentence the rule and demote the individual rules to consequences; (4) **verify, one by one, that each pre-replacement rule (including rejected approximations) is derivable from the new principle** — an underivable rule is evidence the principle is only a necessary condition, so widen the principle (round 9's lesson). Design re-examination is done not as re-search of options but as **extracting the principle generating the rules**. A-8 (default none + `set_member_scope`) was listed alongside item 1 as the owner's alternative, and K-3 was recorded as a later addition. From now on, "called" is written only after "two consecutive rounds with no new option" is satisfied.

### K2-4. Types and set algebra (`all` = U, fail-closed) — candidate (d)

On the wire, `scopeKind` / `scopeEnvironmentIds` are held flat as 2 fields (1:1 with the canonicalization fields). The derived state is `MemberScope = { kind: "all" } | { kind: "listed"; environmentIds }`. Principle 1's containment test runs in the algebra of `EnvironmentSet = { kind: "all" } | { kind: "listed"; ids: Set }`, where `all` denotes U **or a cofinite subset of U** (`all △ listed{X} = U \ X`) — neither can be contained in a `listed` actor's scope, so both collapse to the same "`all` side" at the type level (fail-closed). `all △ all = ∅` (listed's empty set). In round 2 the option "always represent a set as a finite set + complement flag" was considered, but the containment verdicts come out the same and only the representation gets heavier, so it was not taken. **Principle**: "the only sets a listed actor can contain are finite sets" — from which `all ∪ X = all`, `all △ X → the all side`, and `listed ⊉ all` are all derived (verified to agree with every row of the canonical spec's set algebra).

### K2-5. Types of `expires_at_ms` / `timestamp_ms` — candidate (e)

Both are non-negative safe integers (§2.1 numbers = decimal-string encoding, same as the existing `timestamp_ms` shape check). `proposal-expired` is only the comparison `timestamp_ms > expires_at_ms` (equality is accepted — the `proposal-one-vote` derived chain fixes the boundary).

### K2-6. Principle 2's signer set S and `duplicate-approval` / vote count

**→ Revised in K2-11 ②·⑤ on 2026-09-15 (this section records the old ruling)**: S = {proposers who proposed as owner} ∪ {approve actors}, with elements being (user_id, key FP at signing). A promoted proposer's self-approval is not a duplicate — it is 1 vote.

The canonical spec's individual rules "if the proposer is an owner the proposal counts as 1 vote" / "a proposer who proposed as owner" and principle 2's "S = {proposer} ∪ {all approve actors}; vote count = |S ∩ owners at application time|" are **implemented on the principle side**: S always contains the proposer (regardless of role at proposal), so (i) `duplicate-approval` = "the actor is already an element of S" (a proposer's self-approval, a second vote by the same owner), (ii) vote count = the distinct number of **current** owners in S ∪ {this actor}. If a proposer who was an admin at proposal is later promoted to owner, under the principle that proposer is counted as an element of S and a self-approval becomes `duplicate-approval` (a literal reading of the individual rule "proposed as owner" would not count them, but principle 2 declares "the following individual rules are derived from this principle", so the principle wins). This shape does not appear in the vectors (no derived chain has a "proposer promotion" shape), so it goes into the **spec handoff** (below). `proposer_role_at_proposal` stays in the state but is not an input to consensus rules.

### K2-7. Carrying `propose`'s inner op and its structure check

The wire and types carry the inner op structured (`inner: { op, payload }`). Canonicalization is `inner_payload_lp_hex` = hex of the inner op's `payload_bytes` (§6.2); the implementation calls `canonicalChainPayloadBytes` recursively. The structure check inspects the inner op against the shape table of known ops; if the inner op is `propose` / `approve` / `withdraw` it is `invalid-payload` at the structure stage (a nested proposal can never be a policy target, and there is no recursive shape check — negative `propose-inner-op-nested`). Placing `genesis` / `create_environment` / `rotate_epoch` / `checkpoint` as the inner op passes structurally and falls at the authorization stage's `approval-not-required` (not a policy target) (negative `authz-propose-rotate-not-required`). Duplicates in `set_approval_policy`'s `ops` get the same set semantics as `grant_server`'s scope — not rejected at the structure stage, deduplicated when held in derived state.
