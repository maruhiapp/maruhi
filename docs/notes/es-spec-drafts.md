Each draft is shown as a "substitution" or an "addition". Parts of the existing text that do not change are not quoted. Terminology (common to this draft): **scope (environment scope)** = the set of environments for which a member receives DEK wraps. `all` (every environment — including ones created later) or `listed` (a finite set of environment_ids). **Recipient set R(E)** = the complete set of recipients of environment E's DEK wraps = { current member m | E ∈ scope(m) } ∪ { valid grant_server g | E ∈ scope_environments(g) }. **Proposal / approval** = the `propose` / `approve` entries of four-eyes (PF1). **Policy** = the four-eyes configuration that `set_approval_policy` establishes (the target op set and the required approval count).

## A. CRYPTO_SPEC revision proposals

### A-1. Substitution in §3 (one item)

> - ~~In v1, every member receives every environment's DEK (per-environment read restriction is a Phase 2 design item. **Open item #11**)~~ **Revised 2026-09-14 (ES — resolves open item #11)**: each member receives DEKs only for the environments in their on-chain **scope** (a payload of `add_member` / `change_role` — §6.2). scope is `all` (every environment — including ones created later) or `listed` (a finite set of environment ids). Per-environment read restriction is realized by **key distribution, not server policy**: DEK wraps for out-of-scope environments are neither generated nor accepted (§6.3 / AUTH_SPEC §12-6), so even if the server is compromised, no out-of-scope DEK exists to be opened. The design record is docs/notes/es-design.md

### A-2. Substitution in §6.2 (right after the role table; the op table; consensus rules)

> The on-chain role is one of four levels: **owner / admin / member / reader**:
>
> | role | Can do |
> |---|---|
> | `reader` | Only fetch and decrypt values of in-scope environments (receives DEK wraps for in-scope environments). No chain appends |
> | `member` | + update values of in-scope environments (push new versions), `rotate_epoch`, `checkpoint`. `create_environment` if scope = all |
> | `admin` | + `add_member` / `remove_member` / `change_role` targeting readers / members — but only within the range where **the set of environments whose authority the operation changes** (add = the new scope, change_role = old scope ∪ new scope if role changes, symmetric difference if only scope changes, remove = the current scope — principle 1) is contained in their own scope |
> | `owner` | + manage admins, `grant_server` / `revoke_server`, `set_approval_policy`, delete the project. **scope is always all**. The last owner cannot be deleted or demoted |
>
> - **Environment scope (2026-09-14 ES revision — formerly open item #11)**: `genesis` / `add_member` / `change_role` establish a member's **scope**. scope is normalized as the two payload fields `scope_kind` (`"all"` | `"listed"`) and `scope_environments_lp_hex` (a lowercase-hex string of the environment_id list LP-encoded per §2.1 — the same nested LP as `grant_server`'s `scope_environments`. List order is part of the signed byte string. Generation SHOULD sort by code point with no duplicates; verification treats it as a set). `genesis` carries no scope in its payload; the creator's scope is structurally `all`. Consensus rules:
>   - **Structure (the payload structural-check stage — precedes authorization)**: when `scope_kind = "all"`, `scope_environments` must be the empty list (non-empty is `invalid-payload`). The list is at most 256 elements (the same bound as §6.1's `grant_server`). **A list containing duplicate environment_ids is invalid** (`invalid-payload` — the same "nip non-determinism at the structural stage" line as `checkpoint`). An **empty list under `scope_kind = "listed"` is valid** (= a member who receives no environment's DEK. Plaintext metadata is still visible per §6.3)
>   - **Environment existence (authorization stage)**: each environment_id in `listed` must have a preceding `create_environment` on the chain at that entry's point (rejection reason `unknown-environment` — the same reason code as `rotate_epoch` / `checkpoint`; typos fail closed, and pre-scoping to not-yet-existing environments is not allowed). Deleted environments may still be listed since the chain does not observe deletions (no harm)
>   - **Owner is all (authorization stage)**: an `add_member` / `change_role` establishing `role = owner` is invalid unless `scope_kind = "all"` (rejection reason `scope-role-mismatch`). An owner is the "last owner" protection, the performer of `grant_server` (disclosure of every environment) and the fulfiller of rotate obligations for every environment, and cannot hold a scope. admin / member / reader may hold `listed` (an admin dedicated to dev can write — design record ruling C)
>   - **Principle 1 — mutability of authority (authorization stage. 2026-09-14 — design record 3-ter, pullfrog round-9 revision)**: when an entry changes a member's authority in environment E (the ability to read / write values / `rotate_epoch` / `checkpoint` — the role table), **the actor's scope contains E**. That is, the actor's scope must contain the op's **set of environments whose authority changes** (rejection reason `scope-not-contained`. `all` contains everything; `listed` contains only subsets of itself — `listed` does not contain `all`). The environment set of an authority change is derived from the role table (not enumerated): `add_member` = the new scope / `change_role` = old scope ∪ new scope if new role ≠ old role (all environments where role changes), (new \ old) ∪ (old \ new) if new role = old role (only scope in/out changes authority) / `remove_member` = the current scope. **Set algebra (treatment of `all` — addressed per a 2026-09-14 Cursor Bugbot report)**: in containment tests, `all` is treated as **the set U of all environments (including ones created later)** and `listed{X}` as the finite set X. Therefore `all ⊇ anything` is true, `listed{X} ⊇ all` is false, `listed{X} ⊇ listed{Y}` iff Y ⊆ X. `all ∪ listed{X} = all`, `all \ listed{X} = U \ X` (a `listed` actor cannot contain it because it includes uncreated environments), `listed{X} \ all = ∅`, `all △ listed{X} = U \ X`. As a consequence, **a `change_role` where the old or new scope is `all`, and an `add_member` granting `all`, can only be performed by an actor with scope = all**, because the authority-change environment set contains U \ X (or U) (a `listed` admin can neither make a target `all` nor make an `all` target `listed` — they cannot bear the obligation to hand over or collect the DEKs of future environments). **Corollary — fulfillability of obligations**: the §7 / AUTH_SPEC §12-6 obligations (backfill, rotate) arise only for environments whose authority changes, so the obligation's environment set (`add_member` = new scope [backfill] / `change_role` = (new \ old) [backfill] ∪ (old \ new) [rotate] ∪ (new scope, if demoted below member) [rotate] / `remove_member` = current scope [rotate]) is a subset of the authority-change environment set, and an actor bearing an obligation always holds that environment's DEK (DEK wraps are performed by a DEK holder [§7] — consistent with the cryptographic necessity that only a holder of E's DEK can put a person into or out of E). The formulation that makes only the obligation's environment set the containment target (a provisional formulation of 2026-09-14) is merely a necessary condition for authorization and is rejected because it would admit scope-preserving promotions that carry no obligation (a dev-only admin raising a prod reader to member). A dev-only admin can perform a scope-only `change_role` within the symmetric difference. Owner always passes, being all
>   - **Environment-targeting ops**: `rotate_epoch`'s target environment_id and every `checkpoint` tuple's environment_id must be contained in the actor's scope (rejection reason `environment-out-of-scope`). `create_environment`'s new environment_id is decided by the same predicate — a `listed` scope cannot contain a nonexistent environment, so **environment creation is limited to actors with scope = all** (no creating an environment the creator cannot receive; no implicit scope change that is not part of the signed payload)
>   - **Check order (fixed per reason code, by test vectors. Scope-family checks are placed after the existing check sequence, preserving the expected reasons of existing negative cases)**: `add_member` = role rule → `duplicate-member` → `duplicate-member-key` → `unknown-environment` (each id of the scope) → `scope-role-mismatch` → `scope-not-contained`. `change_role` = role rule → `approval-required` (direct appends only — below) → `unknown-target` → `last-owner-protected` → `unknown-environment` → `scope-role-mismatch` → `scope-not-contained` → `approval-quorum-unreachable` (when four-eyes is in effect — below). `remove_member` = role rule → `approval-required` → `unknown-target` → `last-owner-protected` → `scope-not-contained` → `approval-quorum-unreachable`. `approval-required` of `add_member` / `grant_server` / `revoke_server` sits in the same position (right after the role rule). `rotate_epoch` = role rule → `unknown-environment` → `environment-out-of-scope` → epoch ordering. `create_environment` = role rule → `duplicate-environment` → `environment-out-of-scope`. `checkpoint` = role rule → admin role for a non-empty audit head → `unknown-environment` → `environment-out-of-scope` → `checkpoint-epoch-mismatch` → `checkpoint-regression` (all tuples scanned per stage — stage-wise)
>   - **Verification state** derives each current member's scope (inputs to §6.3's wrap-target match check, the declared-head scope check, and AUTH_SPEC §12-3's authorization). The history index keeps the change points (seq) of (role, scope) per member's membership interval
>   - **Recipient set R(E)** (the single definition used by §6.3 / §7 / AUTH_SPEC §12-4 / §12-6): the complete set of recipients of environment E's DEK wraps = { current member m | E ∈ scope(m) } ∪ { valid `grant_server` g | E ∈ scope_environments(g) }. A `grant_server` server key carries its own `scope_environments`, so it is outside ES; the determination is applied identically across recipient classes
>   - **Shrinkage is remove-equivalent (§7)**: when old scope \ new scope is non-empty in a `change_role`, the op carries the same `rotate_epoch` obligation as `remove_member` for each shrunken environment (not a consensus rule — a §7 obligation — in contrast to `grant_server`'s re-grant rejecting scope shrinkage as a consensus rule, member shrinkage is accepted and bears an obligation. To avoid re-invitation and splitting the membership interval — design record ruling F). For the expanded part, the actor backfills all epochs' DEKs (AUTH_SPEC §12-6)
>   - Introducing this rule (2026-09-14) changes the payload format of `add_member` / `change_role`, and **existing chains accepted before introduction become invalid under the new rule** (no compatibility clause — the 2026-09-14 owner ruling "while there are no users, all old implementations may be deleted". Existing projects are recreated — docs/SELF_HOSTING.md "Updates"). `chain-entries.json` is fully regenerated (§11)
>
> | op | payload | authority |
> |---|---|---|
> | `genesis` | the project creator's public keys | the creator themself (becomes owner, scope = all) |
> | `add_member` | target user_id, target enc/sig public keys, role, **scope_kind, scope_environments_lp_hex** | admin or above (granting admin / owner is owner-only). Target scope ⊆ actor scope |
> | `remove_member` | target user_id | admin or above (removing admin / owner is owner-only). Target's current scope ⊆ actor scope. Carries `rotate_epoch` for **all environments of the target's current scope** (§7) |
> | `change_role` | target user_id, new role, **scope_kind, scope_environments_lp_hex** (full replacement of (role, scope)) | admin or above (changes involving admin / owner are owner-only). The authority-change environment set (old scope ∪ new scope if role changes, symmetric difference if scope-only — principle 1) ⊆ actor scope. Demotion below member carries `rotate_epoch` for all environments of the target's scope; scope shrinkage carries it for the shrunken environments (§7) |
> | `create_environment` | target environment_id, epoch 1's dek_commitment_hex (§5.2) | member or above, scope = all |
> | `rotate_epoch` | target environment_id, new epoch number, reason, the new epoch's dek_commitment_hex (§5.2) | member or above, target environment ∈ scope |
> | `grant_server` | the server key's public key and fingerprint, the permitted scope (containing a subset of target environments), the lease policy | owner only (explicit operation) |
> | `revoke_server` | the revocation target | owner only |
> | `checkpoint` | per-environment (environment_id, epoch, manifest_version, manifest_sig_hash, values_digest) + the audit-head cumulative hash (omitted = empty string) | member or above (an actor notarizing a non-empty audit head must be admin or above), every tuple's environment ∈ scope |
> | **`set_approval_policy`** | **target op set (ops_lp_hex), required approvals (required_approvals)** | **owner only. Subject to four-eyes if a policy is currently in effect (below)** |
> | **`propose`** | **inner op name, inner payload (inner_payload_lp_hex — the op's normalized payload_bytes), expiry (expires_at_ms)** | **a role that can execute the inner op (determined by the inner op's rules)** |
> | **`approve`** | **the proposal entry's hash (proposal_hash_hex)** | **owner only (distinct from the proposer. An owner's proposal counts as one vote)** |
> | **`withdraw`** | **the proposal entry's hash (proposal_hash_hex)** | **the proposer or an owner** |
>
> - The normalized field order of payloads (fixed by chain normalization vectors): `add_member` = `[target_user_id, enc_pub_hex, sig_pub_hex, role, scope_kind, scope_environments_lp_hex]`, `change_role` = `[target_user_id, new_role, scope_kind, scope_environments_lp_hex]` (both appended at the **end** of the existing fields), `set_approval_policy` = `[ops_lp_hex, required_approvals]` (`ops_lp_hex` = hex of the nested LP of the op-name list. Order is signed. Generation is code-point ascending SHOULD; verification is set-wise), `propose` = `[inner_op, inner_payload_lp_hex, expires_at_ms]` (`inner_payload_lp_hex` = lowercase hex of the inner op's `payload_bytes` — §6.1's nested LP), `approve` = `[proposal_hash_hex]`, `withdraw` = `[proposal_hash_hex]` (both lowercase hex, 64 chars = the proposal entry's entry_hash)
> - **Four-eyes (2026-09-14 PF1 — multi-signature approval. Design record docs/notes/es-design.md §3)**: dangerous operations are accepted as a two-stage "propose → approve" entry pair, and the inner op is applied **only when the signatures of distinct owners reach the required approval count**. No threshold or aggregate signatures are introduced (the existing Ed25519 signatures are simply counted across 2 entries). Consensus rules:
>   - **Policy**: `set_approval_policy` establishes a policy { ops, required_approvals }. A state where no policy has ever been established (or `required_approvals = 0`) is **off** (the default — nothing changes for a single-owner project). `required_approvals` is 0 (off) or ≥ 2. **Activation or change is invalid unless the current owner count ≥ required_approvals** (rejection reason `approval-quorum-unreachable`). `ops` must be a subset of (structural check — `invalid-payload`): `grant_server` / `revoke_server` / `remove_member` / `change_role` / `add_member` / `set_approval_policy`. `create_environment` / `rotate_epoch` / `checkpoint` (do not stop data-plane or fail-safe operations — rotate is incident response and must not be delayed) and `genesis` / `propose` / `approve` / `withdraw` cannot be targets. **While a policy is in effect, `set_approval_policy` itself and `add_member` / `change_role` establishing the owner role are always targets regardless of the `ops` enumeration** (turning it off also requires four-eyes — otherwise four-eyes is meaningless. Leaving an op that adds owners outside four-eyes would let a single owner directly append their own second keypair as an owner and fill quorum with a self-made second owner — addressed per a 2026-09-14 pullfrog review. Since `distinct` is an on-chain identity, not a person, the identity-addition path itself goes inside four-eyes)
>   - **Reachability invariant**: while a policy is in effect, an op that would bring the current owner count below `required_approvals` (an owner's `remove_member`, a `change_role` from owner to another role) is invalid (`approval-quorum-unreachable` — a generalization of `last-owner-protected`. It sits at the end of each op's check order)
>   - **Principle 2 — authorization by signer set (2026-09-14 — design record 3-ter)**: every entry is authorized by a **signer set S**. For a direct append S = {actor}; via proposal, S = {proposer} ∪ {every `approve` actor}. The approval count `required(op)` an op needs is `required_approvals` if a policy is in effect and the op is a target, else 1. An entry (direct append) or a proposal's application is invalid unless **the number of distinct elements of S that are owners at application time ≥ required(op)** when `required(op) ≥ 2` (principle 2 is an additional condition that applies when `required(op) ≥ 2`; an op with `required = 1` is decided only by the normal role rules [S = {actor} holds the op's role] — it does not deny direct appends by non-owner members / admins). **Invariants (policy monotonicity — two consequences)**: while a policy is in effect, (a) the op that changes the policy (`set_approval_policy`) and ops that add owner identities (`add_member` / `change_role` establishing the owner role) are always targets regardless of the `ops` enumeration, and (b) ops that bring the owner count below `required_approvals` (the "reachability" above) are invalid — there is no path to weaken or bypass the policy with a sub-quorum set of signers. Ops that reduce owners are handled by (b) and are not always targets (they can be directly appended if not in `ops` — the same set as "Policy" above and §14.2-10). The individual rules below are derivations from this principle and these invariants
>   - **Rejecting direct appends of target ops (derived)**: while a policy is in effect, an entry that directly appends a target op is invalid because S = {actor} gives |S ∩ owners| ≤ 1 < required (rejection reason `approval-required`. The check sits **immediately after** the role rule). In the context where `propose` / `approve` evaluate the inner op, this check **does not occur** because the inner op is still collecting S (it is the same determination as principle 2, not an exception)
>   - **`propose`**: the actor must hold a role that can execute the inner op under the normal rules, and the inner op must satisfy the consensus rules (structure, authorization, containment, last owner, reachability … — except `approval-required`) in the state at that point (a proposal that does not satisfy them is invalid — it is not put on pending. The reason code is the inner op's reason, used verbatim). `inner_op` must be a policy target (`ops` + the always-target ops) (`approval-not-required` — proposing a non-target op means nothing). `expires_at_ms` is a non-negative safe integer. A proposal enters the verification state as pending (identifier = the proposal entry's entry_hash). **`propose` while the policy is off is invalid** (`approval-not-required`)
>   - **`approve`**: the actor must be an owner at that point (`insufficient-role`). The referent must be a pending proposal (`unknown-proposal` — already applied, withdrawn, or nonexistent). The actor must not have voted on that proposal yet (if the proposer is an owner, the proposal is one vote — `duplicate-approval`). **The `approve` entry's `timestamp_ms` must be ≤ the proposal's `expires_at_ms` (`proposal-expired`)** — the **only place** in this spec where a timestamp is used in a consensus rule. Because `timestamp_ms` is the approver's self-declaration (the chain has neither monotonicity nor an upper bound), **the expiry is a UX safety device protecting honest approvers from out-of-context approvals, not a guarantee against a malicious approver**: an approver who lies about the time in the past can approve an expired proposal (that approver is a principal legitimately holding a four-eyes vote as an owner — not what the expiry protects. Addressed per a 2026-09-14 pullfrog review — the former claim "rejection direction only = fail-closed" is retracted). §14.2-10's guarantee does not depend on the expiry. Vote count = |S ∩ owners at application time| (a derivation of principle 2): **this `approve` entry's own actor** (an owner — already checked by the role rule) plus the distinct count of past voters (actors of past `approve`s and a proposer who proposed as an owner) **who are still owners at this `approve` entry's point**. Votes of past voters demoted or removed after the proposal are not counted (the state that determines a past voter's owner status is "the state before applying this `approve` entry" — addressed per a 2026-09-14 Cursor Bugbot report: if voter owner-status were checked only at vote time, the remaining single owner could complete a proposal using votes of departed voters. With 2 owners and `required_approvals = 2`, completion takes "an owner's proposal + another owner's approve" or "a non-owner's proposal + two owners' approves"). When the vote count reaches `required_approvals`, **the inner op is applied at this `approve` entry's seq** (inclusive convention — `remove_member`'s membership end and `change_role`'s new role / scope take effect at this seq. The §7 rotate obligation and the rotation-needed detection start at this seq too). At application time, the inner op's consensus rules are re-checked against the **state at application time**, plus **the proposer is still a current member, holds the same key FP as at proposal, and holds the role the inner op requires** (rejection reason `proposal-void` — a proposal cannot be completed after its proposer has been removed, demoted, or changed keys). An `approve` entry that fails the application-time checks is an invalid entry, and the proposal stays pending (closed by `withdraw` — an approval signature is not given a "close" effect). An applied inner op's actor is treated as **the proposer** (the record of membership / attribution). **Relationship to principle 1**: the fulfiller of the inner op's obligations (rotate / backfill) is the approver who completed the application (owner = all), so principle 1 is structurally satisfied. The principle-1 check in the proposer's scope at proposal time and application time confirms that "the op is one the proposer could directly append"; it does not guarantee fulfillability (if the proposer's scope has shrunk since proposing, application fails with `scope-not-contained` and the proposal stays pending — closed by `withdraw`)
>   - **Policy changes vs pending proposals (addressed per a 2026-09-14 pullfrog review)**: a pending proposal does not snapshot the policy at proposal time; it is judged by **the policy in effect at each `approve` entry's point** — the required count is the current policy's `required_approvals`, and if the inner op is no longer a **target** of the current policy (`ops` + always-target ops — the same predicate as for `propose` / direct-append rejection. An always-target op never leaves the target set while a policy is in effect), that `approve` is invalid with `approval-not-required` and the proposal stays pending (closed by `withdraw`. An op that left the target set can be executed by direct append — always-target ops have no such path. Addressed per a 2026-09-14 Cursor Bugbot report). Lowering `required_approvals` takes effect on pending proposals immediately (the next `approve` completes with the votes already gathered)
>   - **`withdraw`**: the actor is the proposer or an owner. The referent must be pending (`unknown-proposal`). Closes the proposal (no state change)
>   - **Check order** (fixed per reason code, by vectors): `set_approval_policy` = role rule (owner) → `approval-required` (a direct append is not allowed if a policy is in effect) → `approval-quorum-unreachable`. `propose` = role rule (determined by the inner op's rules) → `approval-not-required` → the inner op's consensus rules (except `approval-required` — the inner op's reason codes). `approve` = role rule → `unknown-proposal` → `duplicate-approval` → `approval-not-required` (a non-target after a policy change — above) → `proposal-expired` → (at quorum) `proposal-void` → the inner op's consensus rules. `withdraw` = role rule → `unknown-proposal`
>   - The verification state derives the policy (ops, required) and the set of pending proposals (proposal hash → proposer, inner op, expiry, voter set). **No bound on the pending-proposal count is placed in consensus rules** (a server acceptance policy — §6.4 / AUTH_SPEC §12-8)
>   - Introducing the 4 ops requires all implementations to update simultaneously under "unknown op = invalid chain", but it does not touch the payload format of existing ops (independent of ES's add_member / change_role change). The test vectors are bundled into the same regeneration as ES (§11)

### A-3. Additions to §6.3 (3 places)

> - **DEK wrap destinations must exactly match the chain-derived recipient set R(E) (§6.2 — current members in scope + valid grant_servers in disclosure scope) (2026-09-14 ES revision)**. Generating or accepting a wrap addressed to an out-of-scope member is forbidden (the environment-axis version of the ghost-member countermeasure). **Receiving side**: among wraps addressed to you, do not **use** ones for environments ∉ your scope even if you can open them — warn instead (evidence that the server is not enforcing AUTH_SPEC §12-6's acceptance rules. Since writes to that environment are rejected by all verifiers as out of scope, the practical harm is limited to "can read", but as a norm they are not used)
> - Add a **scope authorization-point check** to the verification of values, metadata statements, and manifests (1–6): **3′. Scope (environment-targeting signatures)**: in the chain-derived state at the declared head, the writer / author / issuer's scope contains the environment_id in question (rejection reasons `writer-environment-out-of-scope-at-head` / `author-environment-out-of-scope-at-head` / `issuer-environment-out-of-scope-at-head` — right after the role check of 3). Environment meta-statements (rename / delete), variable meta-statements, and manifests are all environment-targeting and are covered. Bundled statements / manifests of an environment-creation compound have a declared head that is the pre-append head (AUTH_SPEC §12-4), where the environment does not yet exist, but the creator has scope = all (§6.2) so the check holds vacuously
> - **Handling of out-of-scope environments (2026-09-14 ES revision — design record ruling G)**: for environments outside their scope, a member receives and can verify the chain (all entries — including that environment's `checkpoint` tuples), the environment's existence, display name, variable names, schema column, manifests, and tombstones (plaintext metadata = the open-item-#3 line) (metadata-only pull — AUTH_SPEC §12-7). They do not receive ciphertext or DEK wraps addressed to them, and cannot write, rotate, or checkpoint. **Cross-environment verification**: (i) `checkpoint` tuples of out-of-scope environments are verified as consensus rules (§6.2) but are **not used as the basis of the checkpoint match** — the basis is only needed for environments one pulls values from; (ii) manifest verification covers only pulled environments (unchanged); (iii) head attestations and invite-link anchors have no environment and are unchanged. The repo anchor's per-environment epochs are chain-derived values and can be written for out-of-scope environments too (unchanged); (iv) the local floor is "a join of facts verified successfully" — the floor of an out-of-scope environment simply is not established (it is not a target of rejection or warning)
> - The verification state includes the four-eyes policy and pending proposals (§6.2). The client derives its own scope and policy from the verified chain and treats out-of-scope or proposal-requiring operations as typed errors / proposal creation before operating (without waiting for the server's 403)

### A-4. Additions to §6.4 (2 items)
