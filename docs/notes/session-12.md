## 1. 問題定義(何が証明されていなかったか)

CRYPTO_SPEC §5.1(DEK ラップ登録署名)は「誰がこのラップを持ち込んだか」の
**帰属**を証明するが、以下を証明しない:

1. その DEK が当該 (environment, epoch) の**正規** DEK であること
2. そのラップが署名者の**現メンバー在籍中**に登録されたこと(クライアント検証は
   チェーン履歴上の鍵を使う — 削除済みメンバーの過去の正当な登録を検証するための
   性質が、そのまま「削除後の新規登録」を区別できない穴になる)
3. 配布された値が正規 writer の書いた**最新版**であること(値は無署名 — DEK
   保持者なら誰でも任意座標の復号可能な暗号文を作れる)
4. サーバーが正規データを**欠落・巻き戻し・分岐**させていないこと
5. variableId と表示名の対応が正規であること(名前は AAD 外の平文メタデータ)

具体的な攻撃(セッション 11 の既知残余の再構成): 悪意あるサーバー +
チェーン履歴上の鍵保持者(削除済み元メンバー・漏洩した旧鍵)の共謀で、
(i) 実在エポック e に自作 DEK′ のラップを §5.1 検証を通る形で配布し、DEK′ で
暗号化した偽値を復号させる、(ii) 被害者に DEK′ で新しい値を暗号化・push させて
攻撃者が平文を読む(機密性攻撃)、(iii) 実エポックの実 DEK で偽値を暗号化して
配布する(元メンバーは在籍中の全 DEK を保持)、(iv) 名前と暗号文の対応を
付け替える(`DATABASE_URL` ↔ `DEBUG_ENDPOINT`)。

## 2. セキュリティ目標の分解

CRYPTO_SPEC §14.1 に規範として記載(G1 帰属 / G2 認可時点 / G3 内容真正性 /
G4 文脈束縛 / G5 最新性 / G6 完全性 / G7 分岐耐性 / G8 可用性 = 非保証 /
G9 平文の正しさ = 非保証)。本セッションの裁定はすべてこの分解に基づき、
「署名 = 真正性」という混同(§5.1 起草時に既に区別済みの「帰属 ≠ 鮮度」を
値・メタデータへ拡張したもの)を避ける。

特に重要な非目標 2 つを最初に固定した:

- **G8(可用性)**: 悪意あるサーバーの応答拒否・削除・遅延は防げない。全設計案は
  「不可視の改竄」を「可視の障害または帰属付きの証拠」へ変換することを目指す
- **G9(平文の正しさ)**: 悪意ある現行 writer が不正値を書くことは防げない。
  証明できる上限は「正規権限を持つ writer がこの暗号文を書いた」まで

読み方の要点:

- 本改訂で「サーバー単独」は完全に無力化される(全データが署名またはチェーン
  束縛を持つ)
- 共謀攻撃は「在籍区間内の座標への、帰属付きの注入」まで縮む。注入の向きで
  検出可能性が分かれる(レビューループ 1 で当初の主張の誤りを訂正 — §12):
  **後退方向**(差し替え・巻き戻し)は床で検出。**前進方向**(実最新の次の
  version / meta_version の偽造)は巻き戻し不要で素朴な床を素通りし、値は
  エポック単調性 + 床の拡張で閉じるが、**メタはエポックアンカーがなく v1 では
  閉じない**(証拠化まで。閉包は Phase 2)
- 「チェーンごと巻き戻したビュー」(削除済みメンバーが現メンバーに見える)が
  初回同期クライアントへの支配的残余。これはどの署名方式でも解決不能で、
  ヘッドゴシップ・外部チェックポイント・床の責務(責務分離は CRYPTO_SPEC §14.3)

## 4. 設計案の比較

### 案 A: 値ごとの writer 署名 → **採用**(§4.1。C の最小核を統合)

| 検討事項 | 裁定 |
|---|---|
| 署名対象の正規形 | `LP("maruhi/v1/value-sig", project_id, environment_id, epoch, variable_id, version, nonce_hex, ciphertext_hex, prev_value_sig_hash_hex, writer_user_id, chain_head_hash_hex, chain_head_seq)`。§5.1 の規約(ドメイン文字列が suite を束縛・バイナリは hex 小文字・全ワイヤフィールドを列挙し未束縛フィールドを残さない・signer user_id 焼き込み)を踏襲 |
| write 権限の時点証明 | チェーンヘッド束縛(hash + seq)+ 検証側の「宣言ヘッド時点の role」導出。宣言ヘッドは writer の自己申告だが、**自分の検証済みチェーン上に実在するエントリ**でなければならず(fork 検出を兼ねる)、削除済みメンバーは在籍区間内のヘッドしか宣言できない。**宣言ヘッド seq の(version 連鎖に沿った)単調性は規則にできない** — 同期時期の異なる正直な並行 writer は直前 version より古いヘッドで正当に push しうる(レビューループ 1 でセキュリティ観点の対策案を正しさ観点が棄却した論点)。代わりに**エポック単調性**(version 連鎖に沿って非減少 — 受理順に現エポックが非減少であることから正直フローで常に成立)を検証規則にする |
| 削除済み writer の過去値検証 | §5.1 と同じ鍵履歴照合(user_id + FP → チェーン履歴上の当時の鍵)。positive ベクターで固定する(§8) |
| 同一 version の分岐 | 防止は不能(サーバーは並行受理を偽装できる)。`prev_value_sig_hash` の連鎖で**否認不能な証拠**に変換(2 つの有効署名が同一座標に存在 = equivocation の証明) |
| rollback / omission | 単独署名では防げない(署名は鮮度を証明しない — §5.1 の意味論の教訓)。ローカル床(§6.3 SHOULD)+ Phase 2 ゴシップの責務として明示的に切り出す |
| 監査ログとの突合 | `var.version_pushed` 等に署名者鍵 FP を写す(AUDIT_SPEC §3.3 — dek.registered の先例の一般化) |
| AAD との関係 | AAD は不変(GCM 層の防衛として維持、既存ベクター無変更)。「AAD に writer を足す」変種は却下 — AAD の検証者は DEK 保持者に限られ、DEK 保持者こそが攻撃者クラスなので真正性を担えない |

### 案 B: エポック DEK の認証済み descriptor / commitment → **採用**(B-4 = チェーン掲載のコミットメント。§5.2)

| 変種 | 評価 |
|---|---|
| B-1: DEK 自体へのドメイン分離 commitment(掲載場所は別論点) | **原像 = LP(domain, 座標, dek) の SHA-256 を採用**。受信者集合に依存せず、backfill・修復・HPKE ランダム性・add_member による受信者増加のすべてに不変。DEK は一様ランダム 256-bit なので公開しても情報漏洩なし(低エントロピー流用は §12 で禁止) |
| B-2: 受信者ラップ集合への commitment | **却下**: add_member の backfill で集合が増え、修復の再登録で HPKE 暗号文が変わり(Seal はランダム)、集合コミットメントは登録のたびに無効化される。配布が本人宛のみ(§12-6)である以上、受信者は集合全体を検証できない — セッション 09 の §2-1(集合単位署名の却下)と同根 |
| B-3: (environment, epoch) descriptor への署名(データプレーン掲載) | **却下**: 署名者の選定が循環する — 「正規の descriptor はどれか」を決める台帳がなければ、共謀者が自鍵で署名した別 descriptor と区別できない。台帳 = チェーンに掲載するなら B-4 に一致し、独立のデータプレーン置き場は攻撃面を増やすだけ |
| B-4: membership chain への commitment 掲載(採用) | チェーンは既に存在する「全員が検証する認証済みブロードキャスト」であり、rotate_epoch は既にチェーン op。エポックとコミットメントの対応が合意規則の導出値になり、偽 DEK は**チェーン fork なしには注入不能**になる |

必須検討事項への回答:

- **epoch 1(環境作成が chain op でない問題)**: チェーン op `create_environment`
  を新設して解消(§6.2)。副次効果が大きい: (i) 環境の存在がチェーン導出になり、
  AUTH_SPEC §12-4 の「rotate は環境メタデータと突合しない」「rotate 観測で ID を
  焼却する」という 2 つの迂回規則が消える、(ii) 環境 ID 再利用禁止が合意規則へ
  昇格、(iii) エポック 1 の開始 seq が観測可能になり §4.1 のエポック整合検査が
  全エポックで一様になる。代替案(エポック 2 以降のみコミットメント / 初回
  rotate に遡及コミットメントを載せる)は「エポック 1 だけ保証が弱い」非一様性を
  残すため却下
- **rotate_epoch**: payload に新エポックのコミットメントを追加(+64 バイト)
- **新メンバーへの過去エポック backfill**: コミットメントは受信者非依存なので
  無影響(招待者は実 DEK しか持っておらず、実 DEK しかラップできない —
  「攻撃者が鍵を知る偽 DEK の backfill」はコミットメント照合で落ちる)
- **repair(ラップ削除 → 再登録)**: 同一 DEK の再ラップはコミットメント不変。
  DEK 自体が誤っていた場合の修復は rotate(正規手順)
- **HPKE のランダム性**: コミットメント対象はラップでなく DEK なので無影響
- **受信者集合の事後拡大**: 同上
- **commitment 公開による情報漏洩**: なし(SHA-256 の原像困難性 + 256-bit 一様
  ランダム入力。座標を原像に含めるため文脈間の DEK 一致もコミットメント比較から
  漏れない)。「新プリミティブの発明」への抵触も確認: ランダム 256-bit 鍵への
  ハッシュコミットメントは §3 鍵フィンガープリントと同じ「公開ハッシュによる
  同定」の適用であり、salt 付きコミットメントスキーム等の新規構成を要しない
  (低エントロピー入力を §12 で禁止することで hiding の前提を仕様として固定)
- **チェーン上限への影響**: create_environment ≤ 1,000 エントリ(環境上限)、
  rotate +64B。10,000 エントリ / 32 MiB に対し無視できる

### 案 C: 認証済みデータ履歴 → **最小核のみ採用**(prev 連鎖 + ローカル床。マニフェスト・チェックポイントは Phase 2 = 未決 #12)

| 変種 | 評価 |
|---|---|
| C-1: 変数ごとの prev ハッシュ連鎖(値署名に統合) | **採用**: 署名対象に 1 フィールド追加するだけで、version 順序の認証と分岐の証拠化が手に入る。追加の署名・往復なし |
| C-2: 環境単位の署名付きマニフェスト(変数集合 + 最新 version) | **Phase 2 へ**: 変数集合の欠落検出が加わるが、(i) 最新 version をマニフェストに含めると全 push がマニフェスト CAS を通る(ホットパスの直列化点 + 並行 writer の常時競合)、(ii) 含めなければ利得は「変数集合の欠落検出」だけで、それはローカル床(変数ごとの metaVersion 記憶)でも返却クライアントには達成でき、初回同期クライアントにはマニフェストの鮮度自体を保証できないので達成できない。費用対効果が立たない |
| C-3: チェーンへの定期チェックポイント(値・監査ヘッド) | **Phase 2 へ**(未決 #4/#12 と統合): 外部アンカーとして唯一 G5/G6 を初回同期にも与えうるが、チェーン肥大・書き込み頻度の設計論点が大きい。ヘッドゴシップと同時に設計するのが正しい順序 |
| C-4: Merkle tree(バージョン履歴 / 環境全体) | **却下(v1)**: prev 連鎖に対する追加利得は「部分証明のサイズ」だが、v1 の pull は latest-only + 全変数一括であり部分証明の需要がない。実装・ベクターの複雑度だけが増える |

必須検討事項への回答: VersionConflict CAS との接続(409 → 勝者の signed_bytes
ハッシュへ prev を付け替えて再署名 — AUTH_SPEC §12-5)、並行 writer(CAS が
直列化。fork はサーバー equivocation のみ = 証拠化)、同一 version への複数正規
署名(サーバーは 1 行のみ保存。複数の有効署名の観測 = equivocation の証拠)、
初回同期の latest 判定根拠(**ない** — §14.3-3 に明示。head gossip なしで保証
できる範囲は「提示されたビューの内部整合と帰属」まで)、Phase 2 gossip との
組み合わせ(書き込み署名のヘッド束縛が申告ヘッドの運搬役を兼ねる — §6.3)、
DO への影響(+約 350B/行。§12-8)。

### 案 D: 変数名と variableId の認証済み対応 → **D-2 採用**(署名付き versioned メタデータステートメント。§4.2)

| 変種 | 評価 |
|---|---|
| D-1 / D-3: 名前を値 AAD に含める(rename で再暗号化) | **却下**: rename が全バージョン再暗号化(最悪 1,000 版 × 64 KiB)+ 過去バージョンの検証に名前履歴の保持を要求する。「暗号文脈には改名の影響を受けない安定識別子を使う」という既存の設計判断(§3 の environment_id の理由付け)と正面衝突。表示編集が暗号操作になるのは設計の匂いとして最悪 |
| D-2: immutable ID + 署名済み metadata statement(rename = versioned op)(採用) | 名前 ↔ ID の対応が「必要 role を持つ鍵保持者の署名済みステートメント」に限定され、サーバーの付け替えは不能に。metaVersion + prev 連鎖で rename 履歴も分岐証拠化。値署名(A)と同じ検証機構(ヘッド束縛・認可時点)を再利用でき、実装の増分が最小 |

必須検討事項への回答: rename(metaVersion+1 の新ステートメント)、tombstone と
ID 再利用禁止(status=deleted ステートメント + 「deleted 後の再 active 化禁止」。
環境 ID はチェーン合意規則へ昇格 — §6.2)、Unicode 正規化・大文字小文字
(**署名は byte-exact、正規化は入力境界の受理ポリシー** — 正規化を検証規則に
入れると実装間の正規化差異が検証分裂になる。NFC + 大文字小文字区別を §12-1 に
規定)、サーバーによる名前↔暗号文の付け替え(署名で遮断。同名 active 重複の
配布はクライアントが解決拒否)、CLI の環境変数名との関係(名前 → ID 解決は
検証済みステートメント経由を必須化。実行制御系変数名 denylist — session-11 —
は防衛層として残る)。

環境名にも同じ機構を適用した(`env-meta-sig`)。変数名と同じ攻撃(dev / prod の
名前入替による誤環境への push 誘導)が成立し、機構は完全に共通なので、変数のみに
限定する理由がない。**タスク指定(変数名)からのスコープ拡張なので要裁定 §10-2**。

### 案 E: 組み合わせ → B + A(C 最小核込み)+ D を単一仕様改訂で

最小構成の導出: G1〜G4 を閉じるには「鍵の真正性(B)」と「データの真正性
(A・D)」の両方が必要で、どちらか片方では §1 の攻撃が残る —

- B なし(A・D のみ): 偽 DEK での暗号化誘導(機密性攻撃 §1-ii)が残る。値署名は
  暗号文の真正性であって「これから書く値の鍵」を守らない

5. **仕様 PR の一括承認**(§4 案 E の分割判断): 単一 PR での承認を推奨。
   分割を望む場合は §9 の PR 境界で仕様も分割可能
6. **メタステートメントの前進注入残余の扱い**(レビューループ 1 で確定した
   残余 — §14.3-5): v1 は「文書化 + 証拠化まで」を推奨(採用済みドラフトの

   休眠メタへの注入は依然塞げない、(ii) 検証にステートメント履歴の配布が要る、

   裁定を求める
7. **remove_member + 全環境 rotate の複合化(将来 PR 候補)**: 現仕様の
   「remove の後に rotate が続く」窓(§14.3-5 の残余 (ii))は運用義務(§7)で
   狭めているが機構保証ではない。remove_member エントリ + 全環境の rotate

## 11. ハマったこと・設計上の学び

- **「署名は帰属であって鮮度でない」(§5.1 の教訓)が値にもそのまま効く**:
  値署名を入れても rollback は 1 ミリも防げない。G1〜G9 の分解を最初にやって
  「どの目標をどの機構が担うか」を固定しなかったら、値署名で全部解決した気に
  なるところだった(タスク指示の分解要求が正しかった)
- **remove_member ⇒ 全環境 rotate(§7)が認可時点検証の要石**: この既存規則の
  おかげで「削除済みメンバーの在籍区間に、現エポックが現行だったヘッドは存在
  しない」が成立し、エポック整合検査(§6.3-4)だけで「旧鍵は現エポックに書け
  ない」が出てくる。逆に言うと rotate を怠る運用ではこの保証が弱る(正直
  クライアントは rotate を強制するが、悪意 admin は怠れる — その場合も帰属は残る)
- **backfill が「在籍重なり検査」を殺す**: ラップに認可時点検査(署名者の在籍
  区間とエポックの重なり)を課す案は、add_member 後の過去エポック backfill
  (招待者の在籍とエポックが重ならない正当ケース)と正面衝突して不成立。
  ラップ層の真正性はコミットメント(受信者非依存)でしか閉じない —
  タスク指示が backfill を必須検討に挙げていた理由
- **コミットメントの置き場は「既にある認証済みブロードキャスト」一択**:
  データプレーンに置く案(B-3)は「正規はどれか」の循環に必ず落ちる。チェーンが
  既に全員検証の対象である以上、そこ以外に置く理由がない
- **AAD に名前を入れる案の却下理由は「暗号文脈に可変メタデータを入れない」
  という既存原則から機械的に導出できた**(§3 environment_id の理由付けの再利用)
- **「巻き戻しが要るから床で検出できる」は前進方向を見落とす**(レビュー
  ループ 1 の最重要指摘 — 3 観点が独立に同根を検出): 在籍区間内座標への注入は
  実最新の「次の」version / meta_version を名乗れば巻き戻し不要で、連番の
  単調性だけの床は素通りする。値はエポック単調性という「座標に焼き込まれた
  時刻代理」で閉じられるが、メタにはそれがない。「注入は必ず何かの後退を
  伴う」という直感は、**攻撃者が座標空間の未使用部分(次の連番)を選べる**
  ことを忘れている
- **対策案自体もレビューで棄却されうる**: セキュリティ観点が提案した
  「宣言ヘッド seq の単調性」は、正しさ観点の検討(同期時期の異なる正直な
  並行 writer)で正当フローを壊すことが判明して棄却。3 観点の並行レビューは
  指摘の検出だけでなく**修正案の相互検証**として機能した
